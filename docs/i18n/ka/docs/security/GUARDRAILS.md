სურვილისამებრ უარყოს, გარდაქმნას ან ანოტაცია დაურთოს) მოთხოვნის მონაცემები (`preCall`) და
ზედა დონის პროვაიდერების პასუხები (`postCall`).

გადადის. დაბლოკვა აშკარა გადაწყვეტილებაა (`block: true`) და არასოდეს ხდება შემთხვევით.
ერთადერთი გამონაკლისია შეწყვეტილი მოთხოვნა: როდესაც გამომძახებლის `signal` შეწყვეტილია,
გამონაკლისის გამომწვევი დამცავი მექანიზმი გამოტოვების ნაცვლად ჰუკის შესრულებას უარყოფს.

### გამოსახულების ხიდი (`visionBridge.ts`) — მოდალობის ხიდი PR-1

GLM 5.3 საბაზო მოდელსა და `glm-5.3-{low,high,max}`-ს რეესტრის/სპეციფიკაციის მეტამონაცემებში
აშკარად აქვთ მითითებული `supportsVision:false`. GLM 5.3 Flash-ის ვარიანტები
კვლავ რჩება გამოსახულების დამუშავების ჩაშენებული მხარდაჭერის მქონე მოდელებად. Claude Code-ის `/v1/messages` მარშრუტი
Claude-დან OpenAI-ში გარდაქმნამდე **მანამდე** ერთვება
საერთო `handleChat` გამოძახებამდელი დამცავი მექანიზმების ჯაჭვში; ჩაშენებული `Read` ხელსაწყოს შედეგებში არსებული გამოსახულებები უნდა აღიწეროს ან დამუშავდეს
მანამ, სანამ ეს გარდაქმნა მათ OpenAI-ის `image_url` შიგთავსში გადაიტანს (#17069).

იჭერს გამოსახულების შემცველ მოთხოვნებს, რომლებიც მიმართულია **გამოსახულების მხარდაჭერის არმქონე მოდელებისკენ**, და ან
მთელ მოთხოვნას გადაამისამართებს გამოსახულების მხარდაჭერის მქონე მოდელზე, ან ზედა დონის პროვაიდერის გამოძახებამდე გამოსახულების
ნაწილებს ცვლის კონფიგურირებადი გამოსახულების მოდელის მიერ შექმნილი ტექსტური აღწერებით.
ეს მხოლოდ ტექსტზე მომუშავე პროვაიდერებს მულტიმოდალური მონაცემების გამჭვირვალედ დამუშავების საშუალებას აძლევს.

პროცესი:

1. გამოტოვება, თუ სამიზნე მოდელს უკვე აქვს გამოსახულების მხარდაჭერა (გარდა იმ შემთხვევისა, როცა ის
   ხიდის იძულებით გამოყენების სიაშია — `isVisionBridgeForcedModel`).
2. გამოსახულების ნაწილების ამოღება `extractImageParts(messages)`-ის მეშვეობით
   (`visionBridgeHelpers.ts`), რომელიც ამ ამოცანას გადასცემს **მედიის ერთიან
   დეტექტორს** `detectMediaParts()` ფაილში `open-sse/utils/mediaParts.ts` —
   ერთიან სარწმუნო წყაროს, რომელსაც კომბინაციის თავსებადობის ფილტრიც იყენებს.
   ამოღება დასაშვებია მხოლოდ იმ სტრუქტურებისთვის, რომელთა უკან ჩასმაც `replaceImageParts`-ს შეუძლია
   (ამოღება↔ჩანაცვლების კონტრაქტი): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"` და Responses
   API `input_image`. Claude Code-ის
   `tool_result.content`-სა და Responses-ის ხელსაწყოს გამომავალ მონაცემებში ჩაშენებული შესაბამისი გამოსახულებებიც ამოიღება და
   თავდაპირველ მდებარეობებზე ჩანაცვლდება; მხოლოდ ინდიკატორის შემცველი სტრუქტურები კომბინაციის ფილტრისთვისაა
   განკუთვნილი და არ ამოიღება.
   გამოტოვება, თუ ვერაფერი მოიძებნა.
3. გაშვებისას გამოსაყენებელი კონფიგურაციის განსაზღვრა `resolveVisionBridgeRuntimeSettings()`-ით
   (`src/shared/constants/modalityBridgeDefaults.ts`): უპირატესობა ენიჭება ახალ `modalityBridge*`
   პარამეტრების გასაღებებს; ძველი `visionBridge*` გასაღებები რჩება **ერთი ციკლის
   სარეზერვო ვარიანტად** (უკან დაბრუნების პერიოდი). თუ
   ხიდი გამორთულია, გამოტოვება მედიის ნებისმიერ შემოვლამდე.
4. რეჟიმის ამრჩევი (`modalityBridgeVisionMode`, იხილეთ ქვემოთ მოცემული ცხრილი) განსაზღვრავს,
   მოხდება გადამისამართება თუ აღწერა. გადამისამართება აბრუნებს `modifiedPayload`-ს, რომელშიც მხოლოდ `model`
   არის შეცვლილი, და მეტამონაცემებს `{ rerouted, fromModel, toModel, imagesKept }`.
5. აღწერის გზა: გამოსახულებების რაოდენობის შეზღუდვა `maxImages`-ით, დავალებაზე მორგებული პრომპტის შედგენა,
   აღწერების ქეშის შემოწმება, გამოსახულების მოდელის **პარალელურად** გამოძახება
   (`Promise.allSettled`) და გამოსახულებების ადგილას `[Image N]: <description>` ტექსტური ნაწილების
   ჩასმა. წარუმატებელი აღწერა იძლევა `null`-ს: უცნობი ან გამოსახულების მხარდაჭერის მქონე სამიზნეებისთვის თავდაპირველი გამოსახულება ნარჩუნდება
   (#4012), მაგრამ **დადასტურებულად მხოლოდ ტექსტზე მომუშავე პირდაპირი
   სამიზნე** ან გამოსახულების მხარდაჭერის არმქონე კომბინაცია იღებს აშკარა
   `(unavailable — no vision-capable provider connected)` ტექსტურ ჩამნაცვლებელს
   ყოველი აღუწერელი გამოსახულებისთვის, მათ შორის ნაწილობრივი წარუმატებლობებისა და იმ გამოსახულებებისთვის, რომლებიც
   აღწერის გამოძახებების ლიმიტს სცდება (#17069). კომბინაციის აღწერის არსებული სარეზერვო მექანიზმი, რომელიც ყველა აღწერის წარუმატებლობისას ამოქმედდება,
   უცვლელი რჩება (#8430).
6. `modifiedPayload`-ისა და მეტამონაცემების დაბრუნება (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### API გასაღების მოქმედების არეალი (`visionBridgeKeyScope.ts`)

როდესაც გამომძახებლის API გასაღები ზღუდავს `allowedConnections`-ს, კვოტების პულებს
(`allowedQuotas`) ან მოდელებს (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), ხიდი გადამისამართებისა და აღწერისთვის მხოლოდ
იმ მოდელებს ირჩევს, რომელთა გამოყენების უფლებაც გასაღებს აქვს, იმ კავშირებზე, რომელთა გამოყენებაც გასაღებს
შეუძლია. შემდეგ აღწერის გამოძახება ყოველთვის OmniRoute-ის თვითმარყუჟის გავლით სრულდება,
`x-omniroute-self-loop-key-id` სათაურით, რათა ჩატის მიმღებმა მოთხოვნამ
ამ გასაღების კავშირებისა და მოდელების პოლიტიკა ხელახლა აღასრულოს. `enforceApiKeyPolicy()`
ამ სათაურს მხოლოდ თვითმარყუჟის bearer-ტოკენთან ერთად ითვალისწინებს, ამიტომ მას მხოლოდ
წვდომის შევიწროება შეუძლია, ხოლო იდენტიფიკატორი, რომლის ამოცნობაც ვერ ხერხდება, უარყოფილია.

თუ გასაღებისთვის არცერთი ვიზუალური მოდელი არ არის ნებადართული, **დადასტურებულად მხოლოდ ტექსტზე მომუშავე
სამიზნე** გამოსახულების მოთხოვნას ლოკალურად უარყოფს მკაფიო HTTP 400 შეცდომით, ნაცვლად
გამოსახულების ბაიტების უუნარო ზედა დონის სერვისისთვის გადაგზავნისა (#17069). უცნობი ან ჩაშენებული
ვიზუალური შესაძლებლობების მქონე სამიზნეებისთვის აღწერის გზა ინარჩუნებს წინა
ქცევას, რომელიც წარუმატებლობისას დამუშავებას აგრძელებს (მეტამონაცემები `{ skipped: true, reason: "no_permitted_vision_model" }`).
გასაღების გარეშე მოთხოვნები და ამ შეზღუდვების არმქონე გასაღებები ზუსტად ისე იქცევა,
როგორც ადრე.

#### ამოცანის გათვალისწინებით შედგენილი აღწერის პრომპტი (`modalityBridgeVisionTaskAware`)

ნაგულისხმევად **ჩართულია**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`) საბაზისო
აღწერის პრომპტს ამატებს **მომხმარებლის ბოლო შეტყობინების** ტექსტს (შემოკლებულს 500 სიმბოლომდე),
რითაც აღწერას მიმართავს მომხმარებლის რეალური მოთხოვნისკენ
(codex-vision-proxy შაბლონი) და ვიზუალურ მოდელს ხილული ტექსტის გადმოწერას სთხოვს.
როდესაც პარამეტრი გამორთულია — ან მომხმარებლის ტექსტი არ არის — საბაზისო პრომპტი უცვლელად გამოიყენება.

აღწერის თვითმარყუჟის საკუთარი OpenAI-სთან თავსებადი მოთხოვნა (`callVisionModelSingle()`
ფაილში `visionBridgeHelpers.ts`) ყოველთვის ითხოვს `image_url.detail: "high"`-ს —
უპირობოდ, ყველა გამომძახებლისთვის/პროვაიდერისთვის, კლიენტის რაიმე სიგნალზე დამოკიდებულების გარეშე.
დაბალი დეტალიზაციით დამუშავება აუარესებს OCR-ის სიზუსტეს სწორედ ტექსტის გადმოწერის
იმ ამოცანისთვის, რომელსაც ეს პრომპტი ითხოვს, ამიტომ აღწერის გამოძახება ყოველთვის ითხოვს მაღალ
დეტალიზაციას, მიუხედავად იმისა, დეტალიზაციის რა დონე იყო გამოყენებული საწყის შემომავალ მოთხოვნაში. ეს
მხოლოდ შიდა აღწერის მოთხოვნის სხეულზე მოქმედებს; ის არ ცვლის იმას, თუ როგორ
გადააგზავნის OmniRoute გამომძახებლის საკუთარ `image_url.detail`-ს ძირითად მოთხოვნაში —
ეს ნაგულისხმევი მნიშვნელობა ცალკე გამოიყენება და მხოლოდ ამოცნობილი OpenCode კლიენტებისთვის,
`defaultImageDetail()`-ში (`open-sse/handlers/chatCore/upstreamBody.ts`). აღწერის თვითმარყუჟის
Anthropic-ის გადაცემის ფორმატის განშტოებას `detail` ველი არ აქვს
და მასზე არცერთი ნაგულისხმევი მნიშვნელობა არ მოქმედებს.

#### აღწერის შედეგის ზღვარი (`modalityBridgeVisionMaxChars`)

| გასაღები                       | ნაგულისხმევი | დიაპაზონი        |
| ------------------------------ | ------------ | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` ან 100–50000 |

`0` (ნაგულისხმევი) ნიშნავს **ზღვრის არარსებობას** —
`callVisionModel()`-ის მიერ დაბრუნებული აღწერა უცვლელად გადაიცემა, რითაც არსებული
ქცევა ნარჩუნდება. 100–50000 დიაპაზონში ნებისმიერი მნიშვნელობა აღწერას ამოკლებს და
ბოლოში უმატებს `…`-ს, სანამ ის უკან ჩაისმება ფორმატით `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` ფაილში `src/lib/guardrails/visionBridge.ts`).
გაზარდეთ ეს მნიშვნელობა დეტალებით დატვირთული OCR ამოცანებისთვის, როდესაც შემდგომ მოდელს
სრული გადმოწერილი ტექსტი სჭირდება; შეამცირეთ იგი სიტყვაუხვი ვიზუალური მოდელების მიერ ტოკენების მოხმარების შესაზღუდად.
მართვის პანელში ეს ველი მდებარეობს ვიზუალური შესაძლებლობების ჩანართის გაფართოებული პარამეტრების პანელზე
(`modality-bridge-max-chars` ფაილში `ModalityBridgeVisionTab.tsx`) და
1-დან 99-მდე ნებისმიერ მნიშვნელობას ზრდის მინიმალურ ზღვრამდე, 100-მდე, ხოლო აშკარად მითითებულ `0`-ს
უცვლელად ტოვებს — `0` თავისთავად Zod-ის ვალიდური მნიშვნელობაა
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) და არა უბრალოდ
„დაუყენებელი“ ნაგულისხმევი მნიშვნელობა.

#### აღწერის ქეში (`modalityBridge/bridgeCache.ts`)

მეხსიერებაში განთავსებული LRU + TTL ქეში აღწერის შედეგებისთვის, რომელიც მთელ პროცესში საზიაროა.
გასაღები = `sha256(imageRef + composedPrompt + configuredBridgeModel)`,
სიგრძის პრეფიქსით გამიჯვნით (ველების საზღვრების კოლიზიების გარეშე). მოდელის კომპონენტი არის
ხიდის **კონფიგურირებული** მოდელი და არა ის მოდელი, რომელმაც რეალურად უპასუხა —
`callVisionModel`-ს შეუძლია შიგნით სათადარიგო მოდელზე გადავიდეს, ხოლო თითოეული მცდელობისთვის ცალკე გასაღების შექმნა
ქეშს დაანაწევრებდა. წარუმატებელი აღწერები არასოდეს ინახება ქეშში. პარამეტრები:

| გასაღები                        | ნაგულისხმევი | დიაპაზონი |
| ------------------------------- | ------------ | --------- |
| `modalityBridgeCacheEnabled`    | `true`       | —         |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440    |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000   |

#### დისტანციური გამოსახულების ნორმალიზება (თვითმარყუჟის describe/base64 ჩამოტვირთვა)

როდესაც ხიდი **დისტანციურ** გამოსახულებას თავად ჩამოტვირთავს — Anthropic-ის describe
თვითგამოძახებისა და claude-wire-format-ის base64 გარდაქმნისას
(`ensureBase64ImagesForClaudeWire`), ორივე შემთხვევაში
`fetchRemoteImageAsDataUri()`-ის მეშვეობით `visionBridgeHelpers.ts`-ში — მიღებული მონაცემთა
URI გადის `normalizeDataUri()`-ს
(`open-sse/utils/imageNormalize.ts`), სანამ მხედველობის მოდელის
მოთხოვნაში ჩაიშენება. ზედმეტად დიდი გამოსახულებები მცირდება ისე, რომ **გრძელი გვერდი 2048px იყოს** (ეს ემთხვევა
ზომის ცვლილების ზღვარს, რომელსაც OpenAI/Anthropic სერვერის მხარეს უკვე იყენებენ), რაც ამცირებს
ასატვირთი ბაიტების რაოდენობასა და დაყოვნებას ისე, რომ მხედველობის მოდელისთვის ხილული შინაარსი არ იცვლება. ზომის შესაცვლელად
გამოიყენება `sharp`, რომელიც დინამიკური იმპორტით იტვირთება: პლატფორმაზე, სადაც მისი ნატიური
ბინარული ფაილი ვერ იტვირთება, `normalizeDataUri()` **გამონაკლისს არასოდეს წარმოქმნის** — ის უბრუნდება
საწყისი ბაიტების უცვლელად გატარებას, ამიტომ describe/base64 გარდაქმნის
გზა ყოველთვის აგრძელებს მუშაობას. ბაიტები, რომლებიც გამოსახულებას არ წარმოადგენს (ჩამოტვირთვა, რომელმაც
დეკოდირებადი გამოსახულება არ დააბრუნა), ასევე უცვლელად გადაეცემა. ეს ნორმალიზება
ვრცელდება მხოლოდ იმ გამოსახულებებზე, რომლებსაც ხიდი საკუთარი თვითგამოძახებისთვის ჩამოტვირთავს — ის არასოდეს
გამოიყენება გამომძახებლის უცვლელად გასატარებელ ნედლ მონაცემებზე, რაც შეესაბამება
მხოლოდ აშკარა თანხმობით ცვლილების პრინციპს (მკაცრი წესი #20).

### აუდიოხიდი (`audioBridge.ts`) — მოდალობის ხიდი PR-3

იჭერს აუდიოს შემცველ ჩატის მოთხოვნებს მანამდე, სანამ ისინი მიაღწევს სამიზნეს, რომლისთვისაც
აუდიოშეყვანის მხარდაჭერა ცნობილი არ არის. ის ჩატის მოთხოვნას არასოდეს გადაამისამართებს: აუდიონაწილები
ტრანსკრიბირდება არსებული OpenAI-თავსებადი multipart ენდპოინტის მეშვეობით, ხოლო
არჩეული ჩატის მოდელი მუშაობას ტექსტური ტრანსკრიპტებით აგრძელებს.

მიმდინარეობა:

1. განსაზღვრეთ `supportsAudio` ფუნქციის `getResolvedModelCapabilities()` მეშვეობით. უპირატესობა
   ენიჭება პროვაიდერთა რეესტრში აშკარად მითითებულ მეტამონაცემებს, შემდეგ — მოდელის სტატიკურ მეტამონაცემებს, შემდეგ კი სინქრონიზებულ
   `modalities_input`-ს. დეკლარირებული შეყვანის სია, რომელიც `audio`-ს არ შეიცავს, ნიშნავს `false`-ს; შესაძლებლობის
   დამადასტურებელი მონაცემების არარსებობისას მნიშვნელობა რჩება `null`. როგორც `false`, ისე `null` ააქტიურებს
   კონსერვატიულ ხიდს, ხოლო `true` მას გვერდს უვლის.
2. განსაზღვრეთ `modalityBridgeAudio*` პარამეტრები და ყოველი შეტყობინებიდან საერთო `detectMediaParts()`
   დეტექტორის მეშვეობით ამოიღეთ ზედა დონის აუდიონაწილები, რომელთა ჩანაცვლებაც შესაძლებელია.
   მხარდაჭერილი გადაცემის ფორმატებია OpenAI-ის `input_audio`, `audio_url` და
   `source.media_type: "audio/*"`. ჩადგმული აუდიო მარშრუტიზაციისთვის ამოიცნობა, მაგრამ
   ჩანაცვლების პროცესში არ იშლება. დამუშავების მოცულობა შეზღუდულია `modalityBridgeAudioMaxClips`-ით;
   მომდევნო ნაწილები უცვლელი რჩება.
3. გაითვალისწინეთ კონფიგურირებული `provider/model`, ან მიეცით `selectAudioBridgeModel()`-ს საშუალება, გაიაროს
   `AUDIO_TRANSCRIPTION_PROVIDERS` კატალოგის სტაბილური თანმიმდევრობით და აირჩიოს პირველი
   მოდელი, რომლის პროვაიდერის აქტიური ავტორიზაციის მონაცემებიც გამოსაყენებელია.
4. `callAudioTranscription()` გარდაქმნის base64/data-URI აუდიოს multipart
   `file`-ად, ან ჩამოტვირთავს დისტანციურ `audio_url`-ს მხოლოდ საჯარო მისამართებზე გამავალი მოთხოვნების
   დამცავი მექანიზმის მეშვეობით, DNS-ის ფიქსაციითა და 25 MB-იანი შეზღუდვით. შემდეგ ის ფაილსა და არჩეულ
   მოდელს POST მოთხოვნით აგზავნის ლოკალურ `/v1/audio/transcriptions` თვითგამოძახების მარშრუტზე, რომლის ავთენტიფიკაციაც
   ხდება `resolveSelfLoopBearer()`-ით. ტრანსკრიფციის არსებული მარშრუტი ასრულებს
   ავტორიზაციის მონაცემების ჩვეულებრივ მოძიებას, მოცდის პერიოდებისა და სიხშირის ლიმიტების დამუშავებას და პროვაიდერთან გადამისამართებას.
5. წარმატებული გამოძახებები შესაბამის ნაწილებს ანაცვლებს ტექსტით `[Audio N]: <transcript>`. გამოძახებები
   სრულდება `Promise.allSettled`-ით: ცალკეული წარუმატებლობა ინარჩუნებს შესაბამის თავდაპირველ
   აუდიონაწილს (#4012 კონტრაქტი). თუ ყველა გამოძახება წარუმატებელია და სამიზნისთვის დადასტურებულია
   `supportsAudio === false`, ნაწილები ჩანაცვლდება ტექსტით
   `[Audio N]: (unavailable — no STT provider connected)` (#8430 კონტრაქტი). უცნობი
   სამიზნისთვის (`null`) ყველა გამოძახების წარუმატებლობისას შედეგი უცვლელი რჩება. თუ დადასტურებულია, რომ
   სამიზნე მხოლოდ ტექსტს უჭერს მხარს და STT-ის გამოსაყენებელი ავტორიზაციის მონაცემები არ არსებობს, ის იღებს იმავე აშკარა
   ჩანაცვლების ტექსტს ქსელური გამოძახების გარეშე.

წარმატებული ტრანსკრიფციები იყენებს მთელი პროცესისთვის საერთო Modality Bridge-ის LRU/TTL ქეშს.
გასაღები აერთიანებს აუდიობმულს, ოპერაციის სტაბილურ
`audio-transcription` იარლიყსა და არჩეულ STT მოდელს; წარუმატებლობები არასოდეს ქეშირდება. აუდიოს დამუშავების მცდელობები აახლებს
საერთო `bridged`, `cacheHits`, `failures` და `lastUsedAt` მრიცხველებს.

### ვიდეოხიდი (`videoBridge.ts`, `videoBridgePipeline.ts`)

იჭერს ზედა დონის ვიდეონაწილებს Chat Completions-ის `messages`-სა და Responses

მიმდევრობის აღწერა (რომელიც გამომძახებლის მიერ დეკლარირებულ აუდიოტრანსკრიფციასაც აერთიანებს) და თითოეული მცდელობის
მეტრიკები/შეწყვეტა/რესურსების გასუფთავება — ინკაფსულირებულია `processVideoPart`-ში,

ეს მოდული ასევე განსაზღვრავს პორტების აშკარა საზღვრებს: `VideoMediaBrokerPort`

როგორც საწყისი დისტანციური URL-ისთვის, ისე ყოველი გადამისამართებისთვის; გამოიყენება არსებული,
მხოლოდ საჯარო მისამართებზე გამავალი მოთხოვნების დამცავი მექანიზმი DNS-ის ფიქსაციით. შემდეგ ბაიტები გადის ზუსტად განსაზღვრულ შიდა
`POST /api/modality-bridge/video/extract` ბროკერის საზღვარს. ეს მარშრუტი ერთდროულად არის
`LOCAL_ONLY` და `SPAWN_CAPABLE`, იღებს მხოლოდ კონკრეტული პროცესისთვის ავთენტიფიცირებულ

ერთ ჯერზე ერთ ამოღებას ასრულებს, უშვებს ოთხ მომლოდინე დავალებას და მომლოდინე შეყვანის მოცულობას

ბროკერის შიგნით `ffprobe` კითხულობს კერძო ლოკალურ ფაილს; ფორმატების ფიქსირებული

კონტეინერებისთვის გარე MOV მონაცემთა მითითებები ნაგულისხმევად გათიშული რჩება და
ფიქსირებული ბრძანება მათ არ რთავს. როგორც `ffprobe`, ისე `ffmpeg` იყენებს
მხოლოდ `file` პროტოკოლის დაშვებულ სიას, ერთ ნაკადს, არგუმენტების ფიქსირებულ მასივებს, გარსის გარეშე,

დასაკრავ კანდიდატებად არ მიიჩნევა. ყველა დასაკრავი ნაკადი უნდა აკმაყოფილებდეს შეზღუდვებს, ხოლო
აშკარად მითითებულ ნაგულისხმევ ნაკადს უპირატესობა ენიჭება ყველაზე დაბალი ინდექსის მქონე ნაკადის
დეტერმინისტულ სარეზერვო არჩევანთან შედარებით. ვიდეოების შეზღუდვებია 600 წამი, 8,192 პიქსელი თითოეულ განზომილებაში და

არასოდეს იღებს URL-ს. შერჩევა ნაგულისხმევად არის `uniform`. არასავალდებულო
`scene_aware` და ექსპერიმენტული `segment_aware` პოლიტიკები უკვე შემოწმებულ ლოკალურ ნაკადზე ასრულებს ერთ დამატებით
ფიქსირებულ FFmpeg გავლას, არჩევს შეზღუდული რაოდენობის

კანდიდატთა ნაკრების შემთხვევაში დეტერმინისტულად უბრუნდება იმავე
თანაბრად განაწილებულ შუაწერტილებს. სეგმენტების გამთვალისწინებელი რეჟიმი შუაწერტილის ნიმუშებს ანაწილებს
შემოწმებული სცენის ინტერვალების პროპორციულად; სეგმენტების გამთვალისწინებელი მტკიცებულებები და სარეზერვო ქცევა
ქვემოთაა აღწერილი. მკაცრი 16-კადრიანი ზღვარი
ყველა პოლიტიკაში შერჩევის შემდეგ გამოიყენება. როდესაც სცენების გამთვალისწინებელ მოთხოვნას მხოლოდ
ერთი კადრის ბიუჯეტი აქვს, ის იყენებს აქტიური სრული ვიდეოს ან ფოკუსის
ფანჯრის შუაწერტილს და აბრუნებს `policyEffective: uniform`-ს: ერთი შერჩეული სცენის კადრი
ორივე დროით ბოლოს ვერ შეინარჩუნებს. გამომძახებელს სურვილისამებრ შეუძლია მიუთითოს
სასრული ფოკუსის ფანჯარა (`start`/`end` წამები); საზღვრები მედიის
ხანგრძლივობის ფარგლებში იზღუდება, შებრუნებული ან არასასრული ფანჯრები უარყოფილია, ხოლო შერჩევის ყველა
პოლიტიკა სრულდება მხოლოდ ნორმალიზებული ინტერვალის შიგნით. მიღებული
ფანჯარა შედის შერჩევის მეტამონაცემებსა და არასანდო აღწერის
პრეფიქსში, რათა შემდგომ მოდელებს შეეძლოთ ფოკუსირებული ამონარიდის სრული
დროითი ხაზისგან გარჩევა.

აღწერის სემანტიკური ფოკუსი ცალკე, აშკარად მითითებული პარამეტრია. ნაგულისხმევი `full`
ანალიზის რეჟიმი ინარჩუნებს კადრის არსებულ პრომპტს და მოთხოვნის
ტექსტს აღწერის მოდელს არასოდეს გადასცემს. `focused` რეჟიმში ხიდი კითხულობს მხოლოდ უახლეს
არაცარიელ, მომხმარებლის მიერ დაწერილ `text`/`input_text`-ს იმავე Chat ან Responses
კონტეინერიდან, ახდენს მის NFC ნორმალიზაციას, აერთიანებს საკონტროლო სიმბოლოებსა და გამოტოვებებს
და ზღუდავს მას Unicode-ის 500 კოდურ წერტილამდე. ცარიელი შედეგის შემთხვევაში გამოიყენება
ზუსტად იგივე `full` პრომპტი. გამოსადეგი მინიშნება JSON-ის სახით სერიალიზდება გამოყოფილ
არასანდო მომხმარებლის კონტექსტის ბლოკში და მას მხოლოდ დაკვირვებადი დეტალების პრიორიტეტიზაცია შეუძლია;
მას არ შეუძლია გააუქმოს ცალკე გაფრთხილება მედიაში ხილული
ან მოსმენილი ინსტრუქციების შესრულების წინააღმდეგ. ტექსტური ფოკუსი არასოდეს ადგენს `start`/`end`-ს და არ ცვლის
დროით შერჩევის მექანიზმს.

#### FU-07 სტრუქტურული სეგმენტების მტკიცებულებები

`segment_aware` უკვე შემოწმებულ
ლოკალურ ვიდეონაკადზე იყენებს წინასწარი ანალიზის ერთ შეზღუდულ გავლას. ფილტრების ფიქსირებული ჯაჭვი ჯერ მასშტაბს მაქსიმუმ 320 პიქსელის
სიგანემდე ამცირებს, ამოიცნობს სცენის ცვლილებებსა და გაყინულ ინტერვალებს, შემდეგ კი წამში 1 კადრს
არჩევს ბუნდოვანების, საშუალო სიკაშკაშისა და სივრცითი/დროითი ინფორმაციისთვის. გავლა
შეზღუდულია 600 სტრუქტურული ნიმუშით, ერთი FFmpeg/ფილტრის ნაკადით, იმავე

მუშაობს **ორივე** ეტაპზე.

- **`preCall`** ქმნის მონაცემთა პაკეტის ასლს, გადაუვლის `system`, `messages`, `input` და
  `prompt` ელემენტებს (მათ შორის უბრალო სტრიქონულ ელემენტებს) და სტრიქონულ `content`/`text` ველებზე
  იყენებს `processPII()`-ს (`@/shared/utils/inputSanitizer`-დან). როდესაც
  `PII_REDACTION_ENABLED=true`, აღმოჩენილი პერსონალური საიდენტიფიკაციო ინფორმაცია (PII) გამავალ
  მონაცემთა პაკეტში იფარება. ეს არ არის დამოკიდებული `INPUT_SANITIZER_MODE`-ზე (რომელიც მხოლოდ
  პრომპტის ინექციის პოლიტიკას მართავს). როდესაც დაფარვა გამორთულია, გამოძახება აღრიცხავს აღმოჩენების
  რაოდენობას შიგთავსის გადაწერის გარეშე.
- **`postCall`** ქმნის პასუხის ღრმა ასლს, უშვებს `sanitizePIIResponse()`-ს და
  Responses API-ის სტრუქტურის შესაბამის დამფარავს (`maskResponsesOutput` — მოიცავს
  `output_text`-სა და `output[].content[].text`-ს). თუ რაიმე დაიფარა,
  შეცვლილი პასუხი ანაცვლებს თავდაპირველს.

დამცავი მექანიზმი არასდროს ბლოკავს; ის მხოლოდ ამატებს ანოტაციებს (`meta.detections`,
`meta.redacted`) ან გადაწერს შიგთავსს.

#### ტიპების მიხედვით შერჩევა, მორგებული შაბლონები და აღმოჩენების მრიცხველები

**მართვის პანელი → პარამეტრები → უსაფრთხოება → PII-ის დაფარვა** განსაზღვრავს, _რა_ დაიფარება. ის
არ რთავს დაფარვას: ამას კვლავ მართავს `PII_REDACTION_ENABLED` (მოთხოვნისთვის) და
`PII_RESPONSE_SANITIZATION` (პასუხისთვის + SSE), რომლებიც ნაგულისხმევად გამორთულია.

- **ტიპების მიხედვით შერჩევა** — ჩაშენებული იდენტიფიკატორები ჩამოთვლილია
  `src/shared/constants/piiTypes.ts`-ში (`PII_BUILTIN_TYPES`). თუ მნიშვნელობა მითითებული არ არის, იგულისხმება ყველა
  ტიპი (ქცევა, რომელიც ამ პარამეტრის დამატებამდე არსებობდა). მოთხოვნის ძრავის
  `ssn_us` შაბლონი შეესაბამება `ssn`-ს. შაბლონები (მინიმალური, სტანდარტული, ფინანსური,
  ბრაზილიური, აშშ, სრული) მხოლოდ მომხმარებლის ინტერფეისში მონიშვნის ველებს ავსებს.
- **მორგებული შაბლონები** — მაქსიმუმ 20 რეგულარული გამოსახულება ან ჩანაცვლების სიმბოლოებიანი შაბლონი (`*` = მაქსიმუმ 64
  არაჰარითი სიმბოლო, `?` = ერთი). დამთხვევები იცვლება `[CUSTOM_REDACTED]`-ით.
  თითოეული შაბლონი გადის `compilePiiCustomPattern()`-ს
  (`src/shared/utils/piiCustomPatterns.ts`): მაქსიმუმ 500 სიმბოლო, ალმები შეზღუდულია
  `g i m s u`-ით, უნდა კომპილირდებოდეს, უნდა გადიოდეს `safe-regex` შემოწმებას (კატასტროფული
  უკუსვლის გამოსარიცხად) და არ უნდა ემთხვეოდეს ცარიელ სტრიქონს ან დაფარვის ჩანაცვლების მარკერს.
  შაბლონი, რომელიც შემოწმებას ვერ გაივლის, უარყოფილია როგორც შენახვისას, ისე ტესტირებისას, ხოლო შენახული ჩანაწერი,
  რომელიც შემოწმებას ვერ გაივლის, შესრულებისას გამოტოვებულია და არ კომპილირდება. მორგებული შაბლონები მხოლოდ
  მაშინ მუშაობს, როცა დაფარვა ჩართულია.
- **აღმოჩენების მრიცხველები** — რაოდენობები ტიპების მიხედვით (არასდროს ინახება დამთხვევის მნიშვნელობები), ინახება
  მეხსიერებაში და ნულდება გადატვირთვისას (`src/lib/pii/piiDetectionStats.ts`). ისინი მხოლოდ
  მაშინ იზრდება, როცა დაფარვა ჩართულია.

პარამეტრები ინახება `key_value` ცხრილში (სახელთა სივრცე `pii_settings`,
`src/lib/db/piiSettings.ts`) და იკითხება 1-წამიანი ქეშის მეშვეობით. API:

| მეთოდი | გზა                      | დანიშნულება                                                                    |
| ------ | ------------------------ | ------------------------------------------------------------------------------ |

| `PUT`  | `/api/settings/pii`      | `enabledTypes`-ის (`null` = ყველა) და/ან `customPatterns`-ის ჩანაცვლება        |
| `POST` | `/api/settings/pii/test` | ერთი შაბლონის საცდელი გაშვება მაქსიმუმ 8 KB ზომის ნიმუშზე; არაფერი ინახება     |

(`src/shared/validation/schemas/piiSettings.ts`).

### პრომპტის ინექცია (`promptInjection.ts`)

ავლენს მავნე სტრუქტურებს მომხმარებლის მიერ მოწოდებულ შიგთავსში და აღასრულებს
კონფიგურირებულ პოლიტიკას. ქცევა განისაზღვრება გარემოს ცვლადებითა და კონსტრუქტორის
პარამეტრებით:

| პარამეტრი        | გარემოს ცვლადი                                                                                                         | ნაგულისხმევი | მოქმედება                                                                                                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ჩართულია         | `INPUT_SANITIZER_ENABLED`                                                                                              | `true`       | როდესაც მნიშვნელობაა `false`, დამცავი მექანიზმი მუშაობას დაუყოვნებლივ ასრულებს.                                                                                                      |
| რეჟიმი           | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                                        | `warn`       | ინექციის პოლიტიკა: `block`, `warn` ან `log`. (`redact` მიიღება უკუთავსებადობისთვის, თუმცა ინექციის ტექსტს **არ** შლის; მოთხოვნაში PII-ის გადაწერას მართავს `PII_REDACTION_ENABLED`.) |
| დაბლოკვის ზღვარი | `blockThreshold` პარამეტრი / `INPUT_SANITIZER_BLOCK_THRESHOLD` (ალტერნატიული სახელი `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`       | დაბლოკვისთვის საჭირო მინიმალური სიმძიმე. ნაგულისხმევად, საშუალო სიმძიმის შემთხვევებზე მხოლოდ დაკვირვება ხდება.                                                                       |

**რეჟიმის პრიორიტეტულობა** (`getMode`): გამომძახებლის `options.mode` →
`INJECTION_GUARD_MODE` **ფუნქციის ალმის გადამფარავი მნიშვნელობა მონაცემთა ბაზაში** (მართვის პანელი → პარამეტრები →
ფუნქციების ალმები) → `INJECTION_GUARD_MODE` გარემოს ცვლადი → `INPUT_SANITIZER_MODE` გარემოს ცვლადი →
`warn`. ამგვარად, მართვის პანელში მითითებული გადამფარავი მნიშვნელობა გარემოს ცვლადებზე პრიორიტეტულია, ამიტომ ფუნქციების
ალმების ინტერფეისი გაშვებულ დამცავ მექანიზმს რეალურ დროში მართავს (გადატვირთვის გარეშე). მონაცემთა ბაზიდან წაკითხვა შეცდომის მიმართ მდგრადია:
შეცდომის შემთხვევაში დამცავი მექანიზმი გარემოს ცვლადებზე დაფუძნებულ ქცევას უბრუნდება, ხოლო როდესაც
გადამფარავი მნიშვნელობა მითითებული არ არის, ქცევა მხოლოდ გარემოს ცვლადებით განსაზღვრული ქცევის იდენტურია.

აღმოჩენის წყაროები:

1. `sanitizeRequest()` მოდულიდან `@/shared/utils/inputSanitizer` (დეტექტორების საერთო
   ნაკრები, რომელიც დამუშავების ჯაჭვის სხვა ადგილებშიც გამოიყენება).
2. ჩაშენებული `DEFAULT_GUARD_PATTERNS` (ამჟამად `system_override_inline` და
   `markdown_system_block`, ორივე `high` სიმძიმის).
3. არასავალდებულო `customPatterns`, რომლებიც გადაეცემა კონსტრუქტორის პარამეტრებით (სტრიქონები, რეგულარული გამოსახულებები
   ან `{ name, pattern, severity }` ჩანაწერები).

როდესაც `mode === "block"` **და** სულ მცირე ერთი აღმოჩენა აკმაყოფილებს სიმძიმის
ზღვარს, `preCall` აბრუნებს `{ block: true, message: "Request rejected:
suspicious content detected" }`. `warn`/`log` რეჟიმებში დამცავი მექანიზმი ჟურნალში წერს ჩანაწერს, მაგრამ
გამოძახებას უშვებს. საერთო დამხმარე ფუნქცია `evaluatePromptInjection()` ასევე ექსპორტირებულია
მათთვის, ვისაც პრომპტების შეფასება რეესტრის გავლის გარეშე სჭირდება.

**სკანირების ზღვარი (v3.8.20):** დეტექტორი ამოწმებს გაერთიანებული
პრომპტის ტექსტის მხოლოდ **პირველ 16 KB-ს** — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ბაიტი)
`src/shared/utils/inputSanitizer.ts`-ში. როგორც `detectInjection()`, ისე
`evaluatePromptInjection()` შაბლონების ციკლის გაშვებამდე იყენებს
`slice(0, MAX_INJECTION_SCAN_BYTES)`-ს. ინექციის დირექტივები შეყვანილი მონაცემების დასაწყისთან ახლოსაა განთავსებული, ამიტომ ეს
ზღუდავს რეგულარული გამოსახულებების CPU/GC დატვირთვას რამდენიმე ასეული KB-ის მოცულობის მონაცემებზე ისე, რომ აღმოჩენის ეფექტიანობა არ მცირდება (შდრ.
#3932, #4041).

### ავტორიზაციის მონაცემების დამფარავი (`credentialMasker.ts`)

მუშაობს **ორივე** ეტაპზე, ნაგულისხმევ ჯაჭვში ბოლოა (პრიორიტეტი `95`). ფარავს
API-გასაღებებისა და საიდუმლო ტოკენების ცნობილ შაბლონებს გამავალ მონაცემებში (შეტყობინების
შიგთავსი, ინსტრუმენტის გამოძახების არგუმენტები, ინსტრუმენტის შედეგები) **და** პროვაიდერის პასუხში, რათა
პრომპტში ჩასმული ავტორიზაციის მონაცემები (ან ინსტრუმენტის შედეგში გამეორებული მონაცემები) არ გაჟონოს
ზემდგომ პროვაიდერთან ან უკან, კლიენტთან.

- **მხოლოდ აშკარა ჩართვით**, იგივე პრინციპით, როგორც PII-ის დაფარვა (მკაცრ წესთან #20 დაკავშირებული):
  გამორთულია, თუ არ არის `settings.credentialRedactionEnabled === true` **ან**
  `CREDENTIAL_REDACTION_ENABLED=true`. გამორთულ მდგომარეობაში დამცავი მექანიზმი არაფერს აკეთებს —
  არც ბლოკავს და არც გადაწერს.
- `redactCredentials()` გადის მონაცემების/პასუხის მთელ ხეზე (`walkValue()`,
  პროტოტიპის დაბინძურებისგან დაცული, ციკლებისგან დაცული `WeakSet`-ის მეშვეობით) და დამთხვევებს ანაცვლებს
  `[REDACTED:<type>]` ჩანაცვლების ნიშნით; კლონავს მხოლოდ იმ ტოტებს, რომლებიც რეალურად
  შეიცვალა.
- `CREDENTIAL_PATTERNS` მოიცავს LLM პროვაიდერების გასაღებებს (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ტოკენებს (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), გადახდის გასაღებებს (Stripe, Square), ღრუბლოვანი სერვისების
  გასაღებებს (AWS წვდომის გასაღები, Twilio, SendGrid, Mailgun), პირად გასაღებებს / JWT-ებს,
  ავტორიზაციის მონაცემების შემცველ კავშირის სტრიქონებს (`mongodb://user:pass@...` და სხვ.) და
  `Authorization`/`x-api-key`/`api-key`/`apikey` სათაურის მნიშვნელობის ზოგად
  შაბლონს. სათაურის ფორმის გასაღებები (`authorization`, `x-api-key`, `api-key`,
  `apikey`) იფარება სტრუქტურულად (მხოლოდ მნიშვნელობა, სქემის პრეფიქსი, როგორიცაა
  `Bearer `/`Basic `, შენარჩუნებულია) და არა ზოგადი ტექსტური რეგულარული გამოსახულებით.
- დამცავი მექანიზმი არასდროს ბლოკავს; ის მხოლოდ გადაწერს (`modifiedPayload` /
  `modifiedResponse`) და ამატებს ანოტაციებს (`meta.credentialsRedacted`, `meta.count`).

რეგრესიისგან დაცვის ტესტი: `tests/unit/credential-masker-guardrail.test.ts`.

## საბაზისო კონტრაქტი (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ჯაჭვის შესრულებას დაუყოვნებლივ წყვეტს
  message?: string; // ნაჩვენებია დაბლოკვისას
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // ბრუნდება preCall-იდან მოთხოვნის გადასაწერად
  modifiedResponse?: TValue; // ბრუნდება postCall-იდან პასუხის გადასაწერად
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

დამცავი მექანიზმი „ცვლილება არ არის“ მდგომარეობას აღნიშნავს `void`, `{}` ან
`{ block: false }` მნიშვნელობის დაბრუნებით. `modifiedPayload`/`modifiedResponse`-ის დაბრუნება ცვლის
ჯაჭვში გამავალ მნიშვნელობას მომდევნო დამცავი მექანიზმებისთვის.
`signal?: AbortSignal` გამომძახებლის სასიცოცხლო ციკლს დამცავ მექანიზმებს გადასცემს. მოთხოვნის შეწყვეტა არის განზრახ გამონაკლისი fail-open ქცევიდან: მედიის ხიდები წყვეტენ მუშაობას და ასუფთავებენ რესურსებს ისე, რომ დაუმუშავებელ მედიას არ აღადგენენ სამიზნისთვის, რომლის შესახებაც ცნობილია, რომ მას ამ მედიის მხარდაჭერა არ აქვს.

## რეესტრი (`registry.ts`)

ერთადერთი ეგზემპლარის სახით არსებული `guardrailRegistry` ხელმისაწვდომს ხდის:

- `register(guardrail)` — ამატებს დამცავ მექანიზმს (ან ანაცვლებს ნორმალიზებული სახელის მიხედვით) და
  ხელახლა ალაგებს `priority`-ის ზრდის მიხედვით.
- `clear()` / `list()` — ადმინისტრაციული დამხმარე მეთოდები.
- `runPreCallHooks(payload, context)` — გაივლის აქტიურ დამცავ მექანიზმებს, გადასცემს
  მონაცემებს `modifiedPayload`-ის გავლით და ჩერდება პირველივე `block: true`-ზე.
- `runPostCallHooks(response, context)` — იგივე პროცესი პასუხის მხარეს.
- `resetGuardrailsForTests({ registerDefaults })` — ასუფთავებს მდგომარეობას და, სურვილისამებრ,
  ხელახლა არეგისტრირებს ნაგულისხმევ მექანიზმებს ტესტების სრული იზოლაციისთვის.

ორივე გამშვები აბრუნებს `{ blocked, payload|response, results, guardrail?, message? }`-ს,
სადაც `results` არის `GuardrailExecutionResult` ჩანაწერების მასივი, რომელიც შეიცავს
თითოეული დამცავი მექანიზმის `blocked`, `skipped`, `modified`, `error` და `meta` ველებს,
რაც შესრულების თვალყურის დევნებისთვის გამოდგება.

### დამცავი მექანიზმების გამორთვა ცალკეული მოთხოვნისთვის

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` აერთიანებს
დამცავი მექანიზმების სახელების დუბლიკატებისგან გასუფთავებულ სიას, რომლებიც მიმდინარე
მოთხოვნისთვის უნდა გამოტოვდეს. არსებობს ხუთი არხი, რომლებიც ამ თანმიმდევრობით იკითხება და ერთ სიაში ერთიანდება
(დუბლიკატების მოცილებისას უპირატესობა პირველ გამოჩენას ენიჭება):

1. `apiKeyInfo.disabledGuardrails`
2. მოთხოვნის სხეულის `disabledGuardrails` (ზედა დონეზე)
3. მოთხოვნის სხეულის `metadata.disabledGuardrails` (მხოლოდ მაშინ, როცა `metadata` ობიექტია)
4. სათაური `x-omniroute-disabled-guardrails`
5. მოძველებული სათაური `x-disabled-guardrails`

ხუთივე არხი ერთიანდება, ორივე სათაურის ჩათვლით: როგორც
`x-omniroute-disabled-guardrails`-ის, ისე `x-disabled-guardrails`-ის გაგზავნა იწვევს
მათი სიების გაერთიანებაში შესული მექანიზმების გამოტოვებას, ხოლო ცარიელი თანამედროვე სათაური აღარ მალავს მოძველებულს
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), გასწორდა
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)-ში).

მნიშვნელობები შეიძლება იყოს სტრიქონების მასივები ან მძიმით გამოყოფილი სტრიქონი; სახელებს შორდება თავში და ბოლოში არსებული გამოტოვებები
და ისინი ნორმალიზდება ქვედა რეგისტრის kebab-case ფორმატში (`pii_masker` → `pii-masker`), ხოლო ცარიელი
ჩანაწერები იშლება. შედეგი `context.disabledGuardrails`-ის მეშვეობით გადაეცემა
რეესტრს, რომელიც შესაბამის დამცავ მექანიზმებს გამოტოვებს (`skipped: true` ველში `results`).

გამორთვის სია მოქმედებს მხოლოდ **რეესტრზე**. პრომპტში ინიექციის `block` რეჟიმი
სავალდებულო საზღვარია: ინიექციისგან დაცვის შუალედური ფენა
(`src/middleware/promptInjectionGuard.ts`) იძახებს `evaluatePromptInjection()`-ს
გამომძახებლის მიერ კონტროლირებადი გამორთვის სიის გარეშე (გამოუყენებელი
`resolveDisabledGuardrails({ body })` გამოძახება, რომელსაც ის ადრე ასრულებდა, წაიშალა
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)-ში), ამიტომ მოთხოვნა,
რომელიც თიშავს `prompt-injection`-ს, მაინც უარყოფილი იქნება `block` რეჟიმში. ეს
განზრახ არის ასე მოწყობილი. გამორთვის არხებს გამომძახებელი აკონტროლებს (მოთხოვნის სხეული,
მეტამონაცემები, სათაურები), ხოლო გამომძახებელს არ უნდა შეეძლოს ოპერატორის მიერ დაყენებული უსაფრთხოების
კონტროლის გამორთვა
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). სათაურების
გაერთიანება [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)-დან
ცვლის მხოლოდ იმას, თუ რეესტრის რომელი დამცავი მექანიზმები გამოტოვდება; ის კლიენტს
შუალედური ფენის გვერდის ავლის საშუალებას არ აძლევს. თითოეული გასაღებისა და ჯგუფისთვის სავალდებულო დამცავი მექანიზმების პოლიტიკები
აღრიცხულია v4 RFC-ში [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
იხილეთ [დაფარვა და შეზღუდვები](#coverage-and-limits).

## შესრულების თანმიმდევრობა

თითოეული მოთხოვნისთვის, რომელიც გადის `src/sse/handlers/chat.ts`-სა და
`open-sse/handlers/chatCore.ts`-ში (ჩატის ჯგუფის მარშრუტები, რომლებიც ჩამოთვლილია სექციაში
[დაფარვა და შეზღუდვები](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` ქმნის გამოტოვების სიას API გასაღებიდან, მოთხოვნის შიგთავსიდან
   და სათაურებიდან.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` უშვებს დამცავ მექანიზმებს
   პრიორიტეტის ზრდის მიხედვით:
   - გამორთული დამცავი მექანიზმები აღირიცხება როგორც `skipped`.
   - თითოეული დამცავი მექანიზმის `preCall`-ს შეუძლია შეცვალოს გადასაცემი მონაცემები `modifiedPayload`-ის მეშვეობით.
   - პირველი `block: true` წყვეტს ჯაჭვს და დამმუშავებელი აბრუნებს
     დამცავი მექანიზმის მიერ უარყოფის პასუხს.
3. გადასაცემი (შესაძლოა შეცვლილი) მონაცემები გადადის კომბინირებულ მარშრუტიზაციასა და ზედა დონის სერვისზე
   გაგზავნაში.
4. **მხოლოდ არანაკადური რეჟიმისთვის:** პასუხის აწყობის შემდეგ,
   `guardrailRegistry.runPostCallHooks(...)` იმავე ჯაჭვს უშვებს
   პასუხზე. აქ `block: true` უგულებელყოფს ზედა დონის სერვისის პასუხს და აბრუნებს HTTP 400-ს. ნაკადური პასუხები ამ ნაბიჯს მთლიანად გამოტოვებს.

დამცავი მექანიზმები, რომლებიც გამონაკლისს წარმოქმნის, აღირიცხება `error: <message>`-ით და ჟურნალში იწერება
`logger.warn`-ის მეშვეობით, თუმცა ჯაჭვი გრძელდება — განზრახ არჩეული მიდგომაა შეცდომისას გატარება.

  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) რეესტრამდე არასდროს აღწევს. იქ არ სრულდება
  PII-ის შენიღბვა, ავტორიზაციის მონაცემების შენიღბვა ან მოდალობებს შორის ხიდის მექანიზმი. მათი ერთადერთი
  შემოწმებაა ინექციისგან დაცვის მოძველებული შუალედური პროგრამული შრე.
- **ნაკადურ პასუხებზე** გამოძახების შემდგომი დამცავი მექანიზმები არ ვრცელდება: გამოძახების შემდეგ არც `pii-masker` და არც
  `credential-masker` არ სრულდება და არც გამოძახების შემდგომი დაბლოკვა ხდება. გამოიყენება მხოლოდ ნაკადური PII-ის
  გარდაქმნა (როდესაც `PII_RESPONSE_SANITIZATION` ჩართულია). ნაკადურ პასუხში
  გამეორებული ავტორიზაციის მონაცემი არ იფარება.
- **გამორთვის არხები და შუალედური პროგრამული შრე (განზრახ):** შუალედური პროგრამული შრე აფასებს
  პრომპტის ინექციას `evaluatePromptInjection()`-ის საკუთარი გამოძახებით,
  გამომძახებლის მიერ კონტროლირებადი გამორთვის სიის გადაცემის გარეშე. `block` რეჟიმი სავალდებულო
  ზღვარია, რომლის გვერდის ავლაც გამომძახებლის მიერ კონტროლირებადი გამორთვით შეუძლებელია, მათ შორის ჩატის ჯგუფის მარშრუტებზეც
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). `prompt-injection`-ის
  გამორთვა მხოლოდ რეესტრის დამცავ მექანიზმს გამოტოვებს.

### რა ამუშავებს პასუხს გამოძახების შემდგომ შემოწმებამდე

არანაკადურ გზაზე თანმიმდევრობა ასეთია: მეხსიერების ამოღება → ჩაშენებული ხელსაწყოს
შესრულება → გამოძახების შემდგომი დამცავი მექანიზმები → გამოძახების შემდგომი დაბლოკვისას დასრულება → სემანტიკურ ქეშში შენახვა.

- **მეხსიერებისთვის ინფორმაციის ამოღება** და **ინსტრუმენტების შესრულება** პასუხს მანამდე ხედავენ, სანამ გამოძახების შემდგომი
  დამცავი მექანიზმები მის გადაწერას ან დაბლოკვას შეძლებენ.
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401)-დან მოყოლებული, მეხსიერებისთვის
  ინფორმაციის ამოღებისას ამოღებული ტექსტი `sanitizePII`-ს გადაეცემა, როდესაც
  `PII_RESPONSE_SANITIZATION` ჩართულია (როგორც სტრიმინგის, ისე არასტრიმინგის რეჟიმში), თუმცა
  პასუხი, რომელსაც გამოძახების შემდგომი შემოწმება მოგვიანებით ბლოკავს, უკვე მიწოდებულია მეხსიერებისა და
  ინსტრუმენტებისთვის.
- **სემანტიკური ქეში** პასუხს გამოძახების შემდგომი შემოწმების შემდეგ ინახავს, ამიტომ მასში
  გადაწერილი პასუხი ინახება, დაბლოკილი პასუხი კი ქეშში არასდროს ხვდება. ქეშის ჩანაწერები
  თითოეული API გასაღებისთვის ცალ-ცალკე ინახება.

| ცვლადი                                | გამოიყენება                   | ეფექტი                                                                                                                      |
| ------------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`            | აღმოჩენის სრულად გამოსართავად დააყენეთ `false`.                                                                             |

## მორგებული დამცავი მექანიზმები

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ნაბიჯები:

1. შექმენით `src/lib/guardrails/myGuardrail.ts`, რომელიც გააფართოებს `BaseGuardrail`-ს.
2. განახორციელეთ `preCall` და/ან `postCall`.
3. დაარეგისტრირეთ იმპორტის დროს (`registerDefaultGuardrails`-იდან დამატებით) ან
   შესრულების დროს გამოიძახეთ `guardrailRegistry.register(...)` — რეესტრი ჩაანაცვლებს
   იმავე ნორმალიზებული სახელის მქონე ნებისმიერ წინა დამცავ მექანიზმს.
4. დაამატეთ ტესტები `tests/unit/`-ში (არსებული მაგალითები:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## ტესტირება

ტესტებს შორის გამოიყენეთ `resetGuardrailsForTests()`, რათა დაიწყოთ ცნობილი მდგომარეობიდან.
ცარიელი რეესტრით დასაწყებად გადასცით `{ registerDefaults: false }` და

შემოწმებისა და ტრანსკრიფციისთვის. ამიტომ ტესტებს შეუძლია ორივე ნაკადის შემოწმება მონაცემთა ბაზაზე
ან ქსელზე წვდომის გარეშე.

## ინექციისგან დაცვის მარშრუტების დაფარვა და შეტევითი ტესტირება (ფაზა 8 · ბლოკი D)

ინექციისგან დაცვა (`createInjectionGuard` / `withInjectionGuard`) ფარავს ყველა მარშრუტს,
რომელიც მომხმარებლის პრომპტებს იღებს. ის ითვალისწინებს `INJECTION_GUARD_MODE`-ს (ნაგულისხმევი `warn` = მხოლოდ ჟურნალში ჩაწერა;
`block` = აბრუნებს HTTP 400-ს, კოდით `SECURITY_001`).

| ტიპი                | მარშრუტები                                                                                                                                           | ნაგულისხმევი რეჟიმი |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| ტექსტური (არსებული) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                |
| გენერაციული         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                |
| მონაცემები          | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                |

ტექსტის ამოღება (`extractMessageContents`) მოიცავს `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ველებს.

**შეტევითი ტესტირება (ყოველღამიური, `nightly-llm-security.yml`):** promptfoo ამოწმებს, რომ თითოეული მარშრუტი ბლოკავს
OWASP-LLM-ის კორპუსს `INJECTION_GUARD_MODE=block` რეჟიმში; garak ასრულებს საცდელ შეტევებს (საიდუმლო გასაღების გარეშე გამოტოვებს).
`moderations` ჩართულია თანმიმდევრულობისთვის. ბლოკირების რეჟიმი სავალდებულო ზღვარია: `evaluatePromptInjection()`
უგულებელყოფს კონკრეტული მოთხოვნისთვის გამორთვის სიას, რომელსაც მას შუალედური პროგრამული შრე გადასცემს, ამიტომ `disabledGuardrails`
**არ** ათავისუფლებს მარშრუტს ამ დაცვისგან ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

ყოველღამიურ სამუშაო პროცესს (`.github/workflows/nightly-llm-security.yml`, cron + ხელით
გაშვება) ორი დავალება აქვს:

- **`promptfoo-guard` (დამბლოკავი)** — ასრულებს `promptfoo eval -c promptfooconfig.yaml`-ს
  `INJECTION_GUARD_MODE=block` რეჟიმში. თითოეული შეტევითი შემთხვევა (მაგ., „უგულებელყავი ყველა
  წინა ინსტრუქცია…“, DAN-ის სტილის შეზღუდვების გვერდის ავლა) ამოწმებს, რომ პასუხი შეიცავს
  `error.code === "SECURITY_001"`-ს, ანუ დაცვამ მოთხოვნა ნამდვილად უარყო.
- **`garak` (სარეკომენდაციო)** — უშვებს garak-ს `--probes promptinject,dan,leakreplay` პარამეტრით
  OmniRoute-ის ლოკალური ინსტანციის (`http://localhost:20128/v1`) წინააღმდეგ. სრულდება მხოლოდ
  პროვაიდერის საიდუმლო გასაღების (`PROMPTFOO_PROVIDER_KEY`) არსებობისას; წინააღმდეგ შემთხვევაში უსაფრთხოდ გამოტოვებს,
  ბოლოში კი დამატებული აქვს `|| true`, ამიტომ შედეგებს ასახავს CI-ის ჩავარდნის გარეშე.

დაცვის დამხმარე ფუნქციების (`createInjectionGuard` / `withInjectionGuard`) დაფარვა
ვრცელდება პრომპტის შემცველ ყველა `/v1` მარშრუტზე; პრომპტის ტექსტი ამოიღება
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ველებიდან
`src/shared/utils/inputSanitizer.ts`-ში არსებული `extractMessageContents()`-ის მეშვეობით.
