> ബ്ലോക്ക് മോഡ് നിർബന്ധിത അതിർത്തിയായി പ്രവർത്തിക്കുന്നത് (#16413), post-call-ന് മുമ്പ് ഏതൊക്കെ ഘടകങ്ങൾ പ്രതികരണം കാണുന്നു എന്നിവ)

OmniRoute-നും അപ്‌സ്ട്രീം ദാതാക്കൾക്കും ഇടയിലുള്ള അതിർത്തിയിൽ ഗാർഡ്‌റെയിലുകൾ
സുരക്ഷ, നയം, ഉള്ളടക്ക പരിവർത്തനങ്ങൾ എന്നിവ നടപ്പാക്കുന്നു. ഓരോ ഗാർഡ്‌റെയിലിനും അഭ്യർത്ഥന പേലോഡുകളും (`preCall`)
അപ്‌സ്ട്രീം പ്രതികരണങ്ങളും (`postCall`) പരിശോധിക്കാനും
വേണമെങ്കിൽ നിരസിക്കാനും പരിവർത്തനം ചെയ്യാനും കുറിപ്പുകൾ ചേർക്കാനും കഴിയും.

ഈ സംവിധാനം **പിശകുണ്ടായാലും തുടരുന്നതാണ്**: പ്രവർത്തനത്തിനിടെ ഒരു ഗാർഡ്‌റെയിൽ എക്സെപ്ഷൻ ഉയർത്തിയാൽ, രജിസ്ട്രി
ആ പിശക് രേഖപ്പെടുത്തുകയും അഭ്യർത്ഥന പരാജയപ്പെടുത്തുന്നതിനുപകരം അടുത്ത ഗാർഡ്‌റെയിലുമായി
തുടരുകയും ചെയ്യുന്നു. തടയൽ എന്നത് വ്യക്തമായ ഒരു തീരുമാനമാണ് (`block: true`), ഒരിക്കലും യാദൃച്ഛികമല്ല.
റദ്ദാക്കിയ അഭ്യർത്ഥന മാത്രമാണ് ഇതിന് അപവാദം: വിളിക്കുന്ന ഘടകത്തിന്റെ `signal` റദ്ദാക്കപ്പെടുമ്പോൾ,
എക്സെപ്ഷൻ ഉയർത്തുന്ന ഗാർഡ്‌റെയിൽ ഒഴിവാക്കപ്പെടുന്നതിനുപകരം ഹുക്ക് പ്രവർത്തനം നിരസിക്കുന്നു.

ഹുക്കുകൾ എല്ലാ റൂട്ടുകളിലും എല്ലാ പ്രതികരണങ്ങളിലും പ്രവർത്തിക്കുന്നില്ല.
ഒരു സുരക്ഷാ നിയന്ത്രണമായി ഗാർഡ്‌റെയിലിനെ ആശ്രയിക്കുന്നതിനുമുമ്പ്
[പരിധിയും പരിമിതികളും](#coverage-and-limits) വായിക്കുക.

## അന്തർനിർമ്മിത ഗാർഡ്‌റെയിലുകൾ

ഇംപോർട്ട് ചെയ്യുമ്പോൾ രജിസ്ട്രി ആറ് ഗാർഡ്‌റെയിലുകൾ മുൻഗണനാക്രമത്തിൽ സ്വയമേവ ലോഡ് ചെയ്യുന്നു
(`registry.ts` → `registerDefaultGuardrails()` കാണുക):

| മുൻഗണന | പേര്                | ഘട്ടം(ങ്ങൾ)    | ഫയൽ                   |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

കുറഞ്ഞ മുൻഗണനാ സംഖ്യകളുള്ളവ **ആദ്യം** പ്രവർത്തിക്കുന്നു.

### വിഷൻ ബ്രിഡ്ജ് (`visionBridge.ts`) — മൊഡാലിറ്റി ബ്രിഡ്ജ് PR-1

GLM 5.3 അടിസ്ഥാന മോഡലിനും `glm-5.3-{low,high,max}`-നും വ്യക്തമായ
`supportsVision:false` രജിസ്ട്രി/സ്പെക് മെറ്റാഡാറ്റയുണ്ട്. GLM 5.3 Flash വകഭേദങ്ങൾ
നേറ്റീവ് വിഷൻ മോഡലുകളായി തുടരുന്നു. Claude Code-ന്റെ `/v1/messages` റൂട്ട്,
Claude-ൽനിന്ന് OpenAI-യിലേക്കുള്ള പരിവർത്തനത്തിന് **മുമ്പ്**, പങ്കിട്ട
`handleChat` പ്രീ-കോൾ ഗാർഡ്‌റെയിൽ ശൃംഖലയിൽ പ്രവേശിക്കുന്നു; ആ പരിവർത്തനം നെസ്റ്റ് ചെയ്ത `Read` ടൂൾ-ഫല ചിത്രങ്ങളെ
OpenAI `image_url` ഉള്ളടക്കത്തിലേക്ക് ഉയർത്തുന്നതിന് മുമ്പ് അവ വിവരിക്കുകയോ കൈകാര്യം ചെയ്യുകയോ
വേണം (#17069).

**വിഷൻ പിന്തുണയില്ലാത്ത മോഡലുകളെ** ലക്ഷ്യമിടുന്ന, ചിത്രങ്ങൾ ഉൾക്കൊള്ളുന്ന അഭ്യർത്ഥനകളെ തടഞ്ഞെടുത്ത്,
ഒന്നുകിൽ മുഴുവൻ അഭ്യർത്ഥനയും വിഷൻ ശേഷിയുള്ള ഒരു മോഡലിലേക്ക് തിരിച്ചുവിടുന്നു, അല്ലെങ്കിൽ
അപ്‌സ്ട്രീം കോളിന് മുമ്പ് കോൺഫിഗർ ചെയ്യാവുന്ന ഒരു വിഷൻ മോഡൽ സൃഷ്ടിച്ച ടെക്സ്റ്റ് വിവരണങ്ങൾ ഉപയോഗിച്ച്
ചിത്രഭാഗങ്ങൾ മാറ്റിസ്ഥാപിക്കുന്നു. ഇതിലൂടെ ടെക്സ്റ്റ് മാത്രം പിന്തുണയ്ക്കുന്ന ദാതാക്കൾക്ക്
മൾട്ടിമോഡൽ പേലോഡുകൾ സുതാര്യമായി കൈകാര്യം ചെയ്യാൻ കഴിയും.

പ്രവാഹം:

1. ലക്ഷ്യ മോഡൽ ഇതിനകം വിഷൻ പിന്തുണയ്ക്കുന്നുവെങ്കിൽ ഒഴിവാക്കുക (നിർബന്ധിത ബ്രിഡ്ജ് പട്ടികയായ
   `isVisionBridgeForcedModel`-ൽ അത് ഉൾപ്പെട്ടിട്ടില്ലെങ്കിൽ).
2. `extractImageParts(messages)` വഴി ചിത്രഭാഗങ്ങൾ വേർതിരിച്ചെടുക്കുക
   (`visionBridgeHelpers.ts`); ഇത് `open-sse/utils/mediaParts.ts`-ലെ **ഏകീകൃത മീഡിയ
   ഡിറ്റക്ടറായ** `detectMediaParts()`-നെ ചുമതലപ്പെടുത്തുന്നു — കോംബോ അനുയോജ്യതാ ഫിൽട്ടറുമായി
   പങ്കിടുന്ന ഏക ആധികാരിക ഉറവിടമാണിത്.
   `replaceImageParts`-ന് തിരികെ ചേർക്കാൻ കഴിയുന്ന ഘടനകൾക്ക് മാത്രമാണ്
   വേർതിരിച്ചെടുക്കൽ അനുവദിച്ചിരിക്കുന്നത് (extract↔replace കരാർ): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"`, Responses
   API `input_image` എന്നിവ. Claude Code-ന്റെ
   `tool_result.content`-ലും Responses ടൂൾ ഔട്ട്‌പുട്ടുകളിലും നെസ്റ്റ് ചെയ്തിരിക്കുന്ന പൊരുത്തപ്പെടുന്ന ചിത്രങ്ങളും വേർതിരിച്ചെടുത്ത്
   അവയുടെ യഥാർത്ഥ പാതകളിൽ മാറ്റിസ്ഥാപിക്കുന്നു; സൂചകം മാത്രമുള്ള ഘടനകൾ കോംബോ-ഫിൽട്ടറിന്
   വേണ്ടിയുള്ളവയാണ്, അവ വേർതിരിച്ചെടുക്കില്ല.
   ഒന്നും കണ്ടെത്തിയില്ലെങ്കിൽ ഒഴിവാക്കുക.
3. `resolveVisionBridgeRuntimeSettings()` വഴി റൺടൈം കോൺഫിഗറേഷൻ നിർണ്ണയിക്കുക
   (`src/shared/constants/modalityBridgeDefaults.ts`): പുതിയ `modalityBridge*`
   ക്രമീകരണ കീകൾക്കാണ് മുൻഗണന; പഴയ `visionBridge*` കീകൾ **ഒരു സൈക്കിളിലേക്കുള്ള
   ഫാൾബാക്ക്** ആയി തുടരുന്നു (റോൾബാക്ക് കാലയളവ്). ബ്രിഡ്ജ് പ്രവർത്തനരഹിതമാണെങ്കിൽ
   ഏതെങ്കിലും മീഡിയയിലൂടെ സഞ്ചരിക്കുന്നതിന് മുമ്പേ ഒഴിവാക്കുക.
4. മോഡ് സെലക്ടർ (`modalityBridgeVisionMode`, താഴെയുള്ള പട്ടിക കാണുക)
   തിരിച്ചുവിടണോ വിവരിക്കണോ എന്ന് തീരുമാനിക്കുന്നു. തിരിച്ചുവിടൽ `model`
   മാത്രം മാറ്റിയ `modifiedPayload`-ഉം `{ rerouted, fromModel, toModel, imagesKept }` മെറ്റാഡാറ്റയും നൽകുന്നു.
5. വിവരണ പാത: ചിത്രങ്ങളുടെ എണ്ണം `maxImages`-ൽ പരിമിതപ്പെടുത്തുക, ടാസ്കിന് അനുയോജ്യമായ പ്രോംപ്റ്റ് തയ്യാറാക്കുക,
   വിവരണ കാഷെ പരിശോധിക്കുക, വിഷൻ മോഡലിനെ **സമാന്തരമായി**
   (`Promise.allSettled`) വിളിക്കുക, അവയുടെ സ്ഥാനത്ത് `[Image N]: <description>` ടെക്സ്റ്റ് ഭാഗങ്ങൾ
   ചേർക്കുക. വിവരണം പരാജയപ്പെട്ടാൽ `null` ലഭിക്കുന്നു: അജ്ഞാതമായതോ വിഷൻ ശേഷിയുള്ളതോ ആയ
   ലക്ഷ്യങ്ങൾക്കായി യഥാർത്ഥ ചിത്രം നിലനിർത്തുന്നു (#4012), എന്നാൽ **ടെക്സ്റ്റ് മാത്രം പിന്തുണയ്ക്കുന്നതായി സ്ഥിരീകരിച്ച നേരിട്ടുള്ള
   ലക്ഷ്യത്തിനോ** വിഷൻ ശേഷിയൊന്നുമില്ലാത്ത കോംബോയ്ക്കോ, വിവരണം ലഭിക്കാത്ത ഓരോ ചിത്രത്തിനും വ്യക്തമായ
   `(unavailable — no vision-capable provider connected)` ടെക്സ്റ്റ് സ്റ്റബ് നൽകുന്നു;
   ഭാഗിക പരാജയങ്ങളും വിവരണ-കോൾ പരിധിക്ക് പുറത്തുള്ള ചിത്രങ്ങളും ഇതിൽ ഉൾപ്പെടുന്നു
   (#17069). കോംബോയിലെ എല്ലാ വിവരണങ്ങളും പരാജയപ്പെടുമ്പോഴുള്ള നിലവിലെ ഫാൾബാക്ക്
   തുടരുന്നു (#8430).
6. `modifiedPayload` + മെറ്റാഡാറ്റ (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`) നൽകുക.

ഓട്ടോ ഹ്യൂറിസ്റ്റിക് പ്രവർത്തിക്കുന്നതിന് **മുമ്പ്** നിർബന്ധിത മോഡുകൾ തുടർപരിശോധനകൾ ഒഴിവാക്കുന്നു; `auto` പെരുമാറ്റം
PR-1-ന് മുമ്പുള്ള ഗാർഡ്‌റെയിലുമായി ബൈറ്റ് തലത്തിൽ സമാനമാണ്.

#### API കീയുടെ പരിധി (`visionBridgeKeyScope.ts`)

അഭ്യർത്ഥകന്റെ API കീ `allowedConnections`, ക്വോട്ട പൂളുകൾ
(`allowedQuotas`) അല്ലെങ്കിൽ മോഡലുകൾ (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`) എന്നിവ നിയന്ത്രിക്കുമ്പോൾ, ആ കീയ്ക്ക് ഉപയോഗിക്കാവുന്ന
കണക്ഷനുകളിൽ, കീയ്ക്ക് ഉപയോഗിക്കാൻ അനുമതിയുള്ള റീറൂട്ട്, വിവരണ മോഡലുകൾ മാത്രമേ ബ്രിഡ്ജ്
തിരഞ്ഞെടുക്കൂ. തുടർന്ന് വിവരണ കോൾ എല്ലായ്പ്പോഴും
`x-omniroute-self-loop-key-id` ഹെഡറോടുകൂടി OmniRoute സെൽഫ്-ലൂപ്പിലൂടെ കടന്നുപോകുന്നു; അതിനാൽ സ്വീകരിക്കുന്ന ചാറ്റ് അഭ്യർത്ഥന
ആ കീയുടെ കണക്ഷൻ, മോഡൽ നയം വീണ്ടും നടപ്പിലാക്കുന്നു. `enforceApiKeyPolicy()`
സെൽഫ്-ലൂപ്പ് ബെയററിനൊപ്പം മാത്രമേ ആ ഹെഡർ മാനിക്കൂ; അതിനാൽ അതിന്
ആക്സസ് പരിമിതപ്പെടുത്താൻ മാത്രമേ കഴിയൂ, കൂടാതെ തിരിച്ചറിയാനാകാത്ത id നിരസിക്കപ്പെടുന്നു.

കീയ്ക്ക് ഒരു വിഷൻ മോഡലും അനുവദിച്ചിട്ടില്ലെങ്കിൽ, **ടെക്സ്റ്റ്-മാത്രമാണെന്ന് സ്ഥിരീകരിച്ച
ടാർഗെറ്റ്**, ചിത്ര ബൈറ്റുകൾ അവ കൈകാര്യം ചെയ്യാൻ കഴിയാത്ത അപ്‌സ്ട്രീമിലേക്ക് കൈമാറുന്നതിനുപകരം,
വ്യക്തമായ HTTP 400 ഉപയോഗിച്ച് ചിത്ര അഭ്യർത്ഥന ലോക്കലായി നിരസിക്കുന്നു (#17069). വിഷൻ ശേഷി
അജ്ഞാതമായതോ സ്വാഭാവികമായി ലഭ്യമായതോ ആയ ടാർഗെറ്റുകൾക്ക്, വിവരണ പാത അതിന്റെ മുൻപത്തെ
ഫെയിൽ-ഓപ്പൺ പെരുമാറ്റം നിലനിർത്തുന്നു (മെറ്റാ `{ skipped: true, reason: "no_permitted_vision_model" }`).
കീ ഇല്ലാത്ത അഭ്യർത്ഥനകളും ഈ നിയന്ത്രണങ്ങളില്ലാത്ത കീകളും കൃത്യമായി
മുമ്പത്തെപ്പോലെ പ്രവർത്തിക്കുന്നു.

#### ടാസ്ക്-അവബോധമുള്ള വിവരണ പ്രോംപ്റ്റ് (`modalityBridgeVisionTaskAware`)

ഡിഫോൾട്ട് **true**. `composeVisionPrompt()` (`visionBridgeHelpers.ts`)
അടിസ്ഥാന വിവരണ പ്രോംപ്റ്റിലേക്ക് **അവസാന ഉപയോക്തൃ സന്ദേശത്തിന്റെ** ടെക്സ്റ്റ് (500 അക്ഷരങ്ങളായി ചുരുക്കിയത്)
ചേർക്കുന്നു; ഇതിലൂടെ വിവരണത്തെ ഉപയോക്താവ് യഥാർത്ഥത്തിൽ ചോദിച്ച കാര്യത്തിലേക്ക്
നയിക്കുകയും (codex-vision-proxy പാറ്റേൺ), ദൃശ്യമാകുന്ന
ടെക്സ്റ്റ് പകർത്തിയെഴുതാൻ വിഷൻ മോഡലിനോട് ആവശ്യപ്പെടുകയും ചെയ്യുന്നു. ഫ്ലാഗ് ഓഫായിരിക്കുമ്പോൾ — അല്ലെങ്കിൽ ഉപയോക്തൃ ടെക്സ്റ്റ് ഇല്ലെങ്കിൽ — അടിസ്ഥാന പ്രോംപ്റ്റ് മാറ്റമില്ലാതെ ഉപയോഗിക്കുന്നു.

വിവരണ സെൽഫ്-ലൂപ്പിന്റെ സ്വന്തം OpenAI-അനുയോജ്യ അഭ്യർത്ഥന (`visionBridgeHelpers.ts`-ലെ
`callVisionModelSingle()`) എല്ലായ്പ്പോഴും `image_url.detail: "high"` അഭ്യർത്ഥിക്കുന്നു —
എല്ലാ അഭ്യർത്ഥകർക്കും/ദാതാക്കൾക്കും, ഒരു ക്ലയന്റ് സിഗ്നലിനെയും ആശ്രയിക്കാതെ, നിരുപാധികമായി.
ഈ പ്രോംപ്റ്റ് ആവശ്യപ്പെടുന്ന ടെക്സ്റ്റ് പകർത്തിയെഴുത്ത് ടാസ്കിൽത്തന്നെ കുറഞ്ഞ വിശദാംശങ്ങളുള്ള സാമ്പിളിംഗ്
OCR കൃത്യത കുറയ്ക്കുന്നു; അതിനാൽ യഥാർത്ഥ ഇൻബൗണ്ട് അഭ്യർത്ഥന ഏത് വിശദാംശ നില ഉപയോഗിച്ചാലും,
വിവരണ കോൾ തന്നെ എല്ലായ്പ്പോഴും ഉയർന്ന വിശദാംശങ്ങൾ ആവശ്യപ്പെടുന്നു. ഇത്
ആന്തരിക വിവരണ അഭ്യർത്ഥനയുടെ ബോഡിയെ മാത്രമേ ബാധിക്കൂ; പ്രാഥമിക അഭ്യർത്ഥനയിൽ
അഭ്യർത്ഥകന്റെ സ്വന്തം `image_url.detail` OmniRoute കൈമാറുന്ന രീതി ഇത് മാറ്റുന്നില്ല —
ആ ഡിഫോൾട്ട് വെവ്വേറെയാണ് പ്രയോഗിക്കുന്നത്; അതും കണ്ടെത്തിയ OpenCode ക്ലയന്റുകൾക്കു മാത്രം,
`defaultImageDetail()`-ൽ (`open-sse/handlers/chatCore/upstreamBody.ts`). വിവരണ സെൽഫ്-ലൂപ്പിന്റെ
Anthropic വയർ-ഫോർമാറ്റ് ബ്രാഞ്ചിൽ `detail` ഫീൽഡ് ഇല്ല,
അതിനാൽ ഈ രണ്ട് ഡിഫോൾട്ടുകളും അതിനെ ബാധിക്കില്ല.

(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), വെറും
"സജ്ജീകരിച്ചിട്ടില്ല" എന്ന ഡിഫോൾട്ട് മാത്രമല്ല.

#### റിമോട്ട് ഇമേജ് നോർമലൈസേഷൻ (self-loop describe/base64 ഫെച്ച്)

ബ്രിഡ്ജ് തന്നെ ഒരു **റിമോട്ട്** ചിത്രം ഫെച്ച് ചെയ്യുമ്പോൾ — Anthropic describe
self-call, claude-wire-format base64 പരിവർത്തനം
(`ensureBase64ImagesForClaudeWire`) എന്നിവ രണ്ടും
`visionBridgeHelpers.ts`-ലെ `fetchRemoteImageAsDataUri()` വഴി — ലഭിക്കുന്ന ഡാറ്റാ
URI, വിഷൻ മോഡൽ അഭ്യർത്ഥനയിൽ ഉൾപ്പെടുത്തുന്നതിനു മുമ്പ്
`normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) വഴി
കടത്തിവിടുന്നു. വലുപ്പമേറിയ ചിത്രങ്ങളുടെ **നീളമേറിയ വശം 2048px** ആകുന്നവിധം ചെറുതാക്കുന്നു
(OpenAI/Anthropic ഇതിനകം സെർവർ ഭാഗത്ത് പ്രയോഗിക്കുന്ന റീസൈസ് പരിധിക്ക്
അനുസൃതമായി). വിഷൻ മോഡൽ കാണുന്നതിൽ മാറ്റം വരുത്താതെ അപ്‌ലോഡ്
ബൈറ്റുകളും ലേറ്റൻസിയും ഇത് കുറയ്ക്കുന്നു. റീസൈസിങ്ങിന് ഡൈനാമിക് ഇംപോർട്ട് വഴി
ലോഡ് ചെയ്യുന്ന `sharp` ഉപയോഗിക്കുന്നു: അതിന്റെ നേറ്റീവ് ബൈനറി ലോഡ് ചെയ്യാൻ
കഴിയാത്ത പ്ലാറ്റ്‌ഫോമിൽ, `normalizeDataUri()` **ഒരിക്കലും എക്സെപ്ഷൻ എറിയില്ല** —
പകരം യഥാർത്ഥ ബൈറ്റുകൾ അതേപടി കടത്തിവിടുന്നു. അതിനാൽ describe/base64-പരിവർത്തന
പാത എല്ലായ്പ്പോഴും പ്രവർത്തിക്കുന്നു. ഇമേജ് അല്ലാത്ത ബൈറ്റുകളും (ഡീകോഡ് ചെയ്യാവുന്ന
ചിത്രം തിരികെ നൽകാത്ത ഒരു ഫെച്ച്) മാറ്റമില്ലാതെ കടത്തിവിടുന്നു. ഈ നോർമലൈസേഷൻ,
ബ്രിഡ്ജ് സ്വന്തം self-call-നായി ഫെച്ച് ചെയ്യുന്ന ചിത്രങ്ങളിൽ മാത്രം പരിമിതമാണ് —
കോളറുടെ അസംസ്കൃത പാസ്‌ത്രൂ പേലോഡിൽ ഇത് ഒരിക്കലും പ്രയോഗിക്കില്ല. ഇത്
വ്യക്തമായി സമ്മതിച്ചാൽ മാത്രം മാറ്റം വരുത്തുക എന്ന തത്ത്വത്തിന് (കർശന നിയമം #20)
അനുസൃതമാണ്.

Describe വഴി രൂപാന്തരപ്പെടുത്തിയ പ്രതികരണങ്ങളിൽ

റീറൂട്ട് ചെയ്ത അഭ്യർത്ഥനകൾക്ക് ഹെഡർ **ഉണ്ടാകില്ല** — പേലോഡിൽ മാറ്റം വരുത്തിയിട്ടില്ല,
മോഡൽ മാറ്റം പ്രതികരണ ബോഡിയിലെ `model` ഫീൽഡിൽ ഇതിനകം ദൃശ്യമാണ്.

`GET /api/modality-bridge/stats` (മാനേജ്മെന്റ് ഓതന്റിക്കേഷൻ,
`GET /api/settings`-ന്റെ അതേ തലത്തിൽ) `vision`, `audio`,

ഉപയോഗിക്കുന്നു; സമയം രേഖപ്പെടുത്താത്ത ഒരു പ്രവർത്തനം പൂജ്യം മില്ലിസെക്കൻഡിന്റെ

(ടെലിമെട്രിക്കുള്ളതാണ്, അക്കൗണ്ടിങ്ങിനല്ല).

#### ഡാഷ്ബോർഡ് കോൺഫിഗറേഷൻ

ഇതിനായുള്ള പ്രത്യേക ഡാഷ്ബോർഡ് പേജ്
`/dashboard/settings/modality-bridge` ആണ്. URL വഴി നേരിട്ട് തുറക്കാവുന്ന അതിലെ `Vision`, `Audio`,
`Video` ടാബുകൾ, `tab` മൂല്യം മാറ്റുമ്പോൾ ക്വറി പാരാമീറ്ററുകൾ നിലനിർത്തുന്നു.
വിഷൻ ടാബിൽ പ്രവർത്തനക്ഷമമാക്കൽ, മോഡ്, മോഡൽ തിരഞ്ഞെടുക്കൽ (സ്വയമേവയുള്ള
ഡിഫോൾട്ട് ഉൾപ്പെടെ), ടാസ്ക്-അവെയർ പ്രോംപ്റ്റിങ്, വിപുലമായ ടൈംഔട്ട്/ചിത്രം/വിവരണ-ദൈർഘ്യം/കാഷെ
പരിധികൾ, റൺടൈം
കൗണ്ടറുകൾ, സുരക്ഷാനിയന്ത്രണങ്ങളുള്ള ഒരു സാമ്പിൾ അഭ്യർത്ഥന എന്നിവ ലഭ്യമാണ്. ഓഡിയോ ടാബും പ്രവർത്തനക്ഷമമാണ്:
പ്രവർത്തനക്ഷമമാക്കൽ, ഓട്ടോ ഉൾപ്പെടുന്ന STT-മാത്രം മോഡൽ തിരഞ്ഞെടുക്കൽ, ടൈംഔട്ട്/പരമാവധി-ക്ലിപ്പ് പരിധികൾ, ഓഡിയോ
കൗണ്ടറുകൾ, ഒരു `input_audio` സാമ്പിൾ പരിശോധന എന്നിവ അതിൽ ലഭ്യമാണ്. വീഡിയോ ടാബും പ്രവർത്തനക്ഷമമാണ്: അത്
FFmpeg/ffprobe റൺടൈം നില റിപ്പോർട്ട് ചെയ്യുന്നു — വ്യക്തമായ നാല് UI നിലകളിൽ ഒന്ന് (പ്രോബ്
നടന്നുകൊണ്ടിരിക്കുമ്പോഴോ പൂർത്തിയാക്കാൻ കഴിയാതിരിക്കുമ്പോഴോ `unknown`, ക്ലയന്റ് ഭാഗത്ത് പ്രോബ് ഒഴിവാക്കുന്ന
നോൺ-ലൂപ്പ്ബാക്ക് ഡാഷ്ബോർഡ് ഹോസ്റ്റിൽ `restricted`, പ്രോബ് ചെയ്ത്
ഇല്ലെന്ന് സ്ഥിരീകരിച്ചാൽ `unavailable`, അല്ലെങ്കിൽ FFmpeg/ffprobe പതിപ്പുകൾക്കൊപ്പം `available`) — കൂടാതെ
പ്രവർത്തനക്ഷമമാക്കൽ/മോഡൽ/ഫ്രെയിം/വീഡിയോ/ടൈംഔട്ട് പരിധികൾ സംഭരിക്കുന്നു, മോഡൽ തിരഞ്ഞെടുക്കലിൽ വിഷൻ പിന്തുണയുള്ള
മോഡലുകൾ മാത്രം കാണിക്കുന്നു, വീഡിയോ കൗണ്ടറുകളും ലഭ്യമാക്കുന്നു.

AI ക്രമീകരണങ്ങൾക്ക് കീഴിലുണ്ടായിരുന്ന പഴയ വിഷൻ ബ്രിഡ്ജ് കാർഡ്, പുതിയ
പേജിലേക്കുള്ള ഒരു അനുയോജ്യതാ ലിങ്കാണ്; ഫോമിന്റെ രണ്ടാമത്തെ പകർപ്പ് ഇനി അതിനില്ല. മീഡിയ പ്രൊവൈഡേഴ്‌സും
ഇമേജ്-ടു-ടെക്സ്റ്റ്, സ്പീച്ച്-ടു-ടെക്സ്റ്റ് വർക്ക്ഫ്ലോകളെ അനുയോജ്യമായ മോഡാലിറ്റി
ബ്രിഡ്ജ് ടാബുകളിലേക്ക് ലിങ്ക് ചെയ്യുന്നു; നിലവിലുള്ള സ്പീച്ച്-ടു-ടെക്സ്റ്റ് പ്ലേഗ്രൗണ്ട് നീക്കം ചെയ്യുന്നില്ല.

`x-omniroute-admission-bypass: internal` അയയ്ക്കുകയും നിർണയിച്ച
self-loop ക്രെഡൻഷ്യൽ ഉപയോഗിച്ച് ഓതന്റിക്കേറ്റ് ചെയ്യുകയും ചെയ്യുന്നു — ലോക്കൽ മോഡിൽ ലോക്കൽ `sk_omniroute`
സെന്റിനൽ, അല്ലെങ്കിൽ ഓപ്പറേറ്റർ കോൺഫിഗർ ചെയ്ത `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` എൻവയോൺമെന്റ് കീ (#1350).
അതിനാൽ `REQUIRE_API_KEY=true` വിന്യാസങ്ങൾക്കും describe കോൾ പ്രവർത്തിപ്പിക്കാനാകും. ആ കൃത്യമായ
ക്രെഡൻഷ്യലുകൾക്ക് മാത്രമേ ബൈപാസ് അനുവദിക്കൂ; അതിനാൽ ബാഹ്യ ക്ലയന്റുകൾക്ക്
അഡ്മിഷൻ ഒഴിവാക്കാൻ ഈ ഹെഡർ ഉപയോഗിക്കാനാവില്ല.

പഴയ ഡിഫോൾട്ടുകൾ `src/shared/constants/visionBridgeDefaults.ts`-ലാണ്;
പുതിയ മോഡ്/ടാസ്ക്-അവെയർ/കാഷെ ഡിഫോൾട്ടുകളും ക്രമീകരണങ്ങൾ നിർണയിക്കുന്ന സംവിധാനവും
`src/shared/constants/modalityBridgeDefaults.ts`-ലാണ്. ഗാർഡ്‌റെയിൽ ഒരു
`deps` കൺസ്ട്രക്റ്റർ ഓപ്ഷൻ ലഭ്യമാക്കുന്നു; അതുവഴി പരിശോധനകൾക്ക് വ്യാജ `getSettings`,
`callVisionModel` ഇംപ്ലിമെന്റേഷനുകൾ ഇൻജെക്റ്റ് ചെയ്യാനാകും.

### ഓഡിയോ ബ്രിഡ്ജ് (`audioBridge.ts`) — മോഡാലിറ്റി ബ്രിഡ്ജ് PR-3

ഓഡിയോ ഇൻപുട്ട് സ്വീകരിക്കുമെന്ന് അറിയാത്ത ഒരു ലക്ഷ്യസ്ഥാനത്ത് എത്തുന്നതിനു മുമ്പ്,
ഓഡിയോ അടങ്ങിയ ചാറ്റ് അഭ്യർത്ഥനകളെ തടഞ്ഞെടുത്ത് കൈകാര്യം ചെയ്യുന്നു. ഇത് ഒരിക്കലും ചാറ്റ് അഭ്യർത്ഥന റീറൂട്ട് ചെയ്യുന്നില്ല:
നിലവിലുള്ള OpenAI-അനുയോജ്യമായ മൾട്ടിപാർട്ട് എൻഡ്‌പോയിന്റ് വഴി ഓഡിയോ ഭാഗങ്ങൾ
ടെക്സ്റ്റായി ട്രാൻസ്ക്രൈബ് ചെയ്യുന്നു; തിരഞ്ഞെടുത്ത ചാറ്റ് മോഡൽ ആ ടെക്സ്റ്റ് ട്രാൻസ്ക്രിപ്റ്റുകളുമായി തുടരുന്നു.

പ്രവാഹം:

1. `getResolvedModelCapabilities()` വഴി `supportsAudio` നിർണ്ണയിക്കുക. വ്യക്തമായി
   നൽകിയ provider-registry മെറ്റാഡാറ്റയ്ക്കാണ് മുൻഗണന, തുടർന്ന് സ്റ്റാറ്റിക് മോഡൽ
   മെറ്റാഡാറ്റയ്ക്കും, അതിനുശേഷം സമന്വയിപ്പിച്ച `modalities_input`-നും.
   പ്രഖ്യാപിച്ച ഇൻപുട്ട് പട്ടികയിൽ `audio` ഇല്ലെങ്കിൽ മൂല്യം `false` ആണ്; ശേഷി
   സംബന്ധിച്ച തെളിവൊന്നുമില്ലെങ്കിൽ `null` ആയി തുടരും. `false`, `null` എന്നിവ
   രണ്ടും കരുതലോടെയുള്ള ബ്രിഡ്ജ് സജീവമാക്കുന്നു; `true` അതിനെ മറികടക്കുന്നു.
2. `modalityBridgeAudio*` ക്രമീകരണങ്ങൾ നിർണ്ണയിക്കുകയും പങ്കിട്ട
   `detectMediaParts()` ഡിറ്റക്ടർ വഴി ഓരോ സന്ദേശത്തിൽനിന്നും മാറ്റിച്ചേർക്കാവുന്ന
   ടോപ്പ്-ലെവൽ ഓഡിയോ ഭാഗങ്ങൾ വേർതിരിച്ചെടുക്കുകയും ചെയ്യുക. പിന്തുണയ്ക്കുന്ന വയർ
   രൂപങ്ങൾ OpenAI `input_audio`, `audio_url`, `source.media_type: "audio/*"`
   എന്നിവയാണ്. നെസ്റ്റഡ് ഓഡിയോ റൂട്ടിങ്ങിനായി കണ്ടെത്തുന്നു, എന്നാൽ മാറ്റിച്ചേർക്കൽ
   പാത അത് നീക്കം ചെയ്യുന്നില്ല. പ്രവർത്തനം `modalityBridgeAudioMaxClips` വഴി
   പരിമിതപ്പെടുത്തിയിരിക്കുന്നു; പിന്നീടുള്ള ഭാഗങ്ങൾ മാറ്റമില്ലാതെ തുടരും.
3. കോൺഫിഗർ ചെയ്ത `provider/model` മാനിക്കുക, അല്ലെങ്കിൽ
   `selectAudioBridgeModel()`-നെ സ്ഥിരമായ കാറ്റലോഗ് ക്രമത്തിൽ
   `AUDIO_TRANSCRIPTION_PROVIDERS` പരിശോധിച്ച് ഉപയോഗയോഗ്യമായ സജീവ പ്രൊവൈഡർ
   ക്രെഡൻഷ്യലുള്ള ആദ്യ മോഡൽ തിരഞ്ഞെടുക്കാൻ അനുവദിക്കുക.
4. `callAudioTranscription()` base64/data-URI ഓഡിയോയെ ഒരു multipart `file`
   ആക്കി മാറ്റുന്നു, അല്ലെങ്കിൽ DNS പിന്നിങ്ങും 25 MB പരിധിയുമുള്ള,
   പൊതുവിലാസങ്ങൾ മാത്രം അനുവദിക്കുന്ന ഔട്ട്ബൗണ്ട് ഗാർഡ് വഴി റിമോട്ട് `audio_url`
   ഡൗൺലോഡ് ചെയ്യുന്നു. തുടർന്ന് `resolveSelfLoopBearer()` ഉപയോഗിച്ച്
   പ്രാമാണീകരിച്ച്, ഫയലും തിരഞ്ഞെടുത്ത മോഡലും ലോക്കൽ
   `/v1/audio/transcriptions` സെൽഫ്-ലൂപ്പിലേക്ക് POST ചെയ്യുന്നു. നിലവിലുള്ള
   ട്രാൻസ്ക്രിപ്ഷൻ റൂട്ട് സാധാരണ ക്രെഡൻഷ്യൽ ലുക്കപ്പ്, കൂൾഡൗൺ/റേറ്റ്-ലിമിറ്റ്
   കൈകാര്യം ചെയ്യൽ, പ്രൊവൈഡർ ഡിസ്പാച്ച് എന്നിവ നിർവഹിക്കുന്നു.
5. വിജയകരമായ കോളുകൾ അവയുടെ ഭാഗങ്ങൾക്ക് പകരം `[Audio N]: <transcript>`
   ചേർക്കുന്നു. കോളുകൾ `Promise.allSettled` ഉപയോഗിച്ച് പ്രവർത്തിക്കുന്നു:
   ഒരു കോൾ പരാജയപ്പെട്ടാൽ അതിന്റെ യഥാർത്ഥ ഓഡിയോ ഭാഗം നിലനിർത്തുന്നു (#4012 കരാർ).
   എല്ലാ കോളുകളും പരാജയപ്പെടുകയും ലക്ഷ്യത്തിന് `supportsAudio === false` ആണെന്ന്
   സ്ഥിരീകരിക്കപ്പെടുകയും ചെയ്താൽ, ഭാഗങ്ങൾ
   `[Audio N]: (unavailable — no STT provider connected)` ആയി മാറുന്നു (#8430 കരാർ).
   ലക്ഷ്യത്തിന്റെ ശേഷി അജ്ഞാതമാണെങ്കിൽ (`null`), എല്ലാ കോളുകളും പരാജയപ്പെട്ട
   ഫലം മാറ്റമില്ലാതെ തുടരും. ടെക്സ്റ്റ് മാത്രം പിന്തുണയ്ക്കുന്നതായി
   സ്ഥിരീകരിക്കപ്പെട്ട ലക്ഷ്യത്തിന് ഉപയോഗയോഗ്യമായ STT ക്രെഡൻഷ്യൽ ഇല്ലെങ്കിൽ,
   നെറ്റ്‌വർക്ക് കോൾ നടത്താതെ അതേ വ്യക്തമായ സ്റ്റബ് നൽകുന്നു.

വിജയകരമായ ട്രാൻസ്ക്രിപ്റ്റുകൾ പ്രോസസിലുടനീളം പങ്കിടുന്ന Modality Bridge LRU/TTL
കാഷ് ഉപയോഗിക്കുന്നു. ഓഡിയോ റഫറൻസ്, സ്ഥിരമായ `audio-transcription` ഓപ്പറേഷൻ
ലേബൽ, തിരഞ്ഞെടുത്ത STT മോഡൽ എന്നിവ ചേർന്നതാണ് കീ; പരാജയങ്ങൾ ഒരിക്കലും കാഷ്
ചെയ്യുന്നില്ല. ഓഡിയോ ശ്രമങ്ങൾ പങ്കിട്ട `bridged`, `cacheHits`, `failures`,
`lastUsedAt` കൗണ്ടറുകൾ അപ്ഡേറ്റ് ചെയ്യുന്നു.
രൂപാന്തരപ്പെടുത്തിയ പ്രതികരണങ്ങളിൽ
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` ഉണ്ടായിരിക്കും;
മാറ്റമില്ലാത്ത അഭ്യർത്ഥനകൾക്ക് Audio Bridge സെഗ്മെന്റ് ലഭിക്കില്ല.

റൺടൈം ക്രമീകരണങ്ങൾ DB-യിൽ സംഭരിക്കപ്പെടുകയും Zod ഉപയോഗിച്ച് സാധൂകരിക്കപ്പെടുകയും ചെയ്യുന്നു:

| കീ                            | ഡിഫോൾട്ട് | പരിധി                     |
| ----------------------------- | --------- | ------------------------- |
| `modalityBridgeAudioEnabled`  | `true`    | —                         |
| `modalityBridgeAudioModel`    | `""`      | സ്വയമേവ അല്ലെങ്കിൽ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`   | 1000–300000               |
| `modalityBridgeAudioMaxClips` | `3`       | 1–10                      |

പങ്കിട്ട കാഷ് തുടർന്നും `modalityBridgeCacheEnabled`,
`modalityBridgeCacheTtlMinutes`, `modalityBridgeCacheMaxEntries` എന്നിവയാൽ നിയന്ത്രിക്കപ്പെടുന്നു.

### വീഡിയോ ബ്രിഡ്ജ് (`videoBridge.ts`, `videoBridgePipeline.ts`)

നേറ്റീവ് വീഡിയോ പിന്തുണയുണ്ടെന്ന് അറിയാത്ത ഒരു ലക്ഷ്യത്തെ വിളിക്കുന്നതിനുമുമ്പ്,
Chat Completions `messages`-ലെയും Responses API `input`-ലെയും ടോപ്പ്-ലെവൽ
വീഡിയോ ഭാഗങ്ങൾ ഇന്റർസെപ്റ്റ് ചെയ്യുന്നു.
പിന്തുണയ്ക്കുന്ന രൂപങ്ങൾ `input_video`, `video_url`, `video_source`, HTTPS URL-കൾ,
`data:video/*;base64,...` ഡാറ്റ URI-കൾ എന്നിവയാണ്. ടെക്സ്റ്റിലെ സാധാരണ
ഫയൽനാമങ്ങളെ വീഡിയോയായി കണക്കാക്കുന്നില്ല.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) അഭ്യർത്ഥനയിലൂടെയുള്ള സഞ്ചാരം,
ശേഷി/നയ പരിശോധന, ഓരോ അഭ്യർത്ഥനയ്ക്കുമുള്ള സമാഹരണം, പ്രതികരണ പേലോഡ് എന്നിവയുടെ
ഉത്തരവാദിത്തം വഹിക്കുന്നു.
ഓരോ വീഡിയോയ്ക്കുമുള്ള പ്രവർത്തനങ്ങൾ — ലഭ്യമാക്കൽ, പൂർണ്ണഫല കാഷ്, ഫ്രെയിം
സീക്വൻസിന്റെ വിവരണം (വിളിക്കുന്നയാൾ പ്രഖ്യാപിച്ച ഓഡിയോ ട്രാൻസ്ക്രിപ്റ്റ്
ഉണ്ടെങ്കിൽ അതും സംയോജിപ്പിക്കുന്നു), ഓരോ ശ്രമത്തിനുമുള്ള മെട്രിക്കുകൾ/നിർത്തലാക്കൽ/ശുചീകരണം —
`videoBridgePipeline.ts`-ലെ `processVideoPart`-ന് പിന്നിൽ മറച്ചിരിക്കുന്നു.
`preCall`-ന്റെ ലൂപ്പിനുള്ളിൽ ഓരോ വീഡിയോ ഭാഗത്തിനും ഇത് ഒരിക്കൽ വിളിക്കുന്നു.
ആ മൊഡ്യൂൾ വ്യക്തമായ പോർട്ട് അതിർത്തികളും നിർവചിക്കുന്നു:
`VideoMediaBrokerPort` (ബൈറ്റുകൾ ലഭ്യമാക്കലും സാമ്പിൾ ചെയ്ത ഫ്രെയിമുകൾ വേർതിരിച്ചെടുക്കലും),
`VideoAudioTranscriptionPort` (വിളിക്കുന്നയാൾ പ്രഖ്യാപിച്ച ഓഡിയോ ട്രാൻസ്ക്രിപ്റ്റ്
സാമ്പിൾ ചെയ്ത അടിക്കുറിപ്പുകളുമായി സംയോജിപ്പിക്കൽ),
`VideoDrilldownPort` (ഫ്രെയിം ഡ്രിൽ-ഡൗൺ സ്ഥിരസംഭരണ അതിർത്തി; ഇതുവരെ

ടെക്സ്റ്റ് മാർക്കറുകളായി മാറുന്നു; അതിനാൽ അസംസ്കൃത വീഡിയോ ഒന്നും ശേഷിക്കില്ല. ശേഷി അജ്ഞാതമായിരിക്കുമ്പോൾ, ആ ഭാഗങ്ങൾ
അവയുടെ വീഡിയോ കാരിയർ നിലനിർത്തുന്നു; ഏതൊരു ഫോൾബാക്ക് ട്രാൻസ്ക്രിപ്റ്റും മുകളിലെ പരിധിനിർണ്ണയിച്ച ടെക്സ്റ്റ്
പരിവർത്തനം പിന്തുടരുന്നു. `supportsVideo === true` ഉള്ള ടാർഗെറ്റുകൾ ബ്രിഡ്ജിനെ മറികടക്കുന്നു.
ക്ലയന്റ് അഭ്യർത്ഥനയുടെ അബോർട്ട് സിഗ്നൽ ഡൗൺലോഡ്, ബ്രോക്കർ ക്യൂ,
സബ്‌പ്രോസസുകൾ, ക്യാപ്ഷൻ കോളുകൾ എന്നിവയിലൂടെ കൈമാറുന്നു; അബോർട്ടുകൾ വീഡിയോകൾക്കിടയിൽ പ്രോസസ്സിംഗ് നിർത്തുന്നു; ഒരിക്കലും സുരക്ഷാ നിയന്ത്രണങ്ങൾ ഒഴിവാക്കി
അസംസ്കൃത മീഡിയ കടത്തിവിടുന്നില്ല.

റൺടൈം ക്രമീകരണങ്ങൾ DB-യിൽ സംഭരിക്കുകയും Zod ഉപയോഗിച്ച് സാധൂകരിക്കുകയും ചെയ്യുന്നു:

| കീ                                  | സ്ഥിരസ്ഥിതി | പരിധി / പ്രവർത്തനം                                                                                                                     |
| ----------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | ഐച്ഛിക റൺടൈം, വ്യക്തമായി പ്രവർത്തനക്ഷമമാക്കണം                                                                                          |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` പൊതുവായ ക്യാപ്ഷനുകൾ നിലനിർത്തുന്നു; `focused` പരിധിനിർണ്ണയിച്ച, വിശ്വസനീയമല്ലാത്ത ഏറ്റവും പുതിയ ഉപയോക്തൃ സന്ദർഭം ഉപയോഗിക്കുന്നു |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge മോഡൽ പിന്തുടരുന്നു                                                                                                       |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                                                   |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"` | `uniform`, `scene_aware`, അല്ലെങ്കിൽ ആനുപാതികമായ `segment_aware`; ഡിറ്റക്ടർ പരാജയപ്പെട്ടാൽ `uniform` ഉപയോഗിക്കുന്നു                    |
| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                                                    |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 ms                                                                                                                         |

മുമ്പ് സംഭരിച്ച, 120 സെക്കൻഡിനു മുകളിലുള്ള Video ടൈംഔട്ട് മൂല്യങ്ങൾ
ബ്രോക്കർ സമയപരിധിയിലേക്ക് ചുരുക്കുന്നു; ആ പരിധിക്കു മുകളിലുള്ള പുതിയ ക്രമീകരണങ്ങൾ എഴുതുന്നത് നിരസിക്കുന്നു.
`GET /api/modality-bridge/video/runtime`-ന് ഓതന്റിക്കേഷനോ റൺടൈം പരിശോധനയോ നടത്തുന്നതിനു മുമ്പ് വിശ്വസനീയമായ സ്റ്റാമ്പുള്ള ലൂപ്പ്ബാക്ക്
ലോക്കാലിറ്റി ആവശ്യമാണ്; തുടർന്ന് മാനേജ്‌മെന്റ്
ഓതന്റിക്കേഷൻ ആവശ്യമാണ്. ഇത് `available`, സുരക്ഷിതമാക്കിയ FFmpeg/ffprobe പതിപ്പുകൾ, റൺടൈം ലഭ്യമല്ലെങ്കിൽ ഒരു നിശ്ചിത
കാരണം എന്നിവ മാത്രമേ മടക്കിനൽകൂ. ആന്തരിക എക്സ്ട്രാക്ഷൻ എൻഡ്‌പോയിന്റ്
ഒരു പൊതു അപ്‌ലോഡ് API അല്ല: ക്യൂ നിറഞ്ഞാൽ `503`-നൊപ്പം `Retry-After` മടക്കിനൽകുന്നു; കോളർ
വിച്ഛേദിച്ചാൽ `499` മടക്കിനൽകുന്നു; നിശ്ചിത ബ്രോക്കർ സമയപരിധി കഴിഞ്ഞാൽ `504` മടക്കിനൽകുന്നു. പരിവർത്തനം ചെയ്ത പ്രതികരണങ്ങൾ
Vision അല്ലെങ്കിൽ Audio സെഗ്‌മെന്റുകൾ നീക്കം ചെയ്യാതെ കേന്ദ്ര
`x-omniroute-modality-bridge` ഹെഡറിലേക്ക് `video->text;model=<visionModel>;parts=<videos>` ചേർക്കുന്നു.

### PII മാസ്കർ (`piiMasker.ts`)

**രണ്ട്** ഘട്ടങ്ങളിലും പ്രവർത്തിക്കുന്നു.

- **`preCall`** പേലോഡ് ക്ലോൺ ചെയ്യുകയും, `system`, `messages`, `input`,
  `prompt` എന്നിവയിലൂടെ (സാധാരണ സ്ട്രിംഗ് ഇനങ്ങൾ ഉൾപ്പെടെ) സഞ്ചരിക്കുകയും,
  സ്ട്രിംഗ് `content`/`text` ഫീൽഡുകളിൽ `processPII()` (`@/shared/utils/inputSanitizer`-ൽ
  നിന്നുള്ളത്) പ്രയോഗിക്കുകയും ചെയ്യുന്നു. `PII_REDACTION_ENABLED=true`
  ആയിരിക്കുമ്പോൾ, കണ്ടെത്തിയ PII പുറത്തേക്ക് അയക്കുന്ന പേലോഡിൽ മറയ്ക്കപ്പെടും.
  ഇത് `INPUT_SANITIZER_MODE`-ൽ നിന്ന് സ്വതന്ത്രമാണ് (അത് പ്രോംപ്റ്റ്-ഇൻജക്ഷൻ
  നയം മാത്രമേ നിയന്ത്രിക്കൂ). മറയ്ക്കൽ ഓഫായിരിക്കുമ്പോൾ, ഉള്ളടക്കം
  മാറ്റിയെഴുതാതെ കോൾ കണ്ടെത്തലുകളുടെ എണ്ണം രേഖപ്പെടുത്തുന്നു.
- **`postCall`** പ്രതികരണത്തിന്റെ ഡീപ് ക്ലോൺ സൃഷ്ടിക്കുകയും, `sanitizePIIResponse()`-ഉം
  Responses-API-ഘടനയ്ക്കുള്ള മാസ്കറും (`maskResponsesOutput` —
  `output_text`, `output[].content[].text` എന്നിവ ഉൾക്കൊള്ളുന്നു) പ്രവർത്തിപ്പിക്കുകയും
  ചെയ്യുന്നു. എന്തെങ്കിലും മറയ്ക്കൽ നടന്നാൽ, മാറ്റം വരുത്തിയ പ്രതികരണം
  യഥാർത്ഥ പ്രതികരണത്തിന് പകരമാകും.

ഗാർഡ്‌റെയിൽ ഒരിക്കലും തടയുന്നില്ല; അത് അനോട്ടേറ്റ് ചെയ്യുകയോ (`meta.detections`,
`meta.redacted`) മാറ്റിയെഴുതുകയോ മാത്രമേ ചെയ്യുന്നുള്ളൂ.

#### തരം തിരിച്ചുള്ള തിരഞ്ഞെടുപ്പ്, ഇഷ്‌ടാനുസൃത പാറ്റേണുകൾ, കണ്ടെത്തൽ കൗണ്ടറുകൾ

**ഡാഷ്‌ബോർഡ് → ക്രമീകരണങ്ങൾ → സുരക്ഷ → PII മാസ്കിംഗ്** _എന്താണ്_ മറയ്ക്കേണ്ടതെന്ന് തിരഞ്ഞെടുക്കുന്നു. ഇത്
മാസ്കിംഗ് ഓണാക്കുന്നില്ല: അത് ഇപ്പോഴും `PII_REDACTION_ENABLED` (അഭ്യർത്ഥന),
`PII_RESPONSE_SANITIZATION` (പ്രതികരണം + SSE) എന്നിവയാണ് നിയന്ത്രിക്കുന്നത്; രണ്ടും ഡിഫോൾട്ടായി ഓഫാണ്.

- **തരം തിരിച്ചുള്ള തിരഞ്ഞെടുപ്പ്** — ബിൽറ്റ്-ഇൻ ഐഡികൾ
  `src/shared/constants/piiTypes.ts`-ൽ (`PII_BUILTIN_TYPES`) പട്ടികപ്പെടുത്തിയിരിക്കുന്നു. സജ്ജമാക്കിയിട്ടില്ലെങ്കിൽ എല്ലാ
  തരങ്ങളും ഉൾപ്പെടും (ഈ ക്രമീകരണം നിലവിൽ വരുന്നതിന് മുമ്പുണ്ടായിരുന്ന പെരുമാറ്റം). അഭ്യർത്ഥനാ എഞ്ചിന്റെ
  `ssn_us` പാറ്റേൺ `ssn`-ലേക്ക് മാപ്പ് ചെയ്യപ്പെടുന്നു. ടെംപ്ലേറ്റുകൾ (മിനിമൽ, സ്റ്റാൻഡേർഡ്, ഫിനാൻഷ്യൽ,
  ബ്രസീലിയൻ, USA, ഫുൾ) UI-യിലെ ചെക്ക്ബോക്സുകൾ പൂരിപ്പിക്കുക മാത്രമേ ചെയ്യുന്നുള്ളൂ.
- **ഇഷ്‌ടാനുസൃത പാറ്റേണുകൾ** — പരമാവധി 20 regex അല്ലെങ്കിൽ വൈൽഡ്കാർഡ് പാറ്റേണുകൾ (`*` = പരമാവധി 64
  വൈറ്റ്‌സ്‌പേസ് അല്ലാത്ത പ്രതീകങ്ങൾ, `?` = ഒരെണ്ണം). പൊരുത്തപ്പെടുന്നവ `[CUSTOM_REDACTED]` ആയി മാറുന്നു.
  ഓരോ പാറ്റേണും `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`) വഴി കടന്നുപോകുന്നു: പരമാവധി 500 പ്രതീകങ്ങൾ, ഫ്ലാഗുകൾ
  `g i m s u`-ൽ പരിമിതപ്പെടുത്തിയിരിക്കുന്നു, കംപൈൽ ചെയ്യാൻ കഴിയണം, `safe-regex` പരിശോധന വിജയിക്കണം (വിനാശകരമായ
  ബാക്ക്ട്രാക്കിംഗ്), കൂടാതെ ശൂന്യമായ സ്ട്രിംഗുമായോ മറയ്ക്കലിനുള്ള പ്ലേസ്‌ഹോൾഡറുമായോ പൊരുത്തപ്പെടരുത്.
  പരിശോധനയിൽ പരാജയപ്പെടുന്ന പാറ്റേൺ സംരക്ഷിക്കുമ്പോഴും പരീക്ഷിക്കുമ്പോഴും നിരസിക്കപ്പെടും; സംഭരിച്ച ഒരു വരി
  പരാജയപ്പെട്ടാൽ റൺടൈമിൽ അത് കംപൈൽ ചെയ്യുന്നതിന് പകരം ഒഴിവാക്കും. ഇഷ്‌ടാനുസൃത പാറ്റേണുകൾ
  മാസ്കിംഗ് ഓണായിരിക്കുമ്പോൾ മാത്രമേ പ്രവർത്തിക്കൂ.
- **കണ്ടെത്തൽ കൗണ്ടറുകൾ** — ഓരോ തരത്തിനുമുള്ള എണ്ണങ്ങൾ (പൊരുത്തപ്പെട്ട മൂല്യങ്ങൾ ഒരിക്കലും ഉൾപ്പെടില്ല), മെമ്മറിയിൽ
  സൂക്ഷിക്കുകയും പുനരാരംഭിക്കുമ്പോൾ പുനഃസജ്ജമാക്കുകയും ചെയ്യുന്നു (`src/lib/pii/piiDetectionStats.ts`). ഇവ
  മാസ്കിംഗ് ഓണായിരിക്കുമ്പോൾ മാത്രമേ വർധിക്കൂ.

ക്രമീകരണങ്ങൾ `key_value` പട്ടികയിൽ (നെയിംസ്‌പേസ് `pii_settings`,
`src/lib/db/piiSettings.ts`) സൂക്ഷിച്ചിരിക്കുന്നു; 1 സെക്കൻഡ് കാഷെ വഴി വായിക്കുന്നു. API:

| രീതി   | പാത്ത്                   | ഉദ്ദേശ്യം                                                                                       |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | ഫ്ലാഗിന്റെ നില, `enabledTypes`, `customPatterns`, കണ്ടെത്തൽ കൗണ്ടറുകൾ                           |
| `PUT`  | `/api/settings/pii`      | `enabledTypes` (`null` = എല്ലാം) കൂടാതെ/അല്ലെങ്കിൽ `customPatterns` മാറ്റിസ്ഥാപിക്കുക           |
| `POST` | `/api/settings/pii/test` | പരമാവധി 8 KB സാമ്പിളിൽ ഒരു പാറ്റേൺ പരീക്ഷണാടിസ്ഥാനത്തിൽ പ്രവർത്തിപ്പിക്കുക; ഒന്നും സംഭരിക്കില്ല |

മൂന്നിനും മാനേജ്മെന്റ് ഓതന്റിക്കേഷൻ ആവശ്യമാണ്; ബോഡി Zod ഉപയോഗിച്ച് സാധൂകരിക്കുന്നു
(`src/shared/validation/schemas/piiSettings.ts`).

### പ്രോംപ്റ്റ് ഇൻജക്ഷൻ (`promptInjection.ts`)

ഉപയോക്താവ് നൽകിയ ഉള്ളടക്കത്തിലെ ആക്രമണാത്മക ഘടനകൾ കണ്ടെത്തുകയും ക്രമീകരിച്ച
നയം നടപ്പിലാക്കുകയും ചെയ്യുന്നു. പെരുമാറ്റം എൻവയോൺമെന്റ് വേരിയബിളുകളും കൺസ്ട്രക്ടർ
ഓപ്ഷനുകളും നിയന്ത്രിക്കുന്നു:

| ക്രമീകരണം            | എൻവയോൺമെന്റ് വേരിയബിൾ                                                                                               | ഡിഫോൾട്ട് | പ്രഭാവം                                                                                                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| പ്രവർത്തനക്ഷമം       | `INPUT_SANITIZER_ENABLED`                                                                                           | `true`    | `false` ആയിരിക്കുമ്പോൾ, ഗാർഡ്‌റെയിൽ പരിശോധന നടത്താതെ മടങ്ങുന്നു.                                                                                                                                                                              |
| മോഡ്                 | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                                     | `warn`    | ഇൻജക്ഷൻ നയം: `block`, `warn`, അല്ലെങ്കിൽ `log`. (പിന്നോട്ടുള്ള അനുയോജ്യതയ്ക്കായി `redact` സ്വീകരിക്കുന്നു, എന്നാൽ അത് ഇൻജക്ഷൻ ടെക്സ്റ്റ് നീക്കം ചെയ്യുകയില്ല; അഭ്യർത്ഥനയിലെ PII മാറ്റിയെഴുതൽ നിയന്ത്രിക്കുന്നത് `PII_REDACTION_ENABLED` ആണ്.) |
| തടയുന്നതിനുള്ള പരിധി | `blockThreshold` ഓപ്ഷൻ / `INPUT_SANITIZER_BLOCK_THRESHOLD` (`INJECTION_GUARD_BLOCK_THRESHOLD` എന്ന അപരനാമവും ഉണ്ട്) | `high`    | തടയുന്നതിന് ആവശ്യമായ ഏറ്റവും കുറഞ്ഞ തീവ്രത. ഡിഫോൾട്ടായി ഇടത്തരം തീവ്രതയുള്ളവ നിരീക്ഷിക്കുക മാത്രമേ ചെയ്യൂ.                                                                                                                                    |

**മോഡിന്റെ മുൻഗണനാക്രമം** (`getMode`): വിളിക്കുന്നവന്റെ `options.mode` →
`INJECTION_GUARD_MODE` **DB ഫീച്ചർ-ഫ്ലാഗ് ഓവർറൈഡ്** (ഡാഷ്‌ബോർഡ് → ക്രമീകരണങ്ങൾ →
ഫീച്ചർ ഫ്ലാഗുകൾ) → `INJECTION_GUARD_MODE` എൻവയോൺമെന്റ് വേരിയബിൾ → `INPUT_SANITIZER_MODE` എൻവയോൺമെന്റ് വേരിയബിൾ →
`warn`. അതിനാൽ ഡാഷ്‌ബോർഡ് ഓവർറൈഡിന് എൻവയോൺമെന്റ് വേരിയബിളുകളേക്കാൾ മുൻഗണനയുണ്ട്; അതുകൊണ്ട് ഫീച്ചർ
ഫ്ലാഗുകൾ UI പ്രവർത്തിച്ചുകൊണ്ടിരിക്കുന്ന ഗാർഡിനെ തത്സമയം നിയന്ത്രിക്കുന്നു (പുനരാരംഭിക്കേണ്ടതില്ല). DB വായന പരാജയപ്പെട്ടാലും സുരക്ഷിതമായി കൈകാര്യം ചെയ്യപ്പെടുന്നു:
അതിൽ പിശകുണ്ടായാൽ, ഗാർഡ് എൻവയോൺമെന്റ് അടിസ്ഥാനത്തിലുള്ള പെരുമാറ്റത്തിലേക്ക് മടങ്ങുന്നു; ഓവർറൈഡ്
സജ്ജമാക്കിയിട്ടില്ലെങ്കിൽ, പെരുമാറ്റം എൻവയോൺമെന്റ് വേരിയബിളുകൾ മാത്രം അടിസ്ഥാനമാക്കി നിർണയിക്കുന്നതിന് തുല്യമാണ്.

കണ്ടെത്തലിന്റെ ഉറവിടങ്ങൾ:

1. `@/shared/utils/inputSanitizer`-ൽ നിന്നുള്ള `sanitizeRequest()` (പൈപ്പ്‌ലൈനിൽ
   മറ്റിടങ്ങളിലും ഉപയോഗിക്കുന്ന പൊതുവായ ഡിറ്റക്ടർ സെറ്റ്).
2. ബിൽറ്റ്-ഇൻ `DEFAULT_GUARD_PATTERNS` (നിലവിൽ `system_override_inline`,
   `markdown_system_block` എന്നിവ; രണ്ടിന്റെയും തീവ്രത `high` ആണ്).
3. കൺസ്ട്രക്ടർ ഓപ്ഷനുകൾ വഴി നൽകുന്ന ഐച്ഛിക `customPatterns` (സ്ട്രിംഗുകൾ, regex,
   അല്ലെങ്കിൽ `{ name, pattern, severity }` റെക്കോർഡുകൾ).

`mode === "block"` ആയിരിക്കുകയും **അതോടൊപ്പം** കണ്ടെത്തലുകളിൽ കുറഞ്ഞത് ഒന്നെങ്കിലും തീവ്രതയുടെ
പരിധി പാലിക്കുകയും ചെയ്യുമ്പോൾ, `preCall` തിരികെ നൽകുന്നത് `{ block: true, message: "Request rejected:
suspicious content detected" }` ആണ്. `warn`/`log` മോഡുകളിൽ ഗാർഡ്‌റെയിൽ ലോഗ് രേഖപ്പെടുത്തുമെങ്കിലും
കോൾ അനുവദിക്കും. രജിസ്ട്രിയിലൂടെ കടന്നുപോകാതെ പ്രോംപ്റ്റുകൾ വിലയിരുത്തേണ്ട കോളർമാർക്കായി
പങ്കിട്ട ഹെൽപ്പറായ `evaluatePromptInjection()` എക്സ്പോർട്ട് ചെയ്തിട്ടുമുണ്ട്.

**സ്കാൻ പരിധി (v3.8.20):** കൂട്ടിച്ചേർത്ത പ്രോംപ്റ്റ് ടെക്സ്റ്റിന്റെ **ആദ്യത്തെ 16 KB** മാത്രമേ
ഡിറ്റക്ടർ പരിശോധിക്കൂ — `src/shared/utils/inputSanitizer.ts`-ൽ
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ബൈറ്റുകൾ). പാറ്റേൺ ലൂപ്പ് പ്രവർത്തിപ്പിക്കുന്നതിന് മുമ്പ്
`detectInjection()`, `evaluatePromptInjection()` എന്നിവ രണ്ടും
`slice(0, MAX_INJECTION_SCAN_BYTES)` പ്രയോഗിക്കുന്നു. ഇൻജക്ഷൻ നിർദ്ദേശങ്ങൾ ഇൻപുട്ടിന്റെ തുടക്കത്തിനടുത്താണ് ഉണ്ടാകാറുള്ളത്, അതിനാൽ
കണ്ടെത്തലിന്റെ കാര്യക്ഷമത കുറയ്ക്കാതെ നൂറുകണക്കിന് KB വലുപ്പമുള്ള പേലോഡുകളിൽ റെഗെക്സിന്റെ CPU/GC ഉപയോഗം ഇത് പരിമിതപ്പെടുത്തുന്നു (കാണുക:
#3932, #4041).

### ക്രെഡൻഷ്യൽ മാസ്കർ (`credentialMasker.ts`)

**രണ്ട്** ഘട്ടങ്ങളിലും പ്രവർത്തിക്കുന്നു; ഡിഫോൾട്ട് ശൃംഖലയിൽ അവസാനത്തേതാണ് (മുൻഗണന `95`). പുറത്തേക്കയക്കുന്ന
പേലോഡിൽനിന്നും (സന്ദേശത്തിന്റെ ഉള്ളടക്കം, ടൂൾ-കോൾ ആർഗ്യുമെന്റുകൾ, ടൂൾ ഫലങ്ങൾ) **അതോടൊപ്പം** ദാതാവിന്റെ പ്രതികരണത്തിൽനിന്നും
അറിയപ്പെടുന്ന API-കീ / സീക്രട്ട്-ടോക്കൺ പാറ്റേണുകൾ മറയ്ക്കുന്നു. അതിനാൽ പ്രോംപ്റ്റിൽ പേസ്റ്റ് ചെയ്ത
(അല്ലെങ്കിൽ ഒരു ടൂൾ ഫലം തിരികെ ആവർത്തിച്ച) ക്രെഡൻഷ്യൽ അപ്‌സ്ട്രീം ദാതാവിലേക്കോ
ക്ലയന്റിലേക്കു തിരികെയോ ചോരുന്നില്ല.

- **വ്യക്തമായി പ്രവർത്തനക്ഷമമാക്കിയാൽ മാത്രം**, PII മറയ്ക്കലിന്റെ അതേ രീതി (കർശന നിയമം #20-നോട് അനുബന്ധിച്ചത്):
  `settings.credentialRedactionEnabled === true` **അല്ലെങ്കിൽ**
  `CREDENTIAL_REDACTION_ENABLED=true` അല്ലെങ്കിൽ ഇത് പ്രവർത്തനരഹിതമായിരിക്കും. ഇത് ഓഫായിരിക്കുമ്പോൾ ഗാർഡ്‌റെയിൽ ഒന്നും ചെയ്യില്ല —
  ഒരിക്കലും തടയുകയോ മാറ്റിയെഴുതുകയോ ചെയ്യില്ല.
- `redactCredentials()` മുഴുവൻ പേലോഡ്/പ്രതികരണ ട്രീയിലൂടെയും സഞ്ചരിച്ച് (`walkValue()`,
  പ്രോട്ടോടൈപ്പ് പൊള്യൂഷനിൽനിന്ന് സുരക്ഷിതം, `WeakSet` വഴി ചക്രങ്ങളിൽനിന്ന് സുരക്ഷിതം) പൊരുത്തപ്പെടുന്നവയ്ക്ക് പകരം
  `[REDACTED:<type>]` പ്ലേസ്‌ഹോൾഡർ സ്ഥാപിക്കുന്നു; യഥാർത്ഥത്തിൽ മാറ്റം വന്ന ശാഖകൾ മാത്രം
  ക്ലോൺ ചെയ്യുന്നു.
- `CREDENTIAL_PATTERNS` ഉൾക്കൊള്ളുന്നവ: LLM ദാതാക്കളുടെ കീകൾ (OpenAI, OpenAI-proj,
  Anthropic, Google, Hugging Face, Replicate), VCS/SaaS ടോക്കണുകൾ (GitHub, Slack,
  Linear, Notion, npm, Postman, Discord), പേയ്‌മെന്റ് കീകൾ (Stripe, Square), ക്ലൗഡ്
  കീകൾ (AWS ആക്‌സസ് കീ, Twilio, SendGrid, Mailgun), സ്വകാര്യ കീകൾ / JWT-കൾ,
  ക്രെഡൻഷ്യലുകൾ അടങ്ങിയ കണക്ഷൻ സ്ട്രിങ്ങുകൾ (`mongodb://user:pass@...` മുതലായവ), കൂടാതെ
  പൊതുവായ `Authorization`/`x-api-key`/`api-key`/`apikey` ഹെഡർ-മൂല്യ
  പാറ്റേൺ. ഹെഡർ രൂപത്തിലുള്ള കീകൾ (`authorization`, `x-api-key`, `api-key`,
  `apikey`) പൊതുവായ ടെക്സ്റ്റ് റെഗെക്സ് ഉപയോഗിക്കുന്നതിന് പകരം ഘടനാപരമായാണ് മറയ്ക്കുന്നത്
  (മൂല്യം മാത്രം; `Bearer `/`Basic ` പോലുള്ള സ്കീം പ്രിഫിക്സുകൾ
  നിലനിർത്തുന്നു).
- ഗാർഡ്‌റെയിൽ ഒരിക്കലും തടയില്ല; അത് മാറ്റിയെഴുതുകയും (`modifiedPayload` /
  `modifiedResponse`) വ്യാഖ്യാനവിവരങ്ങൾ ചേർക്കുകയും (`meta.credentialsRedacted`, `meta.count`) മാത്രമേ ചെയ്യൂ.

റിഗ്രഷൻ പ്രതിരോധ പരിശോധന: `tests/unit/credential-masker-guardrail.test.ts`.

## അടിസ്ഥാന കരാർ (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true ചെയിനിന്റെ തുടർനിർവഹണം നിർത്തുന്നു
  message?: string; // തടയുമ്പോൾ പ്രദർശിപ്പിക്കുന്നു
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // അഭ്യർത്ഥന മാറ്റിയെഴുതാൻ preCall മടക്കിനൽകുന്നു
  modifiedResponse?: TValue; // പ്രതികരണം മാറ്റിയെഴുതാൻ postCall മടക്കിനൽകുന്നു
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

`void`, `{}`, അല്ലെങ്കിൽ
`{ block: false }` മടക്കിനൽകിക്കൊണ്ട് ഒരു ഗാർഡ്‌റെയിൽ "മാറ്റമില്ല" എന്ന് സൂചിപ്പിക്കുന്നു. `modifiedPayload`/`modifiedResponse` മടക്കിനൽകുന്നത്
ചെയിനിലൂടെ തുടർന്നുള്ള ഗാർഡ്‌റെയിലുകളിലേക്ക് ഒഴുകുന്ന മൂല്യത്തെ മാറ്റിസ്ഥാപിക്കുന്നു.
`signal?: AbortSignal` കോളറിന്റെ ജീവിതചക്രം ഗാർഡ്‌റെയിലുകളിലേക്ക് കൈമാറുന്നു. അഭ്യർത്ഥന റദ്ദാക്കൽ മനഃപൂർവമുള്ള ഫെയിൽ-ഓപ്പൺ ഒഴിവാണ്: മീഡിയ ബ്രിഡ്ജുകൾ പ്രവർത്തനം നിർത്തി ക്ലീനപ്പ് നടത്തുന്നു; അസംസ്കൃത മീഡിയയെ പിന്തുണയ്ക്കില്ലെന്ന് അറിയാവുന്ന ലക്ഷ്യത്തിലേക്ക് അത് പുനഃസ്ഥാപിക്കുന്നില്ല.

## രജിസ്ട്രി (`registry.ts`)

സിംഗിൾട്ടൺ `guardrailRegistry` ലഭ്യമാക്കുന്നവ:

- `register(guardrail)` — ഒരു ഗാർഡ്‌റെയിൽ ചേർക്കുന്നു (അല്ലെങ്കിൽ നോർമലൈസ് ചെയ്ത പേരിന്റെ അടിസ്ഥാനത്തിൽ മാറ്റിസ്ഥാപിക്കുന്നു),
  തുടർന്ന് `priority`-യുടെ ആരോഹണക്രമത്തിൽ വീണ്ടും ക്രമീകരിക്കുന്നു.
- `clear()` / `list()` — അഡ്മിനിസ്ട്രേറ്റീവ് സഹായികൾ.
- `runPreCallHooks(payload, context)` — സജീവ ഗാർഡ്‌റെയിലുകളിലൂടെ ക്രമമായി കടന്നുപോകുന്നു,
  `modifiedPayload` വഴി പേലോഡ് കൈമാറുന്നു, ആദ്യത്തെ `block: true` ലഭിക്കുമ്പോൾ നിർത്തുന്നു.
- `runPostCallHooks(response, context)` — പ്രതികരണത്തിന്റെ ഭാഗത്തും ഇതേ പ്രവാഹം.
- `resetGuardrailsForTests({ registerDefaults })` — ടെസ്റ്റുകൾ തമ്മിൽ പൂർണ്ണമായ വേർതിരിവ് ഉറപ്പാക്കാൻ സ്റ്റേറ്റ് മായ്‌ക്കുകയും ആവശ്യമെങ്കിൽ
  ഡിഫോൾട്ടുകൾ വീണ്ടും രജിസ്റ്റർ ചെയ്യുകയും ചെയ്യുന്നു.

രണ്ട് റണ്ണറുകളും `{ blocked, payload|response, results, guardrail?, message? }` മടക്കിനൽകുന്നു.
ഇതിലെ `results`, ഓരോ ഗാർഡ്‌റെയിലിനുമുള്ള
`blocked`, `skipped`, `modified`, `error`, `meta` ഫീൽഡുകൾ ഉൾപ്പെടുന്ന `GuardrailExecutionResult` റെക്കോർഡുകളുടെ ഒരു അറേയാണ്;
ട്രേസിങ്ങിന് ഇത് ഉപകാരപ്രദമാണ്.

### ഓരോ അഭ്യർത്ഥനയ്ക്കും ഗാർഡ്‌റെയിലുകൾ പ്രവർത്തനരഹിതമാക്കൽ

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` നിലവിലെ
അഭ്യർത്ഥനയിൽ ഒഴിവാക്കേണ്ട ഗാർഡ്‌റെയിൽ പേരുകളുടെ ആവർത്തനങ്ങളില്ലാത്ത ഒരു ലിസ്റ്റ് സമാഹരിക്കുന്നു.
അഞ്ച് ചാനലുകളുണ്ട്; അവ ഈ ക്രമത്തിൽ വായിച്ച് ഒരു ലിസ്റ്റിലേക്ക് ലയിപ്പിക്കുന്നു
(ആവർത്തനങ്ങൾ നീക്കുമ്പോൾ ആദ്യം കണ്ടത് നിലനിർത്തുന്നു):

1. `apiKeyInfo.disabledGuardrails`
2. അഭ്യർത്ഥന ബോഡിയിലെ `disabledGuardrails` (മുകളിലെ തലം)
3. അഭ്യർത്ഥന ബോഡിയിലെ `metadata.disabledGuardrails` (`metadata` ഒരു ഒബ്ജക്റ്റ് ആയിരിക്കുമ്പോൾ മാത്രം)
4. ഹെഡർ `x-omniroute-disabled-guardrails`
5. പഴയ ഹെഡർ `x-disabled-guardrails`

രണ്ട് ഹെഡറുകളും ഉൾപ്പെടെ അഞ്ച് ചാനലുകളും ലയിപ്പിക്കുന്നു:
`x-omniroute-disabled-guardrails`, `x-disabled-guardrails` എന്നിവ രണ്ടും അയച്ചാൽ
അവയുടെ ലിസ്റ്റുകളുടെ യൂണിയനിലുള്ളവ ഒഴിവാക്കപ്പെടുന്നു; കൂടാതെ ശൂന്യമായ പുതിയ ഹെഡർ ഇനി പഴയ ഹെഡറിനെ മറയ്ക്കുന്നില്ല
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412),
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)-ൽ പരിഹരിച്ചു).

മൂല്യങ്ങൾ സ്ട്രിങ്ങുകളുടെ അറേകളോ കോമയാൽ വേർതിരിച്ച സ്ട്രിങ്ങോ ആകാം; പേരുകളുടെ ഇരുവശത്തുമുള്ള ശൂന്യസ്ഥലങ്ങൾ നീക്കി
ചെറിയക്ഷരത്തിലുള്ള kebab-case-ലേക്ക് നോർമലൈസ് ചെയ്യുന്നു (`pii_masker` → `pii-masker`), ശൂന്യമായ
എൻട്രികൾ ഒഴിവാക്കുന്നു. ഫലം `context.disabledGuardrails` വഴി
രജിസ്ട്രിയിലേക്ക് കൈമാറുന്നു; അത് പൊരുത്തപ്പെടുന്ന ഗാർഡ്‌റെയിലുകൾ ഒഴിവാക്കുന്നു (`results`-ൽ `skipped: true`).

പ്രവർത്തനരഹിതമാക്കാനുള്ള ലിസ്റ്റ് **രജിസ്ട്രിയെ** മാത്രമേ ബാധിക്കൂ. പ്രോംപ്റ്റ്-ഇൻജക്ഷൻ `block` മോഡ്
നിർബന്ധിതമായ ഒരു അതിരാണ്: ഇൻജക്ഷൻ-ഗാർഡ് മിഡിൽവെയർ
(`src/middleware/promptInjectionGuard.ts`), കോളർ നിയന്ത്രിക്കുന്ന പ്രവർത്തനരഹിതമാക്കൽ ലിസ്റ്റുകളൊന്നുമില്ലാതെ
`evaluatePromptInjection()` വിളിക്കുന്നു (മുമ്പ് നടത്തിയിരുന്ന, ഉപയോഗശൂന്യമായ
`resolveDisabledGuardrails({ body })` കോൾ
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)-ൽ നീക്കം ചെയ്തു). അതിനാൽ
`prompt-injection` പ്രവർത്തനരഹിതമാക്കുന്ന ഒരു അഭ്യർത്ഥനയും `block` മോഡിൽ നിരസിക്കപ്പെടും. ഇത്
മനഃപൂർവമുള്ള രൂപകൽപ്പനയാണ്. പ്രവർത്തനരഹിതമാക്കാനുള്ള ചാനലുകൾ കോളറിന്റെ നിയന്ത്രണത്തിലാണ് (അഭ്യർത്ഥന ബോഡി,
മെറ്റാഡാറ്റ, ഹെഡറുകൾ); ഓപ്പറേറ്റർ സജ്ജമാക്കിയ ഒരു സുരക്ഷാ നിയന്ത്രണം
ഓഫ് ചെയ്യാൻ കോളറിന് കഴിയരുത്
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).
[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)-ലെ ഹെഡർ
യൂണിയൻ, ഏതൊക്കെ രജിസ്ട്രി ഗാർഡ്‌റെയിലുകൾ ഒഴിവാക്കപ്പെടുന്നു എന്നതിനെ മാത്രമാണ് മാറ്റുന്നത്; മിഡിൽവെയറിനെ
മറികടക്കാൻ അത് ക്ലയന്റിനെ അനുവദിക്കുന്നില്ല. ഓരോ കീയ്ക്കും ഓരോ ഗ്രൂപ്പിനും ബാധകമായ നിർബന്ധിത ഗാർഡ്‌റെയിൽ നയങ്ങൾ
v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417)-ൽ ട്രാക്ക് ചെയ്യുന്നു.
[പരിധിയും പരിമിതികളും](#coverage-and-limits) കാണുക.

## നിർവഹണ ക്രമം

`src/sse/handlers/chat.ts`,
`open-sse/handlers/chatCore.ts` എന്നിവയിലൂടെ കടന്നുപോകുന്ന ഓരോ അഭ്യർത്ഥനയ്ക്കും
([പരിധിയും പരിമിതികളും](#coverage-and-limits) എന്നതിന് കീഴിൽ പട്ടികപ്പെടുത്തിയിരിക്കുന്ന ചാറ്റ്-കുടുംബ റൂട്ടുകൾ):

1. `resolveDisabledGuardrails(...)`, API കീ, ബോഡി,
   ഹെഡറുകൾ എന്നിവയിൽനിന്ന് ഒഴിവാക്കേണ്ടവയുടെ പട്ടിക നിർമ്മിക്കുന്നു.
2. `guardrailRegistry.runPreCallHooks(body, ctx)`, മുൻഗണനയുടെ ആരോഹണ
   ക്രമത്തിൽ ഗാർഡ്‌റെയിലുകൾ പ്രവർത്തിപ്പിക്കുന്നു:
   - പ്രവർത്തനരഹിതമാക്കിയ ഗാർഡ്‌റെയിലുകൾ `skipped` ആയി രേഖപ്പെടുത്തുന്നു.
   - ഓരോ ഗാർഡ്‌റെയിലിന്റെയും `preCall`, `modifiedPayload` വഴി പേലോഡ് മാറ്റിയെഴുതിയേക്കാം.
   - ആദ്യം ലഭിക്കുന്ന `block: true` തുടർ ശൃംഖല നിർത്തുകയും ഹാൻഡ്‌ലർ
     ഒരു ഗാർഡ്‌റെയിൽ നിരസിക്കൽ പ്രതികരണം നൽകുകയും ചെയ്യുന്നു.
3. (മാറ്റിയെഴുതിയിരിക്കാവുന്ന) പേലോഡ് കോംബോ റൂട്ടിങ്ങിലേക്കും അപ്‌സ്ട്രീം
   ഡിസ്പാച്ചിലേക്കും കടക്കുന്നു.
4. **സ്ട്രീമിങ് അല്ലാത്തവയ്ക്ക് മാത്രം:** പ്രതികരണം കൂട്ടിച്ചേർത്തശേഷം,
   `guardrailRegistry.runPostCallHooks(...)` അതേ ശൃംഖല
   പ്രതികരണത്തിൽ പ്രവർത്തിപ്പിക്കുന്നു. ഇവിടെ `block: true` ലഭിച്ചാൽ അപ്‌സ്ട്രീം പ്രതികരണം ഉപേക്ഷിച്ച് HTTP 400 നൽകുന്നു. സ്ട്രീം ചെയ്യുന്ന പ്രതികരണങ്ങൾ ഈ ഘട്ടം പൂർണ്ണമായും ഒഴിവാക്കുന്നു.

എക്സെപ്ഷൻ ഉയർത്തുന്ന ഗാർഡ്‌റെയിലുകൾ `error: <message>` സഹിതം രേഖപ്പെടുത്തുകയും
`logger.warn` വഴി ലോഗ് ചെയ്യുകയും ചെയ്യുന്നു; എന്നിരുന്നാലും ശൃംഖല തുടരുന്നു — രൂപകൽപ്പനപ്രകാരം തന്നെ പരാജയത്തിലും തുടരുന്ന രീതിയാണിത്.

### ഉൾപ്പെടാത്തവ

- **മീഡിയ, എംബെഡിങ്ങുകൾ, ഡാറ്റ റൂട്ടുകൾ** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) ഒരിക്കലും രജിസ്ട്രിയിൽ എത്തുന്നില്ല.
  PII മാസ്കിങ്, ക്രെഡൻഷ്യൽ മാസ്കിങ്, മൊഡാലിറ്റി ബ്രിഡ്ജ് എന്നിവയൊന്നും അവിടെ പ്രവർത്തിക്കുന്നില്ല. അവയുടെ ഏക
  പരിശോധന ലെഗസി ഇൻജക്ഷൻ-ഗാർഡ് മിഡിൽവെയറാണ്.
- **സ്ട്രീം ചെയ്യുന്ന പ്രതികരണങ്ങൾക്ക്** പോസ്റ്റ്-കോൾ ഗാർഡ്‌റെയിലുകൾ ലഭിക്കുന്നില്ല: പോസ്റ്റ്-കോളിൽ `pii-masker` അല്ലെങ്കിൽ
  `credential-masker` ഇല്ല, പോസ്റ്റ്-കോൾ തടയലുമില്ല. സ്ട്രീമിങ് PII
  ട്രാൻസ്ഫോം മാത്രമാണ് ബാധകമാകുന്നത് (`PII_RESPONSE_SANITIZATION` ഓണായിരിക്കുമ്പോൾ). സ്ട്രീം ചെയ്യുന്ന പ്രതികരണത്തിൽ
  തിരികെ ആവർത്തിക്കപ്പെടുന്ന ക്രെഡൻഷ്യൽ മറച്ചുനീക്കപ്പെടുന്നില്ല.
- **പ്രവർത്തനരഹിതമാക്കാനുള്ള ചാനലുകളും മിഡിൽവെയറും (രൂപകൽപ്പനപ്രകാരം):** മിഡിൽവെയർ,
  വിളിക്കുന്നയാൾ നിയന്ത്രിക്കുന്ന പ്രവർത്തനരഹിതമാക്കൽ പട്ടികയൊന്നും കൈമാറാതെ,
  `evaluatePromptInjection()` നേരിട്ട് വിളിച്ച് പ്രോംപ്റ്റ് ഇൻജക്ഷൻ വിലയിരുത്തുന്നു. `block` മോഡ് നിർബന്ധമായ
  ഒരു അതിർത്തിയാണ്; ചാറ്റ്-കുടുംബ റൂട്ടുകളിലും വിളിക്കുന്നയാൾ നിയന്ത്രിക്കുന്ന പ്രവർത്തനരഹിതമാക്കലുകൾക്ക് ഇതിനെ മറികടക്കാനാവില്ല
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). `prompt-injection`
  പ്രവർത്തനരഹിതമാക്കുന്നത് രജിസ്ട്രി ഗാർഡ്‌റെയിലിനെ മാത്രമേ ഒഴിവാക്കൂ.

### പോസ്റ്റ്-കോളിന് മുമ്പ് പ്രതികരണം ഏതെല്ലാം ഘട്ടങ്ങളിലൂടെ കടന്നുപോകുന്നു

സ്ട്രീമിങ് അല്ലാത്ത പാതയിലെ ക്രമം ഇതാണ്: മെമ്മറി എക്സ്ട്രാക്ഷൻ → അന്തർനിർമിത ടൂൾ
നിർവഹണം → പോസ്റ്റ്-കോൾ ഗാർഡ്‌റെയിലുകൾ → പോസ്റ്റ്-കോൾ തടയലിനെത്തുടർന്നുള്ള പുറപ്പെടൽ → സെമാന്റിക്-കാഷിൽ സംഭരിക്കൽ.

- പോസ്റ്റ്-കോൾ ഗാർഡ്‌റെയിലുകൾക്ക് പ്രതികരണം തിരുത്തിയെഴുതാനോ തടയാനോ
  കഴിയുന്നതിന് മുമ്പുതന്നെ **മെമ്മറി എക്സ്ട്രാക്ഷനും** **ടൂൾ എക്സിക്യൂഷനും** അത് ലഭിക്കുന്നു.
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) മുതൽ,
  `PII_RESPONSE_SANITIZATION` ഓണായിരിക്കുമ്പോൾ മെമ്മറി
  എക്സ്ട്രാക്ഷൻ വേർതിരിച്ചെടുത്ത ടെക്സ്റ്റ് `sanitizePII` വഴി പ്രോസസ്സ് ചെയ്യുന്നു
  (സ്ട്രീമിംഗ്, നോൺ-സ്ട്രീമിംഗ് രീതികളിൽ ഒരുപോലെ). എന്നാൽ പോസ്റ്റ്-കോൾ ഘട്ടത്തിൽ
  പിന്നീട് തടയപ്പെടുന്ന പ്രതികരണവും അതിനകം മെമ്മറിക്കും
  ടൂളുകൾക്കും ലഭിച്ചിട്ടുണ്ടാകും.
- **സെമാന്റിക് കാഷ്** പോസ്റ്റ്-കോൾ ഘട്ടത്തിന് ശേഷമാണ് പ്രതികരണം സംഭരിക്കുന്നത്. അതിനാൽ
  തിരുത്തിയെഴുതിയ പ്രതികരണമാണ് അതിൽ സംഭരിക്കപ്പെടുന്നത്; തടയപ്പെട്ട പ്രതികരണം ഒരിക്കലും കാഷിൽ സംഭരിക്കപ്പെടില്ല. കാഷ് എൻട്രികൾക്ക്
  ഓരോ API കീയ്ക്കും പ്രത്യേകം കീ നൽകുന്നു.

## കോൺഫിഗറേഷൻ

അന്തർനിർമ്മിത ഗാർഡ്‌റെയിലുകൾ വായിക്കുന്ന എൻവയോൺമെന്റ് വേരിയബിളുകൾ:

| വേരിയബിൾ                              | ഉപയോഗിക്കുന്നത്              | പ്രഭാവം                                                                                                           |
| ------------------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`           | കണ്ടെത്തൽ പൂർണ്ണമായും പ്രവർത്തനരഹിതമാക്കാൻ `false` ആയി സജ്ജമാക്കുക.                                               |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`           | ഇൻജെക്ഷൻ നയം: `warn`, `block`, അല്ലെങ്കിൽ `log`. പഴയ മൂല്യമായ `redact` ഇൻജെക്ഷൻ ടെക്സ്റ്റ് തിരുത്തിയെഴുതുന്നില്ല. |
| `INJECTION_GUARD_MODE`                | `prompt-injection`           | ഇൻജെക്ഷൻ ഗാർഡിനുള്ള മോഡ്; എൻവയോൺമെന്റ് വേരിയബിളുകളെ **മറികടക്കുന്ന** ഒരു DB ഫീച്ചർ ഫ്ലാഗും കൂടിയാണിത് (DB > ENV). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`           | `MODE=block` നിരസിക്കുന്ന ഏറ്റവും കുറഞ്ഞ തീവ്രത: `high` (സ്ഥിരസ്ഥിതി), `medium`, അല്ലെങ്കിൽ `low`.                |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`           | `INPUT_SANITIZER_BLOCK_THRESHOLD` എന്നതിനുള്ള പഴയ അപരനാമം.                                                        |
| `PII_REDACTION_ENABLED`               | `pii-masker`                 | `true` ആയിരിക്കുമ്പോൾ, അഭ്യർത്ഥനയിലെ PII മറയ്ക്കപ്പെടുന്നു (ഇൻജെക്ഷൻ മോഡിൽനിന്ന് സ്വതന്ത്രമായി).                  |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (തുടർഘട്ടത്തിൽ) | പ്രതികരണഭാഗത്തെ മാസ്കറിന്റെ പ്രവർത്തനം നിയന്ത്രിക്കുന്നു.                                                         |

Modality Bridge ഗാർഡ്‌റെയിലുകൾ റൺടൈം കോൺഫിഗറേഷൻ വായിക്കുന്നത് DB അടിസ്ഥാനമാക്കിയുള്ള ക്രമീകരണ
സ്റ്റോറിൽനിന്നാണ് (`getSettings()`), എൻവയോൺമെന്റ് വേരിയബിളുകളിൽനിന്നല്ല. Vision-ന്റെ പ്രാഥമിക കീകൾ
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes`, കൂടാതെ
`modalityBridgeCacheMaxEntries` എന്നിവയാണ്. പഴയ
`visionBridge*` കീകൾ, രേഖപ്പെടുത്തിയിട്ടുള്ള ഒറ്റ സൈക്കിൾ റീഡ്
ഫോൾബാക്കായി മാത്രമേ സ്വീകരിക്കപ്പെടൂ; ഡാഷ്ബോർഡിൽനിന്നുള്ള എഴുത്തുകൾ പ്രാഥമിക കീകൾ ഉപയോഗിക്കുന്നു. സ്ഥിരസ്ഥിതി മൂല്യങ്ങളും ഫോൾബാക്ക്
റിസോൾവറും `src/shared/constants/modalityBridgeDefaults.ts`-ലാണ് ഉള്ളത്; പഴയ
സ്ഥിരാങ്കങ്ങൾ `src/shared/constants/visionBridgeDefaults.ts`-ൽ നിലനിർത്തിയിരിക്കുന്നു.

Audio ഉപയോഗിക്കുന്നത് `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout`, `modalityBridgeAudioMaxClips` എന്നിവയും, പങ്കിടുന്ന
`modalityBridgeCache*` ക്രമീകരണങ്ങളുമാണ്. Audio-യ്ക്ക് പഴയ കീകളിലേക്കുള്ള ഫോൾബാക്ക് ഇല്ല, കാരണം ഈ
കീകൾ Modality Bridge സ്കീമയോടൊപ്പമാണ് അവതരിപ്പിച്ചത്.

Video ഉപയോഗിക്കുന്നത് `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos`, കൂടാതെ
`modalityBridgeVideoTimeout` എന്നിവയും, പങ്കിടുന്ന `modalityBridgeCache*` ക്രമീകരണങ്ങളുമാണ്.
FFmpeg/ffprobe ഐച്ഛിക പ്രവർത്തനപരമായ
ഡിപെൻഡൻസികളായതിനാലും ഫ്രെയിമുകൾക്ക് അടിക്കുറിപ്പുകൾ നൽകുന്നത് കാലതാമസവും മോഡൽ ചെലവും വർധിപ്പിക്കുന്നതിനാലും ഇത് സ്ഥിരസ്ഥിതിയിൽ പ്രവർത്തനരഹിതമാണ്.

## ഇഷ്‌ടാനുസൃത ഗാർഡ്‌റെയിലുകൾ

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ഘട്ടങ്ങൾ:

1. `BaseGuardrail` വിപുലീകരിക്കുന്ന `src/lib/guardrails/myGuardrail.ts` സൃഷ്‌ടിക്കുക.
2. `preCall` കൂടാതെ/അല്ലെങ്കിൽ `postCall` നടപ്പിലാക്കുക.
3. ഇംപോർട്ട് സമയത്ത് രജിസ്റ്റർ ചെയ്യുക (`registerDefaultGuardrails`-ൽ നിന്ന് ചേർക്കുക) അല്ലെങ്കിൽ
   റൺടൈമിൽ `guardrailRegistry.register(...)` വിളിക്കുക — അതേ നോർമലൈസ് ചെയ്‌ത പേരുള്ള
   ഏതൊരു മുൻ ഗാർഡ്‌റെയിലിനെയും രജിസ്ട്രി മാറ്റിസ്ഥാപിക്കും.
4. `tests/unit/` എന്നതിനു കീഴിൽ ടെസ്റ്റുകൾ ചേർക്കുക (നിലവിലുള്ള ഉദാഹരണങ്ങൾ:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## പരിശോധന

അറിയാവുന്ന ഒരു അവസ്ഥയിൽ നിന്ന് ആരംഭിക്കാൻ ടെസ്റ്റുകൾക്കിടയിൽ `resetGuardrailsForTests()` ഉപയോഗിക്കുക.
ശൂന്യമായ ഒരു രജിസ്ട്രിയോടെ ആരംഭിക്കാനും പരിശോധനയ്‌ക്ക് വിധേയമാക്കുന്ന ഗാർഡ്‌റെയിലുകൾ മാത്രം
രജിസ്റ്റർ ചെയ്യാനും `{ registerDefaults: false }` നൽകുക. Vision Bridge ഡിപെൻഡൻസി
ഇൻജക്ഷൻ (`deps.getSettings`, `deps.callVisionModel`) സ്വീകരിക്കുന്നു; ക്രമീകരണങ്ങൾ, ശേഷികൾ, STT മോഡൽ തിരഞ്ഞെടുപ്പ്, ക്രെഡൻഷ്യൽ
പരിശോധനകൾ, ട്രാൻസ്‌ക്രിപ്ഷൻ എന്നിവയ്‌ക്കായി തത്തുല്യമായ ഇന്റർഫേസുകൾ Audio Bridge ലഭ്യമാക്കുന്നു. അതിനാൽ DB
അല്ലെങ്കിൽ നെറ്റ്‌വർക്ക് ആക്‌സസ് ഇല്ലാതെ തന്നെ ടെസ്റ്റുകൾക്ക് ഇരു ഫ്ലോകളും പരിശോധിക്കാനാകും.

## ഇൻജക്ഷൻ-ഗാർഡ് റൂട്ട് കവറേജും റെഡ്-ടീമും (ഘട്ടം 8 · ബ്ലോക്ക് D)

ഉപയോക്തൃ പ്രോംപ്റ്റുകൾ സ്വീകരിക്കുന്ന എല്ലാ റൂട്ടുകളെയും ഇൻജക്ഷൻ-ഗാർഡ് (`createInjectionGuard` / `withInjectionGuard`)
ഉൾക്കൊള്ളുന്നു. ഇത് `INJECTION_GUARD_MODE` അനുസരിക്കുന്നു (ഡിഫോൾട്ട് `warn` = ലോഗ് ചെയ്യുക മാത്രം;
`block` = HTTP 400 `SECURITY_001` തിരികെ നൽകുന്നു).

| തരം                       | റൂട്ടുകൾ                                                                                                                                             | ഡിഫോൾട്ട് മോഡ് |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| ടെക്സ്റ്റ് (നിലവിലുള്ളത്) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn           |
| ജനറേറ്റീവ്                | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn           |
| ഡാറ്റ                     | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn           |

ടെക്സ്റ്റ് എക്സ്ട്രാക്ഷൻ (`extractMessageContents`) `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` എന്നിവ ഉൾക്കൊള്ളുന്നു.

**റെഡ്-ടീം (എല്ലാ രാത്രിയിലും, `nightly-llm-security.yml`):** `INJECTION_GUARD_MODE=block` ആയിരിക്കുമ്പോൾ ഓരോ റൂട്ടും
OWASP-LLM കോർപ്പസിനെ തടയുന്നുവെന്ന് promptfoo സാധൂകരിക്കുന്നു; garak പ്രോബുകൾ പ്രവർത്തിപ്പിക്കുന്നു (സീക്രട്ട് ഇല്ലെങ്കിൽ ഒഴിവാക്കുന്നു).
സ്ഥിരതയ്‌ക്കായി `moderations` ഉൾപ്പെടുത്തിയിരിക്കുന്നു. ബ്ലോക്ക് മോഡ് നിർബന്ധിതമായ ഒരു അതിർത്തിയാണ്: മിഡിൽവെയർ കൈമാറുന്ന
ഓരോ അഭ്യർത്ഥനയ്‌ക്കുമുള്ള പ്രവർത്തനരഹിതമാക്കൽ പട്ടിക `evaluatePromptInjection()` അവഗണിക്കുന്നു, അതിനാൽ `disabledGuardrails` ഒരു റൂട്ടിനെ
ഇതിൽ നിന്ന് ഒഴിവാക്കുന്നി**ല്ല** ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

രാത്രികാല വർക്ക്‌ഫ്ലോയിൽ (`.github/workflows/nightly-llm-security.yml`, cron + മാനുവൽ
ഡിസ്‌പാച്ച്) രണ്ട് ജോബുകളുണ്ട്:

- **`promptfoo-guard` (തടയുന്നത്)** — `INJECTION_GUARD_MODE=block` ഉപയോഗിച്ച്
  `promptfoo eval -c promptfooconfig.yaml` പ്രവർത്തിപ്പിക്കുന്നു. ഓരോ പ്രതികൂല കേസും (ഉദാ. "മുമ്പത്തെ എല്ലാ
  നിർദ്ദേശങ്ങളും അവഗണിക്കുക…", DAN-ശൈലിയിലുള്ള ജെയിൽബ്രേക്കുകൾ) പ്രതികരണത്തിൽ
  `error.code === "SECURITY_001"` ഉണ്ടെന്ന് ഉറപ്പാക്കുന്നു, അതായത് ഗാർഡ് അഭ്യർത്ഥന യഥാർത്ഥത്തിൽ നിരസിച്ചു.
- **`garak` (ഉപദേശാത്മകം)** — ഒരു ലോക്കൽ OmniRoute ഇൻസ്റ്റൻസിനെ (`http://localhost:20128/v1`) ലക്ഷ്യമാക്കി
  garak `--probes promptinject,dan,leakreplay` പ്രവർത്തിപ്പിക്കുന്നു. ഒരു
  പ്രൊവൈഡർ സീക്രട്ട് (`PROMPTFOO_PROVIDER_KEY`) ഉണ്ടെങ്കിൽ മാത്രമേ പ്രവർത്തിക്കൂ; ഇല്ലെങ്കിൽ പ്രശ്‌നമില്ലാതെ ഒഴിവാക്കുന്നു, കൂടാതെ
  അവസാനം `|| true` ചേർത്തിരിക്കുന്നു, അതിനാൽ CI പരാജയപ്പെടുത്താതെ റിപ്പോർട്ട് ചെയ്യുന്നു.

ഗാർഡ് ഹെൽപ്പറിന്റെ (`createInjectionGuard` / `withInjectionGuard`) കവറേജ്
പ്രോംപ്റ്റ് ഉൾക്കൊള്ളുന്ന എല്ലാ `/v1` റൂട്ടുകളിലേക്കും വ്യാപിക്കുന്നു; പ്രോംപ്റ്റ് ടെക്സ്റ്റ്
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` എന്നിവയിൽ നിന്ന്
`src/shared/utils/inputSanitizer.ts`-ലെ `extractMessageContents()` ഉപയോഗിച്ച് എടുക്കുന്നു.
