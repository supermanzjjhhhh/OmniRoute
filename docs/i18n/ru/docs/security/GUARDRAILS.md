> **Последнее обновление:** 2026-10-17 — v3.8.52 (добавлено [Покрытие и ограничения](#coverage-and-limits):
> какие маршруты и пути ответов обслуживают хуки, объединенные заголовки отключения (#16412), внедрение
> блок-режима в качестве обязательной границы (#16413), и что видит ответ до post-call)

Защитные механизмы обеспечивают безопасность, соблюдение политик и преобразование контента на границе
между OmniRoute и вышестоящими провайдерами. Каждый защитный механизм может проверять (и
опционально отклонять, преобразовывать или аннотировать) полезную нагрузку запроса (`preCall`) и
ответы вышестоящих провайдеров (`postCall`).

Система работает по принципу **fail-open**: если защитный механизм вызывает ошибку во время выполнения, реестр
записывает эту ошибку и продолжает работу со следующим защитным механизмом, вместо того чтобы завершить запрос с ошибкой.
Блокировка является явным решением (`block: true`), а не случайностью.
Единственное исключение — прерванный запрос: когда `signal` вызывающей стороны прерывается,
вызывающий ошибку защитный механизм отклоняет выполнение хука, вместо того чтобы быть пропущенным.

Хуки выполняются **не** для каждого маршрута и не для каждого ответа. Ознакомьтесь с разделом
[Покрытие и ограничения](#coverage-and-limits), прежде чем полагаться на защитный механизм как на средство
обеспечения безопасности.

## Встроенные защитные механизмы

Реестр автоматически загружает шесть защитных механизмов в порядке приоритета при импорте
(см. `registry.ts` → `registerDefaultGuardrails()`):

| Приоритет | Название            | Этап(ы)        | Файл                  |
| --------- | ------------------- | -------------- | --------------------- |
| `5`       | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`       | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`       | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`      | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`      | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`      | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

Меньшие значения приоритета выполняются **первыми**.

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

Базовая модель GLM 5.3 и `glm-5.3-{low,high,max}` имеют явные
метаданные реестра/спецификации `supportsVision:false`. Варианты GLM 5.3 Flash
остаются моделями с нативной поддержкой визуальных данных. Маршрут `/v1/messages` в Claude Code попадает в
общую цепочку пре-вызова защитного механизма `handleChat` **до** перевода из Claude в OpenAI
и вложенные изображения из результатов инструментов `Read` должны быть описаны или обработаны
до того, как этот перевод перенесет их в контент `image_url` OpenAI (#17069).

Перехватывает запросы, содержащие изображения, направленные на **модели без поддержки визуальных данных**, и либо
перенаправляет весь запрос на модель с поддержкой визуальных данных, либо заменяет части с изображениями
на текстовые описания, созданные настраиваемой визуальной моделью перед
вызовом вышестоящего провайдера. Это позволяет провайдерам, работающим только с текстом, прозрачно обрабатывать
мультимодальные полезные нагрузки.

Поток выполнения:

1. Пропускается, если целевая модель уже поддерживает визуальные данные (если только она не указана в
   списке принудительного моста `isVisionBridgeForcedModel`).
2. Извлечение частей с изображениями с помощью `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), который делегирует задачу **унифицированному детектору медиаданных**
   `detectMediaParts()` в `open-sse/utils/mediaParts.ts` — единому
   источнику истины, разделяемому с фильтром совместимости комбинаций.
   Извлечение разрешено только для тех форматов, которые `replaceImageParts` может встроить
   обратно (контракт извлечения и замены): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"` и `input_image` из Responses
   API. Соответствующие изображения, вложенные в `tool_result.content` Claude Code
   и выводы инструментов Responses, также извлекаются и заменяются
   по их исходным путям; форматы, служащие только индикаторами, являются частью комбинированного фильтра
   и не извлекаются.
   Пропускается, если ничего не найдено.
3. Определение конфигурации во время выполнения через `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): новые ключи настроек `modalityBridge*`
   имеют приоритет; устаревшие ключи `visionBridge*` остаются в качестве **резервного варианта на один цикл**
   (окно отката). Пропускается перед любым обходом медиаданных, если мост отключен.
4. Селектор режимов (`modalityBridgeVisionMode`, см. таблицу ниже) определяет,
   выполнять перенаправление или описание. Перенаправление возвращает `modifiedPayload` только с замененной
   `model`, а также метаданные `{ rerouted, fromModel, toModel, imagesKept }`.
5. Путь описания: ограничение количества изображений параметром `maxImages`, составление промпта с учетом задачи,
   проверка кэша описаний, вызов визуальной модели **параллельно**
   (`Promise.allSettled`) и вставка текстовых частей `[Image N]: <description>`
   на их место. Сбой описания возвращает `null`: исходное изображение сохраняется для
   неизвестных целей или целей с поддержкой визуальных данных (#4012), но для **подтвержденной прямой цели, работающей только с текстом**,
   или комбинированной цели без поддержки визуальных данных добавляется явная текстовая заглушка
   `(unavailable — no vision-capable provider connected)` для каждого неописанного изображения,
   включая частичные сбои и изображения сверх лимита вызовов описания (#17069). Существующий резервный вариант
   описания для комбинированных целей при полном сбое остается в силе (#8430).
6. Возврат `modifiedPayload` + метаданных (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режимов (`modalityBridgeVisionMode`)

| Режим      | По умолчанию | Поведение                                                                                                                                                                                                                                                                                                                                                                            |
| ---------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auto`     | ✔            | Устаревшая эвристика, без изменений (#6640/#7204): модели, не являющиеся комбинированными / `auto/`, перенаправляются на лучшую модель компьютерного зрения, если только у исходной модели уже нет пригодных учетных данных (в этом случае выполняется описание); комбинированные цели всегда выполняют описание.                                                                    |
| `describe` |              | Всегда выполнять описание — блок перенаправления полностью пропускается; всегда отвечает выбранная пользователем модель.                                                                                                                                                                                                                                                             |
| `reroute`  |              | Принудительное перенаправление: защитный механизм модели с учетными данными обходится. Защитный механизм учетных данных для **цели** перенаправления по-прежнему применяется — если нет доступной цели компьютерного зрения, мост блокирует запрос с понятной ошибкой, вместо того чтобы выполнять описание или отправлять исходные изображения в цель, поддерживающую только текст. |

Принудительные режимы срабатывают **до** запуска эвристики `auto`; поведение `auto`
полностью идентично (побайтово) защитному механизму до PR-1.

#### Область видимости ключа API (`visionBridgeKeyScope.ts`)

Когда ключ API вызывающего абонента ограничивает `allowedConnections`, пулы квот
(`allowedQuotas`) или модели (`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`), мост выбирает
только те модели для перенаправления и описания, которые разрешено использовать данному ключу,
и в рамках разрешенных для него подключений. Затем вызов описания
всегда проходит через внутренний цикл OmniRoute с заголовком
`x-omniroute-self-loop-key-id`, поэтому получаемый запрос чата
снова применяет политику подключений и моделей для этого ключа. Функция `enforceApiKeyPolicy()`
учитывает этот заголовок только вместе с bearer-токеном внутреннего цикла, поэтому она может только
сужать доступ, а идентификатор, который не удается разрешить, отклоняется.

Если для ключа не разрешена ни одна модель компьютерного зрения, **подтвержденная цель,
поддерживающая только текст**, локально отклоняет запрос изображения с понятной ошибкой HTTP 400 вместо
пересылки байтов изображения неспособному верхнеуровневому сервису (#17069). Для целей с
неизвестными или встроенными возможностями компьютерного зрения путь описания сохраняет свое прежнее
поведение с отказом в открытом режиме (метаданные `{ skipped: true, reason: "no_permitted_vision_model" }`).
Запросы без ключа и ключи без этих ограничений ведут себя точно так же,
как и раньше.

#### Промпт описания с учетом задачи (`modalityBridgeVisionTaskAware`)

По умолчанию **true**. Функция `composeVisionPrompt()` (`visionBridgeHelpers.ts`) добавляет
текст **последнего сообщения пользователя** (обрезанный до 500 символов) к базовому
промпту описания, направляя описание в сторону того, о чем фактически попросил пользователь
(паттерн `codex-vision-proxy`) и запршивая у модели компьютерного зрения транскрипцию видимого
текста. При отключенном флаге — или отсутствии текста пользователя — базовый промпт используется без изменений.

Собственный запрос внутреннего цикла описания, совместимый с OpenAI (`callVisionModelSingle()`
в `visionBridgeHelpers.ts`), всегда запрашивает `image_url.detail: "high"` —
безусловно, для каждого вызывающего абонента / провайдера, без привязки к какому-либо сигналу клиента.
Сэмплирование с низким уровнем детализации снижает точность распознавания текста (OCR) как раз для задачи
транскрипции текста, которую запрашивает этот промпт, поэтому сам вызов описания всегда запрашивает высокую
детализацию независимо от того, какой уровень детализации использовался в исходном входящем запросе.
Это влияет только на тело внутреннего запроса описания; это не меняет того, как
OmniRoute пересылает собственный параметр `image_url.detail` вызывающего абонента в первичном запросе —
это значение по умолчанию применяется отдельно и только для обнаруженных клиентов OpenCode, в
`defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Ветвь формата передачи данных
Anthropic для внутреннего цикла описания не имеет поля `detail`
и не зависит ни от одного из этих значений по умолчанию.

#### Ограничение вывода описания (`modalityBridgeVisionMaxChars`)

| Ключ                           | По умолчанию | Диапазон          |
| ------------------------------ | ------------ | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`          | `0` или 100–50000 |

Значение `0` (по умолчанию) означает **отсутствие ограничения** — описание, возвращаемое
функцией `callVisionModel()`, передается без изменений, сохраняя существующее
поведение. Любое значение в диапазоне 100–50000 обрезает описание с суффиксом
`…` перед тем, как оно будет вставлено обратно в виде `[Image N]: <description>`
(`VisionBridgeGuardrail.preCall()` в `src/lib/guardrails/visionBridge.ts`).
Увеличьте это значение для задач распознавания текста (OCR) с высокой детализацией, где нисходящей модели требуется
полная транскрипция; уменьшите его, чтобы ограничить использование токенов для многословных моделей компьютерного зрения.
Поле в панели управления находится на панели «Дополнительно» вкладки «Зрение»
(`modality-bridge-max-chars` в `ModalityBridgeVisionTab.tsx`) и приводит любое
значение от 1 до 99 к нижнему пределу 100, оставляя явное значение `0`
нетронутым — `0` является само по себе валидным значением Zod
(`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто
значением по умолчанию для «неустановленного» состояния.

#### Кэш описаний (`modalityBridge/bridgeCache.ts`)

Кэш LRU + TTL в оперативной памяти для результатов описания, разделяемый между всеми процессами.
Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` с
фреймингом по префиксу длины (без коллизий границ полей). Компонент модели —
это **настроенная** модель моста, а не модель, которая фактически ответила —
`callVisionModel` может использовать внутренний фоллбэк, и создание ключа для каждой попытки
привело бы к фрагментации кэша. Описания, завершившиеся ошибкой, никогда не кэшируются. Настройки:

| Ключ                            | По умолчанию | Диапазон |
| ------------------------------- | ------------ | -------- |
| `modalityBridgeCacheEnabled`    | `true`       | —        |
| `modalityBridgeCacheTtlMinutes` | `60`         | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`        | 10–5000  |

#### Нормализация удаленных изображений (самовызов `describe` / выборка `base64`)

Когда мост самостоятельно запрашивает **удаленное** изображение — самовызов `describe` Anthropic и преобразование `base64` для формата передачи claude (`ensureBase64ImagesForClaudeWire`), оба через `fetchRemoteImageAsDataUri()` в `visionBridgeHelpers.ts` — полученный URI данных пропускается через `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) перед встраиванием в запрос к Vision-модели. Изображения с превышением размера масштабируются до **длинной стороны 2048px** (что соответствует ограничению изменения размера, которое OpenAI/Anthropic уже применяют на стороне сервера), что сокращает объем передаваемых байт и задержку без изменения того, что видит Vision-модель. Изменение размера использует `sharp`, загружаемый через динамический импорт: на платформе, где его нативный бинарный файл не удается загрузить, `normalizeDataUri()` **никогда не выбрасывает исключений** — он возвращает исходные байты без изменений, поэтому путь `describe`/преобразования в `base64` всегда продолжает работать. Байты не-изображений (запрос, который не вернул декодируемое изображение) также передаются без изменений. Эта нормализация ограничена изображениями, которые мост запрашивает для собственного самовызова — она никогда не применяется к исходной полезной нагрузке вызывающего абонента, что соответствует принципу мутации только по явному согласию (Hard Rule #20).

#### Схема настроек + миграция

Новые ключи `modalityBridge*` проходят валидацию Zod в `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, трио `modalityBridgeCache*` и группа `modalityBridgeAudio*`, используемая аудиомостом (Audio Bridge). Миграция `141_modality_bridge_settings.sql` копирует существующие устаревшие значения `visionBridge*` в соответствующие новые ключи (идемпотентно, никогда не перезаписывает значение `modalityBridge*`, установленное оператором); устаревшие ключи продолжают приниматься в качестве резервного варианта чтения в течение одного цикла выпуска.

#### Заголовок прозрачности + статистика

Ответы, преобразованные через `describe`, содержат заголовок `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (формируется с помощью `buildModalityBridgeHeader()` в `modalityBridge/bridgeStats.ts`, проставляется функцией `withModalityBridgeHeader()` в `src/sse/handlers/chatHelpers.ts`). Перенаправленные запросы **не получают** заголовка — полезная нагрузка осталась неизменной, а замена модели уже видна в поле `model` тела ответа.

`GET /api/modality-bridge/stats` (авторизация управления, тот же уровень, что и `GET /api/settings`) возвращает находящиеся в памяти счетчики для каждой модальности `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` и `video`. `averageLatencyMs` использует `latencySamples`, а не все попытки, в качестве своего знаменателя; операция без замера времени не генерирует нулевой образец в миллисекундах. `bridged` остается обратно совместимым псевдонимом для успешных преобразований; неудачные попытки не увеличивают его значение. Счетчики сбрасываются при перезапуске процесса по задумке (это телеметрия, а не бухгалтерский учет).

#### Конфигурация панели управления

Выделенная страница панели управления — `/dashboard/settings/modality-bridge`. Ее доступные по URL вкладки `Vision`, `Audio` и `Video` сохраняют параметры запроса при переключении значения `tab`. Вкладка Vision предоставляет настройки включения, режима, выбора модели (включая автоматическое значение по умолчанию), промптинга с учетом задач, расширенные ограничения тайм-аута/изображения/длины описания/кэша, счетчики времени выполнения и защищенный тестовый запрос. Вкладка Audio также активна: она предоставляет настройки включения, выбор модели только для STT с опцией Auto, ограничения тайм-аута/максимальной длины клипа, аудиосчетчики и тестовый запрос `input_audio`. Вкладка Video является функциональной: она сообщает о состоянии выполнения FFmpeg/ffprobe — одном из четырех явных состояний пользовательского интерфейса (`unknown`, пока проверка выполняется или не может завершиться; `restricted` на хосте панели управления без loopback, где проверка пропускается на стороне клиента; `unavailable`, если проверка выполнена и подтверждено отсутствие; или `available` с указанием версий FFmpeg/ffprobe) — сохраняет ограничения включения/модели/кадра/видео/тайм-аута, фильтрует выбор модели до моделей, поддерживающих визуальные функции (vision-capable), и предоставляет видеосчетчики.

Бывшая карточка Vision Bridge в настройках AI представляет собой ссылку совместимости на новую страницу; она больше не содержит вторую копию формы. Media Providers также связывает рабочие процессы Image-to-Text и Speech-to-Text с соответствующими вкладками Modality Bridge, не удаляя существующую песочницу Speech-to-Text.

**Обход проверки допуска при самовызове:** когда вызов `describe` направляется через собственный самовызов `/v1` OmniRoute (нестандартная модель провайдера), подзапрос отправляет заголовок `x-omniroute-admission-bypass: internal` и аутентифицируется с использованием разрешенных учетных данных самовызова — локального маркера `sk_omniroute` в локальном режиме или настроенных оператором ключей окружения `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), чтобы развертывания с `REQUIRE_API_KEY=true` по-прежнему могли выполнять вызов `describe`. Обход принимается только для этих точных учетных данных, поэтому внешние клиенты не могут использовать заголовок для пропуска проверки допуска.

Устаревшие значения по умолчанию находятся в `src/shared/constants/visionBridgeDefaults.ts`; новые значения по умолчанию для режима / с учетом задач / кэша и резолвер настроек находятся в `src/shared/constants/modalityBridgeDefaults.ts`. Механизм защиты (guardrail) предоставляет опцию конструктора `deps`, позволяющую тестам внедрять фиктивные реализации `getSettings` и `callVisionModel`.

### Аудиомост (`audioBridge.ts`) — Modality Bridge PR-3

Перехватывает запросы чата, содержащие аудио, до того, как они достигнут цели, которая, как известно, не принимает аудиовход. Он никогда не перенаправляет запрос чата: аудиочасти транскрибируются через существующую конечную точку multipart, совместимую с OpenAI, и выбранная модель чата продолжает работу с текстовыми расшифровками.

Поток:

1. Определение `supportsAudio` через `getResolvedModelCapabilities()`. Сначала учитываются метаданные явного реестра провайдеров, затем статические метаданные модели, а затем синхронизированные `modalities_input`. Заявленный список входных данных без `audio` дает `false`; при отсутствии доказательств возможностей остается `null`. И `false`, и `null` активируют консервативный мост, тогда как `true` обходит его.
2. Разрешение настроек `modalityBridgeAudio*` и извлечение соединяемых аудиочастей верхнего уровня из каждого сообщения с помощью общего детектора `detectMediaParts()`. Поддерживаемые форматы передачи данных — это `input_audio`, `audio_url` и `source.media_type: "audio/*"` от OpenAI. Вложенное аудио обнаруживается для маршрутизации, но не удаляется путем склейки. Объем работы ограничен параметром `modalityBridgeAudioMaxClips`; последующие части остаются без изменений.
3. Учет настроенного `provider/model` или выбор модели с помощью `selectAudioBridgeModel()`, которая обходит `AUDIO_TRANSCRIPTION_PROVIDERS` в стабильном порядке каталога и выбирает первую модель с действующими учетными данными активного провайдера.
4. `callAudioTranscription()` преобразует аудио в формате base64 / data-URI в многочастный файл (multipart `file`) или загружает удаленный `audio_url` через публичный исходящий защитный механизм с привязкой DNS (DNS pinning) и ограничением в 25 МБ. Затем отправляется POST-запрос с файлом и выбранной моделью на локальный внутренний цикл (self-loop) `/v1/audio/transcriptions` с аутентификацией с помощью `resolveSelfLoopBearer()`. Существующий маршрут транскрипции выполняет обычный поиск учетных данных, обработку периодов охлаждения / ограничений частоты запросов и диспетчеризацию провайдеров.
5. Успешные вызовы заменяют свои части на `[Audio N]: <transcript>`. Вызовы выполняются с помощью `Promise.allSettled`: отдельный сбой сохраняет исходную аудиочасть (контракт `#4012`). Если все вызовы завершаются ошибкой и целевой объект явно имеет `supportsAudio === false`, части принимают вид `[Audio N]: (unavailable — no STT provider connected)` (контракт `#8430`). Для неизвестного целевого объекта (`null`) результат при всех сбоях остается без изменений. Проверенный текстовый целевой объект без доступных учетных данных STT получает ту же явную заглушку без выполнения сетевого вызова.

Успешные транскрипции используют общепроцессорный LRU/TTL-кеш Modality Bridge. Ключ объединяет ссылку на аудио, стабильную метку операции `audio-transcription` и выбранную модель STT; сбои никогда не кешируются. Попытки работы с аудио обновляют общие счетчики `bridged`, `cacheHits`, `failures` и `lastUsedAt`. Преобразованные ответы содержат заголовок `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; нетронутые запросы не получают сегмент Audio Bridge.

Настройки среды выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                          | Значение по умолчанию | Диапазон        |
| ----------------------------- | --------------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`                | —               |
| `modalityBridgeAudioModel`    | `""`                  | Авто или ID STT |
| `modalityBridgeAudioTimeout`  | `60000`               | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`                   | 1–10            |

Общий кеш по-прежнему управляется параметрами `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и `modalityBridgeCacheMaxEntries`.

### Видеомост (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехватывает видеочасти верхнего уровня в `messages` Chat Completions и `input` Responses API до вызова целевого объекта без известной встроенной поддержки видео. Поддерживаемые форматы — `input_video`, `video_url`, `video_source`, URL-адреса HTTPS и data-URI `data:video/*;base64,...`. Обычные имена файлов в тексте не рассматриваются как видео.

Метод `VideoBridgeGuardrail.preCall` (`videoBridge.ts`) отвечает за обход запроса, проверку возможностей/политик, агрегацию для каждого запроса и полезную нагрузку ответа. Работа с каждым отдельным видео — получение, кеш всего результата, описание последовательности кадров (которая объединяет любые объявленные вызывающим абонентом стенограммы аудио) и метрики/прерывание/очистка для каждой попытки — скрыта за функцией `processVideoPart` в `videoBridgePipeline.ts`, которая вызывается один раз для каждой видеочасти внутри цикла `preCall`. Этот модуль также определяет явные границы портов: `VideoMediaBrokerPort` (получение байтов и извлечение сэмплированных кадров), `VideoAudioTranscriptionPort` (объединение заявленной вызывающей стороной аудиостенограммы с сэмплированными подписями) и `VideoDrilldownPort` (граница персистентности детализации кадров (drill-down); пока еще не подключен к `processVideoPart` — на сегодняшний день записи детализации записываются только отдельным маршрутом `/api/modality-bridge/video/drilldown`).

Путь запроса `/v1` общего доступа никогда не импортирует и не вызывает подпроцесс. Удаленные видео загружаются с ограничением в 50 МБ; встроенные видео в формате base64 имеют консервативное ограничение в 36 МБ в декодированном виде на одно видео, чтобы конверт модели/сообщений/обрамления оставался в пределах лимита приема публичных JSON-запросов в 50 МБ. Оценки длины встроенного видео и декодированного размера проверяются до выделения памяти. HTTPS требуется для исходного удаленного URL-адреса и каждого перенаправления с использованием существующего защитного механизма исходящего трафика только для общедоступных адресов с привязкой DNS (DNS pinning). Затем байты пересекают точную внутреннюю границу брокера `POST /api/modality-bridge/video/extract`. Этот маршрут является одновременно `LOCAL_ONLY` и `SPAWN_CAPABLE`, принимает только аутентифицированный в рамках процесса запрос через доверенный лупбек (trusted-loopback) и никогда не принимает URL-адрес, путь в файловой системе, исполняемый файл или список аргументов. Конвейер размера тела API и инкрементальный считыватель тела обработчика независимо друг от друга обеспечивают ограничение входных данных брокера в 50 МБ. Его ограниченная очередь выполняет одно извлечение за раз, допускает четыре ожидающих задания и ограничивает объем ожидающих входных данных на уровне 100 МБ.

Внутри брокера `ffprobe` считывает закрытый локальный файл; белый список фиксированных форматов исключает форматы списков воспроизведения и манифестов. Для разрешенных контейнеров семейств MOV внешние ссылки на данные MOV остаются отключенными по умолчанию, и фиксированная команда не активирует их. И `ffprobe`, и `ffmpeg` используют белый список протоколов только для `file`, один поток, фиксированные массивы аргументов, работают без оболочки, а исполняемые файлы разрешаются из `PATH`. Потоки обложек в виде прикрепленных изображений не являются кандидатами для воспроизведения. Все воспроизводимые потоки должны удовлетворять ограничениям, а явный поток по умолчанию имеет приоритет перед детерминированным резервным вариантом с наименьшим индексом. Видео ограничено 600 секундами, 8 192 пикселями на измерение и 33 554 432 исходными пикселями. FFmpeg выбирает 1–16 средних JPEG-кадров, масштабирует длинную сторону максимум до 1024 пикселей без увеличения меньших входных данных и никогда не получает URL. По умолчанию используется выборка `uniform`. Необязательные политики `scene_aware` и экспериментальная `segment_aware` выполняют один дополнительный фиксированный проход FFmpeg по уже проверенному локальному потоку, выбирают ограниченные временные метки сцен `showinfo` и детерминированно возвращаются к тем же равномерным средним точкам при сбое детектора, истечении времени ожидания, некорректном выводе или пустом наборе кандидатов. Режим `segment_aware` распределяет выборки средних точек пропорционально проверенным интервалам сцен; данные для режима `segment_aware` и поведение при возврате к резервному варианту подробно описаны ниже. Жесткое ограничение в 16 кадров применяется после выбора в каждой политике. Когда запрос с политикой `scene_aware` имеет бюджет всего в один кадр, он использует равномерную среднюю точку активного полного видео или окна фокуса и сообщает `policyEffective: uniform`: один выбранный кадр сцены не может сохранить оба временных конца. Вызывающий код может опционально предоставить конечное окно фокуса (`start`/`end` в секундах); границы фиксируются в пределах длительности медиафайла, перевернутые или бесконечные окна отклоняются, а все политики выборки выполняются только внутри нормализованного интервала. Полученное окно включается в метаданные выборки и в префикс недоверенного описания, чтобы нижестоящие модели могли отличать сфокусированный отрывок от всей временной шкалы.

Фокусировка семантических подписей — это отдельная явная настройка. Режим анализа `full` по умолчанию сохраняет существующий промпт кадра и никогда не пересылает текст запроса модели подписей. В режиме `focused` мост считывает только последний непустой созданный пользователем `text`/`input_text` из того же контейнера Chat или Responses, нормализует его в NFC, свертывает управляющие символы и пробелы и ограничивает его 500 кодовыми точками Unicode. Пустой результат возвращается к точному промпту `full`. Полезная подсказка сериализуется как JSON в выделенном блоке `untrusted-user-context` и может только расставлять приоритеты для наблюдаемых деталей; она не может отменять отдельное предупреждение против следования инструкциям, видимым или слышимым в медиафайле. Текстовый фокус никогда не вычисляет `start`/`end` и не изменяет временной семплер.

#### Структурные свидетельства сегментов FU-07

Режим `segment_aware` использует один ограниченный проход предварительного анализа уже проверенного локального видеопотока. Фиксированная цепочка фильтров сначала масштабирует изображение до ширины максимум в 320 пикселей, обнаруживает изменения сцен и замороженные интервалы, а затем выполняет выборку со скоростью 1 кадр в секунду для определения размытия, средней яркости (luma), а также пространственной/временной информации. Проход ограничен 600 структурными выборками, одним потоком FFmpeg/фильтра, теми же белыми списками протоколов (только `file`) и контейнеров, ограничением вывода процесса в 1 МиБ и не более чем 30 секундами в рамках общего таймаута/завершения брокера. Он никогда не принимает команду, фильтр, путь или URL из запроса.

Структурные значения представляют собой детерминированные данные выборки, а не семантическое понимание видео. Они не определяют субъекты, действия, подписи, речь или намерения пользователя. Границы сцен и заморозки образуют сегменты; покрытие заморозки, размытие, экспозиция, пространственная детализация и временные изменения влияют только на то, как распределяется существующий бюджет в 1–16 кадров. Полностью замороженный сегмент ограничен одним кадром, в то время как незамороженные сегменты борются за оставшийся бюджет. Когда границ больше, чем кадров, сохраняется равномерное покрытие временной шкалы, чтобы быстрые ранние склейки не могли скрыть длинный замыкающий сегмент. Границы сцен, находящиеся в пределах разрешения анализа в 1 секунду от границы заморозки, объединяются.

Отсутствующие фильтры, поврежденные/пустые данные, ошибка детектора или истечение времени ожидания ограниченного предварительного анализа приводят к безопасному переходу к точной политике равномерных средних точек. Прерывание вызова или истечение срока дедлайна брокера не вызывают безопасный отказ такого рода: они завершают выполняющийся в данный момент подпроцесс, предотвращают дальнейшее извлечение кадров, а закрытое временное дерево удаляется в блоке `finally`.

Скрипт `scripts/perf/video-bridge-fu07-eval.ts` генерирует детерминированные реальные фикстуры FFmpeg для оценки экономии вызовов подписей после дедупликации, распределения бюджета плотного движения, данных по размытию/экспозиции/SI-TI, быстрых обрезок с длинным хвостом и ложных срабатываний при плавном затухании. Он записывает реальное время предварительного анализа (wall time) и, если доступно `/usr/bin/time`, использование ЦП дочерним процессом и пиковое потребление RSS. Его проверки качества представляют собой исключительно структурные оракулы. Качество реальной модели подписей остается в статусе `HOLD`, поскольку эта тестовая обвязка не имеет авторизованной конечной точки или фиксированного судьи. Денежная экономия также остается в статусе `HOLD`, если параметр `--caption-cost-per-call-usd` не предоставляет явную положительную оценку стоимости за один вызов; скрипт никогда не подделывает ни один из этих результатов.

Размер каждого кадра ограничен 4 MiB, всех необработанных кадров вместе — 23 MiB, а сериализованного ответа брокера — 32 MiB. Приватный временный каталог удаляется в блоке `finally`. OmniRoute не поставляет FFmpeg в комплекте и не принимает пользовательский путь к исполняемому файлу. Перед созданием подписей мост применяет консервативный проход визуальной дедупликации: каждый JPEG-файл уменьшается до буфера градаций серого 16×16 и сравнивается только с последним сохраненным кадром. Для запрошенного бюджета подписей, превышающего один кадр, этап извлечения предоставляет ограниченный пул кандидатов размером до удвоенного бюджета и не более 16 кадров. Запрошенное ограничение применяется только после дедупликации, причем первый и последний выбранные кандидаты сохраняются при финальном прореживании, если бюджет составляет не менее двух. Версионная политика `grayscale-16x16-mean-cells-v2` использует наибольшее из значений между средней дельтой яркости и отношением ячеек миниатюры, у которых нормализованная дельта составляет не менее 0.05. Порог дублирования равен константе 0.04, выбранной ради предсказуемости, а не вынесенной в качестве параметра среды выполнения. Этот вторичный высококонтрастный сигнал сохраняет небольшие движения и изменения видимого текста, которые сравнение только по среднему значению может скрыть. Ошибки компаратора или декодера обрабатываются по принципу fail open и сохраняют охват. Выходные метаданные разделяют извлеченные кандидаты, успешно использованные кадры и отброшенные визуальные дубликаты.

Явно отмеченная часть видео может запрашивать контактный лист с временными метками. Мост строит сетку JPEG максимум из 4 колонок и 16 кадров. В каждую ячейку размером 512 пикселей встраивается исходная временная метка в высококонтрастную нижнюю полосу, в то время как те же временные метки остаются в текстовых метаданных для последующей связи и аудита. Полный файл JPEG по-прежнему ограничен 32 MiB. Если `sharp` не может декодировать или составить сетку, мост возвращается к использованию отдельных кадров JPEG; прерывание со стороны клиента по-прежнему распространяется на операцию с листом.

Свидетельства продвижения намеренно отделены от микробенчмарка синтетической композиции. `scripts/perf/video-bridge-contact-sheet-eval.ts` определяет версионную схему обвязки A/B-тестирования для реальных vision-моделей, совместимых с OpenAI. Он измеряет токены, сообщаемые провайдером, сквозную задержку по реальному времени (включая составление листа), количество вызовов модели и сохранность фактов, определенных в манифесте. Необработанные ответы модели не записываются в отчет; сохраняются только дайджесты SHA-256 и сопоставленные идентификаторы фактов. Обвязка не выполняет сетевых или платных вызовов модели, если не передан флаг `--execute-real` и не настроены `--model`, `OMNIROUTE_BASE_URL` и `OMNIROUTE_API_KEY`. Без этого явного реального запуска ее машиночитаемый вердикт остается `HOLD`; сами по себе измерения синтетической полезной нагрузки или количества вызовов не являются свидетельством для продвижения.

Вызывающий код может прикрепить необязательный массив `transcript.cues` к поддерживаемой части видео, если у него уже есть выровненный текст. Каждый элемент должен содержать `text`, конечный интервал `start`/`end` в пределах исследуемой длительности, а также разрешенный `source` (`client`, `embedded` или `audio-bridge`); значение `confidence` по умолчанию равно `1` и должно находиться в диапазоне от `0` до `1`. Точные дубликаты элементов сворачиваются. OmniRoute никогда не запускает транскрипцию на основе этих метаданных: проверенные элементы копируются в описываемый результат с указанием источника, достоверности и интервала, и выводятся как ненадежные наблюдения наряду с подписями кадров. Неверный, выходящий за допустимые пределы или не имеющий указания происхождения текст отклоняется, а не смешивается с потоком подписей. Оба канала транскрипции в теле запроса нормализуют предоставленное происхождение к `client`, включая самостоятельно заявленные метки `embedded` или `audio-bridge`. Только адаптер, принадлежащий серверу, может назначать эти доверенные метки с помощью доступного только из кода аргумента `trustedSource`; поле JSON в запросе не может обратиться к этому аргументу. Текст транскрипции остается ненадежным контентом, полученным из медиафайла, независимо от его происхождения, и никогда не должен определять авторизацию.

Продвинутый вызывающий код может предоставить дорожку `audioTranscript` для того же видео; она обрабатывается как текст, предоставленный клиентом, а не как доказательство серверной транскрипции. Точка слияния выполняет визуальные и аудио наблюдения в рамках единого дедлайна и сигнала прерывания, упорядочивает их на общей шкале времени, сворачивает точные дубликаты и сообщает о частичном результате, если успешна только одна сторона. Неверный `audioTranscript` деградирует до такого частичного результата — визуальное описание сохраняется, а в аудиоветке записывается очищенный код сбоя — вместо того, чтобы приводить к сбою всего видео. Доступность для каждой ветки, флаг частичного результата и очищенные коды сбоев сохраняются в описываемом результате, в метаданных защитных механизмов (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), в метаданных кэша результатов и в счетчиках слияния моста. Путь Video Bridge по умолчанию не вызывает преобразование речи в текст и не загружает вторую копию медиафайла; без этой явной дорожки он остается чисто видео-ориентированным.

**Хранение транскриптов (#12150 P1).** Это применяется автоматически всякий раз, когда Video Bridge (который требует явного включения) отображает метку транскрипта — отдельного флага хранения не существует. Когда запрос отображает любую метку транскрипта (`transcript`, объявленный вызывающей стороной, или объединенный `audioTranscript`), защитный механизм помечает его как `videoBridgeObserved` и создает отредактированную тень описания видео — идентичное представление, в котором тело произвольного текста каждой метки заменено на `[redacted-video-transcript]`, сформированное путем подстановки структурированного поля метки до сборки строки (а не путем синтаксического анализа сплющенного текста, поэтому ни одно содержимое метки — злонамеренное или обычное, включая тела, содержащие `]`, такие как `[inaudible]`/`[music]` — не может выжить). В сохраненном теле запроса журнала вызовов каждая текстовая часть, полученная из видео, заменяется этой отредактированной тенью на основе равенства содержимого; привязка `fullText` считывается заново из готового полезного загружаемого защитного механизма до вызова, поэтому сопоставление по-прежнему выполняется успешно после последующих защитных механизмов цепочки (маскировщиков PII и учетных данных, приоритеты 10/95), которые перезаписывают текст описания на месте, а также после изменения формы массива сообщений в результате вставки системного промпта / передачи / памяти. Тело, отправляемое вышестоящей модели, остается неизменным. Запрос, для которого зафиксировано наблюдение, также не заполняет постоянную Память (извлечение из запроса и из ответа пропускается), поэтому собственный ответ модели не может отразить текст транскрипта в Память.

**Исходные видеополя (#12430).** Когда мост включен, а собственная поддержка видео неизвестна или отсутствует, определенные поля `transcript`/`audioTranscript` также активируют `videoBridgeObserved` даже после сбоя описания или достижения лимита `maxVideos`. Значения `null` и пустые строки учитываются; отсутствующие поля и невидеометаданные — нет. Сохраненные копии редактируют эти поля или пропускают запрос, а кэши и Память обходятся.

На этих резервных путях допустимые метки вызывающей стороны становятся поддерживаемыми частями `text`/`input_text`, а не нестандартными полями провайдера. Обе дорожки, предоставленные в запросе, остаются ненадежными наблюдениями `client` с явным предупреждением о том, что видео не было описано, а временные метки не проверялись по медиафайлу. Существующие общие и индивидуальные лимиты (256 меток / 64 КиБ) применяются к обеим дорожкам в совокупности; временные метки должны укладываться в ограничение брокера в 600 секунд и любое предоставленное окно фокуса. Недопустимые дорожки отбрасываются, а не пересылаются как произвольный текст; допустимая сопутствующая дорожка все еще может использоваться, если не превышен их совокупный лимит. Поля `null` и пустые поля не добавляют текста. Этот резервный путь не добавляет выборку медиаданных или транскрипцию. Поля расширения транскрипта удаляются из резервного видеоносителя и его объектов `video_url`/`source`. Белый список сетевых протоколов OpenAI остается строгим; неизвестные нативные видеоносители остаются доступными, а известные текстовые цели сохраняют безопасные маркеры. Структурированные тени редактирования защищают добавленный текст транскрипта, в то время как исходный запрос, принадлежащий вызывающей стороне, остается без изменений. Цели с нативной поддержкой и отключенные мосты сохраняют свое текущее поведение обхода.

Дополнительные сохраненные копии используют тот же сигнал наблюдаемого запроса. Необработанный снимок клиентского запроса до защитного механизма, ожидающий запрос в памяти и журнал рано отклоненных запросов структурно заменяют поля транскрипта в частях видео; строковые промпты, синтезированные этапами конвейера и передачей контекста, редактируются в приемнике сохраненного тела запроса. Сохраненный маркер `video_content_removed` приводит к тому, что продолжение `previous_response_id` завершается неудачно (fail closed) вместо восстановления текста, который был намеренно отброшен. Если наблюдаемый запрос теряет свою тень редактирования для каждой части перед логированием или хотя бы одна из нескольких теней видео не совпадает после последующих мутаций запроса, сохраненное тело запроса опускается полностью вместо сохранения частично отредактированного транскрипта.

Для наблюдаемого запроса ответ модели может цитировать любую часть транскрипта без границы структурированной метки. Поэтому его сохраненное поле `responseBody` в журнале вызовов заменяется маркером пропуска; подробный артефакт конвейера (который может включать тела вышестоящих систем / клиентов и фрагменты потока) не сохраняется. Семантические кэши, кэши идемпотентности и повтора рассуждений обходят чтение и запись для этого запроса. Запрос провайдера и видимый клиенту ответ остаются без изменений. Ранние байты keepalive выгружаются из временного буфера при пропуске подробного артефакта. Предупреждение Kiro о некорректном EventStream сообщает только количество байт полезной нагрузки, но никогда не его содержимое или исходную ошибку парсера JSON. Это не означает, что была проведена проверка каждой независимой диагностики провайдера/плагина; более масштабная проверка сохраненных приемников отслеживается в задаче #11658.

Внутренний жизненный цикл `/api/modality-bridge/video/drilldown` представляет собой отдельную кэш-подложку с аутентификацией по петлевому соединению / токену. Для каждой операции также требуется канонический непрозрачный идентификатор субъекта. Перед включением вызывающей стороны в промышленной среде она должна получить этот идентификатор из аутентифицированного арендатора и никогда не должна пересылать значение, выбранное клиентом. Ключи кэша привязывают этого субъекта к каноническим идентификаторам сеанса и ссылок на видео, хранят только их производные ключи SHA-256 и ограничивают как чтение, так и удаление рамками одного и того же субъекта. Кэш хранит не более 16 производных JPEG-кадров на запись, удаляет их по истечении десяти минут и поддерживает ограниченное чтение по параметрам `start`/`end` или явное удаление сеанса.

Каждый субъект ограничен 16 записями и 64 МиБ канонических данных JPEG. Эти ограничения не зависят от глобального предельного значения в 64 записи / 256 МиБ: давление квоты субъекта вытесняет только наименее используемые записи этого субъекта до того, как рассматривается глобальное вытеснение LRU. Истекшие записи удаляются как из учета субъекта, так и из глобального учета при активности кэша, в то время как отмена и сбой валидации не фиксируют частичную замену.

Кэш отклоняет неканонический Base64, избыточное заполнение (padding), медиаданные не в формате JPEG, поврежденные или обрезанные JPEG-файлы, а также файлы JPEG, которые вызывают предупреждения при декодировании ограниченного полноразмерного изображения с помощью `sharp`. Он перекодирует каждое принятое изображение в канонический JPEG, вычисляет ширину и высоту на основе декодированных байтов, а не доверяет полям вызывающей стороны, и отбрасывает любые замыкающие полиглотные байты вместо их сохранения. Только ограниченный канонический сжатый буфер учитывается в обоих лимитах квот. Ограничение для JSON-трафика включает накладные расходы Base64 для ограничения декодированного ввода в 32 MiB. Каждая сохраненная производная запись содержит проверенный формат/разрешение JPEG, политику выборки, версию производной, время создания, вычисленный сервером хэш содержимого, хэшированную ссылку на родительский элемент, а также хэш содержимого родительского элемента от доверенного вызывающего абонента. Отмена проверяется между асинхронными фазами декодирования/хэширования перед атомарной фиксацией в кэше.

Этот транш еще не подключает производственного производителя к маршруту и не предоставляет выбор вариантов с нескольким разрешением. Таким образом, прозрачный путь запроса Video Bridge не влечет за собой дополнительной работы, в то время как вывод принципала, привязанного к клиенту, и полный жизненный цикл нескольких разрешений FU-08 остаются явной последующей работой, а не документируются как завершенное поведение.

Кадры подписываются последовательно с использованием настроенной видеомодели. Пустое переопределение Video наследует настройку Vision; если оба пусты, автомаршрутизатор Vision выбирает эффективную модель с поддержкой компьютерного зрения. Успешные подписи заменяют исходную часть стабильным префиксом `[Video description:`, который также помечает текст как ненадежное наблюдение на основе медиаданных и указывает нижестоящим моделям не следовать инструкциям, обнаруженным в медиафайле. Ключи кэша подписей кадров включают байты JPEG, промпт, метку времени и эффективную модель; кэшируются только успешные подписи. Записи в кэше сохраняют фактическую модель-производитель, успешно выполнившую задачу, включая резервную модель; мост сообщает `mixed`, когда разные кадры были созданы разными моделями. Попадание в кэш повторно использует эту идентичность производителя, а не переименовывает ее в запрошенный план маршрутизации. Кэш результатов для всего видео индексируется по каждому входу, который изменяет выходные данные — промпт, эффективной модели, политике выборки, количеству кадров, режиму семантического анализа, отпечатку SHA-256 нормализованной подсказки фокуса, окну фокусировки, `transcript`, `audioTranscript` и флагу контактного листа — поэтому изменение любого из этих параметров приводит к промаху кэша, а не к повторному использованию устаревших данных. Версия политики визуальной дедупликации, порог и ограниченное количество кадров-кандидатов также явно указаны в ключе кэша результатов и метаданных; таким образом, изменение политики не может привести к повторному использованию устаревшего описания всего видео. Метаданные кэша результатов v4 сохраняют режим и отпечаток, но никогда исходную задачу пользователя. Метаданные механизма защитных барьеров (guardrail) сообщают как запрошенный, так и эффективный режимы анализа; запрошенный режим `focused` без пригодного для использования пользовательского текста сообщается как фактически `full`.

Механизм защитных барьеров извлекает каждую поддерживаемую видеочасть, но описывает не более чем `modalityBridgeVideoMaxVideos`. Для цели, у которой доказано отсутствие поддержки `supportsVideo === false`, не прошедшие обработку и превышающие лимит видео становятся явными безопасными текстовыми маркерами, чтобы ни одно исходное видео не сохранилось. Когда возможности неизвестны, эти части сохраняют свой видеоноситель; любой резервный транскрипт следует указанному выше преобразованию ограниченного текста. Цели с `supportsVideo === true` обходят мост. Сигнал прерывания клиентского запроса распространяется через загрузку, очередь брокера, подпроцессы и вызовы подписей; прерывания останавливаются между видео и никогда не приводят к переходу к необработанным медиаданным при сбое.

Настройки среды выполнения хранятся в БД и проверяются с помощью Zod:

| Ключ                                | По умолчанию | Диапазон / поведение                                                                                           |
| ----------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`      | Необязательное время выполнения, активируется по выбору (opt-in)                                               |
| `modalityBridgeVideoAnalysisMode`   | `"full"`     | `full` сохраняет общие подписи; `focused` использует ограниченный ненадежный контекст последнего пользователя  |
| `modalityBridgeVideoModel`          | `""`         | Наследовать модель Vision Bridge                                                                               |
| `modalityBridgeVideoFrameCount`     | `8`          | 1–16                                                                                                           |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`  | `uniform`, `scene_aware` или пропорциональный `segment_aware`; при сбое детектора происходит откат к `uniform` |
| `modalityBridgeVideoMaxVideos`      | `1`          | 1–4                                                                                                            |
| `modalityBridgeVideoTimeout`        | `120000`     | 1000–120000 мс                                                                                                 |

Устаревшие сохраненные значения тайм-аута Video, превышающие 120 секунд, ограничиваются крайним сроком брокера; новая запись настроек, превышающая этот лимит, отклоняется.
`GET /api/modality-bridge/video/runtime` требует доверенного локального адреса loopback с временной меткой до аутентификации или зондирования среды выполнения, а затем требует аутентификации управления. Он возвращает только `available`, очищенные версии FFmpeg/ffprobe и фиксированную причину, когда среда выполнения недоступна. Внутренняя конечная точка извлечения не является общедоступным API загрузки: переполнение очереди возвращает `503` вместе с `Retry-After`, отключение клиента возвращает `499`, а фиксированный дедлайн брокера возвращает `504`. Преобразованные ответы добавляют
`video->text;model=<visionModel>;parts=<videos>` в центральный
заголовок `x-omniroute-modality-bridge` без удаления сегментов Vision или Audio.

### Маскировщик PII (`piiMasker.ts`)

Запускается на **обоих** этапах.

- **`preCall`** клонирует полезную нагрузку, обходит `system`, `messages`, `input` и `prompt` (включая элементы в виде простых строк) и применяет `processPII()` (из `@/shared/utils/inputSanitizer`) к строковым полям `content`/`text`. Когда `PII_REDACTION_ENABLED=true`, обнаруженные PII маскируются в исходящей полезной нагрузке. Это не зависит от `INPUT_SANITIZER_MODE` (который управляет только политикой защиты от инъекций промптов). Когда маскирование выключено, вызов регистрирует счетчики обнаружения без перезаписи содержимого.
- **`postCall`** выполняет глубокое клонирование ответа, запускает `sanitizePIIResponse()` и маскировщик структуры Responses-API (`maskResponsesOutput` — охватывает `output_text` и `output[].content[].text`). Если происходит какое-либо маскирование, измененный ответ заменяет исходный.

Защитный барьер никогда не блокирует; он только добавляет аннотации (`meta.detections`, `meta.redacted`) или перезаписывает содержимое.

#### Выбор по типам, пользовательские шаблоны и счетчики обнаружения

**Dashboard → Settings → Security → PII masking** выбирает, _что именно_ маскируется. Это не включает маскирование: за это по-прежнему отвечают `PII_REDACTION_ENABLED` (запрос) и `PII_RESPONSE_SANITIZATION` (ответ + SSE), причем оба параметра по умолчанию отключены.

- **Выбор по типам** — встроенные идентификаторы перечислены в `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). Если значение не задано, выбираются все типы (поведение до появления этой настройки). Шаблон `ssn_us` механизма запросов сопоставляется с `ssn`. Шаблоны (Minimal, Standard, Financial, Brazilian, USA, Full) только заполняют флажки в пользовательском интерфейсе.
- **Пользовательские шаблоны** — до 20 регулярных выражений или шаблонов с подстановочными знаками (`*` = до 64 непробельных символов, `?` = один). Совпадения заменяются на `[CUSTOM_REDACTED]`. Каждый шаблон проходит через `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`): не более 500 символов, флаги ограничены `g i m s u`, должен успешно компилироваться, проходить проверку `safe-regex` (на катастрофический возврат) и не соответствовать пустой строке или заполнителю маскирования. Шаблон, не прошедший проверку, отклоняется при сохранении и тестировании, а сохраненная строка с ошибкой пропускается во время выполнения вместо компиляции. Пользовательские шаблоны выполняются только тогда, когда маскирование включено.
- **Счетчики обнаружения** — счетчики по каждому типу (значения совпадений никогда не сохраняются), хранящиеся в памяти и сбрасываемые при перезагрузке (`src/lib/pii/piiDetectionStats.ts`). Они увеличиваются только тогда, когда маскирование включено.

Настройки хранятся в таблице `key_value` (пространство имен `pii_settings`, `src/lib/db/piiSettings.ts`) и считываются через кеш с временем жизни 1 с. API:

| Метод  | Путь                     | Назначение                                                                             |
| ------ | ------------------------ | -------------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | Состояние флага, `enabledTypes`, `customPatterns`, счетчики обнаружения                |
| `PUT`  | `/api/settings/pii`      | Замена `enabledTypes` (`null` = все) и/или `customPatterns`                            |
| `POST` | `/api/settings/pii/test` | Тестовый прогон одного шаблона на выборке объемом не более 8 КБ; ничего не сохраняется |

Все три метода требуют авторизации администратора и проверяют тело запроса с помощью Zod (`src/shared/validation/schemas/piiSettings.ts`).

### Инъекция промптов (`promptInjection.ts`)

Обнаруживает вредоносные структуры в контенте, предоставляемом пользователем, и применяет настроенную политику. Поведение определяется переменными окружения и параметрами конструктора:

| Настройка       | Перем. окружения                                                                                      | По умолч. | Эффект                                                                                                                                                                                                      |
| --------------- | ----------------------------------------------------------------------------------------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Enabled         | `INPUT_SANITIZER_ENABLED`                                                                             | `true`    | Когда `false`, защитный барьер завершается досрочно.                                                                                                                                                        |
| Mode            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`    | Политика инъекций: `block`, `warn` или `log`. (`redact` принимается для обратной совместимости, но **не** удаляет текст инъекции; перезапись PII в запросе управляется параметром `PII_REDACTION_ENABLED`.) |
| Block threshold | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`    | Минимальная критичность, необходимая для блокировки. Medium по умолчанию работает только в режиме наблюдения.                                                                                               |

**Приоритет режимов** (`getMode`): `options.mode` вызывающего кода → переопределение флага функции в БД `INJECTION_GUARD_MODE` (Dashboard → Settings → Feature Flags) → переменная окружения `INJECTION_GUARD_MODE` → переменная окружения `INPUT_SANITIZER_MODE` → `warn`. Таким образом, переопределение в дашборде имеет приоритет над переменными окружения, поэтому пользовательский интерфейс Feature Flags управляет работающим защитным барьером "на лету" (без перезапуска). Чтение из БД является отказоустойчивым: в случае ошибки защитный барьер возвращается к поведению на основе переменных окружения, а если переопределение не задано, поведение идентично разрешению только на основе переменных окружения.

Источники обнаружения:

1. `sanitizeRequest()` из `@/shared/utils/inputSanitizer` (общий набор детекторов, используемый в других частях конвейера).
2. Встроенные `DEFAULT_GUARD_PATTERNS` (в настоящее время `system_override_inline` и `markdown_system_block`, оба имеют высокую критичность — `high`).
3. Необязательные `customPatterns`, передаваемые через параметры конструктора (строки, регулярные выражения или записи `{ name, pattern, severity }`).

Когда `mode === "block"` **и** хотя бы одно обнаружение достигает порога критичности, `preCall` возвращает `{ block: true, message: "Request rejected: suspicious content detected" }`. В режимах `warn`/`log` guardrail логирует запрос, но разрешает его выполнение. Вспомогательная функция `evaluatePromptInjection()` также экспортируется для вызывающего кода, которому необходимо оценивать промпты в обход реестра.

**Ограничение сканирования (v3.8.20):** детектор анализирует только **первые 16 КБ** объединенного текста промпта — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байта) в `src/shared/utils/inputSanitizer.ts`. И `detectInjection()`, и `evaluatePromptInjection()` вызывают `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском цикла проверки паттернов. Инструкции внедрения (инъекций) обычно находятся ближе к началу входных данных, поэтому это ограничивает нагрузку на ЦП/сборщик мусора регулярных выражений для полезных нагрузок размером в сотни килобайт без снижения качества обнаружения (см. #3932, #4041).

### Маскировщик учетных данных (`credentialMasker.ts`)

Запускается на **обоих** этапах, последним в цепочке по умолчанию (приоритет `95`). Удаляет известные паттерны API-ключей и секретных токенов из исходящей полезной нагрузки (содержимое сообщения, аргументы вызовов инструментов, результаты инструментов) **и** из ответа провайдера, благодаря чему учетные данные, вставленные в промпт (или возвращенные в результате вызова инструмента), не утекают к вышестоящему провайдеру или обратно клиенту.

- **Только по явному запросу (opt-in)**, по аналогии с маскировкой PII (согласно жесткому правилу #20): отключено по умолчанию, если не задано `settings.credentialRedactionEnabled === true` **или** `CREDENTIAL_REDACTION_ENABLED=true`. Когда функция отключена, guardrail работает как заглушка (no-op) — он никогда не блокирует запросы и ничего не перезаписывает.
- Функция `redactCredentials()` обходит всё дерево полезной нагрузки/ответа (`walkValue()`, с защитой от загрязнения прототипов (prototype-pollution-safe) и циклических ссылок через `WeakSet`) и заменяет совпадения плейсхолдером `[REDACTED:<type>]`, клонируя только те ветви, которые действительно изменились.
- Константа `CREDENTIAL_PATTERNS` охватывает ключи провайдеров LLM (OpenAI, OpenAI-proj, Anthropic, Google, Hugging Face, Replicate), токены VCS/SaaS (GitHub, Slack, Linear, Notion, npm, Postman, Discord), платежные ключи (Stripe, Square), облачные ключи (AWS access key, Twilio, SendGrid, Mailgun), закрытые ключи / JWT, строки подключения с учетными данными (`mongodb://user:pass@...` и т. д.), а также общий паттерн значения заголовка `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключи в виде заголовков (`authorization`, `x-api-key`, `api-key`, `apikey`) маскируются структурно (маскируется только значение, а префикс схемы, такой как `Bearer `/`Basic `, сохраняется), а не с помощью общего текстового регулярного выражения.
- Guardrail никогда не блокирует запросы; он только выполняет перезапись (`modifiedPayload` / `modifiedResponse`) и добавляет аннотации (`meta.credentialsRedacted`, `meta.count`).

Защита от регрессий: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовый контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // значение true прерывает цепочку досрочно
  message?: string; // выводится при блокировке
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // возвращается preCall для перезаписи запроса
  modifiedResponse?: TValue; // возвращается postCall для перезаписи ответа
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Защитный механизм сигнализирует об отсутствии изменений, возвращая `void`, `{}` или
`{ block: false }`. Возврат `modifiedPayload` или `modifiedResponse` заменяет
значение, проходящее через цепочку для последующих защитных механизмов.
`signal?: AbortSignal` передает жизненный цикл вызывающего кода в защитные механизмы. Прерывание запроса — это намеренное исключение по принципу fail-open: медиамосты прекращают работу и очищают ресурсы, не восстанавливая исходные медиаданные для целевого объекта, который, как известно, не поддерживает их.

## Реестр (`registry.ts`)

Синглтон `guardrailRegistry` предоставляет следующие возможности:

- `register(guardrail)` — добавляет (или заменяет по нормализованному имени) защитный механизм и
  производит повторную сортировку по возрастанию `priority`.
- `clear()` / `list()` — административные вспомогательные функции.
- `runPreCallHooks(payload, context)` — итерирует активные защитные механизмы, прогоняет
  полезную нагрузку через `modifiedPayload` и останавливается на первом `block: true`.
- `runPostCallHooks(response, context)` — аналогичный поток для стороны ответа.
- `resetGuardrailsForTests({ registerDefaults })` — очищает состояние и при необходимости
  заново регистрирует значения по умолчанию для обеспечения чистой изоляции тестов.

Оба обработчика возвращают объект `{ blocked, payload|response, results, guardrail?, message? }`,
где `results` представляет собой массив записей `GuardrailExecutionResult`, содержащих
поля `blocked`, `skipped`, `modified`, `error` и `meta` для каждого защитного механизма,
которые полезны для трассировки.

### Отключение защитных механизмов для каждого запроса

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегирует
дедуплицированный список имен защитных механизмов, которые должны быть пропущены для текущего
запроса. Существует пять каналов, которые считываются в следующем порядке и объединяются в один список
(при дедупликации побеждает первое вхождение):

1. `apiKeyInfo.disabledGuardrails`
2. `disabledGuardrails` в теле запроса (на верхнем уровне)
3. `metadata.disabledGuardrails` в теле запроса (только когда `metadata` является объектом)
4. Заголовок `x-omniroute-disabled-guardrails`
5. Устаревший заголовок `x-disabled-guardrails`

Все пять каналов объединяются, включая оба заголовка: отправка как
`x-omniroute-disabled-guardrails`, так и `x-disabled-guardrails` пропускает объединение
их списков, а пустой современный заголовок больше не скрывает устаревший
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), исправлено в
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)).

Значения могут быть массивами строк или строкой, разделенной запятыми; имена обрезаются
и нормализуются к нижнему регистру в формате kebab-case (`pii_masker` → `pii-masker`),
а пустые элементы отбрасываются. Результат передается через `context.disabledGuardrails`
в реестр, который пропускает соответствующие защитные механизмы (`skipped: true` в `results`).

Список отключения влияет только на **реестр**. Режим `block` для защиты от внедрения подсказок (prompt-injection) является
обязательной границей: промежуточное ПО защиты от внедрения
(`src/middleware/promptInjectionGuard.ts`) вызывает `evaluatePromptInjection()`
без какого-либо контролируемого вызывающей стороной списка отключения (неиспользуемый
вызов `resolveDisabledGuardrails({ body })`, который оно совершало ранее, был удален в
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), поэтому запрос,
отключающий `prompt-injection`, все равно отклоняется в режиме `block`. Это сделано
намеренно. Каналы отключения контролируются вызывающей стороной (тело запроса,
метаданные, заголовки), и вызывающая сторона не должна иметь возможности отключить элемент
управления безопасностью, установленный оператором
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Объединение заголовков
из [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)
изменяет только то, какие защитные механизмы реестра пропускаются; оно не позволяет клиенту
обойти промежуточное ПО. Обязательные политики защитных механизмов для каждого ключа и для каждой группы
отслеживаются в RFC v4 [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
См. [Coverage and limits](#coverage-and-limits).

## Порядок выполнения

Для каждого запроса, проходящего через `src/sse/handlers/chat.ts` и
`open-sse/handlers/chatCore.ts` (маршруты семейств чата, перечисленные в разделе
[Покрытие и ограничения](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` формирует список пропуска на основе ключа API, тела запроса
   и заголовков.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` запускает защитные механизмы в порядке возрастания приоритета:
   - Отключенные механизмы защиты регистрируются как `skipped`.
   - Метод `preCall` каждого механизма защиты может перезаписывать полезную нагрузку через `modifiedPayload`.
   - Первый `block: true` прерывает цепь выполнения (short-circuit), и обработчик возвращает
     ответ об отклонении защитным механизмом.
3. Полезная нагрузка (возможно, перезаписанная) поступает в составную маршрутизацию и вышестоящую
   диспетчеризацию.
4. **Только для ответов без потоковой передачи (non-streaming):** после формирования ответа
   `guardrailRegistry.runPostCallHooks(...)` запускает ту же цепочку для ответа. Значение `block: true` здесь отбрасывает ответ от вышестоящего источника и возвращает HTTP 400. Потоковые ответы полностью пропускают этот шаг.

Защитные механизмы, генерирующие исключения, фиксируются с `error: <message>` и логируются через
`logger.warn`, но цепочка продолжает работу — по задумке реализовано поведение fail-open.

## Покрытие и ограничения

Реестр защитных механизмов встроен только в конвейер чата. Эти ограничения
зафиксированы в тестах `tests/unit/guardrail-pipeline-wiring-characterization.test.ts` и
`tests/unit/guardrail-pipeline-characterization.test.ts`; осознанно обновляйте эти тесты
при изменении поведения.

### Где выполняются хуки

| Хук / элемент управления                     | Выполняется в                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `runPreCallHooks`                            | Запросы, обрабатываемые `handleChat` (`src/sse/handlers/chat.ts`): `/v1/chat/completions`, `/v1/completions`, `/v1/messages`, `/v1/responses` (а также `/v1/responses/*`), `/v1/relay/chat/completions`, `/v1/providers/{provider}/chat/completions`, `/v1/api/chat`, `/v1/antigravity`, `/v1beta/models/*`, а также прокси чата Telegram. Также тестовый эндпоинт панели мониторинга `/api/guardrails/test`. Блокировка pre-call возвращает HTTP 400. |
| `runPostCallHooks`                           | Только ответы чата **без потоковой передачи (non-streaming)** (`open-sse/handlers/chatCore/nonStreamingResponse.ts`). Потоковые ответы до него никогда не доходят.                                                                                                                                                                                                                                                                                     |
| Потоковый PII                                | `createPiiSseTransform` (`src/lib/streamingPiiTransform.ts`), передаваемый по конвейеру в `streamingPipeline.ts`, когда включен `PII_RESPONSE_SANITIZATION`. Это не защитный механизм, поэтому каналы отключения на него не влияют.                                                                                                                                                                                                                    |
| Промежуточное ПО защиты от инъекций (legacy) | Каждый маршрут `/v1`, содержащий промпты, включая семейство чатов (см. [покрытие маршрутов](#injection-guard-route-coverage--red-team-phase-8--block-d)). Только защита от инъекций в промпты.                                                                                                                                                                                                                                                         |

### Что не покрывается

- **Маршруты медиаданных, эмбеддингов и данных** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) никогда не попадают в реестр. Там не
  выполняются маскирование PII, маскирование учетных данных или мост модальностей. Их единственная
  проверка — устаревшее промежуточное ПО защиты от инъекций.
- **Потоковые ответы** не получают защитных механизмов после вызова: нет `pii-masker` или
  `credential-masker` после вызова, а также нет блокировки после вызова. Применяется только преобразование
  потокового PII (когда включен `PII_RESPONSE_SANITIZATION`). Учетные данные,
  эхом возвращенные в потоковом ответе, не маскируются.
- **Каналы отключения по сравнению с промежуточным ПО (по замыслу):** промежуточное ПО оценивает
  инъекции в промпты с помощью собственного вызова `evaluatePromptInjection()`, без
  передачи управляемого вызывающим абонентом списка отключений. Режим `block` — это обязательная
  граница, которую отключения, управляемые вызывающим абонентом, не могут обойти, в том числе на маршрутах семейства чатов
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Отключение
  `prompt-injection` пропускает только механизм защиты реестра.

### Что видит ответ перед этапом post-call

На пути без потоковой передачи порядок следующий: извлечение памяти → выполнение встроенных
инструментов → защитные механизмы после вызова (post-call guardrails) → выход из блока post-call → сохранение в семантический кэш.

- **Извлечение памяти** и **выполнение инструментов** видят ответ до того, как
  защитные механизмы post-call смогут перезаписать или заблокировать его. Начиная с
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401), извлечение памяти
  прогоняет извлеченный текст через `sanitizePII`, когда
  `PII_RESPONSE_SANITIZATION` включена (как в потоковом режиме, так и без него), но
  ответ, который впоследствии блокируется на этапе post-call, все равно
  передается в память и инструменты.
- **Семантический кэш** сохраняет ответ после этапа post-call, поэтому он сохраняет
  перезаписанный ответ, а заблокированный ответ никогда не кэшируется. Ключи записей
  кэша соответствуют ключам API.

## Конфигурация

Переменные среды, считываемые встроенными защитными механизмами:

| Переменная                            | Используется              | Эффект                                                                                                                 |
| ------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | Установите `false`, чтобы полностью отключить обнаружение.                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | Политика инъекций: `warn`, `block` или `log`. Устаревшее значение `redact` не перезаписывает текст инъекции.           |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | Режим для защитного фильтра инъекций; также флаг функции БД, который **переопределяет** переменные среды (БД > ENV).   |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | Минимальная степень серьезности, при которой `MODE=block` отклоняет запрос: `high` (по умолчанию), `medium` или `low`. |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | Устаревший псевдоним для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                            |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | Если установлено значение `true`, персональные данные (PII) в запросе маскируются (независимо от режима инъекций).     |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (downstream) | Управляет поведением маскировщика на стороне ответа.                                                                   |

Защитные механизмы Modality Bridge считывают конфигурацию времени выполнения из хранилища настроек на базе БД (`getSettings()`), а не из переменных среды. Основными ключами для Vision являются
`modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`,
`modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`,
`modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`,
`modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`,
`modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` и
`modalityBridgeCacheMaxEntries`. Устаревшие ключи
`visionBridge*` принимаются только в качестве документированного резервного варианта чтения на один цикл; при записи из панели управления используются основные ключи. Значения по умолчанию и механизм разрешения резервных вариантов находятся в `src/shared/constants/modalityBridgeDefaults.ts`, а устаревшие константы сохранены в `src/shared/constants/visionBridgeDefaults.ts`.

Для Audio используются `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`,
`modalityBridgeAudioTimeout` и `modalityBridgeAudioMaxClips`, а также общие
настройки `modalityBridgeCache*`. У Audio нет резервного варианта для устаревших ключей, поскольку эти
ключи были введены вместе со схемой Modality Bridge.

Для Video используются `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`,
`modalityBridgeVideoModel`,
`modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`,
`modalityBridgeVideoMaxVideos` и
`modalityBridgeVideoTimeout`, а также общие настройки `modalityBridgeCache*`.
Функция отключена по умолчанию, поскольку FFmpeg/ffprobe являются необязательными операционными
зависимостями, а создание подписей к кадрам добавляет задержку и увеличивает стоимость использования модели.

## Пользовательские guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Шаги:

1. Создайте `src/lib/guardrails/myGuardrail.ts`, наследующий `BaseGuardrail`.
2. Реализуйте `preCall` и/или `postCall`.
3. Зарегистрируйте защитный механизм либо во время импорта (добавив в `registerDefaultGuardrails`), либо вызовите `guardrailRegistry.register(...)` во время выполнения (runtime) — реестр заменяет любой предыдущий guardrail с тем же нормализованным именем.
4. Добавьте тесты в `tests/unit/` (существующие примеры: `tests/unit/guardrails-registry.test.ts`, `tests/unit/prompt-injection-guard.test.ts`, `tests/unit/guardrails/visionBridge.test.ts`).

## Тестирование

Используйте `resetGuardrailsForTests()` между тестами для запуска из известного состояния. Передайте `{ registerDefaults: false }`, чтобы начать с пустого реестра и зарегистрировать только тестируемые guardrails. Vision Bridge принимает внедрение зависимостей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge предоставляет эквивалентные точки интеграции для настроек, возможностей, выбора модели STT, проверки учетных данных и транскрипции. Таким образом, тесты могут проверять оба потока без доступа к БД или сети.

## Покрытие маршрутов защитой от инъекций и Red-team (Фаза 8 · Блок D)

Защита от инъекций (`createInjectionGuard` / `withInjectionGuard`) охватывает все маршруты, принимающие пользовательские промпты. Она учитывает `INJECTION_GUARD_MODE` (по умолчанию `warn` = только логирование; `block` = возвращает HTTP 400 `SECURITY_001`).

| Тип                  | Маршруты                                                                                                                                             | Режим по умолчанию |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| Текст (существующий) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn               |
| Генеративный         | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn               |
| Данные               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn               |

Извлечение текста (`extractMessageContents`) охватывает `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (ночной запуск, `nightly-llm-security.yml`):** promptfoo проверяет, что каждый маршрут блокирует корпус OWASP-LLM при `INJECTION_GUARD_MODE=block`; garak запускает зондирование (пропускается при отсутствии секретного ключа). Маршрут `moderations` включен для согласованности. Режим блокировки является обязательной границей: `evaluatePromptInjection()` игнорирует список отключений для конкретного запроса, передаваемый middleware, поэтому `disabledGuardrails` **не** освобождает маршрут от этой проверки ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

Ночной рабочий процесс (`.github/workflows/nightly-llm-security.yml`, cron + ручной запуск) состоит из двух заданий:

- **`promptfoo-guard` (блокирующее)** — запускает `promptfoo eval -c promptfooconfig.yaml` с `INJECTION_GUARD_MODE=block`. Каждый состязательный сценарий (например, «ignore all previous instructions…», джейлбрейки в стиле DAN) проверяет, что ответ содержит `error.code === "SECURITY_001"`, т. е. защита действительно отклонила запрос.
- **`garak` (информационное)** — запускает garak со флагами `--probes promptinject,dan,leakreplay` против локального экземпляра OmniRoute (`http://localhost:20128/v1`). Защищено проверкой секретного ключа провайдера (`PROMPTFOO_PROVIDER_KEY`); корректно пропускается при его отсутствии и имеет суффикс `|| true`, поэтому формирует отчет без падения CI.

Покрытие вспомогательной функции защиты (`createInjectionGuard` / `withInjectionGuard`) охватывает каждый маршрут `/v1`, принимающий промпты; текст промпта извлекается из `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` с помощью `extractMessageContents()` в `src/shared/utils/inputSanitizer.ts`.
