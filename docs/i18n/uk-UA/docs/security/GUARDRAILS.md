> до яких маршрутів та шляхів відповідей дотягуються хуки, об'єднані заголовки вимкнення (#16412), ін'єкція
> як режим блокування у ролі обов'язкової межі (#16413), а також те, що бачить відповідь до post-call)

Захисні бар'єри забезпечують дотримання безпеки, політик та трансформацію контенту на межі
між OmniRoute та висхідними провайдерами. Кожен захисний бар'єр може перевіряти (і
за бажанням відхиляти, трансформувати чи анотувати) корисні дані запитів (`preCall`) та
відповіді висхідних провайдерів (`postCall`).

Система працює за принципом **fail-open**: якщо під час виконання захисний бар'єр викидає помилку, реєстр
записує її та продовжує роботу з наступним бар'єром, замість того щоб завершити запит
помилкою. Блокування є явним рішенням (`block: true`), а не випадковістю.
Єдиним винятком є скасований запит: коли `signal` ініціатора скасовується,
захисний бар'єр, що викинув помилку, відхиляє виконання хука замість того, щоб бути пропущеним.

Хуки **не** виконуються на кожному маршруті чи кожній відповіді. Ознайомтеся з розділом
[Покриття та обмеження](#coverage-and-limits), перш ніж покладатися на захисний бар'єр як на
засіб безпеки.

| Пріоритет | Назва               | Етап(и)        | Файл                  |

### Міст зору (`visionBridge.ts`) — Modality Bridge PR-1

Базова модель GLM 5.3 та `glm-5.3-{low,high,max}` мають явні
метадані реєстру/специфікації `supportsVision:false`. Варіанти GLM 5.3 Flash
залишаються моделями з нативною підтримкою зору. Маршрут `/v1/messages` від Claude Code потрапляє до
спільного ланцюжка передопераційних захисних бар'єрів `handleChat` **до** перетворення з Claude у формат OpenAI;
вкладені зображення з результатів інструменту `Read` мають бути описані або оброблені
до того, як це перетворення підніме їх у вміст `image_url` для OpenAI (#17069).

Перехоплює запити, що містять зображення і спрямовані на **моделі без підтримки зору**, і або
перенаправляє весь запит на модель із підтримкою зору, або замінює частини зображень
текстовими описами, створеними налаштовуваною моделлю зору перед
висхідним викликом. Це дозволяє провайдерам, які працюють лише з текстом, прозоро обробляти
мультимодальні корисні дані.

Потік виконання:

1. Пропустити, якщо цільова модель вже підтримує зір (якщо вона не з'являється у
   списку примусового мосту `isVisionBridgeForcedModel`).
2. Витягти частини зображень за допомогою `extractImageParts(messages)`
   (`visionBridgeHelpers.ts`), яка делегує роботу **універсальному детектеру
   медіа** `detectMediaParts()` у `open-sse/utils/mediaParts.ts` —
   єдиному джерелу істини, спільному з комбінованим фільтром сумісності.
   Витягнення дозволено лише для структур, які `replaceImageParts` може знову
   об'єднати (контракт витягнення↔заміни): OpenAI `image_url`, Anthropic base64
   `source.type:"base64"`, Anthropic URL `source.type:"url"`, та Responses
   API `input_image`. Зображення, що відповідають критеріям і вкладені всередину Claude Code
   `tool_result.content` та виводів інструментів Responses, також витягуються та
   замінюються за їхніми початковими шляхами; структури, що є лише індикаторами, є матеріалом
   комбінованого фільтра і не витягуються.
   Пропустити, якщо нічого не знайдено.
3. Визначити конфігурацію часу виконання через `resolveVisionBridgeRuntimeSettings()`
   (`src/shared/constants/modalityBridgeDefaults.ts`): нові ключі налаштувань `modalityBridge*`
   перемагають; застарілі ключі `visionBridge*` залишаються як **резервний варіант на один цикл**
   (вікно відкату). Пропустити перед будь-яким обходом медіа, коли міст вимкнено.
4. Селектор режимів (`modalityBridgeVisionMode`, див. таблицю нижче) вирішує,
   що робити: перенаправляти чи описувати. Перенаправлення повертає `modifiedPayload` лише зі зміненою
   `model` та метаданими `{ rerouted, fromModel, toModel, imagesKept }`.
5. Шлях опису: обмежити зображення параметром `maxImages`, скласти контекстно-орієнтований промпт,
   звернутися до кешу описів, викликати модель зору **паралельно**
   (`Promise.allSettled`), а також вставити текстові частини `[Image N]: <description>`
   на їхнє місце. Збій опису дає `null`: вихідне зображення зберігається для
   невідомих цілей або цілей із підтримкою зору (#4012), але **підтверджена пряма ціль лише для тексту**
   або комбінація без зору отримує явну
   текстову заглушку `(unavailable — no vision-capable provider connected)` для
   кожного неописаного зображення, включаючи часткові збої та зображення понад
   ліміт викликів опису (#17069). Наявний резервний механізм комбінованого опису у разі повного збою
   залишається в силі (#8430).
6. Повернути `modifiedPayload` + метадані (`imagesProcessed`, `descriptions`,
   `processingTimeMs`, `visionModel`).

#### Селектор режимів (`modalityBridgeVisionMode`)

| Mode       | Default | Behavior                                                                                                                                                                                                                                                                                                                           |
| ---------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | Застаріла евристика, без змін (#6640/#7204): некомбіновані моделі / моделі `auto/` перенаправляються на найкращу візуальну модель, якщо початкова модель ще не має придатних облікових даних (у такому разі виконується опис); комбіновані цілі завжди виконують опис.                                                             |
| `describe` |         | Завжди описувати — блок перенаправлення повністю пропускається; завжди відповідає обрана користувачем модель.                                                                                                                                                                                                                      |
| `reroute`  |         | Примусове перенаправлення: захисний механізм збереження моделі з обліковими даними обминається. Захисний механізм облікових даних для **цілі** перенаправлення все ще діє — якщо немає придатної візуальної цілі, міст блокує запит чіткою помилкою замість опису чи надсилання сирих зображень на ціль, яка підтримує лише текст. |

Примусові режими спрацьовують накоротко **до** запуску евристики `auto`; поведінка `auto` є побайтово ідентичною захисному механізму до PR-1.

#### Область дії ключа API (`visionBridgeKeyScope.ts`)

Коли ключ API викликаючого боку обмежує `allowedConnections`, пули квот (`allowedQuotas`) або моделі (`allowedModels` / `blockedModels` / `modelAccessMode: "restricted"` / `disableNonPublicModels`), міст вибирає лише ті моделі перенаправлення та опису, які ключ може використовувати, на з'єднаннях, які ключ може використовувати. Виклик опису потім завжди проходить через внутрішню петлю OmniRoute із заголовком `x-omniroute-self-loop-key-id`, тому отриманий запит чату знову застосовує політику з'єднань і моделей цього ключа. Функція `enforceApiKeyPolicy()` враховує цей заголовок лише разом із токеном носія внутрішньої петлі, тому вона може лише звузити доступ, а ідентифікатор, який не вдається розпізнати, відхиляється.

Якщо для ключа не дозволено жодної візуальної моделі, **підтверджена ціль, що працює лише з текстом**, локально відхиляє запит зображення з чіткою помилкою HTTP 400 замість пересилання байтів зображення на нездатну до цього висхідну систему (#17069). Для цілей із невідомими можливостями зору або його нативною підтримкою шлях опису зберігає попередню поведінку у разі збою на відкриття (meta `{ skipped: true, reason: "no_permitted_vision_model" }`). Запити без ключа та ключі без таких обмежень поводяться точно так само, як і раніше.

#### Промпт опису з урахуванням завдання (`modalityBridgeVisionTaskAware`)

За замовчуванням **true**. Функція `composeVisionPrompt()` (`visionBridgeHelpers.ts`) додає текст **останнього повідомлення користувача** (обрізаний до 500 символів) до базового промпту опису, спрямовуючи опис на те, що насправді попросив користувач (патерн codex-vision-proxy), і просячи візуальну модель транскрибувати видимий текст. Якщо прапорець вимкнено або текст користувача відсутній, базовий промпт використовується без змін.

Власний сумісний з OpenAI запит внутрішньої петлі опису (`callVisionModelSingle()` у `visionBridgeHelpers.ts`) завжди вимагає `image_url.detail: "high"` — безумовно, для кожного викликаючого боку / провайдера, без прив'язки до жодних сигналів клієнта. Вибірка з низькою деталізацією погіршує точність розпізнавання тексту саме для завдання транскрипції тексту, яке запитує цей промпт, тому сам виклик опису завжди запитує високу деталізацію незалежно від того, який рівень деталізації використовував оригінальний вхідний запит. Це стосується лише тіла внутрішнього запиту опису; це не змінює того, як OmniRoute пересилає власний `image_url.detail` викликаючого боку в первинному запиті — значення за замовчуванням застосовується окремо і лише для виявлених клієнтів OpenCode у функції `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`). Гілка формату передачі даних Anthropic для внутрішньої петлі опису не має поля `detail` і не залежить від жодного з цих значень за замовчуванням.

#### Обмеження виводу опису (`modalityBridgeVisionMaxChars`)

| Ключ                           | За замовчуванням | Діапазон          |
| ------------------------------ | ---------------- | ----------------- |
| `modalityBridgeVisionMaxChars` | `0`              | `0` або 100–50000 |

`0` (за замовчуванням) означає **відсутність обмеження** — опис, повернутий функцією `callVisionModel()`, передається без змін, зберігаючи поточну поведінку. Будь-яке значення в діапазоні 100–50000 обрізає опис із суфіксом `…` перед тим, як він вставляється назад у форматі `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` у `src/lib/guardrails/visionBridge.ts`). Збільште це значення для завдань оптичного розпізнавання символів (OCR) із високим ступенем деталізації, де нижня модель потребує повної транскрипції; зменште його, щоб обмежити використання токенів на багатослівних візуальних моделях. Поле панелі керування розташоване на розширеній панелі вкладки Vision (`modality-bridge-max-chars` у `ModalityBridgeVisionTab.tsx`) і округлює будь-яке значення від 1 до 99 до нижньої межі 100, залишаючи явне `0` без змін — `0` саме по собі є валідним значенням Zod (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`), а не просто значенням «не встановлено» за замовчуванням.

#### Кеш описів (`modalityBridge/bridgeCache.ts`)

Розподілений у межах процесу кеш LRU + TTL у пам'яті для результатів опису. Ключ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` із форматуванням із префіксом довжини (без колізій на межах полів). Компонент моделі — це **налаштована** модель мосту, а не та модель, яка фактично відповіла — `callVisionModel` може виконувати внутрішній резервний перехід, і створення ключів для кожної спроби призвело б до фрагментації кешу. Невдалі описи ніколи не кешуються. Налаштування:

| Ключ                            | За замовчуванням | Діапазон |
| ------------------------------- | ---------------- | -------- |
| `modalityBridgeCacheEnabled`    | `true`           | —        |
| `modalityBridgeCacheTtlMinutes` | `60`             | 1–1440   |
| `modalityBridgeCacheMaxEntries` | `200`            | 10–5000  |

#### Нормалізація віддалених зображень (self-loop describe/base64 fetch)

Коли міст самостійно отримує **віддалене** зображення (self-call опису Anthropic та перетворення base64 у форматі claude-wire (`ensureBase64ImagesForClaudeWire`), обидва за допомогою `fetchRemoteImageAsDataUri()` у `visionBridgeHelpers.ts`), отриманий URI даних проходить через `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) перед вбудуванням у запит до моделі зору. Зображення надмірного розміру зменшуються до **довгого краю 2048px** (що відповідає обмеженню зміни розміру, яке OpenAI/Anthropic вже застосовують на серверній стороні), що зменшує обсяг байтів завантаження / затримку без зміни того, що бачить модель зору. Зміна розміру використовує `sharp`, який завантажується через динамічний імпорт: на платформі, де його нативний бінарний файл не вдається завантажити, `normalizeDataUri()` **ніколи не викидає винятків** — він повертається до пропуску оригінальних байтів, тому шлях опису / перетворення base64 завжди продовжує працювати. Байти, що не є зображеннями (отримані дані, які не повернули зображення, що декодується), також пропускаються без змін. Ця нормалізація обмежується зображеннями, які міст отримує для власного виклику self-call — вона ніколи не застосовується до сирого корисного навантаження пропуску виклику від викликаючого абонента, що узгоджується з принципом мутацій виключно за згодою (Hard Rule #20).

#### Схема налаштувань + міграція

Нові ключі `modalityBridge*` проходять перевірку Zod у `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, тріо `modalityBridgeCache*`, а також група `modalityBridgeAudio*`, яка використовується Audio Bridge. Міграція `141_modality_bridge_settings.sql` копіює існуючі застарілі значення `visionBridge*` у відповідні нові ключі (ідентемпентно, ніколи не перезаписує встановлене оператором значення `modalityBridge*`); застарілі ключі залишаються прийнятими як резервний варіант читання на один цикл випуску.

#### Заголовок прозорості + статистика

Відповіді, перетворені описом, містять `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` (створений за допомогою `buildModalityBridgeHeader()` у `modalityBridge/bridgeStats.ts`, проставлений за допомогою `withModalityBridgeHeader()` у `src/sse/handlers/chatHelpers.ts`). Перенаправлені запити **не** отримують заголовка — корисне навантаження залишилося недоторканим, а заміна моделі вже видима в полі `model` тіла відповіді.

`GET /api/modality-bridge/stats` (авторизація керування, той самий рівень, що й `GET /api/settings`) повертає лічильники в оперативній пам'яті для кожної модальності `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` для `vision`, `audio` та `video`. `averageLatencyMs` використовує `latencySamples`, а не всі спроби, як свій знаменник; операція без вимірювання часу не створює нульову мілісекундну вибірку. `bridged` залишається сумісним зі старішими версіями псевдонімом для успішних перетворень; невдалі спроби не збільшують його значення. Лічильники скидаються під час перезапуску процесу за задумом (телетеметрія, а не бухоблік).

#### Конфігурація панелі керування

Виділена сторінка панелі керування — `/dashboard/settings/modality-bridge`. Її вкладки `Vision`, `Audio` та `Video`, доступні за URL-адресою, зберігають параметри запиту під час перемикання значення `tab`. Вкладка Vision містить параметри увімкнення, режиму, вибору моделі (включно з автоматичним значенням за замовчуванням), підказок із урахуванням завдань, розширених лімітів часу очікування / зображень / довжини опису / кешу, лічильників часу виконання та захищеного запиту-прикладу. Вкладка Audio також активна: вона містить параметри увімкнення, вибору моделі виключно для STT з опцією Auto, ліміти часу очікування / максимального кліпу, аудіолічильники та тестовий приклад `input_audio`. Вкладка Video є функціональною: вона повідомляє про стан середовища виконання FFmpeg/ffprobe — один із чотирьох явних станів інтерфейсу (`unknown`, поки перевірка виконується або не може завершитися; `restricted` на хості панелі керування, що не є зворотним зв'язком, де перевірка пропущена на клієнтській стороні; `unavailable`, якщо перевірено та підтверджено відсутність; або `available` з версіями FFmpeg/ffprobe) — зберігає ліміти увімкнення / моделі / кадрів / відео / часу очікування, фільтрує вибір моделей до моделей із підтримкою зору та виводить відеолічильники.

Колишня картка Vision Bridge у налаштуваннях штучного інтелекту є посиланням сумісності на нову сторінку; вона більше не містить другу копію форми. Розділ Media Providers також пов'язує робочі процеси «Зображення в текст» (Image-to-Text) та «Мовлення в текст» (Speech-to-Text) із відповідними вкладками Modality Bridge без видалення існуючого майданчика тестування Speech-to-Text.

**Обхід допуску self-loop:** коли виклик опису спрямовується через власний self-loop `/v1` від OmniRoute (нестандартна модель провайдера), підзапит надсилає `x-omniroute-admission-bypass: internal` та автентифікується за допомогою вирішених облікових даних self-loop — локального варти (sentinel) `sk_omniroute` у локальному режимі або налаштованого оператором ключа середовища `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` (#1350), щоб розгортання з `REQUIRE_API_KEY=true` все ще могли виконувати виклик опису. Цей обхід застосовується лише для цих точних облікових даних, тому зовнішні клієнти не можуть використовувати заголовок для пропуску допуску.

Застарілі значення за замовчуванням знаходяться у `src/shared/constants/visionBridgeDefaults.ts`; нові значення за замовчуванням для режиму / task-aware / кешу та розв'язувач налаштувань розташовані у `src/shared/constants/modalityBridgeDefaults.ts`. Захисний механізм надає параметр конструктора `deps`, щоб тести могли впроваджувати фіктивні реалізації `getSettings` та `callVisionModel`.

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

Перехоплює аудіовмісні запити чату до того, як вони досягнуть цілі, яка, як відомо, не приймає аудіовхід. Він ніколи не перенаправляє запит чату: аудіочастини транскрибуються через існуючу багаточастинну кінцеву точку, сумісну з OpenAI, а вибрана модель чату продовжує роботу з текстовими транскриптами.

Потік:

1. Визначте `supportsAudio` через `getResolvedModelCapabilities()`. Метадані явного реєстру провайдерів мають перевагу, потім статичні метадані моделі, потім синхронізовані `modalities_input`. Оголошений список вхідних даних без `audio` стає `false`; відсутність доказів можливостей залишається `null`. Як `false`, так і `null` активують консервативний міст, тоді як `true` обходить його.
2. Визначте налаштування `modalityBridgeAudio*` та витягніть верхньорівневі аудіочастини, які підлягають об'єднанню, з кожного повідомлення за допомогою спільного детекторного методу `detectMediaParts()`. Підтримувані формати зв'язку: `input_audio`, `audio_url` від OpenAI та `source.media_type: "audio/*"`. Вкладене аудіо виявляється для маршрутизації, але не видаляється шляхом об'єднання. Обсяг роботи обмежений за допомогою `modalityBridgeAudioMaxClips`; пізніші частини залишаються без змін.
3. Дотримуйтеся налаштованого `provider/model` або дозвольте `selectAudioBridgeModel()` переглянути `AUDIO_TRANSCRIPTION_PROVIDERS` у стабільному порядку каталогу та вибрати першу модель із доступними активними обліковими даними провайдера.
4. `callAudioTranscription()` перетворює аудіо `base64`/`data-URI` у багаточастинний `file` або завантажує віддалений `audio_url` через вихідний захист лише для загальнодоступних запитів із закріпленням DNS та обмеженням у 25 МБ. Потім він надсилає запит POST з файлом та вибраною моделлю на локальний цикл самозвернення `/v1/audio/transcriptions`, автентифікований за допомогою `resolveSelfLoopBearer()`. Існуючий маршрут транскрипції виконує звичайний пошук облікових даних, обробку обмежень швидкості/охолодження та диспетчеризацію провайдера.
5. Успішні виклики замінюють свої частини на `[Audio N]: <transcript>`. Виклики виконуються за допомогою `Promise.allSettled`: індивідуальна помилка зберігає цю початкову аудіочастину (контракт `#4012`). Якщо кожен виклик завершується помилкою і доведено, що ціль має `supportsAudio === false`, частини перетворюються на `[Audio N]: (unavailable — no STT provider connected)` (контракт `#8430`). Для невідомої цілі (`null`) результат повного збою залишається без змін. Доведена текстовмісна ціль без зручних облікових даних STT отримує таку саму явну заглушку без здійснення мережевого виклику.

Успішні транскрипції використовують загальнопроцесний кеш LRU/TTL для модального мосту (Modality Bridge). Ключ поєднує посилання на аудіо, мітку стабільної операції `audio-transcription` та вибрану модель STT; збої ніколи не кешуються. Спроби аудіо оновлюють спільні лічильники `bridged`, `cacheHits`, `failures` та `lastUsedAt`. Трансформовані відповіді містять заголовок `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; незмінені запити не отримують сегмент моста аудіо.

Налаштування середовища виконання підтримуються базою даних та перевіряються за допомогою Zod:

| Ключ                          | За замовчуванням | Діапазон        |
| ----------------------------- | ---------------- | --------------- |
| `modalityBridgeAudioEnabled`  | `true`           | —               |
| `modalityBridgeAudioModel`    | `""`             | Авто або ID STT |
| `modalityBridgeAudioTimeout`  | `60000`          | 1000–300000     |
| `modalityBridgeAudioMaxClips` | `3`              | 1–10            |

Спільний кеш контролюється параметрами `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`.

### Відеоміст (`videoBridge.ts`, `videoBridgePipeline.ts`)

Перехоплює верхньорівневі відеочастини в `messages` для Chat Completions та `input` для Responses API до того, як буде викликано ціль без відомої нативної підтримки відео. Підтримувані формати: `input_video`, `video_url`, `video_source`, URL-адреси `HTTPS` та дані у форматі `data:video/*;base64,...`. Звичайні назви файлів у тексті не розглядаються як відео.

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) відповідає за обхід запитів, перевірку можливостей/політик, агрегацію для кожного запиту та корисне навантаження відповіді. Робота для кожного відео — отримання, кеш для всього результату, опис послідовності кадрів (який поєднує будь-яку заявлену викликачем аудіотранскрипцію) та метрики/переривання/очищення для кожної спроби — прихована за функцією `processVideoPart` у `videoBridgePipeline.ts`, яка викликається один раз для кожної відеочастини всередині циклу `preCall`. Цей модуль також визначає явні межі портів `VideoMediaBrokerPort` (отримання байтів та вилучення вибіркових кадрів), `VideoAudioTranscriptionPort` (об’єднання заявленої викликачем аудіотранскрипції з вибірковими субтитрами) та `VideoDrilldownPort` (межа персистенції деталізації кадрів; ще не інтегровано в `processVideoPart` — наразі лише окремий маршрут `/api/modality-bridge/video/drilldown` записує записи деталізації).

Загальнодоступний шлях запиту `/v1` ніколи не імпортує та не викликає підпроцес. Віддалені відео завантажуються з обмеженням у 50 МБ; вбудовані відео `base64` мають консервативне декодоване обмеження в 36 МБ на одне відео, щоб модель/повідомлення/конверт форматування залишалися в межах публічного ліміту прийняття JSON-запитів у 50 МБ. Оцінки довжини вбудованого рядка та декодованого розміру перевіряються до виділення пам'яті. Для початкової віддаленої URL-адреси та кожного перенаправлення потрібен протокол `HTTPS` із використанням існуючого вихідного захисту лише для публічних запитів із закріпленням DNS. Потім байти перетинають точну внутрішню межу брокера `POST /api/modality-bridge/video/extract`. Цей маршрут є водночас `LOCAL_ONLY` та `SPAWN_CAPABLE`, приймає лише автентифіковані в межах процесу запити на довірений зворотний зв'язок і ніколи не приймає URL-адресу, шлях до файлової системи, виконуваний файл або список аргументів. Конвеєр розміру тіла API та інкрементальний зчитувач тіла обробника незалежно забезпечують обмеження вхідних даних брокера у 50 МБ. Його обмежена черга виконує одне вилучення за раз, допускає чотири очікувані завдання та обмежує очікувані вхідні дані на рівні 100 МБ.

Усередині брокера `ffprobe` читає приватний локальний файл; фіксований список дозволених форматів виключає формати плейлистів та маніфестів. Для дозволених контейнерів родини MOV зовнішні посилання на дані MOV залишаються вимкненими за замовчуванням, і фіксована команда не вмикає їх. І `ffprobe`, і `ffmpeg` використовують білий список протоколів лише для `file`, один потік, фіксовані масиви аргументів, без оболонки, а виконувані файли визначаються через `PATH`. Потоки обкладинок із вкладеними зображеннями не є придатними для відтворення кандидатами. Усі потоки, придатні для відтворення, мають відповідати обмеженням, причому явний потік за замовчуванням має перевагу перед детермінованим резервним варіантом із найнижчим індексом. Відео обмежені 600 секундами, 8 192 пікселями на вимір та 33 554 432 вихідними пікселями. FFmpeg здійснює вибірку від 1 до 16 серединних кадрів у форматі JPEG, зменшує довгий край щонайбільше до 1 024 пікселів без збільшення менших вхідних даних і ніколи не отримує URL. Вибірка за замовчуванням є `uniform`. Необов'язкова політика `scene_aware` та експериментальна `segment_aware` виконують один додатковий фіксований прохід FFmpeg по вже перевіреному локальному потоку, вибирають обмежені мітки часу сцен `showinfo` та детерміновано повертаються до тих самих рівномірних серединних точок у разі збою детектора, тайм-ауту, неправильно сформованого виводу або порожнього набору кандидатів. Режим з урахуванням сегментів виділяє серединні зразки пропорційно до перевірених інтервалів сцен; докази та поведінка резервного варіанта для режиму з урахуванням сегментів описані нижче. Жорстке обмеження у 16 кадрів застосовується після вибору в кожній політиці. Коли запит із підтримкою сцен має бюджет лише на один кадр, він використовує рівномірну серединну точку активного повного відео або вікна фокусування та повідомляє `policyEffective: uniform`: один вибраний кадр сцени не може зберегти обидва часові кінці. Викликувач може додатково надати скінченне вікно фокусування (секунди `start`/`end`); межі закріплюються тривалістю медіафайлу, зворотно спрямовані або нескінченні вікна відхиляються, а всі політики вибірки виконуються лише всередині нормалізованого інтервалу. Отримане вікно включається до метаданих вибірки та неперевіреного префікса опису, щоб подальші моделі могли відрізнити сфокусований уривок від повної шкали часу.

Семантичне фокусування підписів — це окреме, явне налаштування. Режим аналізу за замовчуванням `full` зберігає наявний промпт кадру і ніколи не пересилає текст запиту до моделі створення підписів. У режимі `focused` міст читає лише останній непорожній `text`/`input_text`, написаний користувачем, із того самого контейнера Chat або Responses, нормалізує його до NFC, згортає керуючі символи й пробіли та обмежує його 500 кодовими точками Unicode. Порожній результат повертається до точного промпту `full`. Придатна для використання підказка серіалізується у форматі JSON у спеціальному блоці untrusted-user-context і може лише розставляти пріоритети для спостережуваних деталей; вона не може скасовувати окреме попередження проти дотримання інструкцій, видимих чи чутних у медіафайлі. Текстовий фокус ніколи не визначає `start`/`end` і не змінює часовий семплер.

#### Структурні докази сегментів FU-07

`segment_aware` використовує один обмежений попередній прохід аналізу по вже перевіреному локальному відеопотоку. Фіксований ланцюжок фільтрів спочатку масштабує зображення до ширини не більше 320 пікселів, виявляє зміни сцен та заморожені інтервали, а потім здійснює вибірку з частотою 1 кадр на секунду для визначення розмиття, середньої яскравості та просторової/часової інформації. Прохід обмежений 600 структурними зразками, одним потоком FFmpeg/фільтра, тими самими списками дозволених протоколів і контейнерів `file`-only, обмеженням виводу процесу в 1 МБ та щонайбільше 30 секундами в межах спільного переривання/дедлайну брокера. Він ніколи не приймає команду, фільтр, шлях чи URL із запиту.

Структурні значення є детермінованими доказами вибірки, а не семантичним розумінням відео. Вони не виводять об'єкти, дії, підписи, мовлення чи наміри користувача. Межі сцен і заморожування утворюють сегменти; покриття заморожування, розмиття, експозиція, просторові деталі та часові зміни впливають лише на те, як розподіляється наявний бюджет у 1–16 кадрів. Повністю заморожений сегмент обмежений одним кадром, тоді як незаморожені сегменти конкурують за решту бюджету. Якщо меж більше, ніж кадрів, зберігається рівномірне покриття шкали часу, щоб швидкі початкові монтажні склейки не могли приховати довгий хвостовий сегмент. Межі сцен у межах роздільної здатності аналізу в 1 секунду від межі заморожування об'єднуються.

Відсутні фільтри, пошкоджені/порожні докази, помилка детектора або тайм-аут обмеженого попереднього аналізу призводять до спрацьовування режиму fail open за точною політикою рівномірних серединних точок. Переривання від викликувача або дедлайн брокера не викликають fail open: вони завершують виконуваний підпроцес, запобігають подальшому вилученню кадрів, а приватне тимчасове дерево видаляється у блоці `finally`.

`scripts/perf/video-bridge-fu07-eval.ts` генерує детерміновані реальні фікстури FFmpeg для економії викликів підписів після дедуплікації, розподілу бюджету інтенсивного руху, доказів розмиття/експозиції/SI-TI, швидких склейок із довгим хвостом та хибнопозитивних результатів поступового згасання. Він записує реальний час попереднього аналізу та, за наявності `/usr/bin/time`, процесорний час дочірнього процесу та пікове значення RSS. Його перевірки якості є лише структурними оракулами. Якість реальної моделі створення підписів залишається на рівні `HOLD`, оскільки цей тестовий каркас не має авторизованої кінцевої точки або замороженого судді. Грошова економія також залишається на рівні `HOLD`, якщо `--caption-cost-per-call-usd` не надає явну позитивну оцінку вартості за один виклик; сценарій ніколи не вигадує жодного з цих результатів.

Кожен кадр обмежений до 4 МіБ, усі необроблені кадри разом — до 23 МіБ, а серіалізована відповідь брокера — до 32 МіБ. Приватна тимчасова директорія видаляється в блоці `finally`. OmniRoute не постачається разом із FFmpeg і не приймає користувацький шлях до виконуваного файлу. Перед створенням підписів міст застосовує консервативний прохід візуальної дедуплікації: кожен JPEG зменшується до буфера відтінків сірого розміром 16×16 і порівнюється лише з останнім збереженим кадром. Для запитаного бюджету підписів, що перевищує один кадр, витяг надає обмежений пул кандидатів розміром до подвійного значення цього бюджету і не більше 16 кадрів. Запитане обмеження застосовується лише після дедуплікації, причому перший та останній вибрані кандидати зберігаються під час остаточного проріджування, якщо бюджет становить принаймні два. Версіонована політика `grayscale-16x16-mean-cells-v2` використовує найбільше значення між середньою дельтою яскравості та співвідношенням клітинок мініатюри, чия нормалізована дельта становить принаймні 0.05. Поріг дублікатів є константою 0.04, обраною заради передбачуваності, а не винесеною як налаштування середовища виконання. Цей вторинний сигнал високої контрастності зберігає невеликий рух та зміни видимого тексту, які порівняння лише за середнім значенням може приховати. Помилки компаратора або декодера спрацьовують за принципом `fail open` і зберігають покриття. Вихідні метадані відокремлюють витягнуті кандидати, успішно використані кадри та відкинуті візуальні дублікати.

Явно позначена частина відео може запитувати контактний лист із мітками часу. Міст створює сітку JPEG щонайбільше на 4 стовпчики та 16 кадрів. Кожна комірка розміром 512 пікселів випалює свою вихідну мітку часу у висококонтрастну нижню смугу, тоді як самі мітки часу залишаються в текстових метаданих для подальшого зіставлення та аудиту. Повний файл JPEG залишається обмеженим 32 МіБ. Якщо `sharp` не може декодувати або сформувати сітку, міст повертається до використання окремих кадрів JPEG; переривання з боку клієнта все одно поширюється на операцію створення листа.

Докази просування навмисно відокремлені від мікробенчмарку синтетичної композиції. `scripts/perf/video-bridge-contact-sheet-eval.ts` визначає версіонований за схемою A/B-тестувальник для реальних візуальних моделей, сумісних з OpenAI. Він вимірює кількість токенів, про яку звітує провайдер, загальну затримку (end-to-end wall latency, включаючи композицію листа), кількість викликів моделі та збереження фактів, визначених маніфестом. Необроблені відповіді моделі не записуються у звіт; зберігаються лише дайджести SHA-256 та знайдені ідентифікатори фактів. Тестувальник не здійснює жодних мережевих чи платних викликів моделей, якщо не передано `--execute-real` і не налаштовано `--model`, `OMNIROUTE_BASE_URL` та `OMNIROUTE_API_KEY`. Без такого ясного реального запуску його машиночитаний вердикт залишається `HOLD`; самі лише вимірювання синтетичного корисного навантаження / кількості викликів не є доказами просування.

Клієнти можуть додати необов'язковий масив `transcript.cues` до підтримуваної частини відео, якщо у них уже є вирівняний текст. Кожна підказка повинна містити `text`, скінченний інтервал `start`/`end` у межах досліджуваної тривалості, а також дозволений `source` (`client`, `embedded` або `audio-bridge`); `confidence` за замовчуванням дорівнює `1` і має залишатися в межах від `0` до `1`. Точні дублікати підказок згортаються. OmniRoute ніколи не починає транскрипцію на основі цих метаданих: перевірені підказки копіюються в описаний результат із джерелом, ступенем впевненості та інтервалом, і відображаються як неперевірені спостереження разом із підписами кадрів. Недійсний текст, текст поза межами діапазону або без зазначеного походження відхиляється, замість того щоб змішуватися з потоком підписів. Обидва канали транскрипції в тілі запиту нормалізують надане походження до `client`, включаючи самостійно зазначені мітки `embedded` або `audio-bridge`. Лише адаптер, що належить серверу, може призначати ці довірені мітки через доступний лише в коді аргумент `trustedSource`; поле JSON запиту не може досягти цього аргументу. Текст транскрипції залишається неперевіреним контентом, отриманим із медіафайлу, незалежно від його походження, і ніколи не повинен визначати авторизацію.

Досвідчений клієнт може надати трек `audioTranscript` для того ж самого відео; він розглядається як наданий клієнтом текст, а не як доказ серверної транскрипції. Механізм об'єднання виконує візуальні та аудіоспостереження під єдиним дедлайном і сигналом переривання, впорядковує їх на загальній часовій шкалі, згортає точні дублікати та повідомляє про частковий результат, якщо успішною є лише одна сторона. Недійсний `audioTranscript` деградує до такого часткового результату — візуальний опис зберігається, а аудіогілка записує очищений код помилки — замість того, щоб спричинити збій усього відео. Доступність за гілками, прапорець часткового результату та очищені коди помилок зберігаються в описаному результаті, в метаданих механізму захисту (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), у метаданих кешу результатів та в лічильниках об'єднання мосту. Стандартний шлях Video Bridge не викликає перетворення мовлення на текст і не завантажує другу копію медіафайлу; без цього ясного треку він залишається лише відеофайлом.

**Збереження транскриптів (#12150 P1).** Це застосовується автоматично щоразу, коли Video Bridge (який сам по собі є опціональним) рендерить репліку транскрипту — окремого прапорця збереження не існує. Коли запит рендерить будь-яку репліку транскрипту (оголошений викликачем `transcript` або зведений `audioTranscript`), система захисту позначає його як `videoBridgeObserved` та створює замасковану тінь опису відео — ідентичний рендерінг, у якому тіло кожної репліки з довільним текстом замінено на `[redacted-video-transcript]`, створений шляхом підстановки поля структурованої репліки до того, як рядок буде зібрано (ніколи шляхом аналізу зплющеного тексту, тому жоден вміст репліки — зловмисний чи звичайний, включно з тілами, що містять `]`, наприклад `[inaudible]`/`[music]` — не може вижити). Збережене тіло запиту журналу викликів замінює кожну отриману з відео текстову частину на цю замасковану тінь, зіставлену за рівністю вмісту; якір `fullText` перечитується з готового корисного навантаження системи захисту перед викликом, тому зіставлення все одно відбувається успішно після пізніших систем захисту ланцюжка (маскувальників PII та облікових даних з пріоритетами 10/95), які перезаписують текст опису на місці, а також після того, як системний підказчик/передача/ін'єкція пам'яті змінюють форму масиву повідомлень. Тіло, що надсилається вгору до моделі, залишається незмінним. Спостережуваний запит також не заповнює стійку Пам'ять (пропускається як вилучення на основі запиту, так і на основі відповіді), тому власна відповідь моделі не може відлунити текст транскрипту в Пам'ять.

**Сирі поля відео (#12430).** Коли міст увімкнено, а нативна підтримка відео невідома або відсутня, визначені поля `transcript`/`audioTranscript` також активують `videoBridgeObserved`, навіть після збою опису або досягнення ліміту `maxVideos`. `null` та порожні рядки враховуються; відсутні поля та невідеометадані — ні. Збережені копії маскують ці поля або пропускають запит, а кеші/Пам'ять обходяться.

На цих резервних шляхах дійсні репліки від викликача стають підтримуваними частинами `text`/`input_text`, а не нестандартними полями провайдера. Обидва надані запитом треки залишаються недовіреними спостереженнями `client` з явним попередженням про те, що відео не було описано, а часові мітки не були перевірені щодо медіа. Існуючі бюджети — загальний у 256 реплік / 64 КіБ та на кожну репліку — застосовуються до обох треків разом; часові мітки повинні відповідати стелі брокера у 600 секунд і будь-якому наданому вікну фокусування. Недійсні треки відкидаються, а не пересилаються як довільний текст; дійсний споріднений трек усе ще може використовуватися, якщо не перевищено їхній сукупний бюджет. `null`/порожні поля не додають тексту. Жодне завантаження медіа чи транскрипція не додаються цим резервним варіантом. Поля розширення транскрипту видаляються з резервного відеоносія та його об'єктів `video_url`/`source`. Білий список протоколу OpenAI залишається суворим; носії відео з невідомою нативною підтримкою залишаються доступними, а відомі цілі лише для тексту зберігають безпечні мітки. Структуровані замасковані тіні захищають доданий текст транскрипту, тоді як початковий запит, що належить викликачу, залишається незмінним. Нативно підтримувані цілі та вимкнені мости зберігають свою існуючу поведінку обходу.

Додаткові збережені копії використовують той самий сигнал спостережуваного запиту. Необроблений знімок клієнтського запиту до системи захисту, запит у пам'яті, що очікує на виконання, та ранній журнал відхилених запитів структурно замінюють поля транскрипту у відеочастинах; рядкові підказки, синтезовані етапами конвеєра та передачею контексту, маскуються у приймачі збереженого тіла запиту. Збережений маркер `video_content_removed` змушує продовження `previous_response_id` завершуватися з помилкою замість реконструкції тексту, який був навмисно відкинутий. Якщо спостережуваний запит втрачає свою почастинну замасковану тінь перед логуванням, або навіть одна з кількох тіней відео не збігається після пізніших мутацій запиту, тіло збереженого запиту повністю опускається замість збереження частково замаскованого транскрипту.

Для спостережуваного запиту відповідь моделі може цитувати будь-яку частину транскрипту без межі структурованої репліки. Тому його збережений `responseBody` у журналі викликів замінюється маркером пропуску; детальний артефакт конвеєра (який може включати тіла провайдера/клієнта та фрагменти потоку) не зберігається. Семантичні кеші, кеші ідемпотентності та повтору міркувань обходять операції читання та запису для цього запиту. Запит провайдера та видима клієнту відповідь залишаються незмінними. Ранні байти keepalive зливаються з тимчасового буфера, коли детальний артефакт опускається. Попередження Kiro про пошкоджений EventStream повідомляє лише кількість байтів корисного навантаження, але ніколи його вміст чи необроблену помилку парсера JSON. Це не стверджує, що кожна незв'язана діагностика провайдера/плагіна була перевірена; ширша перевірка збережених приймачів відстежується в #11658.

Внутрішній життєвий цикл `/api/modality-bridge/video/drilldown` є окремим кеш-субстратом з аутентифікацією через loopback/токен. Кожна операція також вимагає канонічного непрозорого ідентифікатора принципала. Перед тим як викликач у продакшні буде ввімкнено, він повинен отримати цей ідентифікатор з аутентифікованого тенанта і ніколи не повинен пересилати значення, вибране клієнтом. Ключі кешу прив'язують цього принципала до канонічних ідентифікаторів сеансу та посилання на відео, зберігають лише їхні ключі, отримані за допомогою SHA-256, і обмежують як читання, так і видалення тим самим принципалом. Кеш зберігає щонайбільше 16 похідних кадрів JPEG на запис, термін їх дії закінчується через десять хвилин, а також підтримує обмежене читання `start`/`end` або явне видалення сеансу.

Кожен принципал обмежений 16 записами та 64 МіБ канонічних даних JPEG. Ці ліміти не залежать від глобальної межі у 64 записи / 256 МіБ: тиск квоти принципала витісняє лише найменш нещодавно використовувані записи цього принципала, перш ніж розглядається глобальне витіснення LRU. Прострочені записи видаляються як з обліку принципала, так і з глобального обліку під час активності кешу, тоді як скасування та помилка валідації не фіксують часткову заміну.

Кеш відхиляє неканонічний Base64, надлишкове доповнення, медіафайли не у форматі JPEG, пошкоджені або обрізані JPEG, а також JPEG, які викликають попередження під час обмеженого декодування всього зображення за допомогою `sharp`. Він перекодовує кожне прийняте зображення у канонічний JPEG, визначає ширину та висоту з декодованих байтів замість довіри до полів виклику, а також відкидає будь-які хвостові поліглотні байти замість їх збереження. Тільки обмежений канонічний стиснений буфер враховується в обох квотах. Ліміт передачі JSON включає накладні витрати Base64 для стелі декодованого входу у 32 МіБ. Кожна збережена деривація записує свій перевірений формат/роздільну здатність JPEG, політику дискретизації, версію деривації, час створення, обчислений сервером геш вмісту та гешоване посилання на батьківський елемент разом із гешем батьківського вмісту довіреного ініціатора. Перевірка скасування виконується між асинхронними фазами декодування/гешування перед атомарним фіксуванням у кеші.

Цей транш ще не підключає виробника для продакшну до маршруту та не надає вибір багатороздільних варіантів. Тому прозорий шлях запитів Video Bridge не призводить до додаткової роботи, тоді як похідна принципала, прив'язана до тенанта, та повний життєвий цикл багатороздільності FU-08 залишаються явною подальшою роботою, а не документуються як завершена поведінка.

Кадри підписуються послідовно за допомогою налаштованої моделі Video. Порожнє перевизначення Video успадковує налаштування Vision; якщо обидва порожні, автомаршрутизатор Vision вибирає ефективну модель із підтримкою зору. Успішні підписи замінюють оригінальну частину стабільним префіксом `[Video description:`, який також позначає текст як ненадійне спостереження, отримане з медіафайлів, і вказує подальшим моделям не виконувати інструкції, знайдені в медіа. Ключі кешу підписів кадрів включають байти JPEG, промпт, мітку часу та ефективну модель; кешуються лише успішні підписи. Записи кешу зберігають фактичну успішну модель-виробника, включаючи резервну модель; міст повідомляє про `mixed`, коли різні кадри були створені різними моделями. Потрапляння в кеш повторно використовує цю ідентичність виробника, а не перейменовує її на запропонований план маршрутизації. Кеш результатів для всього відео ключується за кожним вхідним даним, що змінює вихідні дані — промпт, ефективна модель, політика дискретизації, кількість кадрів, режим семантичного аналізу, відбиток SHA-256 нормалізованої підказки фокусування, вікно фокусування, `transcript`, `audioTranscript` та прапорець контакт-листа — тому зміна будь-якого з цих вимірів призводить до промаху кешу, а не до повторного використання застарілих даних. Версія політики візуального дедупу, поріг та обмежена кількість кадрів-кандидатів також явно вказані в ключі кешу результатів та метаданих; тому зміна політики не може повторно використовувати застарілий опис всього відео. Метадані кешу результатів v4 зберігають режим і відбиток, але ніколи не зберігають вихідне завдання користувача. Метадані захисного екрана повідомляють як про запропонований, так і про ефективний режими аналізу; запитаний режим `focused` без корисного користувацького тексту звітується як ефективно `full`.

Захисний екран витягує кожну підтримувану частину відео, але описує не більше ніж `modalityBridgeVideoMaxVideos`. Для цілі, для якої доведено значення `supportsVideo === false`, невдалі відео та відео, що перевищують ліміт, перетворюються на явні безпечні текстові маркери, тож жодне вихідне відео не зберігається. Якщо можливості невідомі, ці частини зберігають свій відеоносій; будь-який резервний стенограм відповідає обмеженому перетворенню тексту, описаному вище. Цілі з `supportsVideo === true` обходять міст. Сигнал переривання запиту клієнта поширюється через завантаження, чергу брокера, підпроцеси та виклики підписів; переривання зупиняються між відео та ніколи не відкривають доступ до необробленого медіа у разі збою.

Налаштування часу виконання підтримуються базою даних та перевіряються за допомогою Zod:

| Ключ                                | За замовчуванням | Діапазон / поведінка                                                                                                  |
| ----------------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`          | Додатковий час виконання, за згодою (opt-in)                                                                          |
| `modalityBridgeVideoAnalysisMode`   | `"full"`         | `full` зберігає загальні підписи; `focused` використовує обмежений, ненадійний найсвіжіший контекст користувача       |
| `modalityBridgeVideoModel`          | `""`             | Успадкувати модель Vision Bridge                                                                                      |
| `modalityBridgeVideoFrameCount`     | `8`              | 1–16                                                                                                                  |
| `modalityBridgeVideoSamplingPolicy` | `"uniform"`      | `uniform`, `scene_aware` або пропорційний `segment_aware`; у разі збою детектора відбувається повернення до `uniform` |
| `modalityBridgeVideoMaxVideos`      | `1`              | 1–4                                                                                                                   |
| `modalityBridgeVideoTimeout`        | `120000`         | 1000–120000 мс                                                                                                        |

Застарілі збережені значення таймауту відео, що перевищують 120 секунд, обмежуються дедлайном брокера; нові записи налаштувань, що перевищують цей ліміт, відхиляються.
Запит `GET /api/modality-bridge/video/runtime` вимагає довіреної локальності loopback з міткою перед автентикацією або зондуванням часу виконання, а потім вимагає автентикації керування. Він повертає лише `available`, очищені версії FFmpeg/ffprobe та фіксовану причину, коли час виконання недоступний. Внутрішня кінцева точка вилучення не є загальнодоступним API завантаження: пересичення черги повертає `503` плюс `Retry-After`, відключення клієнта повертає `499`, а фіксований дедлайн брокера повертає `504`. Перетворені відповіді додають `video->text;model=<visionModel>;parts=<videos>` до центрального заголовка `x-omniroute-modality-bridge` без видалення сегментів Vision або Audio.

### PII Masker (`piiMasker.ts`)

Працює на **обох** етапах.

- **`preCall`** клонує корисне навантаження, обходить `system`, `messages`, `input` та
  `prompt` (включаючи елементи у вигляді звичайних рядків) і застосовує `processPII()` (з
  `@/shared/utils/inputSanitizer`) до рядкових полів `content`/`text`. Коли
  `PII_REDACTION_ENABLED=true`, виявлені PII редагуються у вихідному
  корисному навантаженні. Це не залежить від `INPUT_SANITIZER_MODE` (який керує лише
  політикою prompt-injection). Коли редагування вимкнено, виклик записує лічильники виявлень
  без перезаписування вмісту.
- **`postCall`** робить глибоке клонування відповіді, запускає `sanitizePIIResponse()` плюс
  маскерувальник формату Responses API (`maskResponsesOutput` — охоплює
  `output_text` і `output[].content[].text`). Якщо відбувається будь-яке редагування,
  змінена відповідь замінює оригінальну.

Захисний механізм ніколи не блокує; він лише додає анотації (`meta.detections`,
`meta.redacted`) або перезаписує вміст.

#### Вибір за типами, власні шаблони та лічильники виявлень

**Dashboard → Settings → Security → PII masking** визначає, _що_ саме маскується. Це
не вмикає маскування: за це все ще відповідають `PII_REDACTION_ENABLED` (запит) та
`PII_RESPONSE_SANITIZATION` (відповідь + SSE), які за замовчуванням вимкнені для обох.

- **Вибір за типами** — вбудовані ідентифікатори перелічено в
  `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`). Якщо нічого не вибрано, це означає кожен
  тип (поведінка до появи цього налаштування). Шаблон `ssn_us`
  механізму запитів зіставляється з `ssn`. Шаблони (Minimal, Standard, Financial,
  Brazilian, USA, Full) лише заповнюють прапорці в інтерфейсі.
- **Власні шаблони** — до 20 регулярних виразів або шаблонів із підстановочними знаками (`*` = до 64
  символів, що не є пробілами, `?` = один). Збіги стають `[CUSTOM_REDACTED]`.
  Кожен шаблон проходить через `compilePiiCustomPattern()`
  (`src/shared/utils/piiCustomPatterns.ts`): не більше 500 символів, прапорці обмежені
  `g i m s u`, повинен компілюватися, проходити перевірку `safe-regex` (на катастрофічний
  бектрекінг) і не збігатися з порожнім рядком або заповнювачем редагування.
  Шаблон, який не проходить перевірку, відхиляється під час збереження та тестування, а збережений рядок,
  який дає збій, пропускається під час виконання замість компіляції. Власні шаблони
  працюють лише тоді, коли маскування увімкнено.
- **Лічильники виявлень** — кількість для кожного типу (значення, що збіглися, ніколи не зберігаються), що утримуються в
  пам'яті та скидаються при перезапуску (`src/lib/pii/piiDetectionStats.ts`). Вони лише
  збільшуються, поки маскування увімкнено.

Налаштування зберігаються в таблиці `key_value` (простір імен `pii_settings`,
`src/lib/db/piiSettings.ts`) і зчитуються через кеш тривалістю 1 с. API:

| Метод  | Шлях                     | Призначення                                                                              |
| ------ | ------------------------ | ---------------------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | Стан прапорців, `enabledTypes`, `customPatterns`, лічильники виявлень                    |
| `PUT`  | `/api/settings/pii`      | Замінити `enabledTypes` (`null` = усі) та/або `customPatterns`                           |
| `POST` | `/api/settings/pii/test` | Тестовий запуск одного шаблону на зразку розміром не більше 8 КБ; нічого не зберігається |

Усі три вимагають автентифікації керування та перевіряють тіло за допомогою Zod
(`src/shared/validation/schemas/piiSettings.ts`).

### Ін'єкції у підказки (`promptInjection.ts`)

Виявляє зловмисні структури у вмісті, наданому користувачем, і застосовує
налаштовану політику. Поведінка визначається змінними середовища та параметрами конструктора:

| Налаштування    | Змінна середовища                                                                                         | За замовчуванням | Ефект                                                                                                                                                                                     |
| --------------- | --------------------------------------------------------------------------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Enabled         | `INPUT_SANITIZER_ENABLED`                                                                                 | `true`           | Коли `false`, захисний механізм перериває виконання (short-circuits).                                                                                                                     |
| Mode            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                           | `warn`           | Політика ін'єкцій: `block`, `warn` або `log`. (`redact` приймається для зворотної сумісності, але **не** видаляє текст ін'єкції; перезаписом PII у запиті керує `PII_REDACTION_ENABLED`.) |
| Block threshold | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (псевдонім `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`           | Мінімальний рівень серйозності, необхідний для блокування. Середній рівень за замовчуванням працює лише в режимі спостереження.                                                           |

**Пріоритет режимів** (`getMode`): `options.mode` від викликаючого →
**перевизначення файр-флагів БД** для `INJECTION_GUARD_MODE` (Dashboard → Settings →
Feature Flags) → змінна середовища `INJECTION_GUARD_MODE` → змінна середовища `INPUT_SANITIZER_MODE` →
`warn`. Таким чином, перевизначення через панель керування має пріоритет над змінними середовища, тому інтерфейс
Feature Flags керує працюючим захистом у реальному часі (без перезапуску). Читання з БД є відмовостійким:
якщо воно викликає помилку, захисний механізм повертається до поведінки на основі змінних середовища, а коли жодного перевизначення
не встановлено, поведінка ідентична вирішенню лише на основі змінних середовища.

Джерела виявлення:

1. `sanitizeRequest()` з `@/shared/utils/inputSanitizer` (спільний набір детекторів,
   що використовується в інших місцях конвеєра).
2. Вбудовані `DEFAULT_GUARD_PATTERNS` (наразі `system_override_inline` та
   `markdown_system_block`, обидва мають рівень серйозності `high`).
3. Необов'язкові `customPatterns`, що передаються через параметри конструктора (рядки, регулярні вирази
   або записи `{ name, pattern, severity }`).

Коли `mode === "block"` **та** принаймні одна детекція досягає порогового значення серйозності, `preCall` повертає `{ block: true, message: "Request rejected: suspicious content detected" }`. У режимах `warn`/`log` захисний механізм виконує логування, але дозволяє виклик. Спільна допоміжна функція `evaluatePromptInjection()` також експортується для викликальників, яким потрібно оцінювати промпти без проходження через реєстр.

**Межа сканування (v3.8.20):** детектор перевіряє лише **перші 16 КБ** об'єднаного тексту промпту — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 байти) у файлі `src/shared/utils/inputSanitizer.ts`. Як `detectInjection()`, так і `evaluatePromptInjection()` виконують `slice(0, MAX_INJECTION_SCAN_BYTES)` перед запуском циклу шаблонів. Директиви ін'єкцій розташовуються ближче до початку вхідних даних, тому це обмежує використання CPU/GC для регулярних виразів на корисних навантаженнях розміром у сотні кілобайт без послаблення детекції (див. #3932, #4041).

### Маскер облікових даних (`credentialMasker.ts`)

Виконується на **обох** етапах, останнім у стандартному ланцюжку (пріоритет `95`). Маскує загальновідомі шаблони API-ключів / секретних токенів у вихідному корисному навантаженні (вміст повідомлення, аргументи викликів інструментів, результати інструментів) **а також** у відповіді провайдера, тож облікові дані, вставлені в промпт (або відлунені назад у результаті інструмента), не витікають до висхідного провайдера або назад клієнту.

- **Лише за вибором (opt-in)**, за такою ж угодою, що й маскування PII (поряд із суворим правилом №20): вимкнено, якщо не встановлено `settings.credentialRedactionEnabled === true` **або** `CREDENTIAL_REDACTION_ENABLED=true`. Коли він вимкнений, захисний механізм є операцією-заглушкою (no-op) — він ніколи не блокує і ніколи не перезаписує.
- Функція `redactCredentials()` обходить усе дерево корисного навантаження / відповіді (`walkValue()`, захищено від забруднення прототипу, безпечно щодо циклів за допомогою `WeakSet`) і замінює збіги на заповнювач `[REDACTED:<type>]`, клонуючи лише ті гілки, які фактично змінилися.
- `CREDENTIAL_PATTERNS` охоплює ключі провайдерів LLM (OpenAI, OpenAI-proj, Anthropic, Google, Hugging Face, Replicate), токени VCS/SaaS (GitHub, Slack, Linear, Notion, npm, Postman, Discord), платіжні ключі (Stripe, Square), хмарні ключі (AWS access key, Twilio, SendGrid, Mailgun), приватні ключі / JWT, рядки підключення з обліковими даними (`mongodb://user:pass@...` тощо), а також загальний шаблон значень заголовків `Authorization`/`x-api-key`/`api-key`/`apikey`. Ключі у вигляді заголовків (`authorization`, `x-api-key`, `api-key`, `apikey`) маскуються структурно (лише значення, префікс схеми на зразок `Bearer `/`Basic ` зберігається), а не за допомогою загального текстового регулярного виразу.
- Захисний механізм ніколи не блокує; він лише перезаписує (`modifiedPayload` / `modifiedResponse`) та додає анотації (`meta.credentialsRedacted`, `meta.count`).

Захист від регресій: `tests/unit/credential-masker-guardrail.test.ts`.

## Базовий контракт (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true перериває ланцюжок
  message?: string; // показується при блокуванні
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // повертається preCall для перезапису запиту
  modifiedResponse?: TValue; // повертається postCall для перезапису відповіді
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

Гардрейл сигналізує «відсутність змін», повертаючи `void`, `{}` або
`{ block: false }`. Повернення `modifiedPayload`/`modifiedResponse` замінює
значення, що проходить через ланцюжок для наступних гардрейлів.
`signal?: AbortSignal` передає життєвий цикл ініціатора в гардрейли. Скасування запиту є навмисним виключенням fail-open: медіаморти припиняють роботу та очищення, не відновлюючи вихідні медіа для цілі, яка, як відомо, їх не підтримує.

## Реєстр (`registry.ts`)

Синглтон `guardrailRegistry` надає такі можливості:

- `register(guardrail)` — додає (або замінює за нормалізованим ім'ям) гардрейл і
  сортує повторно за зростанням `priority`.
- `clear()` / `list()` — адміністративні допоміжні функції.
- `runPreCallHooks(payload, context)` — перебирає активні гардрейли,
  пропускає `payload` через `modifiedPayload` і зупиняється на першому `block: true`.
- `runPostCallHooks(response, context)` — такий самий потік з боку відповіді.
- `resetGuardrailsForTests({ registerDefaults })` — очищає стан і за необхідності
  повторно реєструє значення за замовчуванням для ізоляції чистих тестів.

Обидва виконавці повертають `{ blocked, payload|response, results, guardrail?, message? }`
де `results` — це масив записів `GuardrailExecutionResult`, які містять
поля `blocked`, `skipped`, `modified`, `error` та `meta` для кожного гардрейла,
що корисно для трасування.

### Вимкнення гардрейлів для кожного запиту

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` агрегує
дедуплікований список імен гардрейлів, які слід пропустити для поточного
запиту. Існує п'ять каналів, які читаються в цьому порядку та об'єднуються в один список
(перше входження виграє під час дедуплікації):

1. `apiKeyInfo.disabledGuardrails`
2. Поле `disabledGuardrails` у тілі запиту (верхнього рівня)
3. Поле `metadata.disabledGuardrails` у тілі запиту (лише коли `metadata` є об'єктом)
4. Заголовок `x-omniroute-disabled-guardrails`
5. Застарілий заголовок `x-disabled-guardrails`

Усі п'ять каналів об'єднуються, включаючи два заголовки: надсилання як
`x-omniroute-disabled-guardrails`, так і `x-disabled-guardrails` пропускає об'єднання
їхніх списків, а порожній сучасний заголовок більше не приховує застарілий
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), виправлено в
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805)).

Значення можуть бути масивами рядків або рядком, розділеним комами; імена обрізаються
та нормалізуються до нижнього регістру у форматі kebab-case (`pii_masker` → `pii-masker`),
а порожні записи відкидаються. Результат передається через `context.disabledGuardrails`
до реєстру, який пропускає відповідні гардрейли (`skipped: true` у `results`).

Список вимкнення впливає лише на **реєстр**. Режим `block` для захисту від впровадження промптів (prompt-injection) є
обов'язковою межею: проміжне ПЗ захисту від впровадження
(`src/middleware/promptInjectionGuard.ts`) викликає `evaluatePromptInjection()`
без будь-якого списку вимкнення, контрольованого викликувачем (мертвий
виклик `resolveDisabledGuardrails({ body })`, який воно раніше робило, було видалено в
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), тому запит,
який вимикає `prompt-injection`, все одно відхиляється в режимі `block`. Це зроблено
навмисно. Канали вимкнення контролюються викликувачем (тіло запиту,
метадані, заголовки), і викликувач не повинен мати можливості вимкнути елемент керування
безпекою, встановлений оператором
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Об'єднання заголовків
з [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)
змінює лише те, які гардрейли реєстру пропускаються; воно не дозволяє клієнту
обійти проміжне ПЗ. Обов'язкові політики гардрейлів для кожного ключа та кожної групи
відстежуються у v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
Див. [Coverage and limits](#coverage-and-limits).

## Порядок виконання

Для кожного запиту, що проходить через `src/sse/handlers/chat.ts` та
`open-sse/handlers/chatCore.ts` (маршрути сімейства чату, перелічені в розділі
[Покриття та обмеження](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` формує список пропуску на основі ключа API, тіла запиту
   та заголовків.
2. `guardrailRegistry.runPreCallHooks(body, ctx)` запускає захисні бар'єри (guardrails) у порядку зростання пріоритету:
   - Вимкнені захисні бар'єри реєструються як `skipped`.
   - Функція `preCall` кожного захисного бар'єра може перезаписати корисне навантаження за допомогою `modifiedPayload`.
   - Перший `block: true` перериває ланцюжок, і обробник повертає відповідь про відхилення захисним бар'єром.
3. (Потенційно перезаписане) корисне навантаження надходить до комбінованої маршрутизації та диспетчеризації висхідного потоку.
4. **Лише для нестрічкових запитів:** після формування відповіді
   `guardrailRegistry.runPostCallHooks(...)` запускає той самий ланцюжок для відповіді. Значення `block: true` тут відкидає відповідь висхідного потоку і повертає HTTP 400. Стрічкові відповіді повністю пропускають цей крок.

Захисні бар'єри, що викидають помилки, реєструються з `error: <message>` та записуються в логи за допомогою `logger.warn`, але ланцюжок продовжує роботу — це працює за принципом fail-open за проєктним рішенням.

Реєстр захисних бар'єрів інтегровано лише в конвеєр чату. Ці обмеження
зафіксовані в `tests/unit/guardrail-pipeline-wiring-characterization.test.ts` та
`tests/unit/guardrail-pipeline-characterization.test.ts`; оновлюйте ці тести свідомо, коли поведінка змінюється.

### Де виконуються хуки

| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Також тестовий ендпоінт панелі керування `/api/guardrails/test`. Блокування перед викликом повертає HTTP 400. |
| `runPostCallHooks`                  | Лише для **нестрічкових** відповідей чату (`open-sse/handlers/chatCore/nonStreamingResponse.ts`). Це не захисний бар'єр, тому канали вимкнення на нього не впливають.                                                                                                                                                                                                                           |

Тільки ін'єкції промптів.                                                                                                                                                                                                                                                                  |

### Що не покривається

- **Маршрути медіа, ембеддингів та даних** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) ніколи не потрапляють до реєстру. Маскування PII, маскування облікових даних або міст модальностей там не виконуються. Їхня єдина перевірка — це застаріле проміжне ПЗ захисту від ін'єкцій.
- **Стрічкові відповіді** не отримують захисних бар'єрів після виклику: немає ані `pii-masker`, ані `credential-masker` після виклику, а також немає блокування після виклику. Застосовується лише потокове перетворення PII (коли ввімкнено `PII_RESPONSE_SANITIZATION`). Облікові дані, повернуті у стрічковій відповіді, не маскуються.
- **Канали вимкнення проти проміжного ПЗ (за проєктним рішенням):** проміжне ПЗ оцінює ін'єкції промптів за допомогою власного виклику `evaluatePromptInjection()`, без передачі будь-яких списків вимкнення, контрольованих викликом. Режим `block` є обов'язковою межею, яку вимкнення, контрольовані викликом, не можуть обійти, зокрема на маршрутах сімейства чату ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). Вимкнення `prompt-injection` пропускає лише захисний бар'єр реєстру.

### Що бачить відповідь до етапу після виклику

На нестрічковому шляху порядок такий: вилучення пам'яті → виконання вбудованих інструментів → захисні бар'єри після виклику → вихід із блокування після виклику → збереження в семантичному кеші.

- **Вилучення пам'яті** та **виконання інструментів** бачать відповідь до того, як захисні бар'єри post-call
  зможуть її переписати або заблокувати. Починаючи з
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401), вилучення пам'яті
  пропускає вилучений текст через `sanitizePII`, коли
  `PII_RESPONSE_SANITIZATION` увімкнено (як для потокового, так і для непотокового режиму), але
  відповідь, яку захисні бар'єри post-call згодом блокують, все одно передається в пам'ять та
  інструменти.
- **Семантичний кеш** зберігає відповідь після post-call, тому він зберігає
  переписану відповідь, а заблокована відповідь ніколи не кешується. Записи в кеші
  індексуються за ключем API.

## Конфігурація

Змінні середовища, які зчитуються вбудованими захисними бар'єрами:

| Змінна                                | Використовується          | Ефект                                                                                                                 |
| ------------------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | Встановіть `false`, щоб повністю вимкнути виявлення.                                                                  |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | Політика ін'єкцій: `warn`, `block` або `log`. Застаріле значення `redact` не перезаписує текст ін'єкції.              |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | Режим для захисту від ін'єкцій; також функціональний прапорець БД, який **перевизначає** змінні середовища (БД > ЗС). |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | Мінімальний рівень серйозності, який відхиляє `MODE=block`: `high` (за замовчуванням), `medium` або `low`.            |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | Застарілий псевдонім для `INPUT_SANITIZER_BLOCK_THRESHOLD`.                                                           |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | Коли встановлено `true`, дані PII запиту редагуються (незалежно від режиму ін'єкцій).                                 |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (downstream) | Керує поведінкою маскувальника на стороні відповіді.                                                                  |

Захисні бар'єри Modality Bridge зчитують конфігурацію часу виконання зі сховища налаштувань на базі БД (`getSettings()`), а не зі змінних середовища. Основними ключами для зору (Vision) є `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` та `modalityBridgeCacheMaxEntries`. Застарілі ключі `visionBridge*` приймаються лише як документований одноцикловий резервний варіант читання; записи з панелі керування використовують основні ключі. Значення за замовчуванням та резервний резолвер знаходяться в `src/shared/constants/modalityBridgeDefaults.ts`, а застарілі константи збережено в `src/shared/constants/visionBridgeDefaults.ts`.

Для аудіо використовуються `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`, `modalityBridgeAudioTimeout` та `modalityBridgeAudioMaxClips`, а також спільні налаштування `modalityBridgeCache*`. Аудіо не має резервного варіанту для застарілих ключів, оскільки ці ключі були введені разом зі схемою Modality Bridge.

Для відео використовуються `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`, `modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` та `modalityBridgeVideoTimeout`, а також спільні налаштування `modalityBridgeCache*`. Воно вимкнено за замовчуванням, оскільки FFmpeg/ffprobe є необов'язковими операційними залежностями, а створення підписів до кадрів додає затримки та витрат на моделі.

## Користувацькі guardrails

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

Кроки:

1. Створіть `src/lib/guardrails/myGuardrail.ts`, що розширює `BaseGuardrail`.
2. Реалізуйте `preCall` та/або `postCall`.
3. Або зареєструйте під час імпорту (додайте через `registerDefaultGuardrails`), або
   викликайте `guardrailRegistry.register(...)` під час виконання — реєстр замінює
   будь-який попередній guardrail із таким самим нормалізованим ім'ям.
4. Додайте тести в `tests/unit/` (існуючі приклади:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`).

## Тестування

Використовуйте `resetGuardrailsForTests()` між тестами, щоб починати з відомого стану.
Передайте `{ registerDefaults: false }`, щоб почати з порожнього реєстру та
зареєструвати лише ті guardrails, що тестуються. Vision Bridge приймає впровадження
залежностей (`deps.getSettings`, `deps.callVisionModel`); Audio Bridge надає
еквівалентні точки розширення для налаштувань, можливостей, вибору моделі STT, перевірки
облікових даних та транскрипції. Таким чином, тести можуть перевіряти обидва потоки без
доступу до бази даних чи мережі.

## Покриття маршрутів захисту від ін'єкцій та red-team (Фаза 8 · Блок D)

Захист від ін'єкцій (`createInjectionGuard` / `withInjectionGuard`) охоплює всі маршрути,
що приймають запити користувача. Він враховує `INJECTION_GUARD_MODE` (за замовчуванням `warn` = лише логування;
`block` = повертає HTTP 400 `SECURITY_001`).

| Тип                | Маршрути                                                                                                                                             | Режим за замовчуванням |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| Текстові (існуючі) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn                   |
| Генеративні        | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn                   |
| Дані               | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn                   |

Витяг тексту (`extractMessageContents`) охоплює `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**Red-team (нічні збірки, `nightly-llm-security.yml`):** promptfoo перевіряє, що кожен маршрут блокує
корпус OWASP-LLM у режимі `INJECTION_GUARD_MODE=block`; garak запускає зондування (пропускається за відсутності секрету).
`moderations` включено для узгодженості. Режим блокування є обов'язковим кордоном: `evaluatePromptInjection()`
ігнорує список вимкнення для конкретного запиту, який передає проміжне програмне забезпечення, тому `disabledGuardrails` does
**не** звільняє маршрут від цього захисту ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

Нічний робочий процес (`.github/workflows/nightly-llm-security.yml`, cron + ручний
запуск) має два завдання:

- **`promptfoo-guard` (блокуюче)** — запускає `promptfoo eval -c promptfooconfig.yaml`
  з `INJECTION_GUARD_MODE=block`. Кожен атакувальний випадок (наприклад, "ignore all
  previous instructions…", джейлбрейки в стилі DAN) перевіряє, чи містить відповідь
  `error.code === "SECURITY_001"`, тобто що захист дійсно відхилив запит.
- **`garak` (дорадче)** — запускає garak зі скануванням `--probes promptinject,dan,leakreplay`
  проти локального екземпляра OmniRoute (`http://localhost:20128/v1`). Захищено секретом
  провайдера (`PROMPTFOO_PROVIDER_KEY`); коректно пропускається та має суфікс
  `|| true`, тому формує звіт без падіння CI.

Покриття допоміжної функції захисту (`createInjectionGuard` / `withInjectionGuard`)
охоплює кожен маршрут `/v1`, що приймає промпти; текст промпту витягується з
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` за допомогою
`extractMessageContents()` у `src/shared/utils/inputSanitizer.ts`.
