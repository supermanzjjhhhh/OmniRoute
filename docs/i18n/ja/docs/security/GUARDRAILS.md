ガードレールは、OmniRoute と上流プロバイダーの境界で、
安全対策、ポリシーの適用、コンテンツ変換を実施します。各ガードレールは、
リクエストペイロード（`preCall`）と上流レスポンス（`postCall`）を検査でき、
必要に応じて拒否、変換、注釈の付加を行えます。

このシステムは**フェイルオープン**です。ガードレールの実行中に例外がスローされた場合、
レジストリはエラーを記録し、リクエストを失敗させるのではなく、
次のガードレールに進みます。ブロックは明示的な判断（`block: true`）によってのみ行われ、偶発的には発生しません。
唯一の例外は、中止されたリクエストです。呼び出し元の `signal` が中止されている場合、
例外をスローしたガードレールはスキップされず、フックの実行が拒否されます。

フックは、すべてのルートやすべてのレスポンスで実行される**わけではありません**。
ガードレールをセキュリティ制御として利用する前に、
[適用範囲と制限](#coverage-and-limits)をお読みください。

## 組み込みガードレール

レジストリはインポート時に、6 つのガードレールを優先度順に自動読み込みします
（`registry.ts` → `registerDefaultGuardrails()` を参照）。

| 優先度 | 名前                | ステージ       | ファイル              |
| ------ | ------------------- | -------------- | --------------------- |
| `5`    | `vision-bridge`     | `preCall`      | `visionBridge.ts`     |
| `6`    | `audio-bridge`      | `preCall`      | `audioBridge.ts`      |
| `7`    | `video-bridge`      | `preCall`      | `videoBridge.ts`      |
| `10`   | `pii-masker`        | `pre` + `post` | `piiMasker.ts`        |
| `20`   | `prompt-injection`  | `preCall`      | `promptInjection.ts`  |
| `95`   | `credential-masker` | `pre` + `post` | `credentialMasker.ts` |

優先度の数値が小さいものほど**先に**実行されます。

### Vision Bridge（`visionBridge.ts`）— モダリティブリッジ PR-1

GLM 5.3 のベースモデルと `glm-5.3-{low,high,max}` には、レジストリ／仕様メタデータとして
`supportsVision:false` が明示されています。GLM 5.3 Flash の各バリアントは、
引き続きネイティブの画像認識モデルです。Claude Code の `/v1/messages` ルートは、
Claude 形式から OpenAI 形式への変換**より前に**、共有の `handleChat` pre-call ガードレールチェーンに入ります。
ネストされた `Read` ツール結果の画像は、その変換によって OpenAI の `image_url` コンテンツに引き上げられる前に、
説明文への変換などの処理を行う必要があります（#17069）。

**画像認識非対応モデル**宛ての画像付きリクエストを捕捉し、
リクエスト全体を画像認識対応モデルに再ルーティングするか、上流への呼び出し前に、
画像部分を、設定可能な画像認識モデルが生成したテキストの説明に置き換えます。
これにより、テキスト専用プロバイダーでもマルチモーダルのペイロードを透過的に処理できます。

処理フロー:

1. 対象モデルがすでに画像認識に対応している場合はスキップします（ただし、
   強制ブリッジリスト `isVisionBridgeForcedModel` に含まれている場合を除きます）。
2. `extractImageParts(messages)`
   （`visionBridgeHelpers.ts`）で画像部分を抽出します。この関数は、
   `open-sse/utils/mediaParts.ts` にある**統合メディア検出器** `detectMediaParts()` に処理を委譲します。
   これは、コンボ互換性フィルターと共有される唯一の信頼できる情報源です。
   抽出対象は、`replaceImageParts` が元の位置に差し戻せる形式に限定されます
   （抽出↔置換の契約）。対象は、OpenAI の `image_url`、Anthropic の base64
   `source.type:"base64"`、Anthropic の URL `source.type:"url"`、および Responses
   API の `input_image` です。Claude Code の
   `tool_result.content` や Responses のツール出力内にネストされた該当画像も抽出され、
   元のパスで置換されます。画像の存在を示すだけの形式はコンボフィルターの処理対象であり、
   抽出されません。
   画像が見つからない場合はスキップします。
3. `resolveVisionBridgeRuntimeSettings()`
   （`src/shared/constants/modalityBridgeDefaults.ts`）で実行時設定を解決します。新しい `modalityBridge*`
   設定キーが優先され、従来の `visionBridge*` キーは**1 サイクル限りの
   フォールバック**（ロールバック期間）として維持されます。ブリッジが無効な場合は、
   メディアの走査を行う前にスキップします。
4. モードセレクター（`modalityBridgeVisionMode`、下表を参照）が、
   再ルーティングか説明文への変換かを決定します。再ルーティングでは、`model` だけを
   差し替えた `modifiedPayload` と、メタデータ `{ rerouted, fromModel, toModel, imagesKept }` を返します。
5. 説明文への変換経路では、画像数を `maxImages` に制限し、タスクに応じたプロンプトを作成し、
   説明キャッシュを参照し、画像認識モデルを**並列に**呼び出して
   （`Promise.allSettled`）、画像の代わりに `[Image N]: <description>` のテキスト部分を挿入します。
   説明の生成に失敗すると `null` が返されます。対象の対応能力が不明な場合や画像認識対応の場合は、
   元の画像が保持されます（#4012）。一方、**テキスト専用であることが確認済みの直接の
   呼び出し先**、または画像認識対応モデルがないコンボでは、説明を生成できなかったすべての画像に対し、
   明示的な `(unavailable — no vision-capable provider connected)` という代替テキストを挿入します。
   これには、一部の生成失敗や、説明生成呼び出しの上限を超えた画像も含まれます
   （#17069）。コンボで説明生成がすべて失敗した場合の既存のフォールバックは、
   引き続き維持されます（#8430）。
6. `modifiedPayload` とメタデータ（`imagesProcessed`、`descriptions`、
   `processingTimeMs`、`visionModel`）を返します。

#### モードセレクター（`modalityBridgeVisionMode`）

| モード     | デフォルト | 動作                                                                                                                                                                                                                                                                                                                        |
| ---------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔          | 従来のヒューリスティックを変更せずに使用（#6640/#7204）：コンボ以外のモデル/`auto/` モデルは、元のモデルに使用可能な認証情報がすでにある場合（その場合は説明を生成）を除き、最適なビジョンモデルに再ルーティングします。コンボのターゲットでは常に説明を生成します。                                                        |
| `describe` |            | 常に説明を生成します — 再ルーティングのブロックは完全にスキップされ、ユーザーが選択したモデルが常に応答します。                                                                                                                                                                                                             |
| `reroute`  |            | 再ルーティングを強制します。認証情報のあるモデルを維持するガードはバイパスされます。再ルーティングの**ターゲット**に対する認証情報ガードは引き続き適用されます — 使用可能なビジョンターゲットがない場合、ブリッジは説明を生成したり、テキスト専用ターゲットに生の画像を送信したりせず、明確なエラーで処理をブロックします。 |

強制モードは、auto のヒューリスティックが実行される**前に**処理を短絡します。`auto` の動作は
PR-1 以前のガードレールとバイト単位で同一です。

#### API キーのスコープ (`visionBridgeKeyScope.ts`)

呼び出し元の API キーで `allowedConnections`、クォータプール
（`allowedQuotas`）、またはモデル（`allowedModels` / `blockedModels` /
`modelAccessMode: "restricted"` / `disableNonPublicModels`）が制限されている場合、ブリッジは
そのキーが使用できる接続上で、そのキーが使用できる再ルーティング先モデルと説明用モデルのみを
選択します。その後、説明生成の呼び出しは常に
`x-omniroute-self-loop-key-id` ヘッダー付きで OmniRoute のセルフループを経由するため、受信側のチャットリクエストで
そのキーの接続ポリシーとモデルポリシーが再度適用されます。`enforceApiKeyPolicy()` が
このヘッダーを受け入れるのはセルフループの Bearer と併用されている場合のみなので、
アクセスを狭めることしかできず、解決できない ID は拒否されます。

そのキーで許可されているビジョンモデルがない場合、**テキスト専用であることが確認済みの
ターゲット**は、対応できないアップストリームに画像のバイト列を転送する代わりに、
明確な HTTP 400 で画像リクエストをローカルに拒否します（#17069）。ビジョン機能が
不明なターゲット、またはネイティブでビジョンに対応するターゲットでは、説明生成の経路は従来の
フェイルオープン動作を維持します（メタデータ `{ skipped: true, reason: "no_permitted_vision_model" }`）。
キーのないリクエストや、これらの制限がないキーは、
これまでとまったく同じように動作します。

#### タスクを考慮した説明生成プロンプト (`modalityBridgeVisionTaskAware`)

デフォルトは **true** です。`composeVisionPrompt()`（`visionBridgeHelpers.ts`）は、
**最後のユーザーメッセージ**のテキスト（500 文字に切り詰め）を基本の
説明生成プロンプトに追加し、ユーザーが実際に尋ねた内容に沿った説明になるよう誘導するとともに
（codex-vision-proxy パターン）、画像内のテキストを文字起こしするようビジョンモデルに要求します。
フラグがオフの場合、またはユーザーテキストがない場合は、基本プロンプトがそのまま使用されます。

説明生成セルフループ自体の OpenAI 互換リクエスト（`visionBridgeHelpers.ts` の
`callVisionModelSingle()`）は、常に `image_url.detail: "high"` を要求します —
クライアントからのシグナルを条件とせず、すべての呼び出し元/プロバイダーに対して無条件に適用されます。
低詳細度のサンプリングでは、このプロンプトが求めるテキストの文字起こしタスクで
OCR 精度が低下するため、説明生成の呼び出し自体は、元の受信リクエストで使用された
詳細度に関係なく、常に高詳細度を要求します。これは
内部の説明生成リクエスト本文にのみ影響し、メインリクエストで
OmniRoute が呼び出し元自身の `image_url.detail` を転送する方法は変更しません —
そのデフォルトは、検出された OpenCode クライアントに限り、
`defaultImageDetail()`（`open-sse/handlers/chatCore/upstreamBody.ts`）で別途適用されます。
説明生成セルフループの Anthropic ワイヤーフォーマット分岐には `detail` フィールドがなく、
どちらのデフォルトの影響も受けません。

#### 説明出力の上限 (`modalityBridgeVisionMaxChars`)

| キー                           | デフォルト | 範囲                 |
| ------------------------------ | ---------- | -------------------- |
| `modalityBridgeVisionMaxChars` | `0`        | `0` または 100–50000 |

`0`（デフォルト）は**上限なし**を意味します — `callVisionModel()` が返す
説明は変更せずにそのまま渡され、既存の
動作が維持されます。100–50000 の範囲の値を指定すると、説明は
`…` サフィックス付きで切り詰められてから、`[Image N]: <description>` として差し戻されます
（`src/lib/guardrails/visionBridge.ts` の `VisionBridgeGuardrail.preCall()`）。
後段のモデルで完全な文字起こしが必要な、細部の多い OCR タスクでは値を
大きくしてください。冗長になりがちなビジョンモデルのトークン使用量を抑えるには、小さくしてください。
ダッシュボードのフィールドは「ビジョン」タブの「詳細設定」パネルにあり
（`ModalityBridgeVisionTab.tsx` の `modality-bridge-max-chars`）、1 から 99 までの
値は下限の 100 に引き上げられますが、明示的な `0` は
そのまま維持されます — `0` は単なる
「未設定」のデフォルトではなく、それ自体が有効な Zod の値です
（`z.union([z.literal(0), z.number().int().min(100).max(50000)])`）。

#### 説明生成キャッシュ (`modalityBridge/bridgeCache.ts`)

説明出力用のインメモリ LRU + TTL キャッシュで、プロセス全体で共有されます。
キー = `sha256(imageRef + composedPrompt + configuredBridgeModel)` で、
長さプレフィックスによるフレーミングを使用します（フィールド境界の衝突はありません）。モデルの要素は
実際に応答したモデルではなく、**設定された**ブリッジモデルです —
`callVisionModel` は内部でフォールバックする可能性があり、試行ごとにキーを作成すると
キャッシュが断片化するためです。失敗した説明生成はキャッシュされません。設定：

| キー                            | デフォルト | 範囲    |
| ------------------------------- | ---------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`     | —       |
| `modalityBridgeCacheTtlMinutes` | `60`       | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`      | 10–5000 |

#### リモート画像の正規化（セルフループの describe/base64 取得）

ブリッジ自体が**リモート**画像を取得する場合 — Anthropic の describe
自己呼び出しと claude-wire-format の base64 変換
（`ensureBase64ImagesForClaudeWire`）は、どちらも
`visionBridgeHelpers.ts` の `fetchRemoteImageAsDataUri()` を経由します —
生成されたデータ URI は、ビジョンモデルへのリクエストに埋め込まれる前に
`normalizeDataUri()`
（`open-sse/utils/imageNormalize.ts`）で処理されます。サイズが大きすぎる画像は
**長辺 2048px** に縮小されます（OpenAI/Anthropic がサーバー側ですでに適用している
リサイズ上限と同じです）。これにより、ビジョンモデルが見る内容を変えずに、
アップロードのバイト数とレイテンシを削減できます。リサイズには動的インポートで読み込まれる
`sharp` を使用します。そのネイティブバイナリを読み込めないプラットフォームでも、
`normalizeDataUri()` は**例外をスローせず**、元のバイト列をそのまま渡す処理に
フォールバックするため、describe/base64 変換の経路は常に動作し続けます。
画像ではないバイト列（取得結果がデコード可能な画像でなかった場合）も、
変更せずにそのまま渡されます。この正規化の対象は、ブリッジが自身の自己呼び出し用に
取得する画像に限定されます。オプトイン時のみ変更を行う原則（厳守ルール #20）に従い、
呼び出し元の未加工のパススルーペイロードには一切適用されません。

#### 設定スキーマ + 移行

新しい `modalityBridge*` キーは、`updateSettingsSchema`
（`src/shared/validation/settingsSchemas.ts`）で Zod による検証を受けます。
対象は `modalityBridgeVisionEnabled`、
`modalityBridgeVisionMode`、`modalityBridgeVisionModel`、
`modalityBridgeVisionTaskAware`、`modalityBridgeVisionPrompt`、
`modalityBridgeVisionTimeout`、`modalityBridgeVisionMaxImages`、
`modalityBridgeVisionMaxChars`、3 つの `modalityBridgeCache*` キー、および
Audio Bridge で使用される `modalityBridgeAudio*` グループです。移行ファイル
`141_modality_bridge_settings.sql` は、既存のレガシー
`visionBridge*` の値を対応する新しいキーにコピーします（冪等であり、運用者が設定した
`modalityBridge*` の値を上書きすることはありません）。レガシーキーは、
1 リリースサイクルの間、読み取り時のフォールバックとして引き続き受け付けられます。

#### 透明性ヘッダー + 統計

describe で変換されたレスポンスには、
`x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>`
が付与されます
（`modalityBridge/bridgeStats.ts` の `buildModalityBridgeHeader()` で生成し、
`src/sse/handlers/chatHelpers.ts` の `withModalityBridgeHeader()` で付与します）。
ルーティング先を変更したリクエストには、ヘッダーを**付与しません**。ペイロードは変更されておらず、
モデルの切り替えはレスポンス本文の `model` フィールドですでに確認できるためです。

`GET /api/modality-bridge/stats`（管理用認証が必要で、
`GET /api/settings` と同じ権限レベル）は、`vision`、`audio`、
`video` について、メモリ内のモダリティ別カウンター
`{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs,
latencySamples, averageLatencyMs, lastUsedAt }` を返します。
`averageLatencyMs` は、すべての試行回数ではなく `latencySamples` を
分母として使用します。時間が計測されていない操作について、0 ミリ秒のサンプルを
作り出すことはありません。`bridged` は、変換成功数を表す後方互換のエイリアスとして
維持されます。失敗した試行では増加しません。
設計上、カウンターはプロセスの再起動時にリセットされます
（使用量の精算ではなく、テレメトリを目的としています）。

#### ダッシュボードの設定

専用のダッシュボードページは
`/dashboard/settings/modality-bridge` です。URL で直接指定できる `Vision`、`Audio`、
`Video` タブは、`tab` の値を切り替える際にクエリパラメーターを保持します。
Vision タブでは、有効化、モード、モデル選択（自動選択のデフォルトを含む）、
タスクに応じたプロンプト、タイムアウト・画像数・説明文の長さ・キャッシュに関する
詳細な上限設定、実行時
カウンター、およびガード付きのサンプルリクエストを利用できます。Audio タブも稼働しており、
有効化、Auto を含む STT 専用のモデル選択、タイムアウトとクリップの上限、音声
カウンター、`input_audio` のサンプルテストを利用できます。Video タブも機能しており、
FFmpeg/ffprobe の実行環境の状態を表示します。UI の状態は明確に 4 つに分かれています（
調査中または調査を完了できなかった場合は `unknown`、
ループバック以外のダッシュボードホストでクライアント側の調査がスキップされる場合は `restricted`、
調査によって未インストールと確認された場合は `unavailable`、
利用可能な場合は FFmpeg/ffprobe のバージョンとともに `available`）。
また、有効化・モデル・フレーム・動画・タイムアウトの上限設定を永続化し、
モデル選択をビジョン対応モデルに絞り込み、動画カウンターを表示します。

AI 設定にあった従来の Vision Bridge カードは、新しいページへの互換性維持用リンクに
なっており、フォームの別コピーは保持しません。Media Providers も、
既存の Speech-to-Text プレイグラウンドを削除せずに、
Image-to-Text および Speech-to-Text のワークフローを対応する Modality
Bridge タブにリンクしています。

**セルフループのアドミッション制御バイパス:** describe 呼び出しが OmniRoute 自身の
`/v1` セルフループを経由する場合（非標準プロバイダーのモデル）、サブリクエストは
`x-omniroute-admission-bypass: internal` を送信し、解決された
セルフループ用認証情報で認証されます。ローカルモードではローカルの `sk_omniroute`
センチネルを、それ以外では運用者が設定した環境変数 `OMNIROUTE_API_KEY` /
`ROUTER_API_KEY` のキー（#1350）を使用するため、
`REQUIRE_API_KEY=true` のデプロイでも describe 呼び出しを実行できます。
このバイパスは、これらの認証情報と完全に一致する場合にのみ認められるため、
外部クライアントがこのヘッダーを使ってアドミッション制御を回避することはできません。

レガシーのデフォルト値は `src/shared/constants/visionBridgeDefaults.ts` にあります。
新しいモード・タスク対応・キャッシュのデフォルト値と設定リゾルバーは、
`src/shared/constants/modalityBridgeDefaults.ts` にあります。ガードレールは
コンストラクターオプション `deps` を公開しており、テストで偽の `getSettings` および
`callVisionModel` 実装を注入できます。

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

音声入力を受け付けることが確認されていないターゲットに到達する前に、音声を含む
チャットリクエストを捕捉します。チャットリクエストのルーティング先は変更しません。
音声パートは既存の OpenAI 互換マルチパートエンドポイントで文字起こしされ、
選択されたチャットモデルがその文字起こしテキストを使って処理を続行します。

処理の流れ:

1. `getResolvedModelCapabilities()` を通じて `supportsAudio` を解決します。明示的な
   プロバイダーレジストリのメタデータを最優先し、次に静的なモデルメタデータ、最後に同期済みの
   `modalities_input` を参照します。宣言された入力リストに `audio` がなければ `false`、
   機能を裏付ける情報がなければ `null` のままです。`false` と `null` はどちらも
   保守的なブリッジ処理を有効にし、`true` はそれをバイパスします。
2. `modalityBridgeAudio*` 設定を解決し、共有の `detectMediaParts()`
   検出器を通じて、すべてのメッセージから差し替え可能なトップレベルの音声パートを抽出します。
   サポートされる通信形式は、OpenAI の `input_audio`、`audio_url`、
   `source.media_type: "audio/*"` です。ネストされた音声はルーティングのために検出されますが、
   差し替え処理では削除されません。処理数は `modalityBridgeAudioMaxClips` によって制限され、
   それ以降のパートは変更されません。
3. 設定された `provider/model` を使用します。設定されていない場合は、`selectAudioBridgeModel()` が
   `AUDIO_TRANSCRIPTION_PROVIDERS` を安定したカタログ順で走査し、
   利用可能な有効なプロバイダー認証情報を持つ最初のモデルを選択します。
4. `callAudioTranscription()` は、base64/data URI の音声をマルチパートの
   `file` に変換するか、DNS ピンニングと 25 MB の上限を備えた公開宛先限定の
   アウトバウンドガードを通じてリモートの `audio_url` をダウンロードします。その後、
   `resolveSelfLoopBearer()` で認証し、ファイルと選択したモデルをローカルの
   `/v1/audio/transcriptions` セルフループに POST します。既存の文字起こしルートが、
   通常の認証情報検索、クールダウン／レート制限処理、およびプロバイダーへのディスパッチを実行します。
5. 呼び出しが成功すると、対象のパートは `[Audio N]: <transcript>` に置き換えられます。呼び出しは
   `Promise.allSettled` で実行され、個々の呼び出しが失敗した場合は元の音声パートが保持されます
   （#4012 の契約）。すべての呼び出しが失敗し、対象が
   `supportsAudio === false` であると確認されている場合、パートは
   `[Audio N]: (unavailable — no STT provider connected)` に置き換えられます（#8430 の契約）。対象の機能が
   不明（`null`）の場合、すべて失敗しても変更されません。テキスト専用であることが確認された対象に
   利用可能な STT 認証情報がない場合は、ネットワーク呼び出しを行わずに、同じ明示的な
   スタブを使用します。

成功した文字起こしは、プロセス全体で共有される Modality Bridge の LRU/TTL キャッシュを使用します。
キーは、音声参照、固定の `audio-transcription` 操作ラベル、
選択された STT モデルを組み合わせたものです。失敗はキャッシュされません。音声処理の試行は、
共有の `bridged`、`cacheHits`、`failures`、`lastUsedAt` カウンターを更新します。
変換されたレスポンスには
`x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>` が付与されます。変更されていない
リクエストには Audio Bridge セグメントは付与されません。

ランタイム設定は DB に保存され、Zod で検証されます。

| キー                          | デフォルト | 範囲              |
| ----------------------------- | ---------- | ----------------- |
| `modalityBridgeAudioEnabled`  | `true`     | —                 |
| `modalityBridgeAudioModel`    | `""`       | 自動または STT ID |
| `modalityBridgeAudioTimeout`  | `60000`    | 1000–300000       |
| `modalityBridgeAudioMaxClips` | `3`        | 1–10              |

共有キャッシュは引き続き `modalityBridgeCacheEnabled`、
`modalityBridgeCacheTtlMinutes`、`modalityBridgeCacheMaxEntries` によって制御されます。

### Video Bridge (`videoBridge.ts`, `videoBridgePipeline.ts`)

ネイティブの動画サポートが確認されていない対象を呼び出す前に、Chat Completions の `messages` および Responses
API の `input` に含まれるトップレベルの動画パートをインターセプトします。
サポートされる形式は、`input_video`、`video_url`、`video_source`、HTTPS URL、
および `data:video/*;base64,...` データ URI です。テキスト内の単なるファイル名は
動画として扱われません。

`VideoBridgeGuardrail.preCall`（`videoBridge.ts`）は、リクエストの走査、
機能／ポリシーチェック、リクエスト単位の集約、およびレスポンスペイロードを担当します。
動画ごとの処理（取得、結果全体のキャッシュ、フレーム
シーケンスの説明（呼び出し元が宣言した音声の文字起こしも統合）、および試行ごとの
メトリクス／中断／クリーンアップ）は、`videoBridgePipeline.ts` の `processVideoPart` に
隠蔽されており、`preCall` のループ内で動画パートごとに 1 回呼び出されます。
このモジュールは、明示的なポート境界として `VideoMediaBrokerPort`
（バイト列の取得とサンプリングされたフレームの抽出）、`VideoAudioTranscriptionPort`
（呼び出し元が宣言した音声の文字起こしとサンプリングされたキャプションの統合）、および
`VideoDrilldownPort`（フレームのドリルダウン永続化の境界。まだ
`processVideoPart` には接続されておらず、現在ドリルダウンエントリを書き込むのは
独立した `/api/modality-bridge/video/drilldown` ルートのみ）も定義しています。

公開の `/v1` リクエスト経路では、サブプロセスをインポートすることも呼び出すこともありません。リモート
動画は 50 MiB の上限でダウンロードされます。インライン base64 動画には、
モデル／メッセージ／フレーミングを含む全体を公開 JSON リクエストの受け入れ上限である 50 MiB 以内に収められるよう、
動画ごとにデコード後 36 MiB という保守的な上限が設けられています。インラインの
長さとデコード後の推定サイズは、メモリ確保前に検査されます。最初のリモート URL と
すべてのリダイレクトで HTTPS が必須であり、DNS ピンニングを備えた既存の
公開宛先限定のアウトバウンドガードを使用します。その後、バイト列は厳密に定められた内部の
`POST /api/modality-bridge/video/extract` ブローカー境界を通過します。このルートは
`LOCAL_ONLY` と `SPAWN_CAPABLE` の両方であり、プロセスごとに認証された
信頼済みループバックリクエストのみを受け付けます。URL、ファイルシステムパス、実行可能ファイル、
引数リストは一切受け付けません。API のボディサイズ処理パイプラインとハンドラーの逐次ボディ
リーダーは、それぞれ独立してブローカー入力に 50 MiB の上限を適用します。上限付きキューは
一度に 1 件の抽出を実行し、待機中のジョブを 4 件まで許容し、待機中の入力の合計を
100 MiB に制限します。

ブローカー内では、`ffprobe` が非公開のローカルファイルを読み取ります。固定の形式許可リストには、プレイリスト形式とマニフェスト形式は含まれません。許可された MOV 系コンテナでも、外部 MOV データ参照はデフォルトで無効のままであり、固定コマンドで有効化されることもありません。`ffprobe` と `ffmpeg` はどちらも、`file` のみのプロトコルホワイトリスト、1 スレッド、固定の引数配列を使用し、シェルを介さず、`PATH` から解決された実行ファイルを使用します。添付画像のカバーストリームは再生可能な候補にはなりません。すべての再生可能なストリームが制限を満たす必要があり、明示的にデフォルト指定されたストリームが優先され、それがない場合は決定論的に最小インデックスのストリームへフォールバックします。動画の上限は、長さ 600 秒、各辺 8,192 ピクセル、ソース画素数 33,554,432 です。FFmpeg は各サンプリング区間の中点から 1～16 枚の JPEG フレームを抽出し、長辺が最大 1,024 ピクセルになるよう縮小します。小さい入力を拡大することはなく、URL を受け取ることもありません。サンプリングのデフォルトは `uniform` です。オプションの `scene_aware` ポリシーと実験的な `segment_aware` ポリシーは、検証済みのローカルストリームに対して固定の FFmpeg 処理をもう 1 回実行し、範囲を制限した `showinfo` のシーンタイムスタンプを選択します。検出器の失敗、タイムアウト、不正な出力、または候補集合が空の場合は、同じ均等配置の中点へ決定論的にフォールバックします。セグメント対応モードでは、検証済みのシーン区間に比例して中点サンプルを割り当てます。セグメント対応の根拠データとフォールバック動作については、後述します。すべてのポリシーで、選択後に厳格な 16 フレームの上限が適用されます。シーン対応のリクエストでフレーム予算が 1 枚しかない場合は、有効な動画全体またはフォーカスウィンドウの均等サンプリング時の中点を使用し、`policyEffective: uniform` を報告します。選択された 1 枚のシーンフレームだけでは、時間軸の両端を維持できないためです。呼び出し元は、有限値のフォーカスウィンドウ（`start`/`end`、秒単位）を任意で指定できます。境界はメディアの長さに収まるよう制限され、開始と終了が逆転したウィンドウや非有限値のウィンドウは拒否されます。すべてのサンプリングポリシーは、正規化された区間内でのみ実行されます。結果のウィンドウはサンプリングメタデータと、信頼できない説明プレフィックスに含められるため、後段のモデルはフォーカスされた抜粋とタイムライン全体を区別できます。

キャプションの意味的なフォーカスは、独立した明示的な設定です。デフォルトの `full` 分析モードでは、既存のフレームプロンプトを維持し、リクエストのテキストをキャプションモデルに転送することはありません。`focused` モードでは、ブリッジは同じ Chat または Responses コンテナから、ユーザーが記述した最新の空でない `text`/`input_text` のみを読み取り、NFC に正規化し、制御文字と空白をまとめ、500 Unicode コードポイントに制限します。結果が空の場合は、元の `full` プロンプトにそのままフォールバックします。利用可能なヒントは、専用の信頼できないユーザーコンテキストブロック内で JSON としてシリアライズされ、観察可能な詳細の優先順位付けにのみ使用できます。メディア内で見える、または聞こえる指示に従わないよう求める別の警告を上書きすることはできません。テキストによるフォーカスが `start`/`end` を推定したり、時間方向のサンプラーを変更したりすることはありません。

#### FU-07 構造的セグメントの根拠データ

`segment_aware` は、検証済みのローカル動画ストリームに対して、制限付きの事前分析処理を 1 回実行します。固定のフィルターチェーンは、まず幅を最大 320 ピクセルに縮小し、シーンの変化とフリーズ区間を検出した後、毎秒 1 フレームをサンプリングして、ぼけ、平均輝度、空間的・時間的情報を取得します。この処理は、構造分析用サンプル 600 個、FFmpeg/フィルターのスレッド 1 本、同じ `file` のみのプロトコル許可リストとコンテナ許可リスト、プロセス出力の上限 1 MiB、およびブローカーの共有中断処理・期限内で最大 30 秒に制限されます。リクエストからコマンド、フィルター、パス、URL を受け付けることはありません。

構造値は、決定論的なサンプリングの根拠データであり、動画の意味理解ではありません。被写体、動作、キャプション、音声、ユーザーの意図を推定するものではありません。シーン境界とフリーズ境界によってセグメントが形成されます。フリーズの割合、ぼけ、露出、空間的な細部、時間的変化は、既存の 1～16 フレームの予算配分にのみ影響します。完全にフリーズしたセグメントは最大 1 フレームに制限され、フリーズしていないセグメント間で残りの予算が配分されます。境界の数がフレーム数を上回る場合は、タイムライン全体の均等な網羅を維持し、序盤の急速なカットによって末尾の長いセグメントが隠れないようにします。フリーズ境界から分析解像度の 1 秒以内にあるシーン境界は統合されます。

フィルターの欠落、不正または空の根拠データ、検出器のエラー、制限付き事前分析のタイムアウトが発生した場合は、フェイルオープンとして、元の均等中点ポリシーにそのままフォールバックします。呼び出し元による中断やブローカーの期限到達ではフェイルオープンしません。実行中のサブプロセスを終了し、後続のフレーム抽出を防止し、`finally` で非公開の一時ディレクトリツリーを削除します。

`scripts/perf/video-bridge-fu07-eval.ts` は、重複排除後のキャプション呼び出し削減、動きの多い映像への予算配分、ぼけ・露出・SI-TI の根拠データ、末尾に長い区間が続く急速なカット、および緩やかなフェードによる偽陽性を評価するため、実際の FFmpeg を用いた決定論的なフィクスチャを生成します。事前分析の実経過時間を記録し、`/usr/bin/time` が利用できる場合は、子プロセスの CPU 時間とピーク RSS も記録します。品質チェックは、構造上の正しさを判定するものに限られます。このハーネスには承認済みのエンドポイントも固定済みの評価器もないため、実際のキャプションモデルの品質は `HOLD` のままです。金銭的な削減額も、`--caption-cost-per-call-usd` によって明示的な正の呼び出し単価の見積もりが指定されない限り、`HOLD` のままです。スクリプトがいずれかの結果を捏造することはありません。

各フレームは4 MiB、すべての生フレームの合計は23 MiB、シリアライズされたブローカー応答は32 MiBに制限されます。非公開の一時ディレクトリは
`finally` で削除されます。OmniRouteはFFmpegを同梱せず、カスタムの
実行ファイルパスも受け付けません。キャプション生成前に、ブリッジは保守的な視覚的
重複排除処理を適用します。各JPEGを16×16のグレースケールバッファに縮小し、
最後に保持したフレームとのみ比較します。要求されたキャプション用のフレーム数の上限が
1を超える場合、抽出処理はその上限の最大2倍、かつ最大16フレームまでの
制限付き候補プールを提供します。
要求された上限は重複排除後にのみ適用され、上限が2以上の場合は、
最終的な間引きの際に、選択された候補の最初と最後が保持されます。
バージョン管理された
`grayscale-16x16-mean-cells-v2` ポリシーは、平均輝度差と、
正規化された差が0.05以上のサムネイルセルの割合のうち、大きい方を使用します。
重複判定のしきい値は定数0.04です。実行時設定として公開するのではなく、
予測可能性を重視して選ばれています。この補助的な
高コントラストの指標により、平均値のみの比較では見逃すおそれのある小さな動きや表示テキストの変化が
保持されます。比較器やデコーダーでエラーが発生した場合は、フレームを除外せずに保持して
カバレッジを維持します。出力メタデータでは、抽出された候補、正常に使用された
フレーム、除外された視覚的重複が区別されます。

明示的にマークされた動画パートは、タイムスタンプ付きコンタクトシートを要求できます。
ブリッジは、最大4列、16フレームのJPEGグリッドを構築します。512ピクセルの各セルでは、
高コントラストの下部帯にソースのタイムスタンプが焼き込まれます。同じタイムスタンプは、
後段での関連付けと監査のため、テキストメタデータにも保持されます。完成した
JPEGの上限は32 MiBです。`sharp` がグリッドをデコードまたは合成できない場合、
ブリッジは個別のJPEGフレームにフォールバックします。クライアントによる中止は、
シート処理中でも引き続き伝播します。

本採用の根拠は、合成データによる合成処理の
マイクロベンチマークとは意図的に分離されています。`scripts/perf/video-bridge-contact-sheet-eval.ts` は、
実際のOpenAI互換ビジョンモデル向けに、スキーマがバージョン管理されたA/Bテストハーネスを定義します。これは、
プロバイダーが報告するトークン数、エンドツーエンドの実経過時間（シート合成を含む）、
モデル呼び出し回数、マニフェストで定義された事実の保持率を測定します。生のモデル応答は
レポートに書き込まれず、SHA-256ダイジェストと一致した事実IDのみが保持されます。
このハーネスは、`--execute-real` が渡され、
`--model`、`OMNIROUTE_BASE_URL`、`OMNIROUTE_API_KEY` が設定されていない限り、ネットワーク呼び出しも有料のモデル呼び出しも行いません。
この明示的な実行を行わない場合、機械可読の判定は `HOLD` のままです。合成データによる
ペイロードや呼び出し回数の測定だけでは、本採用の根拠にはなりません。

呼び出し元がすでに時刻対応済みのテキストを持っている場合、対応する動画
パートに任意の `transcript.cues` 配列を添付できます。各キューには、`text`、
プローブで確認された再生時間内に収まる有限値の `start`/`end` 区間、および許可リストに含まれる
`source`（`client`、`embedded`、または `audio-bridge`）が必要です。`confidence` のデフォルトは
`1` で、`0` から `1` の範囲内でなければなりません。完全に重複するキューは統合されます。
OmniRouteがこのメタデータから文字起こしを開始することはありません。検証済みのキューは、
ソース、信頼度、区間とともに説明結果へコピーされ、
フレームのキャプションと並んで、信頼されていない観測情報として表示されます。無効なテキスト、
範囲外のテキスト、または出所情報のないテキストは、キャプションストリームに混在させずに
拒否されます。リクエストボディ内の両方のトランスクリプトチャネルでは、提供された
出所情報を `client` に正規化します。これには、自己申告された `embedded` または `audio-bridge`
ラベルも含まれます。これらの信頼されたラベルを割り当てられるのは、
コード内でのみ指定できる `trustedSource` 引数を使用する、サーバー管理下のアダプターだけです。リクエストのJSONフィールドから
その引数にアクセスすることはできません。トランスクリプトのテキストは、その出所にかかわらず、
信頼されていないメディア由来のコンテンツであり、
認可の判断に使用してはなりません。

高度な利用を行う呼び出し元は、同じ動画に対して `audioTranscript` トラックを提供できます。
これはクライアント提供のテキストとして扱われ、サーバーによる文字起こしの証拠とは見なされません。
融合処理の接続部分では、視覚と音声の観測処理を
共通の期限と中止シグナルの下で実行し、共通のタイムライン上で順序付け、完全な
重複を統合し、片側のみが成功した場合は部分的な結果を報告します。
無効な `audioTranscript` が渡された場合は、動画全体を失敗させるのではなく、
その部分的な結果へと縮退します。視覚的な説明は保持され、
音声側の分岐にはサニタイズ済みの失敗コードが記録されます。
各分岐の利用可否、部分結果フラグ、
サニタイズ済みの失敗コードは、説明結果、
ガードレールメタデータ（`audioFusionRuns`/`audioFusionPartials`/
`audioFusionFailureCodes`）、結果キャッシュのメタデータ、およびブリッジの
融合カウンターに保持されます。デフォルトのVideo Bridge処理経路では、音声認識を呼び出すことも、
メディアの2つ目のコピーをダウンロードすることもありません。その明示的なトラックがなければ、
動画のみを扱います。

**トランスクリプトの保持 (#12150 P1)。** これは、Video Bridge（それ自体がオプトイン）がトランスクリプトのキューをレンダリングするたびに自動的に適用されます。個別の保持フラグはありません。リクエストがトランスクリプトのキュー（呼び出し元が宣言した `transcript` または融合された `audioTranscript`）をレンダリングすると、ガードレールはそのリクエストに `videoBridgeObserved` を設定し、動画説明の墨消し済みシャドーを生成します。これは、各キューの自由記述本文をすべて `[redacted-video-transcript]` に置き換えた、それ以外は同一のレンダリングです。文字列を組み立てる前に構造化されたキューフィールドを置換して生成します（フラット化されたテキストを解析することは決してないため、悪意のある内容か通常の内容かを問わず、`[inaudible]`/`[music]` のように `]` を含む本文も含め、キューの内容が残ることはありません）。永続化される呼び出しログのリクエスト本文では、内容の一致に基づき、動画由来の各テキストパートをその墨消し済みシャドーに差し替えます。`fullText` アンカーは、完成した呼び出し前ガードレールのペイロードから再読み取りされるため、後続のチェーンガードレール（優先度 10/95 の PII および認証情報マスカー）が説明文をその場で書き換えた後や、システムプロンプト、ハンドオフ、メモリの注入によってメッセージ配列が再構成された後でも、一致を検出できます。上流のモデルに送信される本文は変更されません。また、観測済みリクエストでは永続的な Memory への格納も行われません（リクエスト由来とレスポンス由来の両方の抽出をスキップします）。そのため、モデル自身の応答によってトランスクリプトのテキストが Memory に書き戻されることもありません。

**生の動画フィールド (#12430)。** ブリッジが有効で、ネイティブ動画サポートが不明または存在しない場合、定義済みの `transcript`/`audioTranscript` フィールドも `videoBridgeObserved` を有効にします。これは、説明の生成に失敗した後や、`maxVideos` の上限に達した後でも同様です。`null` と空文字列も対象になりますが、存在しないフィールドや動画以外のメタデータは対象になりません。保持されるコピーでは、これらのフィールドを墨消しするか、リクエスト自体を省略し、キャッシュと Memory はバイパスします。

これらのフォールバック経路では、有効な呼び出し元のキューは、プロバイダーの非標準フィールドではなく、サポートされている `text`/`input_text` パートになります。リクエストで指定された両方のトラックは、引き続き信頼されていない `client` 観測情報として扱われ、動画の説明が生成されておらず、タイムスタンプがメディアと照合されていないことを明示する警告が付けられます。既存の合計 256 キュー/64 KiB の上限とキューごとの上限は、2 つのトラックを合わせて適用されます。タイムスタンプは、ブローカーの 600 秒の上限と、指定されているフォーカス区間の範囲内でなければなりません。無効なトラックは破棄され、任意のテキストとして転送されることはありません。合計上限を超えない限り、もう一方の有効なトラックは引き続き使用できます。null/空のフィールドはテキストを追加しません。このフォールバックによってメディアの取得や文字起こしが追加されることはありません。トランスクリプト拡張フィールドは、フォールバック用の動画キャリアと、その `video_url`/`source` オブジェクトから削除されます。OpenAI 通信形式の許可リストは厳格なままです。ネイティブサポートが不明な動画キャリアは引き続き利用可能で、テキスト専用であることが判明しているターゲットでは安全なマーカーが維持されます。構造化された墨消し済みシャドーが追加されたトランスクリプトのテキストを保護する一方、呼び出し元が所有する元のリクエストは変更されません。ネイティブサポートのあるターゲットと無効化されたブリッジでは、既存のバイパス動作が維持されます。

そのほかの保持されるコピーも、同じ観測済みリクエストのシグナルを使用します。ガードレール適用前の生のクライアントリクエストのスナップショット、メモリ内の保留中リクエスト、早期に拒否されたリクエストのログでは、動画パート内のトランスクリプトフィールドを構造的に置換します。パイプラインの各段階やコンテキストハンドオフによって合成された文字列プロンプトは、リクエスト本文の永続化先で墨消しされます。永続化された `video_content_removed` マーカーにより、`previous_response_id` による継続は、意図的に破棄されたテキストを再構築するのではなく、安全側に失敗します。観測済みリクエストで、ログ記録前にパートごとの墨消し済みシャドーが失われた場合、または後続のリクエスト変更後に複数の動画シャドーのうち 1 つでも一致しなくなった場合は、部分的に墨消しされたトランスクリプトを保持するのではなく、保持対象のリクエスト本文全体を省略します。

観測済みリクエストでは、モデルのレスポンスが、構造化されたキューの境界なしにトランスクリプトの任意の部分を引用する可能性があります。そのため、永続化される呼び出しログの `responseBody` は省略マーカーに置き換えられ、詳細なパイプラインアーティファクト（上流/クライアントの本文やストリームチャンクを含む場合があります）は保持されません。セマンティック、冪等性、推論再生の各キャッシュは、そのリクエストについて読み取りと書き込みをバイパスします。プロバイダーへのリクエストとクライアントに表示されるレスポンスは変更されません。詳細アーティファクトを省略する際は、早期の keepalive バイトを一時バッファーから排出します。Kiro の不正な EventStream 警告は、ペイロードのバイト数のみを報告し、その内容や JSON パーサーの生のエラーは決して報告しません。
これは、無関係なすべてのプロバイダー/プラグインの診断情報が監査済みであると主張するものではありません。より広範な保持先の総点検は #11658 で追跡されています。

内部の `/api/modality-bridge/video/drilldown` ライフサイクルは、ループバック/トークン認証を使用する独立したキャッシュ基盤です。すべての操作には、正規の不透明なプリンシパル ID も必要です。本番環境の呼び出し元を有効にする前に、その呼び出し元は認証済みテナントからこの ID を導出する必要があり、クライアントが選択した値を転送してはなりません。キャッシュキーは、そのプリンシパルを正規のセッション ID および動画参照 ID に結び付け、それらから SHA-256 で導出したキーのみを保存し、読み取りと削除の両方を同じプリンシパルの範囲に限定します。キャッシュは、エントリごとに最大 16 枚の派生 JPEG フレームを保存し、10 分後に期限切れにします。また、範囲を限定した `start`/`end` の読み取りや、明示的なセッション削除をサポートします。

各プリンシパルの上限は、16 エントリおよび 64 MiB の正規 JPEG データです。これらの上限は、グローバルな 64 エントリ/256 MiB の上限とは独立しています。プリンシパルのクォータが逼迫した場合は、グローバル LRU による削除を検討する前に、そのプリンシパルのエントリだけを、最後に使用されてから最も時間が経過した順に削除します。期限切れのエントリは、キャッシュ操作時にプリンシパル別とグローバルの両方の集計から除去されます。一方、キャンセルや検証失敗の場合は、部分的な置換を確定しません。

キャッシュは、非正規の Base64、過剰なパディング、JPEG 以外のメディア、不正または
切り詰められた JPEG、および制限付きの全画像 `sharp`
デコード中に警告が発生する JPEG を拒否します。受け入れた各画像を正規の JPEG として再エンコードし、呼び出し元のフィールドを信用せずに
デコード済みバイト列から幅と高さを取得し、末尾の
ポリグロットバイト列は保持せずに破棄します。両方のクォータに計上されるのは、サイズ制限内の正規圧縮バッファ
のみです。JSON の通信サイズ上限には、デコード後の入力の上限である 32 MiB に対応する Base64 のオーバーヘッドが含まれます。保存されるすべての
派生データには、検証済みの JPEG 形式と解像度、サンプリングポリシー、
派生バージョン、作成時刻、サーバーで計算されたコンテンツハッシュ、およびハッシュ化された親
参照と、信頼された呼び出し元が提供する親コンテンツのハッシュが記録されます。キャンセルは、
アトミックなキャッシュコミットの前に、非同期のデコード処理とハッシュ処理の間で確認されます。

今回の実装範囲では、本番用の生成元をルートにまだ接続しておらず、
複数解像度のバリアント選択も提供していません。そのため、透過的な Video Bridge リクエスト
経路には追加の処理は発生しません。一方、テナントに紐づくプリンシパルの導出と
FU-08 の複数解像度ライフサイクル全体は、完了済みの動作として
文書化するのではなく、明示的な今後の作業として残されています。

フレームのキャプションは、設定された Video モデルを使用して順次生成されます。Video の
オーバーライドが空の場合は Vision の設定を継承し、両方が空の場合は Vision の
自動ルーターが実際に使用する視覚対応モデルを選択します。キャプション生成に成功すると、
元のパートは固定の `[Video description:` プレフィックスを持つテキストに置き換えられます。このプレフィックスは、
そのテキストがメディア由来の信頼できない観察内容であることも示し、メディア内にある指示に従わないよう後続の
モデルに伝えます。フレームキャプションのキャッシュキーには、
JPEG バイト列、プロンプト、タイムスタンプ、および実際に使用するモデルが含まれます。キャッシュされるのは、生成に成功した
キャプションのみです。キャッシュエントリには、フォールバックモデルを含め、実際に生成に成功したモデルが
保持されます。フレームごとに異なるモデルで
生成された場合、ブリッジは `mixed` を報告します。キャッシュヒット時には、その生成元の識別情報を再利用し、
要求されたルーティング計画に合わせてラベルを付け直すことはありません。動画全体の結果
キャッシュは、出力を変化させるすべての入力をキーに含めます。具体的には、プロンプト、実際に使用する
モデル、サンプリングポリシー、フレーム数、セマンティック分析モード、正規化されたフォーカスヒントの SHA-256
フィンガープリント、フォーカスウィンドウ、`transcript`、
`audioTranscript`、およびコンタクトシートフラグです。そのため、これらの
要素のいずれかを変更するとキャッシュミスとなり、古い結果が再利用されることはありません。視覚的重複排除ポリシーの
バージョン、しきい値、および上限付きの候補フレーム数も、
結果キャッシュのキーとメタデータに明示的に含まれます。そのため、ポリシーを変更しても古い
動画全体の説明が再利用されることはありません。結果キャッシュ v4 のメタデータには、モードと
フィンガープリントが保持され、生のユーザータスクは保持されません。ガードレールのメタデータは、
要求された分析モードと実際に使用される分析モードの両方を報告します。使用可能なユーザーテキストがない状態で
`focused` モードが要求された場合、実際のモードは `full` として報告されます。

ガードレールは、対応するすべての動画パートを抽出しますが、説明する動画数は
`modalityBridgeVideoMaxVideos` 以下に制限されます。
`supportsVideo === false` であると確認されたターゲットでは、処理に失敗した動画と上限を超えた動画は明示的な安全な
テキストマーカーに変換されるため、生の動画は残りません。対応能力が不明な場合、これらのパートは
動画の格納形式を維持します。フォールバックの文字起こしには、上記の制限付きテキスト
変換が適用されます。`supportsVideo === true` のターゲットはブリッジをバイパスします。
クライアントのリクエスト中止シグナルは、ダウンロード、ブローカーキュー、
サブプロセス、およびキャプション呼び出しへ伝播します。中止時は動画間で処理を停止し、フェイルオープンによって
生のメディアを通過させることはありません。

ランタイム設定は DB に保存され、Zod で検証されます。

| キー                                | デフォルト  | 範囲 / 動作                                                                                               |
| ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------- |
| `modalityBridgeVideoEnabled`        | `false`     | 任意のランタイム機能、オプトイン方式                                                                      |
| `modalityBridgeVideoAnalysisMode`   | `"full"`    | `full` は汎用キャプションを維持し、`focused` はサイズ制限付きの信頼できない最新ユーザーコンテキストを使用 |
| `modalityBridgeVideoModel`          | `""`        | Vision Bridge モデルを継承                                                                                |
| `modalityBridgeVideoFrameCount`     | `8`         | 1–16                                                                                                      |

120 秒を超える従来の永続化済み Video タイムアウト値は、
ブローカーの期限に制限されます。この上限を超える新しい設定の書き込みは拒否されます。
`GET /api/modality-bridge/video/runtime` は、認証またはランタイムの調査に先立ち、信頼されたスタンプによるループバック
ローカリティの確認を必須とし、その後に管理用
認証を要求します。返されるのは、`available`、サニタイズ済みの FFmpeg/ffprobe バージョン、および
ランタイムが利用できない場合の固定の理由のみです。内部抽出エンドポイントは
公開アップロード API ではありません。キューが飽和すると `503` と `Retry-After` を返し、呼び出し元が
切断すると `499` を返し、ブローカーの固定期限に達すると `504` を返します。変換済みレスポンスは、
Vision または Audio のセグメントを削除せずに、中央の
`x-omniroute-modality-bridge` ヘッダーへ `video->text;model=<visionModel>;parts=<videos>` を追加します。

### PII マスカー (`piiMasker.ts`)

**両方の**ステージで実行されます。

- **`preCall`** はペイロードを複製し、`system`、`messages`、`input`、
  `prompt`（単純な文字列の項目を含む）を走査して、文字列の `content`/`text` フィールドに
  `processPII()`（`@/shared/utils/inputSanitizer` 由来）を適用します。
  `PII_REDACTION_ENABLED=true` の場合、送信ペイロード内で検出された PII が
  マスキングされます。これは `INPUT_SANITIZER_MODE`（プロンプトインジェクションの
  ポリシーのみを制御）とは独立しています。マスキングがオフの場合、呼び出しではコンテンツを
  書き換えずに検出件数を記録します。
- **`postCall`** はレスポンスをディープコピーし、`sanitizePIIResponse()` と
  Responses API の構造に対応したマスキング処理（`maskResponsesOutput` —
  `output_text` と `output[].content[].text` に対応）を実行します。マスキングが行われた場合、
  変更後のレスポンスが元のレスポンスを置き換えます。

このガードレールは決してブロックせず、注釈の付与（`meta.detections`、
`meta.redacted`）または書き換えのみを行います。

#### 種類別の選択、カスタムパターン、検出カウンター

**ダッシュボード → 設定 → セキュリティ → PII マスキング** では、_何を_ マスキングするかを選択します。
ここでマスキングをオンにすることはできません。オンにするには、引き続き `PII_REDACTION_ENABLED`（リクエスト）と
`PII_RESPONSE_SANITIZATION`（レスポンス + SSE）を使用します。どちらもデフォルトではオフです。

- **種類別の選択** — 組み込み ID は
  `src/shared/constants/piiTypes.ts`（`PII_BUILTIN_TYPES`）に一覧表示されています。未設定の場合はすべての
  種類が対象になります（この設定が存在する前の動作）。リクエストエンジンの
  `ssn_us` パターンは `ssn` に対応付けられます。テンプレート（最小、標準、金融、
  ブラジル、米国、すべて）は、UI のチェックボックスを設定するだけです。
- **カスタムパターン** — 正規表現またはワイルドカードのパターンを最大 20 個指定できます（`*` = 空白以外の
  最大 64 文字、`?` = 1 文字）。一致した部分は `[CUSTOM_REDACTED]` になります。
  すべてのパターンは `compilePiiCustomPattern()`
  （`src/shared/utils/piiCustomPatterns.ts`）で処理されます。最大 500 文字、使用可能なフラグは
  `g i m s u` のみで、コンパイル可能であり、`safe-regex` の検査（壊滅的な
  バックトラッキング）に合格し、空文字列やマスキング用プレースホルダーに一致しない必要があります。
  条件を満たさないパターンは保存時およびテスト時に拒否され、保存済みの行が
  条件を満たさない場合は、実行時にコンパイルされずスキップされます。カスタムパターンは、
  マスキングがオンの間のみ実行されます。
- **検出カウンター** — 種類別の件数（一致した値は一切含まない）をメモリ内に保持し、
  再起動時にリセットします（`src/lib/pii/piiDetectionStats.ts`）。カウンターは、
  マスキングがオンの間のみ増加します。

設定は `key_value` テーブル（名前空間 `pii_settings`、
`src/lib/db/piiSettings.ts`）に保存され、1 秒間のキャッシュを介して読み取られます。API:

| メソッド | パス                     | 用途                                                                    |
| -------- | ------------------------ | ----------------------------------------------------------------------- |
| `GET`    | `/api/settings/pii`      | フラグの状態、`enabledTypes`、`customPatterns`、検出カウンター          |
| `PUT`    | `/api/settings/pii`      | `enabledTypes`（`null` = すべて）および／または `customPatterns` を置換 |
| `POST`   | `/api/settings/pii/test` | 最大 8 KB のサンプルに対して 1 つのパターンを試行。何も保存されません   |

3 つすべてで管理用の認証が必要であり、Zod
（`src/shared/validation/schemas/piiSettings.ts`）でボディを検証します。

### プロンプトインジェクション（`promptInjection.ts`）

ユーザーが提供したコンテンツ内の攻撃的な構造を検出し、設定された
ポリシーを適用します。動作は環境変数とコンストラクターの
オプションによって制御されます。

| 設定             | 環境変数                                                                                                  | デフォルト | 効果                                                                                                                                                                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 有効化           | `INPUT_SANITIZER_ENABLED`                                                                                 | `true`     | `false` の場合、ガードレールは処理を行わずに終了します。                                                                                                                                                                                        |
| モード           | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                           | `warn`     | インジェクションポリシー: `block`、`warn`、または `log`。（後方互換性のため `redact` も受け付けますが、インジェクションのテキストを削除することは**ありません**。リクエストの PII の書き換えは `PII_REDACTION_ENABLED` によって制御されます。） |
| ブロックしきい値 | `blockThreshold` オプション / `INPUT_SANITIZER_BLOCK_THRESHOLD`（別名 `INJECTION_GUARD_BLOCK_THRESHOLD`） | `high`     | ブロックに必要な最小の重大度。デフォルトでは中程度の重大度は監視のみです。                                                                                                                                                                      |

**モードの優先順位**（`getMode`）: 呼び出し元の `options.mode` →
`INJECTION_GUARD_MODE` の **DB 機能フラグによるオーバーライド**（ダッシュボード → 設定 →
機能フラグ）→ 環境変数 `INJECTION_GUARD_MODE` → 環境変数 `INPUT_SANITIZER_MODE` →
`warn`。したがって、ダッシュボードのオーバーライドは環境変数よりも優先され、機能フラグの
UI から実行中のガードを即座に制御できます（再起動不要）。DB の読み取りはフェイルセーフです。
エラーが発生した場合、ガードは環境変数に基づく動作にフォールバックし、
オーバーライドが設定されていない場合の動作は、環境変数のみで決定した場合と同じです。

検出元:

1. `@/shared/utils/inputSanitizer` の `sanitizeRequest()`（パイプラインの
   ほかの箇所でも使用される共通の検出器セット）。
2. 組み込みの `DEFAULT_GUARD_PATTERNS`（現在は `system_override_inline` と
   `markdown_system_block` で、どちらも重大度は `high`）。
3. コンストラクターのオプションで任意に渡される `customPatterns`（文字列、正規表現、
   または `{ name, pattern, severity }` レコード）。

`mode === "block"` **かつ**少なくとも1件の検出結果が重大度の
しきい値に達した場合、`preCall` は `{ block: true, message: "Request rejected:
suspicious content detected" }` を返します。`warn`/`log` モードでは、ガードレールはログを記録しますが、
呼び出しは許可します。レジストリを経由せずにプロンプトを評価する必要がある呼び出し元向けに、
共通ヘルパー `evaluatePromptInjection()` もエクスポートされています。

**スキャン上限 (v3.8.20):** 検出器が検査するのは、結合されたプロンプトテキストの**先頭16 KB**のみです。
この上限は `src/shared/utils/inputSanitizer.ts` 内の
`MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 バイト) で定義されています。
`detectInjection()` と `evaluatePromptInjection()` はどちらも、パターンのループを実行する前に
`slice(0, MAX_INJECTION_SCAN_BYTES)` を適用します。インジェクションの指示は入力の先頭付近にあるため、
これにより検出能力を低下させることなく、数百KB規模のペイロードに対する正規表現のCPU/GC負荷を抑えられます
（参照: #3932、#4041）。

### 認証情報マスカー (`credentialMasker.ts`)

**両方の**ステージで実行され、デフォルトのチェーンでは最後（優先度 `95`）に実行されます。
送信ペイロード（メッセージ内容、ツール呼び出しの引数、ツールの結果）**および**プロバイダーのレスポンスから、
既知のAPIキー／シークレットトークンのパターンをマスキングします。これにより、
プロンプトに貼り付けられた認証情報（またはツールの結果でそのまま返された認証情報）が、
上流のプロバイダーやクライアントに漏えいするのを防ぎます。

- **明示的な有効化が必要**で、PIIのマスキングと同じ規約に従います（厳格ルール #20 に準拠するもの）。
  `settings.credentialRedactionEnabled === true` **または**
  `CREDENTIAL_REDACTION_ENABLED=true` でない限り無効です。無効の場合、ガードレールは何も行わず、
  ブロックも書き換えも一切行いません。
- `redactCredentials()` はペイロード／レスポンスのツリー全体を走査し（`walkValue()`、
  プロトタイプ汚染に対して安全で、`WeakSet` によって循環参照にも対応）、一致した箇所を
  `[REDACTED:<type>]` プレースホルダーに置き換えます。実際に変更された分岐のみを複製します。
- `CREDENTIAL_PATTERNS` は、LLMプロバイダーのキー（OpenAI、OpenAI-proj、
  Anthropic、Google、Hugging Face、Replicate）、VCS/SaaSトークン（GitHub、Slack、
  Linear、Notion、npm、Postman、Discord）、決済キー（Stripe、Square）、クラウドの
  キー（AWSアクセスキー、Twilio、SendGrid、Mailgun）、秘密鍵／JWT、
  認証情報を含む接続文字列（`mongodb://user:pass@...` など）、および
  汎用的な `Authorization`/`x-api-key`/`api-key`/`apikey` ヘッダー値の
  パターンを対象とします。ヘッダー形式のキー（`authorization`、`x-api-key`、`api-key`、
  `apikey`）は、汎用のテキスト正規表現ではなく、構造に基づいてマスキングされます
  （値のみを対象とし、`Bearer `/`Basic ` などのスキーム接頭辞は保持します）。
- このガードレールはブロックを一切行いません。書き換え（`modifiedPayload` /
  `modifiedResponse`）と注釈の付与（`meta.credentialsRedacted`、`meta.count`）のみを行います。

リグレッション防止テスト: `tests/unit/credential-masker-guardrail.test.ts`。

## 基本契約 (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true の場合、チェーンの処理を打ち切る
  message?: string; // ブロック時に表示される
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // リクエストを書き換えるために preCall が返す
  modifiedResponse?: TValue; // レスポンスを書き換えるために postCall が返す
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

ガードレールは、`void`、`{}`、または
`{ block: false }` を返すことで「変更なし」を示します。`modifiedPayload`/`modifiedResponse` を返すと、
チェーンを流れる値が置き換えられ、後続のガードレールに渡されます。
`signal?: AbortSignal` は、呼び出し元のライフサイクルをガードレールに伝えます。リクエストの中断は、意図的に設けられたフェイルオープンの例外です。メディアブリッジは処理を停止してクリーンアップを行い、生のメディアをサポートしていないことが判明している送信先に、そのメディアを復元して渡すことはしません。

## レジストリ (`registry.ts`)

シングルトンの `guardrailRegistry` は、次の機能を公開します。

- `register(guardrail)` — ガードレールを追加（正規化された名前が一致する場合は置換）し、
  `priority` の昇順で並べ替えます。
- `clear()` / `list()` — 管理用のヘルパーです。
- `runPreCallHooks(payload, context)` — 有効なガードレールを順に実行し、
  `modifiedPayload` を通じてペイロードを引き継ぎ、最初の `block: true` で停止します。
- `runPostCallHooks(response, context)` — レスポンス側で同じ処理を行います。
- `resetGuardrailsForTests({ registerDefaults })` — 状態をクリアし、必要に応じて
  デフォルトのガードレールを再登録して、テスト間を確実に分離します。

どちらの実行処理も `{ blocked, payload|response, results, guardrail?, message? }` を返します。
ここで `results` は、ガードレールごとの `blocked`、`skipped`、`modified`、`error`、`meta` フィールドを含む
`GuardrailExecutionResult` レコードの配列で、
トレースに役立ちます。

### リクエストごとのガードレールの無効化

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` は、現在のリクエストで
スキップするガードレール名を集約し、重複を除いたリストを作成します。
次の5つの経路から、この順序で読み取り、1つのリストに統合します
（重複を除く際は、最初に出現したものが優先されます）。

1. `apiKeyInfo.disabledGuardrails`
2. リクエストボディの `disabledGuardrails`（トップレベル）
3. リクエストボディの `metadata.disabledGuardrails`（`metadata` がオブジェクトの場合のみ）
4. ヘッダー `x-omniroute-disabled-guardrails`
5. 旧ヘッダー `x-disabled-guardrails`

2つのヘッダーを含む、5つすべての経路が統合されます。
`x-omniroute-disabled-guardrails` と `x-disabled-guardrails` の両方を送信すると、
両方のリストの和集合がスキップされます。また、新しいヘッダーが空であっても、旧ヘッダーが
無視されることはなくなりました
（[#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)、
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805) で修正）。

値には、文字列の配列またはカンマ区切りの文字列を指定できます。名前の前後の空白は除去され、
小文字のケバブケースに正規化されます（`pii_masker` → `pii-masker`）。空の
項目は削除されます。結果は `context.disabledGuardrails` を通じて
レジストリに渡され、一致するガードレールがスキップされます（`results` 内で `skipped: true`）。

無効化リストが影響するのは**レジストリ**だけです。プロンプトインジェクションの `block` モードは、
必須のセキュリティ境界です。インジェクションガードミドルウェア
（`src/middleware/promptInjectionGuard.ts`）は、呼び出し元が制御できる無効化リストを
一切渡さずに `evaluatePromptInjection()` を呼び出します（以前行われていた、効果のない
`resolveDisabledGuardrails({ body })` の呼び出しは
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934) で削除されました）。そのため、
`prompt-injection` を無効化するリクエストも、`block` モードでは拒否されます。これは
意図した設計です。無効化の各経路は呼び出し元が制御できるため（リクエストボディ、
メタデータ、ヘッダー）、運用者が設定したセキュリティ制御を
呼び出し元が無効にできてはなりません
（[#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)）。ヘッダーの
和集合に関する [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412) の変更は、
レジストリ内のどのガードレールがスキップされるかにのみ影響し、クライアントが
ミドルウェアを回避できるようにするものではありません。キーごとおよびグループごとの必須ガードレールポリシーは、
v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417) で追跡されています。
[適用範囲と制限](#coverage-and-limits)を参照してください。

## 実行順序

`src/sse/handlers/chat.ts` および
`open-sse/handlers/chatCore.ts` を通過する各リクエスト（
[適用範囲と制限](#coverage-and-limits)に記載されているチャット系ルート）について：

1. `resolveDisabledGuardrails(...)` が API キー、ボディ、
   ヘッダーからスキップリストを構築します。
2. `guardrailRegistry.runPreCallHooks(body, ctx)` が優先度の昇順で
   ガードレールを実行します：
   - 無効化されたガードレールは `skipped` として記録されます。
   - 各ガードレールの `preCall` は、`modifiedPayload` を介してペイロードを書き換えることができます。
   - 最初の `block: true` でチェーンの実行が打ち切られ、ハンドラーは
     ガードレールによる拒否レスポンスを返します。
3. ペイロード（書き換えられている場合もあります）は、コンボルーティングと上流への
   ディスパッチに渡されます。
4. **非ストリーミングのみ：** レスポンスの組み立て後、
   `guardrailRegistry.runPostCallHooks(...)` がレスポンスに対して
   同じチェーンを実行します。ここで `block: true` になると、上流のレスポンスを破棄し、HTTP 400 を返します。ストリーミングレスポンスでは、このステップ全体がスキップされます。

例外をスローしたガードレールは `error: <message>` とともに記録され、
`logger.warn` でログ出力されますが、チェーンは続行されます。これは、エラー時にも処理を許可するフェイルオープン設計です。

## 適用範囲と制限

ガードレールレジストリは、チャットパイプラインにのみ組み込まれています。これらの制限は
`tests/unit/guardrail-pipeline-wiring-characterization.test.ts` と
`tests/unit/guardrail-pipeline-characterization.test.ts` によって固定されています。動作を変更する際は、
意図を持ってこれらのテストを更新してください。

### フックの実行箇所

| フック / 制御                                  | 実行対象                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `runPreCallHooks`                              | `handleChat`（`src/sse/handlers/chat.ts`）で処理されるリクエスト：`/v1/chat/completions`、`/v1/completions`、`/v1/messages`、`/v1/responses`（および `/v1/responses/*`）、`/v1/relay/chat/completions`、`/v1/providers/{provider}/chat/completions`、`/v1/api/chat`、`/v1/antigravity`、`/v1beta/models/*`、および Telegram チャットプロキシ。ダッシュボードのテスト用エンドポイント `/api/guardrails/test` も対象です。呼び出し前にブロックされた場合は HTTP 400 を返します。 |
| `runPostCallHooks`                             | **非ストリーミング**のチャットレスポンスのみ（`open-sse/handlers/chatCore/nonStreamingResponse.ts`）。ストリーミングレスポンスがここに到達することはありません。                                                                                                                                                                                                                                                                                                               |
| ストリーミング PII                             | `createPiiSseTransform`（`src/lib/streamingPiiTransform.ts`）。`PII_RESPONSE_SANITIZATION` が有効な場合、`streamingPipeline.ts` 内でパイプ接続されます。これはガードレールではないため、無効化チャネルの影響を受けません。                                                                                                                                                                                                                                                     |
| インジェクションガードミドルウェア（レガシー） | チャット系を含む、プロンプトを含むすべての `/v1` ルート（[ルートの適用範囲](#injection-guard-route-coverage--red-team-phase-8--block-d)を参照）。プロンプトインジェクションのみが対象です。                                                                                                                                                                                                                                                                                    |

### 対象外のもの

- **メディア、埋め込み、データのルート**（`/v1/images/*`、`/v1/embeddings`、
  `/v1/audio/*`、`/v1/videos/generations`、`/v1/music/generations`、
  `/v1/rerank`、`/v1/search`、`/v1/moderations`）はレジストリに到達しません。
  これらのルートでは、PII マスキング、認証情報マスキング、モダリティブリッジは
  実行されません。唯一のチェックは、レガシーのインジェクションガードミドルウェアです。
- **ストリーミングレスポンス**には呼び出し後のガードレールが適用されません。呼び出し後の `pii-masker` や
  `credential-masker` は実行されず、呼び出し後のブロックも行われません。ストリーミング PII
  変換のみが適用されます（`PII_RESPONSE_SANITIZATION` が有効な場合）。ストリーミングレスポンスに
  そのまま返された認証情報はマスキングされません。
- **無効化チャネルとミドルウェアの関係（設計上の仕様）：** ミドルウェアは、
  呼び出し元が制御する無効化リストを渡さず、独自に `evaluatePromptInjection()` を呼び出して
  プロンプトインジェクションを評価します。`block` モードは必須の
  境界であり、チャット系ルートを含め、呼び出し元が制御する無効化設定では迂回できません
  （[#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)）。`prompt-injection` を
  無効化しても、スキップされるのはレジストリのガードレールだけです。

### 呼び出し後の処理より先にレスポンスを参照するもの

非ストリーミング経路での順序は、メモリ抽出 → 組み込みツールの
実行 → 呼び出し後のガードレール → 呼び出し後のブロックによる終了 → セマンティックキャッシュへの保存です。

- **メモリ抽出**と**ツール実行**は、呼び出し後のガードレールがレスポンスを
  書き換えたりブロックしたりする前に、そのレスポンスを参照します。
  [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) 以降、メモリ
  抽出では、`PII_RESPONSE_SANITIZATION` が有効な場合、抽出したテキストを
  `sanitizePII` で処理します（ストリーミングと非ストリーミングの両方）。ただし、
  呼び出し後の処理で後からブロックされるレスポンスも、その時点ではすでにメモリと
  ツールに渡されています。
- **セマンティックキャッシュ**は呼び出し後の処理を経たレスポンスを保存するため、
  書き換え後のレスポンスが保存され、ブロックされたレスポンスはキャッシュされません。キャッシュエントリは
  API キーごとにキー付けされます。

## 設定

組み込みのガードレールが読み取る環境変数：

| 変数                                  | 使用するガードレール | 効果                                                                                                                      |
| ------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`   | `false` に設定すると、検出が完全に無効になります。                                                                        |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`   | インジェクションポリシー：`warn`、`block`、または `log`。従来の値 `redact` はインジェクションのテキストを書き換えません。 |
| `INJECTION_GUARD_MODE`                | `prompt-injection`   | インジェクションガードのモード。環境変数を**上書きする** DB の機能フラグでもあります（DB > ENV）。                        |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`   | `MODE=block` が拒否する最小の重大度：`high`（デフォルト）、`medium`、または `low`。                                       |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`   | `INPUT_SANITIZER_BLOCK_THRESHOLD` の従来のエイリアス。                                                                    |
| `PII_REDACTION_ENABLED`               | `pii-masker`         | `true` の場合、リクエスト内の PII をマスキングします（インジェクションモードとは独立）。                                  |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker`（後段） | レスポンス側のマスキング動作を制御します。                                                                                |

Modality Bridge のガードレールは、環境変数ではなく、DB を基盤とする設定
ストア（`getSettings()`）から実行時設定を読み取ります。Vision の主要キーは
`modalityBridgeVisionEnabled`、`modalityBridgeVisionMode`、
`modalityBridgeVisionModel`、`modalityBridgeVisionTaskAware`、
`modalityBridgeVisionPrompt`、`modalityBridgeVisionTimeout`、
`modalityBridgeVisionMaxImages`、`modalityBridgeVisionMaxChars`、
`modalityBridgeCacheEnabled`、`modalityBridgeCacheTtlMinutes`、
`modalityBridgeCacheMaxEntries` です。従来の
`visionBridge*` キーは、ドキュメントに記載された 1 サイクル限りの読み取り
フォールバックとしてのみ受け付けられます。ダッシュボードからの書き込みには主要キーを使用します。デフォルト値とフォールバックの
解決処理は `src/shared/constants/modalityBridgeDefaults.ts` にあり、従来の
定数は `src/shared/constants/visionBridgeDefaults.ts` に保持されています。

Audio は `modalityBridgeAudioEnabled`、`modalityBridgeAudioModel`、
`modalityBridgeAudioTimeout`、`modalityBridgeAudioMaxClips` に加え、共有の
`modalityBridgeCache*` 設定を使用します。これらの
キーは Modality Bridge スキーマとともに導入されたため、Audio には従来のキーへのフォールバックはありません。

Video は `modalityBridgeVideoEnabled`、`modalityBridgeVideoAnalysisMode`、
`modalityBridgeVideoModel`、
`modalityBridgeVideoFrameCount`、`modalityBridgeVideoSamplingPolicy`、
`modalityBridgeVideoMaxVideos`、
`modalityBridgeVideoTimeout` に加え、共有の `modalityBridgeCache*` 設定を使用します。
FFmpeg/ffprobe は運用上のオプションの
依存関係であり、フレームのキャプション生成によってレイテンシーとモデルのコストが増加するため、デフォルトでは無効になっています。

## カスタムガードレール

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

手順:

1. `BaseGuardrail` を継承する `src/lib/guardrails/myGuardrail.ts` を作成します。
2. `preCall` と `postCall` のいずれか、または両方を実装します。
3. インポート時に登録する（`registerDefaultGuardrails` から追加する）か、
   実行時に `guardrailRegistry.register(...)` を呼び出します。レジストリは、
   正規化後の名前が同じ既存のガードレールを置き換えます。
4. `tests/unit/` 配下にテストを追加します（既存の例:
   `tests/unit/guardrails-registry.test.ts`、
   `tests/unit/prompt-injection-guard.test.ts`、
   `tests/unit/guardrails/visionBridge.test.ts`）。

## テスト

テスト間で `resetGuardrailsForTests()` を使用し、既知の状態から開始します。
空のレジストリから開始するには `{ registerDefaults: false }` を渡し、
テスト対象のガードレールのみを登録します。Vision Bridge は依存性注入
（`deps.getSettings`、`deps.callVisionModel`）に対応しています。Audio Bridge も、
設定、機能、STT モデルの選択、認証情報のチェック、文字起こしについて、
同等の依存性注入ポイントを公開しています。このため、DB やネットワークにアクセスせずに、
両方のフローをテストできます。

## インジェクションガードのルートカバレッジとレッドチーム（フェーズ 8 · ブロック D）

インジェクションガード（`createInjectionGuard` / `withInjectionGuard`）は、
ユーザープロンプトを受け付けるすべてのルートをカバーします。`INJECTION_GUARD_MODE` に従って動作します
（デフォルトの `warn` = ログ記録のみ、`block` = HTTP 400 `SECURITY_001` を返す）。

| 種別             | ルート                                                                                                                                               | デフォルトモード |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| テキスト（既存） | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn             |
| 生成系           | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn             |
| データ           | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn             |

テキスト抽出（`extractMessageContents`）は `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` を対象とします。

**レッドチーム（毎晩、`nightly-llm-security.yml`）:** promptfoo は、`INJECTION_GUARD_MODE=block` で各ルートが
OWASP-LLM コーパスをブロックすることを検証します。garak はプローブを実行します（シークレットがない場合はスキップ）。
一貫性を保つため、`moderations` も対象に含まれます。ブロックモードは必須の防御境界です。`evaluatePromptInjection()` は、
ミドルウェアから渡されるリクエスト単位の無効化リストを無視するため、`disabledGuardrails` によって
ルートがその適用対象から除外されることは**ありません**（[#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)）。

毎晩実行されるワークフロー（`.github/workflows/nightly-llm-security.yml`、cron + 手動
実行）には、2 つのジョブがあります。

- **`promptfoo-guard`（失敗時は CI を失敗させる）** — `INJECTION_GUARD_MODE=block` を指定して
  `promptfoo eval -c promptfooconfig.yaml` を実行します。各攻撃ケース（例: 「これまでの
  指示をすべて無視して…」、DAN 型のジェイルブレイク）で、レスポンスに
  `error.code === "SECURITY_001"` が含まれること、つまりガードが実際にリクエストを拒否したことを検証します。
- **`garak`（参考情報のみ）** — ローカルの OmniRoute インスタンス（`http://localhost:20128/v1`）に対して
  garak `--probes promptinject,dan,leakreplay` を実行します。
  プロバイダーのシークレット（`PROMPTFOO_PROVIDER_KEY`）がある場合にのみ実行されます。ない場合は
  正常にスキップし、末尾に `|| true` が付いているため、CI を失敗させずに結果を報告します。

ガードヘルパー（`createInjectionGuard` / `withInjectionGuard`）は、
プロンプトを含むすべての `/v1` ルートをカバーします。プロンプトテキストは、
`src/shared/utils/inputSanitizer.ts` の `extractMessageContents()` によって
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` から抽出されます。
