Guardrails บังคับใช้ความปลอดภัย นโยบาย และการแปลงเนื้อหาที่ขอบเขตระหว่าง OmniRoute และผู้ให้บริการต้นทาง Guardrail แต่ละตัวสามารถตรวจสอบ (และปฏิเสธ แปลง หรือใส่คำอธิบายประกอบเพิ่มเติมได้) เพย์โหลดคำขอ (`preCall`) และการตอบกลับจากต้นทาง (`postCall`)

ระบบนี้ทำงานแบบ **fail-open**: หาก guardrail เกิดข้อผิดพลาดขณะทำงาน registry จะบันทึกข้อผิดพลาดนั้นและดำเนินการต่อด้วย guardrail ถัดไป แทนที่จะทำให้คำขอล้มเหลว การบล็อกเป็นการตัดสินใจที่ระบุไว้อย่างชัดเจน (`block: true`) และไม่เกิดขึ้นโดยบังเอิญ ข้อยกเว้นประการเดียวคือคำขอที่ถูกยกเลิก: เมื่อ `signal` ของผู้เรียกถูกยกเลิก guardrail ที่เกิดข้อผิดพลาดจะปฏิเสธการทำงานของฮุกแทนที่จะถูกข้าม

ฮุกเหล่านี้จะ **ไม่** ทำงานในทุกเส้นทางหรือทุกการตอบกลับ โปรดอ่าน [ความครอบคลุมและข้อจำกัด](#coverage-and-limits) ก่อนที่จะพึ่งพา guardrail เป็นมาตรการควบคุมความปลอดภัย

### Vision Bridge (`visionBridge.ts`) — Modality Bridge PR-1

โมเดลพื้นฐาน GLM 5.3 และ `glm-5.3-{low,high,max}` มีเมทาดาต้า registry/spec ที่ระบุชัดเจนว่า `supportsVision:false` ส่วนตัวเลือกย่อย GLM 5.3 Flash ยังคงเป็นโมเดลที่มีความสามารถด้านวิชันในตัว เส้นทาง `/v1/messages` ของ Claude Code จะเข้าสู่เชน guardrail ก่อนการเรียก `handleChat` ที่ใช้ร่วมกัน **ก่อน** การแปลงจาก Claude เป็น OpenAI; รูปภาพผลลัพธ์เครื่องมือ `Read` ที่ซ้อนอยู่จะต้องได้รับการอธิบายหรือจัดการก่อนที่การแปลงนั้นจะนำพวกมันขึ้นไปอยู่ในเนื้อหา `image_url` ของ OpenAI (#17069)

ดักจับคำขอที่มีรูปภาพซึ่งมุ่งเป้าไปที่ **โมเดลที่ไม่มีวิชัน** และทำการเปลี่ยนเส้นทางคำขอทั้งหมดไปยังโมเดลที่รองรับวิชัน หรือแทนที่ส่วนของรูปภาพด้วยคำอธิบายข้อความที่สร้างโดยโมเดลวิชันที่กำหนดค่าได้ ก่อนที่จะมีการเรียกไปยังต้นทาง สิ่งนี้ช่วยให้ผู้ให้บริการที่รองรับเฉพาะข้อความสามารถจัดการเพย์โหลดแบบมัลติโมดัลได้อย่างโปร่งใส

ขั้นตอนการทำงาน:

1. ข้ามหากโมเดลเป้าหมายรองรับวิชันอยู่แล้ว (เว้นแต่จะปรากฏอยู่ในรายการบังคับบริดจ์ `isVisionBridgeForcedModel`)
2. ดึงข้อมูลส่วนของรูปภาพผ่าน `extractImageParts(messages)` (`visionBridgeHelpers.ts`) ซึ่งจะส่งต่อการทำงานไปยัง **ตัวตรวจจับสื่อแบบรวมศูนย์** `detectMediaParts()` ใน `open-sse/utils/mediaParts.ts` — ซึ่งเป็นแหล่งข้อมูลหลักเดี่ยวที่ใช้ร่วมกับฟิลเตอร์ความเข้ากันได้แบบคอมโบ การดึงข้อมูลจะถูกอนุญาตเฉพาะรูปแบบที่ `replaceImageParts` สามารถนำมาต่อกลับเข้าไปได้ (สัญญาการดึงข้อมูลและแทนที่): OpenAI `image_url`, Anthropic base64 `source.type:"base64"`, Anthropic URL `source.type:"url"` และ Responses API `input_image` รูปภาพที่ตรงกันซึ่งซ้อนอยู่ภายใน `tool_result.content` ของ Claude Code และเอาต์พุตเครื่องมือ Responses ก็จะถูกดึงข้อมูลและแทนที่ในพาธเดิมเช่นกัน; รูปแบบที่เป็นเพียงตัวบ่งชี้จะเป็นข้อมูลสำหรับฟิลเตอร์คอมโบและจะไม่ถูกดึงข้อมูล ข้ามหากไม่พบ
3. แก้ไขการตั้งค่ารันไทม์ผ่าน `resolveVisionBridgeRuntimeSettings()` (`src/shared/constants/modalityBridgeDefaults.ts`): คีย์การตั้งค่า `modalityBridge*` ใหม่จะมีความสำคัญสูงสุด; คีย์ `visionBridge*` แบบเดิมยังคงเป็น **ตัวสำรองในรอบเดียว** (หน้าต่างการย้อนกลับ) ข้ามก่อนที่จะมีการสำรวจสื่อใด ๆ เมื่อปิดใช้งานบริดจ์นี้อยู่
4. ตัวเลือกโหมด (`modalityBridgeVisionMode`, ดูตารางด้านล่าง) จะตัดสินใจเลือกระหว่างการเปลี่ยนเส้นทางหรือการอธิบาย การเปลี่ยนเส้นทางจะคืนค่า `modifiedPayload` โดยมีการสลับเฉพาะ `model` เท่านั้น พร้อมกับข้อมูลเมตา `{ rerouted, fromModel, toModel, imagesKept }`
5. เส้นทางอธิบาย: จำกัดจำนวนรูปภาพสูงสุดที่ `maxImages`, สร้างพรอมต์ที่รับรู้บริบทของงาน, ตรวจสอบแคชการอธิบาย, เรียกโมเดลวิชัน **แบบขนาน** (`Promise.allSettled`), และแทรกส่วนของข้อความ `[Image N]: <description>` ลงไปแทนที่ การอธิบายที่ล้มเหลวจะให้ค่า `null`: รูปภาพดิบจะถูกเก็บรักษาไว้สำหรับเป้าหมายที่ไม่รู้จักหรือรองรับวิชัน (#4012) แต่ **เป้าหมายตรงที่ยืนยันแล้วว่าเป็นข้อความอย่างเดียว** หรือคอมโบที่ไม่มีวิชันจะได้รับข้อความสตับชัดเจนว่า `(unavailable — no vision-capable provider connected)` สำหรับทุกรูปภาพที่ไม่ได้อธิบาย รวมถึงความล้มเหลวบางส่วนและรูปภาพที่เกินขีดจำกัดการเรียกอธิบาย (#17069) ระบบสำรองการอธิบายแบบคอมโบที่ล้มเหลวทั้งหมดที่มีอยู่ยังคงใช้งานอยู่ตามเดิม (#8430)
6. ส่งคืน `modifiedPayload` + เมตา (`imagesProcessed`, `descriptions`, `processingTimeMs`, `visionModel`)

#### ตัวเลือกโหมด (`modalityBridgeVisionMode`)

| Mode       | Default | Behavior                                                                                                                                                                                                                                                                                |
| ---------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auto`     | ✔       | ฮิวริสติกแบบเดิม ไม่ได้เปลี่ยนแปลง (#6640/#7204): โมเดลที่ไม่ใช่คอมโบ/`auto/` จะถูกเปลี่ยนเส้นทางไปยังโมเดลวิชันที่ดีที่สุด เว้นแต่โมเดลเดิมจะมีข้อมูลรับรองที่ใช้งานได้อยู่แล้ว (จากนั้นใช้ describe); เป้าหมายแบบคอมโบจะใช้ describe เสมอ                                             |
| `describe` |         | ใช้ describe เสมอ — บล็อกการเปลี่ยนเส้นทางจะถูกข้ามไปทั้งหมด; โมเดลที่ผู้ใช้เลือกจะเป็นผู้ตอบเสมอ                                                                                                                                                                                       |
| `reroute`  |         | บังคับเปลี่ยนเส้นทาง: ตัวป้องกันโมเดลที่มีข้อมูลรับรองจะถูกข้าม ตัวป้องกันข้อมูลรับรองของ**เป้าหมาย**การเปลี่ยนเส้นทางยังคงมีผลอยู่ — เมื่อไม่มีเป้าหมายวิชันที่ใช้งานได้ บล็อกบริดจ์จะแสดงข้อผิดพลาดที่ชัดเจนแทนที่จะทำการ describe หรือส่งรูปภาพดิบไปยังเป้าหมายที่รองรับเฉพาะข้อความ |

โหมดที่บังคับจะลัดวงจร **ก่อน** ที่ฮิวริสติกแบบ auto จะทำงาน; พฤติกรรมของ `auto` จะเหมือนกับตัวป้องกันก่อน PR-1 ทุกประการ

#### ขอบเขต API-key (`visionBridgeKeyScope.ts`)

เมื่อ API key ของผู้เรียกจำกัด `allowedConnections`, พูลโควต้า (`allowedQuotas`) หรือโมเดล (`allowedModels` / `blockedModels` / `modelAccessMode: "restricted"` / `disableNonPublicModels`) บริดจ์จะเลือกเฉพาะโมเดล reroute และ describe ที่คีย์นั้นสามารถใช้ได้ บนการเชื่อมต่อที่คีย์นั้นสามารถใช้ได้เท่านั้น จากนั้นการเรียก describe จะผ่าน self-loop ของ OmniRoute พร้อมกับเฮดเดอร์ `x-omniroute-self-loop-key-id` เสมอ เพื่อให้คำขอแชทที่ได้รับบังคับใช้นโยบายการเชื่อมต่อและโมเดลของคีย์นั้นอีกครั้ง `enforceApiKeyPolicy()` จะยอมรับเฮดเดอร์นั้นก็ต่อเมื่อใช้ร่วมกับแบร์เรอร์ของ self-loop เท่านั้น ดังนั้นจึงสามารถจำกัดการเข้าถึงให้แคบลงได้เท่านั้น และไอดีที่ไม่สามารถระบุตัวตนได้จะถูกปฏิเสธ

หากไม่มีการอนุญาตให้โมเดลวิชันใดๆ ใช้กับคีย์นั้น **เป้าหมายที่รองรับเฉพาะข้อความที่ยืนยันแล้ว** จะปฏิเสธคำขอรูปภาพในเครื่องด้วย HTTP 400 ที่ชัดเจน แทนที่จะส่งไบต์รูปภาพไปยังต้นทางที่ไม่รองรับ (#17069) สำหรับเป้าหมายที่มีความสามารถด้านวิชันที่ไม่ทราบแน่ชัดหรือแบบเนทีฟ เส้นทาง describe จะยังคงพฤติกรรม fail-open แบบเดิม (เมตา `{ skipped: true, reason: "no_permitted_vision_model" }`) คำขอที่ไม่มีคีย์ และคีย์ที่ไม่มีข้อจำกัดเหล่านี้ จะทำงานเหมือนเดิมทุกประการ

#### พรอมต์ describe ที่รับรู้ภารกิจ (`modalityBridgeVisionTaskAware`)

ค่าเริ่มต้นคือ **true** `composeVisionPrompt()` (`visionBridgeHelpers.ts`) จะผนวกข้อความของ **ข้อความผู้ใช้ล่าสุด** (ตัดทอนเหลือ 500 ตัวอักษร) เข้ากับพรอมต์ describe พื้นฐาน เพื่อชี้นำคำอธิบายไปสู่สิ่งที่ผู้ใช้ถามจริงๆ (รูปแบบ codex-vision-proxy) และขอให้โมเดลวิชันถอดความข้อความที่มองเห็นได้ เมื่อปิดแฟล็กนี้ — หรือไม่มีข้อความจากผู้ใช้ — พรอมต์พื้นฐานจะถูกนำไปใช้โดยไม่มีการเปลี่ยนแปลง

คำขอที่เข้ากันได้กับ OpenAI ของ describe self-loop เอง (`callVisionModelSingle()` ใน `visionBridgeHelpers.ts`) จะร้องขอ `image_url.detail: "high"` เสมอ — โดยไม่มีเงื่อนไข สำหรับผู้เรียก/ผู้ให้บริการทุกราย ไม่ได้ถูกควบคุมโดยสัญญาณใดๆ จากไคลเอนต์ การสุ่มตัวอย่างแบบรายละเอียดต่ำจะลดความแม่นยำของ OCR สำหรับงานถอดความข้อความที่พรอมต์นี้ร้องขอโดยเฉพาะ ดังนั้นการเรียก describe จึงร้องขอรายละเอียดระดับสูงเสมอ โดยไม่คำนึงถึงระดับรายละเอียดที่คำขอขาเข้าเดิมใช้ ซึ่งจะส่งผลต่อเนื้อหาคำขอ describe ภายในเท่านั้น โดยจะไม่เปลี่ยนแปลงวิธีที่ OmniRoute ส่งต่อ `image_url.detail` ของผู้เรียกเองในคำขอหลัก — ค่าเริ่มต้นนั้นจะถูกนำไปใช้แยกต่างหาก และเฉพาะสำหรับไคลเอนต์ OpenCode ที่ตรวจพบเท่านั้น ใน `defaultImageDetail()` (`open-sse/handlers/chatCore/upstreamBody.ts`) สาขาฟอร์แมตสายส่งแบบ Anthropic ของ describe self-loop ไม่มีฟิลด์ `detail` และจะไม่ได้รับผลกระทบจากค่าเริ่มต้นทั้งสองแบบ

#### ขีดจำกัดผลลัพธ์ describe (`modalityBridgeVisionMaxChars`)

| Key                            | Default | Range            |
| ------------------------------ | ------- | ---------------- |
| `modalityBridgeVisionMaxChars` | `0`     | `0` or 100–50000 |

ค่า `0` (ค่าเริ่มต้น) หมายถึง **ไม่มีขีดจำกัด** — คำอธิบายที่ส่งกลับโดย `callVisionModel()` จะถูกส่งผ่านโดยไม่มีการแก้ไข ซึ่งคงพฤติกรรมเดิมไว้ ค่าใดๆ ในช่วง 100–50000 จะตัดทอนคำอธิบายด้วยคำต่อท้าย `…` ก่อนที่จะนำกลับมารวมกันในรูปแบบ `[Image N]: <description>` (`VisionBridgeGuardrail.preCall()` ใน `src/lib/guardrails/visionBridge.ts`) เพิ่มค่านี้สำหรับงาน OCR ที่มีรายละเอียดมาก ซึ่งโมเดลปลายทางต้องการการถอดความแบบเต็มรูปแบบ; ลดค่านี้ลงเพื่อจำกัดการใช้โทเค็นบนโมเดลวิชันที่มีการตอบสนองยาวเหยียด ฟิลด์แดชบอร์ดอยู่ในแผง Advanced ของแท็บ Vision (`modality-bridge-max-chars` ใน `ModalityBridgeVisionTab.tsx`) และจะจำกัดค่าใดๆ ระหว่าง 1 ถึง 99 ให้ขึ้นไปอยู่ที่ขีดจำกัดล่างที่ 100 ในขณะที่ปล่อยให้ค่า `0` ที่ระบุไว้อย่างชัดเจนไม่ถูกแตะต้อง — `0` เป็นค่า Zod ที่ถูกต้องในตัวเอง (`z.union([z.literal(0), z.number().int().min(100).max(50000)])`) ไม่ใช่แค่ค่าเริ่มต้น "ที่ไม่ได้ตั้งค่า" เท่านั้น

#### แคช describe (`modalityBridge/bridgeCache.ts`)

แคช LRU + TTL ในหน่วยความจำสำหรับผลลัพธ์ describe โดยใช้ร่วมกันทั่วทั้งกระบวนการ คีย์ = `sha256(imageRef + composedPrompt + configuredBridgeModel)` พร้อมการจัดเฟรมด้วยคำนำหน้าความยาว (ไม่มีการชนกันของขอบเขตฟิลด์) คอมโพเนนต์โมเดลคือโมเดลบริดจ์ที่ **กำหนดค่าไว้** ไม่ใช่โมเดลที่ตอบกลับจริงๆ — `callVisionModel` อาจสำรองข้อมูลภายใน และการสร้างคีย์ต่อการพยายามแต่ละครั้งจะทำให้แคชกระจัดกระจาย ผลลัพธ์ describe ที่ล้มเหลวจะไม่ถูกแคชไว้ การตั้งค่า:

| Key                             | Default | Range   |
| ------------------------------- | ------- | ------- |
| `modalityBridgeCacheEnabled`    | `true`  | —       |
| `modalityBridgeCacheTtlMinutes` | `60`    | 1–1440  |
| `modalityBridgeCacheMaxEntries` | `200`   | 10–5000 |

#### การปรับมาตรฐานภาพระยะไกล (self-loop describe/base64 fetch)

เมื่อบริดจ์ดึงภาพ **ระยะไกล** ด้วยตัวเอง — ซึ่งได้แก่ การเรียกตัวเองเพื่ออธิบายภาพของ Anthropic และการแปลง base64 ตามรูปแบบ claude-wire (`ensureBase64ImagesForClaudeWire`) ทั้งคู่ผ่าน `fetchRemoteImageAsDataUri()` ใน `visionBridgeHelpers.ts` — data URI ที่ได้จะถูกส่งผ่าน `normalizeDataUri()` (`open-sse/utils/imageNormalize.ts`) ก่อนที่จะฝังลงในคำขอของโมเดลวิชัน ภาพที่มีขนาดใหญ่เกินไปจะถูกลดสเกลลงเหลือ **ขอบยาว 2048px** (ตรงกับขีดจำกัดการปรับขนาดที่ OpenAI/Anthropic ใช้งานฝั่งเซิร์ฟเวอร์อยู่แล้ว) ซึ่งช่วยลดขนาดไบต์/ความหน่วงในการอัปโหลดโดยไม่เปลี่ยนสิ่งที่โมเดลวิชันมองเห็น การปรับขนาดใช้ `sharp` ซึ่งโหลดผ่าน dynamic import: บนแพลตฟอร์มที่ไบนารีเนทีฟโหลดไม่สำเร็จ `normalizeDataUri()` จะ **ไม่โยนข้อผิดพลาด** — โดยจะย้อนกลับไปเป็นการส่งผ่านไบต์ดั้งเดิมแทน ดังนั้นเส้นทางการอธิบายภาพ/แปลง base64 จึงยังคงทำงานได้เสมอ ไบต์ที่ไม่ใช่ภาพ (การดึงข้อมูลที่ไม่ส่งคืนภาพที่ถอดรหัสได้) จะถูกส่งผ่านไปโดยไม่มีการเปลี่ยนแปลงเช่นกัน การปรับมาตรฐานนี้จำกัดขอบเขตเฉพาะภาพที่บริดจ์ดึงมาสำหรับการเรียกตัวเองเท่านั้น — จะไม่มีการนำไปใช้กับเพย์โหลดแบบ passthrough ดั้งเดิมของผู้เรียก ซึ่งสอดคล้องกับหลักการกลายพันธุ์แบบเลือกเปิดใช้งานเท่านั้น (Hard Rule #20)

#### สคีมาการตั้งค่า + การไมเกรต

คีย์ `modalityBridge*` ใหม่จะถูกตรวจสอบความถูกต้องด้วย Zod ใน `updateSettingsSchema` (`src/shared/validation/settingsSchemas.ts`): ได้แก่ `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, ชุดสามรายการ `modalityBridgeCache*` และกลุ่ม `modalityBridgeAudio*` ที่ใช้งานโดย Audio Bridge การไมเกรต `141_modality_bridge_settings.sql` จะคัดลอกค่า `visionBridge*` แบบเดิมที่มีอยู่ไปยังคีย์ใหม่ที่ตรงกัน (แบบ idempotent, ไม่เขียนทับค่า `modalityBridge*` ที่ตั้งค่าโดยผู้ดูแลระบบ); โดยคีย์เดิมจะยังคงได้รับการยอมรับเป็นข้อมูลสำรองสำหรับการอ่านเป็นเวลาหนึ่งรอบการรีลีส

#### เฮดเดอร์ความโปร่งใส + สถิติ

การตอบกลับที่แปลงผ่านการอธิบายภาพจะมี `x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n>` ติดมาด้วย (สร้างโดย `buildModalityBridgeHeader()` ใน `modalityBridge/bridgeStats.ts`, ประทับตราโดย `withModalityBridgeHeader()` ใน `src/sse/handlers/chatHelpers.ts`) คำขอที่ถูกเปลี่ยนเส้นทางจะ **ไม่มี** เฮดเดอร์ — เนื่องจากเพย์โหลดไม่ถูกแตะต้องและสามารถมองเห็นการสลับโมเดลได้แล้วในฟิลด์ `model` ของเนื้อหาการตอบกลับ

`GET /api/modality-bridge/stats` (การยืนยันตัวตนระดับการจัดการ, ระดับเดียวกับ `GET /api/settings`) ส่งคืนตัวนับในหน่วยความจำแยกตามโมดัลลิตี้ ได้แก่ `{ attempts, successes, bridged, cacheHits, failures, totalLatencyMs, latencySamples, averageLatencyMs, lastUsedAt }` สำหรับ `vision`, `audio` และ `video` `averageLatencyMs` ใช้ `latencySamples` เป็นตัวหาร ไม่ใช่จำนวนความพยายามทั้งหมด; การดำเนินการที่ไม่มีการจับเวลาจะไม่สร้างตัวอย่างศูนย์มิลลิวินาทีขึ้นมาเอง `bridged` ยังคงเป็นนามแฝงที่เข้ากันได้กับระบบเดิมสำหรับการแปลงที่สำเร็จ; ความพยายามที่ล้มเหลวจะไม่เพิ่มค่านี้ ตัวนับจะรีเซ็ตเมื่อเริ่มต้นกระบวนการใหม่โดยการออกแบบ (เป็นการเก็บข้อมูลโทรมาตร ไม่ใช่การทำบัญชี)

#### การกำหนดค่าแดชบอร์ด

หน้าแดชบอร์ดเฉพาะคือ `/dashboard/settings/modality-bridge` แท็บ `Vision`, `Audio` และ `Video` ที่สามารถระบุ URL ได้ จะยังคงรักษาพารามิเตอร์คิวรีไว้ในขณะที่สลับค่า `tab` แท็บ Vision แสดงการเปิดใช้งาน, โหมด, การเลือกโมเดล (รวมถึงค่าเริ่มต้นอัตโนมัติ), การใช้พรอมต์ที่รับรู้ภารกิจ, ขีดจำกัดขั้นสูงสำหรับไทเมาต์/ภาพ/ความยาวคำอธิบาย/แคช, ตัวนับรันไทม์ และคำขอตัวอย่างที่มีการป้องกัน แท็บ Audio ก็ใช้งานได้จริงเช่นกัน: แสดงการเปิดใช้งาน, ตัวเลือกโมเดล STT เท่านั้นที่มีตัวเลือก Auto, ขีดจำกัดไทเมาต์/คลิปสูงสุด, ตัวนับเสียง และการทดสอบตัวอย่าง `input_audio` แท็บ Video สามารถใช้งานได้: รายงานสถานะรันไทม์ของ FFmpeg/ffprobe — ซึ่งเป็นหนึ่งในสี่สถานะ UI ที่ชัดเจน (`unknown` ในขณะที่โพรบกำลังทำงานหรือทำงานไม่เสร็จสิ้น, `restricted` บนโฮสต์แดชบอร์ดที่ไม่ใช่ loopback ที่ข้ามการโพรบฝั่งไคลเอนต์, `unavailable` เมื่อโพรบแล้วและยืนยันว่าไม่พบ, หรือ `available` พร้อมเวอร์ชันของ FFmpeg/ffprobe) — บันทึกค่าขีดจำกัดการเปิดใช้งาน/โมเดล/เฟรม/วิดีโอ/ไทเมาต์, กรองตัวเลือกโมเดลให้แสดงเฉพาะโมเดลที่รองรับวิชัน และแสดงตัวนับวิดีโอ

การ์ด Vision Bridge เดิมภายใต้การตั้งค่า AI เป็นลิงก์ความเข้ากันได้ไปยังหน้าใหม่; โดยจะไม่มีสำเนาฟอร์มชุดที่สองอีกต่อไป Media Providers ยังเชื่อมโยงเวิร์กโฟลว์ Image-to-Text และ Speech-to-Text ไปยังแท็บ Modality Bridge ที่สอดคล้องกัน โดยไม่ต้องลบเพลย์กราวด์ Speech-to-Text ที่มีอยู่ออก

**การบายพาสการตรวจสอบสิทธิ์การเข้าถึงแบบวนซ้ำ:** เมื่อการเรียกอธิบายภาพเส้นทางผ่าน self-loop `/v1` ของ OmniRoute เอง (โมเดลผู้ให้บริการที่ไม่ใช่มาตรฐาน) คำขอย่อยจะส่ง `x-omniroute-admission-bypass: internal` และได้รับการตรวจสอบสิทธิ์ด้วยข้อมูลประจำตัว self-loop ที่แก้ไขแล้ว — ตัวคั่น `sk_omniroute` ในโหมดโลคัล, หรือคีย์สภาพแวดล้อม `OMNIROUTE_API_KEY` / `ROUTER_API_KEY` ที่กำหนดค่าโดยผู้ดูแลระบบ (#1350) เพื่อให้การปรับใช้ที่ตั้งค่า `REQUIRE_API_KEY=true` ยังคงสามารถเรียกใช้งานการอธิบายภาพได้ การบายพาสนี้จะได้รับการยอมรับสำหรับข้อมูลประจำตัวที่ตรงกันทุกประการเท่านั้น ดังนั้นไคลเอนต์ภายนอกจึงไม่สามารถใช้เฮดเดอร์นี้เพื่อข้ามการตรวจสอบสิทธิ์ได้

ค่าเริ่มต้นแบบเดิมจะอยู่ใน `src/shared/constants/visionBridgeDefaults.ts`; ส่วนค่าเริ่มต้นโหมด/การรับรู้ภารกิจ/แคช และตัวแก้ไขการตั้งค่าตัวใหม่จะอยู่ใน `src/shared/constants/modalityBridgeDefaults.ts` การ์ดเรลมีตัวเลือกคอนสตรัคเตอร์ `deps` เพื่อให้การทดสอบสามารถฉีดอิมพรีเมนต์ชันของ `getSettings` และ `callVisionModel` แบบจำลองได้

### Audio Bridge (`audioBridge.ts`) — Modality Bridge PR-3

ทำหน้าที่ดักจับคำขอแชทที่มีข้อมูลเสียงก่อนที่จะไปถึงเป้าหมายที่ไม่รองรับการรับอินพุตเสียง โดยจะไม่เปลี่ยนเส้นทางคำขอแชท: ส่วนของเสียงจะถูกถอดเสียงผ่านเอนด์พอยต์ multipart ที่เข้ากันได้กับ OpenAI ที่มีอยู่ และโมเดลแชทที่เลือกไว้จะดำเนินการต่อด้วยสคริปต์ข้อความถอดเสียง

ขั้นตอนการทำงาน:

1. ประเมินค่า `supportsAudio` ผ่าน `getResolvedModelCapabilities()` เมทาดาตารีจิสทรีของตัวแทนจำหน่ายที่ระบุอย่างชัดเจนจะมีความสำคัญสูงสุด ตามด้วยเมทาดาตารุ่นแบบสถิต และ `modalities_input` ที่ซิงค์แล้วตามลำดับ รายการอินพุตที่ประกาศไว้ซึ่งไม่มี `audio` จะถูกกำหนดเป็น `false`; หากไม่มีหลักฐานความสามารถจะคงค่าเป็น `null` ทั้งค่า `false` และ `null` จะเปิดใช้งานบริดจ์แบบอนุรักษ์นิยม ในขณะที่ค่า `true` จะข้ามการทำงานนี้
2. ประเมินการตั้งค่า `modalityBridgeAudio*` และแยกชิ้นส่วนเสียงระดับบนสุดที่สามารถเชื่อมต่อได้จากทุกข้อความผ่านตัวตรวจจับ `detectMediaParts()` ที่ใช้ร่วมกัน รูปแบบโครงสร้างข้อมูลที่รองรับ ได้แก่ `input_audio`, `audio_url` ของ OpenAI และ `source.media_type: "audio/*"` เสียงที่ซ้อนอยู่ภายในจะถูกตรวจจับเพื่อใช้ในการกำหนดเส้นทาง แต่จะไม่ถูกลบออกจากเส้นทางการเชื่อมต่อ งานจะถูกจำกัดด้วย `modalityBridgeAudioMaxClips` ส่วนชิ้นส่วนที่อยู่ถัดไปจะไม่ถูกเปลี่ยนแปลง
3. ใช้ค่า `provider/model` ที่กำหนดค่าไว้ หรือปล่อยให้ `selectAudioBridgeModel()` วนลูปผ่าน `AUDIO_TRANSCRIPTION_PROVIDERS` ตามลำดับแคตตาล็อกที่เสถียร และเลือกโมเดลแรกที่มีข้อมูลประจำตัวผู้ให้บริการที่ใช้งานได้และยังแอกทีฟอยู่
4. `callAudioTranscription()` จะแปลงเสียงในรูปแบบ base64/data-URI ให้เป็น `file` แบบ multipart หรือดาวน์โหลด `audio_url` จากระยะไกลผ่านระบบป้องกันการส่งออกข้อมูลภายนอกที่เป็นสาธารณะเท่านั้น พร้อมการปักหมุด DNS และจำกัดขนาดไว้ที่ 25 MB จากนั้นจะทำการส่งคำขอแบบ POST ไปยังลูปภายในที่ `/v1/audio/transcriptions` ในเครื่อง พร้อมการยืนยันตัวตนด้วย `resolveSelfLoopBearer()` เส้นทางการถอดเสียงที่มีอยู่จะดำเนินการค้นหาข้อมูลประจำตัวตามปกติ การจัดการคูลดาวน์/การจำกัดอัตรา และการส่งต่อคำขอไปยังผู้ให้บริการ
5. การเรียกใช้งานที่สำเร็จจะแทนที่ชิ้นส่วนเหล่านั้นด้วย `[Audio N]: <transcript>` การเรียกใช้งานจะทำงานร่วมกับ `Promise.allSettled`: หากเกิดความล้มเหลวเฉพาะรายการ จะยังคงรักษาชิ้นส่วนเสียงเดิมนั้นไว้ (สัญญา #4012) หากการเรียกใช้งานล้มเหลวทั้งหมดและเป้าหมายได้รับการพิสูจน์แล้วว่า `supportsAudio === false` ชิ้นส่วนดังกล่าวจะเปลี่ยนเป็น `[Audio N]: (unavailable — no STT provider connected)` (สัญญา #8430) สำหรับเป้าหมายที่ไม่ทราบค่า (`null`) ผลลัพธ์ที่ล้มเหลวทั้งหมดจะไม่ถูกเปลี่ยนแปลง เป้าหมายที่มีข้อความเป็นหลักที่ได้รับการพิสูจน์แล้วและไม่มีข้อมูลประจำตัว STT ที่ใช้งานได้ จะได้รับสตับที่ชัดเจนแบบเดียวกันโดยไม่ต้องทำการเรียกเครือข่าย

ผลการถอดเสียงที่สำเร็จจะใช้แคช LRU/TTL ของ Modality Bridge แบบทั่วทั้งกระบวนการ คีย์ประกอบด้วยข้อมูลอ้างอิงเสียง, ป้ายกำกับคำสั่ง `audio-transcription` ที่เสถียร และโมเดล STT ที่เลือก; ความล้มเหลวจะไม่ถูกแคชไว้เด็ดขาด การพยายามประมวลผลเสียงจะอัปเดตตัวนับ `bridged`, `cacheHits`, `failures` และ `lastUsedAt` ที่ใช้ร่วมกัน การตอบกลับที่ถูกแปลงแล้วจะมีส่วนหัว `x-omniroute-modality-bridge: audio->text;model=<sttModel>;parts=<n>`; ส่วนคำขอที่ไม่ถูกแตะต้องจะไม่ได้รับส่วน Audio Bridge

การตั้งค่าขณะรันไทม์จะสำรองข้อมูลด้วยฐานข้อมูลและผ่านการตรวจสอบความถูกต้องด้วย Zod:

| คีย์                          | ค่าเริ่มต้น | ช่วง             |
| ----------------------------- | ----------- | ---------------- |
| `modalityBridgeAudioEnabled`  | `true`      | —                |
| `modalityBridgeAudioModel`    | `""`        | Auto หรือ STT ID |
| `modalityBridgeAudioTimeout`  | `60000`     | 1000–300000      |
| `modalityBridgeAudioMaxClips` | `3`         | 1–10             |

แคชที่ใช้ร่วมกันยังคงควบคุมโดย `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` และ `modalityBridgeCacheMaxEntries`

### วิดีโอบริดจ์ (`videoBridge.ts`, `videoBridgePipeline.ts`)

ดักจับชิ้นส่วนวิดีโอระดับบนสุดใน `messages` ของ Chat Completions และ `input` ของ Responses API ก่อนที่จะเรียกใช้เป้าหมายที่ไม่มีการรองรับวิดีโอแบบเนทีฟที่ทราบแน่ชัด รูปแบบที่รองรับ ได้แก่ `input_video`, `video_url`, `video_source`, HTTPS URLs และ data URIs แบบ `data:video/*;base64,...` ชื่อไฟล์ธรรมดาในข้อความจะไม่ถูกถือว่าเป็นวิดีโอ

`VideoBridgeGuardrail.preCall` (`videoBridge.ts`) ทำหน้าที่จัดการการเคลื่อนผ่านคำขอ, การตรวจสอบความสามารถ/นโยบาย, การรวมข้อมูลต่อคำขอ และเพย์โหลดของการตอบกลับ งานสำหรับแต่ละวิดีโอ ได้แก่ การจัดหาข้อมูล, แคชผลลัพธ์ทั้งหมด, การอธิบายลำดับเฟรม (ซึ่งรวมเข้ากับข้อความถอดเสียงที่ผู้เรียกประกาศไว้), และเมตริก/การยกเลิก/การทำความสะอาดต่อความพยายาม จะถูกซ่อนไว้เบื้องหลัง `processVideoPart` ใน `videoBridgePipeline.ts` ซึ่งจะถูกเรียกใช้งานหนึ่งครั้งต่อหนึ่งชิ้นส่วนวิดีโอภายในลูปของ `preCall` โมดูลดังกล่าวยังกำหนดขอบเขตพอร์ตที่ชัดเจน ได้แก่ `VideoMediaBrokerPort` (สำหรับการจัดหาไบต์และการแยกเฟรมตัวอย่าง), `VideoAudioTranscriptionPort` (สำหรับการรวมข้อความถอดเสียงที่ผู้เรียกประกาศเข้ากับคำบรรยายตัวอย่าง) และ `VideoDrilldownPort` (ขอบเขตการคงอยู่ของการเจาะลึกเฟรม; ซึ่งยังไม่ได้เชื่อมต่อเข้ากับ `processVideoPart` ในปัจจุบัน โดยมีเพียงเส้นทางแยกต่างหาก `/api/modality-bridge/video/drilldown` เท่านั้นที่เขียนรายการเจาะลึกในปัจจุบัน)

เส้นทางคำขอ `/v1` สาธารณะจะไม่นำเข้าหรือเรียกใช้ย่อยกระบวนการใดๆ ทั้งสิ้น วิดีโอจากระยะไกลจะถูกดาวน์โหลดภายใต้ขีดจำกัด 50 MiB; วิดีโอ base64 แบบอินไลน์จะมีขีดจำกัดขนาดที่ถอดรหัสแล้วแบบอนุรักษ์นิยมที่ 36 MiB ต่อวิดีโอ เพื่อให้กรอบของโมเดล/ข้อความ/โครงสร้างยังคงอยู่ภายในขีดจำกัดการรับคำขอ JSON สาธารณะที่ 50 MiB การประมาณความยาวและขนาดที่ถอดรหัสแล้วของอินไลน์จะถูกตรวจสอบก่อนการจัดสรรหน่วยความจำ จำเป็นต้องใช้ HTTPS สำหรับ URL เริ่มต้นจากระยะไกลและการเปลี่ยนเส้นทางทั้งหมด โดยใช้ระบบป้องกันการส่งออกข้อมูลภายนอกที่เป็นสาธารณะเท่านั้นที่มีอยู่พร้อมการปักหมุด DNS จากนั้นข้อมูลไบต์จะข้ามผ่านขอบเขตของโบรกเกอร์ภายใน `POST /api/modality-bridge/video/extract` อย่างแม่นยำ เส้นทางดังกล่าวมีสถานะทั้ง `LOCAL_ONLY` และ `SPAWN_CAPABLE` โดยจะยอมรับเฉพาะคำขอแบบลูปแบ็คที่เชื่อถือได้และมีการยืนยันตัวตนต่อกระบวนการเท่านั้น และจะไม่ยอมรับ URL, เส้นทางระบบไฟล์, ไฟล์ปฏิบัติการ หรือรายการอาร์กิวเมนต์ใดๆ เลย ไปป์ไลน์ขนาดเนื้อหาคำขอ API และตัวอ่านเนื้อหาแบบเพิ่มทีละส่วนของตัวจัดการ จะบังคับใช้ขีดจำกัดอินพุตของโบรกเกอร์ที่ 50 MiB อย่างเป็นอิสระต่อกัน คิวที่มีขอบเขตนี้จะรันการแยกข้อมูลทีละรายการ อนุญาตให้มีงานที่รอดำเนินการได้สี่รายการ และจำกัดอินพุตที่รอดำเนินการไว้สูงสุดที่ 100 MiB

ภายใน broker ตัว `ffprobe` จะอ่านไฟล์ในเครื่องที่เป็นส่วนตัว โดยรายการอนุญาตรูปแบบไฟล์แบบตายตัวจะยกเว้นรูปแบบเพลย์ลิสต์และรูปแบบแมนิเฟส สำหรับคอนเทนเนอร์ในตระกูล MOV ที่ได้รับอนุญาต การอ้างอิงข้อมูล MOV ภายนอกจะยังคงถูกปิดใช้งานตามค่าเริ่มต้น และคำสั่งแบบตายตัวจะไม่เปิดใช้งานส่วนดังกล่าว ทั้ง `ffprobe` และ `ffmpeg` จะใช้ไวท์ลิสต์โปรโตคอล `file` เท่านั้น, ใช้หนึ่งเทรด, อาร์เรย์อาร์กิวเมนต์แบบตายตัว, ไม่มีเชลล์ และแก้ไขพาธของไฟล์ปฏิบัติการจาก `PATH` สตรีมภาพปกที่แนบมาไม่ใช่สตรีมที่มีสิทธิ์เล่นได้ สตรีมที่เล่นได้ทั้งหมดต้องเป็นไปตามขีดจำกัด และจะให้ความสำคัญกับสตรีมเริ่มต้นที่ระบุไว้อย่างชัดเจน ก่อนที่จะใช้การสำรองข้อมูลแบบดีเทอร์มิเนสติกไปยังดัชนีต่ำสุด วิดีโอจะถูกจำกัดไว้ที่ 600 วินาที, 8,192 พิกเซลต่อมิติ และ 33,554,432 พิกเซลของต้นฉบับ FFmpeg จะสุ่มตัวอย่างเฟรม JPEG ตรงกลาง 1–16 เฟรม ย่อขอบด้านที่ยาวที่สุดให้เหลือสูงสุด 1,024 พิกเซลโดยไม่มีการขยายขนาดอินพุตที่มีขนาดเล็กกว่า และจะไม่รับ URL เลย การสุ่มตัวอย่างจะใช้ค่า `uniform` เป็นค่าเริ่มต้น นโยบาย `scene_aware` ที่เป็นทางเลือกและนโยบายทดลอง `segment_aware` จะดำเนินการประมวลผล FFmpeg เพิ่มเติมอีกหนึ่งรอบบนสตรีมในเครื่องที่ได้รับการตรวจสอบความถูกต้องแล้ว, เลือกประทับเวลาฉาก `showinfo` ที่มีขอบเขต และจะสำรองข้อมูลกลับไปใช้จุดกึ่งกลางแบบ uniform ตัวเดิมอย่างแม่นยำ หากตัวตรวจจับล้มเหลว, หมดเวลา, ผลลัพธ์ผิดรูปแบบ หรือชุดตัวสมัครว่างเปล่า โหมด segment-aware จะจัดสรรตัวอย่างจุดกึ่งกลางตามสัดส่วนของช่วงฉากที่ตรวจสอบความถูกต้องแล้ว โดยหลักฐานและพฤติกรรมการสำรองข้อมูลของโหมด segment-aware จะมีรายละเอียดอธิบายไว้ด้านล่าง ขีดจำกัดสูงสุดที่ 16 เฟรมจะถูกนำมาใช้หลังจากการเลือกในทุกนโยบาย เมื่อคำขอแบบ scene-aware มีงบประมาณเพียงหนึ่งเฟรม ระบบจะใช้จุดกึ่งกลางแบบ uniform ของวิดีโอเต็มรูปแบบหรือหน้าต่างโฟกัสที่ใช้งานอยู่ และรายงาน `policyEffective: uniform`: เฟรมฉากที่เลือกมาเพียงเฟรมเดียวไม่สามารถรักษาจุดสิ้นสุดทั้งสองด้านตามเวลาไว้ได้ ผู้เรียกสามารถระบุหน้าต่างโฟกัสที่มีขอบเขตสิ้นสุดได้ (วินาที `start`/`end`) โดยขอบเขตจะถูกจำกัดให้อยู่ภายในระยะเวลาของสื่อ, หน้าต่างที่กลับด้านหรือไม่สิ้นสุดจะถูกปฏิเสธ และนโยบายการสุ่มตัวอย่างทั้งหมดจะถูกดำเนินการเฉพาะภายในช่วงเวลาที่ถูกปรับค่าให้เป็นมาตรฐานแล้วเท่านั้น หน้าต่างผลลัพธ์จะถูกรวมไว้ในข้อมูลเมตาของการสุ่มตัวอย่างและในคำนำคำอธิบายที่ไม่น่าเชื่อถือ เพื่อให้โมเดลปลายทางสามารถแยกแยะข้อความตัดตอนที่โฟกัสออกจากไทม์ไลน์ทั้งหมดได้

การโฟกัสคำบรรยายเชิงความหมายเป็นการตั้งค่าแยกต่างหากและชัดเจน โหมดการวิเคราะห์ `full` เริ่มต้นจะคงพรอมต์เฟรมเดิมไว้และจะไม่ส่งข้อความคำขอไปยังโมเดลคำบรรยายเลย ในโหมด `focused` บริดจ์จะอ่านเฉพาะ `text`/`input_text` ล่าสุดที่ผู้ใช้เขียนขึ้นและไม่ว่างเปล่าจากคอนเทนเนอร์ Chat หรือ Responses เดียวกัน, ปรับค่าให้เป็นมาตรฐานเป็น NFC, ย่อตัวอักษรควบคุมและช่องว่าง และจำกัดไว้ที่ไม่เกิน 500 ยูนิโค้ดโค้ดพอยต์ ผลลัพธ์ที่ว่างเปล่าจะกลับไปใช้พรอมต์ `full` ตามต้นฉบับ คำใบ้ที่ใช้งานได้จะถูกซีเรียลไลซ์เป็น JSON ในบล็อก `untrusted-user-context` โดยเฉพาะ และสามารถให้ความสำคัญเฉพาะรายละเอียดที่สังเกตเห็นได้เท่านั้น โดยจะไม่สามารถลบล้างคำเตือนแยกต่างหากเกี่ยวกับการปฏิบัติตามคำแนะนำที่มองเห็นหรือได้ยินในสื่อได้ การโฟกัสด้วยข้อความจะไม่เคยอนุมานค่า `start`/`end` หรือเปลี่ยนแปลงตัวสุ่มตัวอย่างตามเวลา

#### FU-07 หลักฐานส่วนโครงสร้าง

`segment_aware` ใช้รอบการวิเคราะห์ล่วงหน้าที่มีขอบเขตหนึ่งรอบบนสตรีมวิดีโอในเครื่องที่ได้รับการตรวจสอบความถูกต้องแล้ว สายโซ่ตัวกรองแบบตายตัวจะทำการปรับขนาดให้มีความกว้างสูงสุด 320 พิกเซลก่อน, ตรวจจับการเปลี่ยนแปลงของฉากและช่วงเวลาที่ภาพนิ่ง จากนั้นจะสุ่มตัวอย่างที่ 1 เฟรมต่อวินาทีสำหรับข้อมูลความเบลอ, ความสว่างเฉลี่ย และข้อมูลเชิงพื้นที่/เวลา รอบการทำงานนี้จะถูกจำกัดไว้ที่ 600 ตัวอย่างเชิงโครงสร้าง, หนึ่งเทรดของ FFmpeg/ตัวกรอง, ไวท์ลิสต์โปรโตคอลและคอนเทนเนอร์แบบ `file` เท่านั้น, ขีดจำกัดเอาต์พุตของกระบวนการที่ 1 MiB และเวลาไม่เกิน 30 วินาทีภายในกำหนดเวลา/การยกเลิกที่ใช้ร่วมกันของ broker ระบบจะไม่รับคำสั่ง, ตัวกรอง, พาธ หรือ URL จากคำขอเลย

ค่าเชิงโครงสร้างเหล่านี้คือหลักฐานการสุ่มตัวอย่างแบบดีเทอร์มิเนสติก ไม่ใช่ความเข้าใจวิดีโอเชิงความหมาย ค่าเหล่านี้ไม่ได้อนุมานเรื่องของตัวละคร, การกระทำ, คำบรรยาย, คำพูด หรือเจตนาของผู้ใช้ ขอบเขตของฉากและภาพนิ่งจะก่อตัวเป็นส่วนต่างๆ; โดยความครอบคลุมของภาพนิ่ง, ความเบลอ, การรับแสง, รายละเอียดเชิงพื้นที่ และการเปลี่ยนแปลงตามเวลาจะส่งผลต่อวิธีการจัดสรรงบประมาณเฟรม 1–16 เฟรมที่มีอยู่เท่านั้น ส่วนที่เป็นภาพนิ่งทั้งหมดจะถูกจำกัดไว้ที่หนึ่งเฟรม ในขณะที่ส่วนที่ไม่ใช่ภาพนิ่งจะแข่งขันกันเพื่อใช้งบประมาณที่เหลือ เมื่อขอบเขตมีจำนวนมากกว่าเฟรม ความครอบคลุมของไทม์ไลน์แบบ uniform จะยังคงอยู่ เพื่อไม่ให้การตัดต่ออย่างรวดเร็วในช่วงแรกซ่อนส่วนท้ายที่ยาวนานได้ ขอบเขตของฉากที่อยู่ภายในความละเอียดการวิเคราะห์ระดับ 1 วินาทีของขอบเขตภาพนิ่งจะถูกรวมเข้าด้วยกัน

ตัวกรองที่หายไป, หลักฐานที่ผิดรูปแบบ/ว่างเปล่า, ข้อผิดพลาดของตัวตรวจจับ หรือการหมดเวลาของการวิเคราะห์ล่วงหน้าที่มีขอบเขต จะล้มเหลวแบบเปิดไปยังนโยบายจุดกึ่งกลางแบบ uniform ตามต้นฉบับ การยกเลิกของผู้เรียกหรือกำหนดเวลาของ broker จะไม่ล้มเหลวแบบเปิด: แต่มันจะยุติกระบวนการย่อยที่กำลังทำงานอยู่, ป้องกันการแยกเฟรมในภายหลัง และต้นไม้ไฟล์ชั่วคราวส่วนตัวจะถูกลบออกในบล็อก `finally`

`scripts/perf/video-bridge-fu07-eval.ts` สร้างฟิกเจอร์ FFmpeg จริงแบบดีเทอร์มิเนสติกสำหรับการประหยัดการเรียกคำบรรยายหลังการ dedup, การจัดสรรงบประมาณสำหรับการเคลื่อนไหวหนาแน่น, หลักฐานความเบลอ/การรับแสง/SI-TI, การตัดต่ออย่างรวดเร็วที่มีส่วนท้ายยาว และผลบวกปลอมจากการเฟดค่อยเป็นค่อยไป สคริปต์นี้จะบันทึกเวลาจริงของการวิเคราะห์ล่วงหน้า และบันทึก CPU ของกระบวนการลูกและ Peak RSS ในกรณีที่มี `/usr/bin/time` ใช้งานได้ การตรวจสอบคุณภาพของสคริปต์นี้จะเป็นออราเคิลเชิงโครงสร้างเท่านั้น คุณภาพของโมเดลคำบรรยายจริงยังคงสถานะเป็น `HOLD` เนื่องจากชุดทดสอบนี้ไม่มีเอนด์พอยต์ที่ได้รับอนุญาตหรือผู้ตัดสินที่ถูกล็อกไว้ การประหยัดเงินจะยังคงสถานะเป็น `HOLD` เช่นกัน เว้นแต่จะมีการระบุ `--caption-cost-per-call-usd` เพื่อให้ค่าประมาณการต้นทุนต่อการเรียกที่เป็นบวกอย่างชัดเจน โดยสคริปต์จะไม่สร้างผลลัพธ์ทั้งสองนี้ขึ้นมาเองเด็ดขาด

แต่ละเฟรมถูกจำกัดไว้ที่ 4 MiB, เฟรมดิบทั้งหมดรวมกันไม่เกิน 23 MiB และการตอบสนองของโบรกเกอร์แบบ serialize แล้วไม่เกิน 32 MiB ไดเรกทอรีชั่วคราวแบบ private จะถูกลบออกในบล็อก `finally` OmniRoute ไม่ได้รวม FFmpeg มาในตัวและไม่รับเส้นทาง executable แบบกำหนดเอง ก่อนทำการสร้างคำอธิบายภาพ ตัวบริดจ์จะดำเนินการกรองภาพซ้ำ (visual deduplication) แบบอนุรักษ์นิยม: JPEG แต่ละภาพจะถูกลดขนาดลงเป็นบัฟเฟอร์ระดับสีเทาขนาด 16×16 และเปรียบเทียบเฉพาะกับเฟรมสุดท้ายที่ถูกเก็บรักษาไว้เท่านั้น สำหรับงบประมาณคำอธิบายภาพที่ขอมามากกว่าหนึ่งเฟรม การสกัดจะจัดเตรียมชุดผู้สมัครที่มีขอบเขตสูงสุดไม่เกินสองเท่าของงบประมาณนั้น และไม่เกิน 16 เฟรมเสมอ ขีดจำกัดที่ขอจะถูกนำมาใช้หลังจากกระบวนการกำจัดภาพซ้ำแล้วเท่านั้น โดยที่ผู้สมัครตัวแรกและตัวสุดท้ายที่ถูกเลือกจะถูกเก็บรักษาไว้ในระหว่างการลดจำนวนครั้งสุดท้ายเมื่อมีงบประมาณอย่างน้อยสองเฟรม นโยบาย `grayscale-16x16-mean-cells-v2` แบบมีเวอร์ชันจะใช้ค่าที่มากกว่าระหว่างค่าเฉลี่ยผลต่างความสว่างและสัดส่วนของเซลล์ภาพย่อที่มีผลต่างปกติแล้วอย่างน้อย 0.05 เกณฑ์สำหรับภาพซ้ำคือค่าคงที่ 0.04 ซึ่งถูกเลือกมาเพื่อความสามารถในการคาดการณ์ได้ มากกว่าที่จะเปิดเผยเป็นค่าการตั้งค่ารันไทม์ สัญญาณคอนทราสต์สูงสำรองนี้ช่วยรักษาการเคลื่อนไหวขนาดเล็กและการเปลี่ยนแปลงของข้อความที่มองเห็นได้ ซึ่งการเปรียบเทียบด้วยค่าเฉลี่ยอย่างเดียวอาจมองไม่เห็น ข้อผิดพลาดของตัวเปรียบเทียบหรือตัวถอดรหัสจะทำงานแบบ fail open และยังคงความครอบคลุมไว้ เมทาดาตาของผลลัพธ์จะแยกผู้สมัครที่ถูกสกัด เฟรมที่ใช้งานได้สำเร็จ และภาพซ้ำที่ถูกตัดออกออกจากกัน

ส่วนวิดีโอที่ทำเครื่องหมายไว้อย่างชัดเจนอาจขอแผ่นภาพรวม (contact sheet) ที่มีประทับเวลาได้ บริดจ์จะสร้างตาราง JPEG ขนาดสูงสุด 4 คอลัมน์ 16 เฟรม ทุกๆ เซลล์ขนาด 512 พิกเซลจะฝังประทับเวลาต้นฉบับลงในแถบด้านล่างที่มีความคอนทราสต์สูง ในขณะที่ประทับเวลาชุดเดียวกันจะยังคงอยู่ในเมทาดาตาที่เป็นข้อความสำหรับการเชื่อมโยงและการตรวจสอบในขั้นตอนถัดไป ไฟล์ JPEG ทั้งหมดจะยังคงถูกจำกัดไว้ที่ไม่เกิน 32 MiB หาก `sharp` ไม่สามารถถอดรหัสหรือประกอบตารางได้ บริดจ์จะสำรองไปใช้เฟรม JPEG เดี่ยวๆ แทน และการยกเลิกโดยไคลเอนต์จะยังคงส่งผ่านการทำงานของแผ่นภาพนี้ต่อไป

หลักฐานการโปรโมทถูกแยกออกจากไมโครเบนช์มาร์กการประกอบแบบสังเคราะห์อย่างจงใจ `scripts/perf/video-bridge-contact-sheet-eval.ts` กำหนดชุดทดสอบแบบ A/B ที่มีเวอร์ชันสกีมาสำหรับโมเดลวิชันจริงที่เข้ากันได้กับ OpenAI โดยจะวัดโทเค็นที่รายงานโดยผู้ให้บริการ ความหน่วงแบบ wall latency แบบ end-to-end (รวมถึงการประกอบแผ่นภาพ) จำนวนการเรียกใช้โมเดล และอัตราการคงอยู่ของข้อเท็จจริงที่กำหนดโดยแมนิเฟส การตอบสนองของโมเดลแบบดิบจะไม่ถูกบันทึกรูปลงในรายงาน โดยจะเก็บรักษาเฉพาะค่าไดเจสต์ SHA-256 และ ID ของข้อเท็จจริงที่ตรงกันเท่านั้น ชุดทดสอบนี้จะไม่ทำการเรียกเครือข่ายหรือโมเดลที่มีค่าใช้จ่าย เว้นแต่จะมีการส่งแฟล็ก `--execute-real` และมีการกำหนดค่า `--model`, `OMNIROUTE_BASE_URL`, และ `OMNIROUTE_API_KEY` หากไม่มีการรันจริงแบบชัดเจนดังกล่าว คำวินิจฉัยที่เครื่องอ่านได้จะยังคงเป็น `HOLD` และการวัดขนาดเพย์โหลด/จำนวนการเรียกแบบสังเคราะห์อย่างเดียวจะไม่ถือเป็นหลักฐานการโปรโมท

ผู้เรียกสามารถแนบอาร์เรย์ `transcript.cues` ที่เป็นทางเลือกเข้ากับส่วนวิดีโอที่รองรับได้ เมื่อพวกเขามีข้อความที่จัดเรียงเวลาไว้แล้ว คิวแต่ละรายการต้องมี `text`, ช่วงเวลา `start`/`end` ที่จำกัดขอบเขตภายในระยะเวลาที่ตรวจสอบ และ `source` ที่อยู่ในไวต์ลิสต์ (`client`, `embedded`, หรือ `audio-bridge`); โดยค่าเริ่มต้น `confidence` จะมีค่าเป็น `1` และต้องอยู่ระหว่าง `0` ถึง `1` คิวที่ซ้ำกันทุกประการจะถูกยุบรวมเข้าด้วยกัน OmniRoute จะไม่เริ่มกระบวนการถอดเสียงจากเมทาดาตานี้: คิวที่ผ่านการตรวจสอบแล้วจะถูกคัดลอกไปยังผลลัพธ์ที่มีคำอธิบาย พร้อมด้วยแหล่งที่มา ความเชื่อมั่น และช่วงเวลา และจะถูกแสดงผลเป็นข้อสังเกตที่ไม่น่าเชื่อถือควบคู่ไปกับคำอธิบายภาพ ข้อความที่ไม่ถูกต้อง อยู่นอกช่วง หรือไม่มีที่มาจะถูกปฏิเสธ แทนที่จะถูกนำไปปะปนกับสตรีมคำอธิบายภาพ ช่องทางการถอดเสียงในเนื้อหาคำขอทั้งหมดจะแปลงที่มาที่ให้มาให้เป็นมาตรฐานว่าเป็น `client` รวมถึงป้ายกำกับ `embedded` หรือ `audio-bridge` ที่ระบุเข้ามาเอง มีเพียงแอดพตเตอร์ที่เป็นของฝั่งเซิร์ฟเวอร์เท่านั้นที่สามารถกำหนดป้ายกำกับที่เชื่อถือได้เหล่านี้ผ่านทางอาร์กิวเมนต์ `trustedSource` ที่อยู่ในโค้ดเท่านั้น โดยฟิลด์ JSON ในคำขอจะไม่สามารถเข้าถึงอาร์กิวเมนต์ดังกล่าวได้ ข้อความถอดเสียงยังคงเป็นเนื้อหาที่ได้จากสื่อที่ไม่น่าเชื่อถือ โดยไม่คำนึงถึงแหล่งที่มา และจะต้องไม่นำมาใช้ในการกำหนดสิทธิ์การเข้าถึงเป็นอันขาด

ผู้เรียกขั้นสูงอาจระบุแทร็ก `audioTranscript` สำหรับวิดีโอเดียวกันได้ โดยจะปฏิบัติเสมือนเป็นข้อความที่ไคลเอนต์จัดเตรียมมา ไม่ใช่เครื่องพิสูจน์ว่ามีการถอดเสียงจากฝั่งเซิร์ฟเวอร์ รอยต่อการผสานจะรันการสังเกตการณ์ทั้งภาพและเสียงภายใต้กำหนดเวลาและสัญญาณยกเลิกเดียวกัน จัดเรียงลำดับบนไทม์ไลน์เดียวกัน ยุบรวมคิวที่ซ้ำกันทุกประการ และรายงานผลลัพธ์แบบบางส่วนเมื่อมีฝั่งใดฝั่งหนึ่งสำเร็จเพียงฝั่งเดียว กรณีที่ `audioTranscript` ไม่ถูกต้อง ระบบจะลดระดับลงเหลือผลลัพธ์แบบบางส่วนดังกล่าว (โดยเก็บคำอธิบายภาพไว้และบันทึกรหัสข้อผิดพลาดที่ทำความสะอาดแล้วสำหรับฝั่งเสียง) แทนที่จะทำให้วิดีโอทั้งหมดล้มเหลว สถานะความพร้อมใช้งานในแต่ละฝั่ง แฟล็กผลลัพธ์บางส่วน และรหัสข้อผิดพลาดที่ทำความสะอาดแล้ว จะถูกเก็บรักษาไว้ในผลลัพธ์ที่มีคำอธิบาย, ในเมทาดาตาของ guardrail (`audioFusionRuns`/`audioFusionPartials`/`audioFusionFailureCodes`), ในเมทาดาตาของแคชผลลัพธ์, และในตัวนับการผสานของบริดจ์ เส้นทาง Video Bridge เริ่มต้นจะไม่เรียกใช้ฟังก์ชันแปลงเสียงเป็นข้อความหรือดาวน์โหลดสำเนาสื่อชุดที่สอง และหากไม่มีแทร็กดังกล่าวอย่างชัดเจน ระบบจะยังคงเป็นวิดีโออย่างเดียวเช่นเดิม

**Transcript retention (#12150 P1).** สิ่งนี้จะทำงานโดยอัตโนมัติเมื่อ Video Bridge (ซึ่งต้องเลือกเปิดใช้งานเอง) แสดงคิว Transcript ออกมา โดยไม่มีแฟล็กการเก็บรักษาแยกต่างหาก เมื่อคำขอใดๆ แสดงคิว Transcript (ไม่ว่าจะเป็น `transcript` ที่ผู้เรียกประกาศไว้หรือ `audioTranscript` ที่ผสานรวมกัน) ตัว guardrail จะทำเครื่องหมายคำขอนั้นเป็น `videoBridgeObserved` และสร้างเงาที่ถูกเซ็นเซอร์ของคำอธิบายวิดีโอขึ้นมา ซึ่งเป็นการแสดงผลที่เหมือนกันทุกประการแต่เนื้อหาข้อความอิสระของทุกคิวจะถูกแทนที่ด้วย `[redacted-video-transcript]` ซึ่งสร้างขึ้นจากการแทนที่ฟิลด์คิวที่มีโครงสร้างก่อนที่จะประกอบสตริงเข้าด้วยกัน (ไม่ใช่ด้วยการแยกวิเคราะห์ข้อความที่ยุบรวมแล้ว ดังนั้นเนื้อหาของคิวใดๆ ไม่ว่าจะเป็นแบบประสงค์ร้ายหรือปกติ รวมถึงเนื้อหาที่มี `]` เช่น `[inaudible]`/`[music]` จะไม่สามารถรอดพ้นไปได้) เนื้อหาคำขอในบันทึกการโทรที่ถูกบันทึกไว้จะสลับส่วนข้อความที่มาจากวิดีโอแต่ละส่วนด้วยเงาที่ถูกเซ็นเซอร์นั้น โดยจับคู่ด้วยความเท่ากันของเนื้อหา ส่วนยึดเหนี่ยว `fullText` จะถูกอ่านใหม่ออกจากเพย์โหลด guardrail ก่อนการโทรที่เสร็จสมบูรณ์ ดังนั้นการจับคู่จึงยังคงสำเร็จหลังจากที่ chain guardrails ภายหลัง (ตัวกรอง PII และข้อมูลประจำตัว ที่ลำดับความสำคัญ 10/95) เขียนทับข้อความอธิบายในตำแหน่งเดิม และหลังจากที่การแทรก system-prompt/handoff/memory ปรับเปลี่ยนอาร์เรย์ข้อความใหม่ ส่วนเนื้อหาที่ส่งไปยังโมเดลต้นทางจะไม่เปลี่ยนแปลง คำขอที่ถูกสังเกตการณ์นี้จะไม่เติมข้อมูลลงใน Memory แบบถาวรด้วย (ข้ามการดึงข้อมูลที่มาจากทั้งฝากคำขอและฝากการตอบกลับ) ดังนั้นการตอบกลับของตัวโมเดลเองจึงไม่สามารถสะท้อนข้อความ Transcript กลับเข้าไปใน Memory ได้

**Raw video fields (#12430).** เมื่อเปิดใช้งาน bridge และไม่ทราบสถานะหรือไม่มีการรองรับวิดีโอแบบเนทีฟ ฟิลด์ `transcript`/`audioTranscript` ที่มีการกำหนดค่าไว้ก็จะเปิดใช้งาน `videoBridgeObserved` เช่นกัน แม้ว่าจะเกิดความล้มเหลวในการอธิบายหรือถึงขีดจำกัด `maxVideos` แล้วก็ตาม ค่า `null` และสตริงว่างจะถูกนับรวมด้วย ส่วนฟิลด์ที่ไม่มีอยู่และข้อมูลเมตาที่ไม่ใช่วิดีโอจะไม่ถูกนับ สำเนาที่ถูกเก็บรักษาไว้จะทำการเซ็นเซอร์ฟิลด์เหล่านี้หรือละเว้นคำขอนั้นไป และจะข้ามแคชและ Memory

ในเส้นทางสำรองเหล่านั้น คิวที่ถูกต้องของผู้เรียกจะกลายเป็นส่วนของ `text`/`input_text` ที่รองรับ แทนที่จะเป็นฟิลด์ของผู้ให้บริการที่ไม่เป็นมาตรฐาน แทร็กทั้งสองที่จัดเตรียมมาโดยคำขอยังคงเป็นการสังเกตการณ์จาก `client` ที่ไม่น่าเชื่อถือ โดยมีคำเตือนอย่างชัดเจนว่าวิดีโอดังกล่าวไม่ได้รับการอธิบายและประทับเวลาไม่ได้รับการตรวจสอบเทียบกับสื่อ งบประมาณรวมและต่องวดคิว (per-cue budgets) ที่มีอยู่คือ 256 คิว / 64-KiB จะถูกนำมาใช้ร่วมกันทั้งสองแทร็ก โดยการประทับเวลาจะต้องอยู่ในเพดาน 600 วินาทีของโบรกเกอร์และหน้าต่างโฟกัสใดๆ ที่ระบุมา แทร็กที่ไม่ถูกต้องจะถูกละทิ้ง ไม่ถูกส่งต่อเป็นข้อความตามอำเภอใจ แต่แทร็กคู่กันที่ถูกต้องยังคงสามารถใช้ได้เว้นแต่งบประมาณรวมของพวกมันจะเกินกำหนด ฟิลด์ที่เป็นค่า Null หรือว่างจะไม่เพิ่มข้อความใดๆ เส้นทางสำรองนี้ไม่มีการดึงข้อมูลสื่อหรือการถอดเสียงเพิ่มเติม ฟิลด์ส่วนขยายของ Transcript จะถูกลบออกจากตัวส่งสัญญาณวิดีโอสำรองและออบเจ็กต์ `video_url`/`source` ของมัน รายการอนุญาตของการเชื่อมต่อ OpenAI ยังคงเข้มงวด ตัวส่งสัญญาณวิดีโอแบบเนทีฟที่ไม่รู้จักจะยังคงใช้งานได้ และเป้าหมายที่มีแต่ข้อความที่รู้จักจะยังคงรักษาเครื่องหมายปลอดภัยไว้ เงาการเซ็นเซอร์แบบมีโครงสร้างจะปกป้องข้อความ Transcript ที่ต่อท้าย ในขณะที่คำขอเดิมที่เป็นของผู้เรียกยังคงไม่เปลี่ยนแปลง เป้าหมายที่รองรับแบบเนทีฟและบริดจ์ที่ถูกปิดใช้งานจะยังคงรักษาพฤติกรรมการบายพาสเดิมเอาไว้

สำเนาที่เก็บรักษาเพิ่มเติมจะใช้สัญญาณคำขอที่ถูกสังเกตการณ์เดียวกัน ส냅ช็อตคำขอของไคลเอนต์ดิบก่อนเข้า guardrail, คำขอที่รอดำเนินการในหน่วยความจำ และบันทึกคำขอที่ถูกปฏิเสธตั้งแต่เนิ่นๆ จะเข้ามาแทนที่ฟิลด์ Transcript ในส่วนวิดีโอตามโครงสร้าง; ข้อความพรอมต์ที่สังเคราะห์ขึ้นโดยขั้นตอนของไปป์ไลน์และการส่งมอบบริบทจะถูกเซ็นเซอร์ที่จุดรับคำขอที่บันทึกไว้ เครื่องหมาย `video_content_removed` ที่ถูกบันทึกไว้ทำให้การดำเนินการต่อของ `previous_response_id` ล้มเหลวแบบปิด แทนที่จะทำการสร้างข้อความขึ้นมาใหม่ซึ่งตั้งใจถูกละทิ้งไปแล้ว หากคำขอที่ถูกสังเกตการณ์สูญเสียเงาการเซ็นเซอร์แบบแยกส่วนก่อนการบันทึก หรือแม้แต่เงาของวิดีโออันใดอันหนึ่งจากหลายๆ อันไม่สามารถจับคู่ได้หลังจากมีการแก้ไขคำขอในภายหลัง เนื้อหาคำขอที่ถูกเก็บรักษาไว้จะถูกละเว้นไปทั้งหมดแทนที่จะเก็บรักษา Transcript ที่ถูกเซ็นเซอร์เพียงบางส่วนไว้

สำหรับคำขอที่ถูกสังเกตการณ์ การตอบกลับของโมเดลอาจมีการอ้างอิงข้อความส่วนใดส่วนหนึ่งของ Transcript โดยไม่มีขอบเขตคิวที่มีโครงสร้าง ดังนั้น ฟิลด์ `responseBody` ในบันทึกการโทรที่บันทึกไว้จึงถูกแทนที่ด้วยเครื่องหมายการละเว้น; และอาร์ติแฟกต์ของไปป์ไลน์โดยละเอียด (ซึ่งอาจรวมถึงเนื้อหาฝั่งต้นทาง/ไคลเอนต์และชิ้นส่วนสตรีม) จะไม่ถูกเก็บรักษาไว้ แคชเชิงความหมาย, แคชความสมมูลซ้ำ, และแคชการเล่นซ้ำการให้เหตุผลจะข้ามการอ่านและการเขียนสำหรับคำขอนั้น คำขอของผู้ให้บริการและการตอบกลับที่มองเห็นได้ฝั่งไคลเอนต์จะยังคงไม่เปลี่ยนแปลง ไบต์ keepalive ช่วงต้นจะถูกระบายออกจากบัฟเฟอร์ชั่วคราวเมื่อมีการละเว้นอาร์ติแฟกต์โดยละเอียด คำเตือน EventStream ที่รูปแบบไม่ถูกต้องของ Kiro จะรายงานเฉพาะจำนวนไบต์ของเพย์โหลดเท่านั้น โดยจะไม่รายงานเนื้อหาหรือข้อผิดพลาดดิบของตัววิเคราะห์ JSON เลย

สิ่งนี้ไม่ได้หมายความว่าการวินิจฉัยของผู้ให้บริการ/ปลั๊กอินอื่นๆ ที่ไม่เกี่ยวข้องทั้งหมดได้รับการตรวจสอบแล้ว โดยการกวาดล้างจุดรับข้อมูลที่เก็บรักษาไว้ในวงกว้างจะถูกติดตามไว้ใน #11658

วงจรชีวิตของ `/api/modality-bridge/video/drilldown` ภายใน เป็นซับสเตรตแคชแยกต่างหากที่ผ่านการตรวจสอบสิทธิ์ด้วย loopback/token ทุกการดำเนินการยังต้องใช้ ID ของผู้มีอำนาจหลักแบบทึบแสงที่เป็นมาตรฐาน ก่อนที่จะเปิดใช้งานผู้เรียกในระดับโปรดักชัน จะต้องอนุพันธ์ ID นั้นมาจากเทแนนต์ที่ได้รับการตรวจสอบสิทธิ์แล้ว และห้ามส่งต่อค่าที่ถูกเลือกโดยไคลเอนต์เด็ดขาด คีย์แคชจะผูกผู้มีอำนาจหลักนั้นเข้ากับ ID เซสชันและ ID อ้างอิงวิดีโอที่เป็นมาตรฐาน โดยจะจัดเก็บเฉพาะคีย์ที่ได้จากการแปลงแบบ SHA-256 เท่านั้น และกำหนดขอบเขตทั้งการอ่านและการลบให้อยู่ภายใต้ผู้มีอำนาจหลักรายเดียวกัน แคชนี้จะจัดเก็บเฟรม JPEG ที่แปลงแล้วสูงสุดไม่เกิน 16 เฟรมต่อหนึ่งรายการ, จะหมดอายุหลังจากผ่านไปสิบนาที, และรองรับการอ่านแบบจำกัดขอบเขต `start`/`end` หรือการลบเซสชันอย่างชัดเจน

ผู้มีอำนาจหลักแต่ละรายจะถูกจำกัดไว้ที่ 16 รายการ และข้อมูล JPEG มาตรฐานขนาด 64 MiB ขีดจำกัดเหล่านี้ไม่ขึ้นอยู่กับเพดานระดับโกลบอลที่ 64 รายการ / 256 MiB โดยแรงกดดันด้านโควตาของผู้มีอำนาจหลักจะทำการขับออกเฉพาะรายการที่ใช้งานน้อยที่สุดของผู้มีอำนาจหลักรายนั้นก่อนที่จะพิจารณาการขับออกตามระบบ LRU ระดับโกลบอล รายการที่หมดอายุจะถูกล้างออกจากระบบบัญชีทั้งของผู้มีอำนาจหลักและระดับโกลบอลเมื่อมีกิจกรรมแคชเกิดขึ้น ในขณะที่การยกเลิกและความล้มเหลวในการตรวจสอบความถูกต้องจะไม่ทำการคอมมิตการแทนที่บางส่วน

แคชจะปฏิเสธ Base64 ที่ไม่ใช่รูปแบบแคนอนิคอล (canonical), พอดดิ้ง (padding) ที่เกินมา, สื่อที่ไม่ใช่ JPEG, ไฟล์ JPEG ที่ผิดรูปแบบหรือถูกตัดทอน, และไฟล์ JPEG ที่ทำให้เกิดคำเตือนระหว่างการถอดรหัสภาพเต็มรูปแบบผ่าน `sharp` แบบจำกัดขอบเขต ระบบจะเข้ารหัสภาพที่ยอมรับแต่ละภาพใหม่เป็น JPEG แบบแคนอนิคอล, คำนวณความกว้างและความสูงจากไบต์ที่ถอดรหัสแล้วแทนที่จะเชื่อฟิลด์ของผู้เรียก, และทิ้งไบต์โพลีกลอตที่อยู่ท้ายไฟล์แทนที่จะเก็บไว้ เฉพาะบัฟเฟอร์บีบอัดแบบแคนอนิคอลที่มีขอบเขตจำกัดเท่านั้นที่จะถูกคิดโควตาไปยังโควตาทั้งสอง ขีดจำกัดของ JSON wire จะรวมเอาค่าโอเวอร์เฮดของ Base64 สำหรับเพดานอินพุตที่ถอดรหัสแล้วขนาด 32 MiB ด้วย การสืบทอด (derivation) ที่จัดเก็บทุกรายการจะบันทึกรูปแบบ/ความละเอียดของ JPEG ที่ผ่านการตรวจสอบแล้ว, นโยบายการสุ่มตัวอย่าง, เวอร์ชันของการสืบทอด, เวลาที่สร้าง, แฮชเนื้อหาที่คำนวณโดยเซิร์ฟเวอร์, และการอ้างอิงถึงพาเรนต์ที่ถูกแฮช พร้อมด้วยแฮชเนื้อหาพาเรนต์จากผู้เรียกที่เชื่อถือได้ การยกเลิกจะถูกตรวจสอบระหว่างขั้นตอนการถอดรหัส/การแฮชแบบอะซิงโครนัส ก่อนที่จะทำการคอมมิตแคชแบบอะตอมมิค

ชุดงาน (tranche) นี้ยังไม่ได้เชื่อมต่อผู้ผลิตระดับโปรดักชันเข้ากับเส้นทาง และยังไม่มีการเลือกตัวเลือกแบบหลายความละเอียด ดังนั้น เส้นคำขอของ Video Bridge แบบโปร่งใสจึงไม่มีภาระงานเพิ่มขึ้น ในขณะที่การสืบทอดสิทธิ์ (principal derivation) ที่ผูกกับเทแนนท์ และวงจรชีวิตแบบหลายความละเอียด FU-08 เต็มรูปแบบยังคงเป็นงานติดตามผลที่ระบุไว้อย่างชัดเจน แทนที่จะถูกบันทึกว่าเป็นพฤติกรรมที่เสร็จสมบูรณ์

เฟรมต่างๆ จะถูกใส่คำบรรยายตามลำดับด้วยโมเดล Video ที่กำหนดค่าไว้ การแทนที่ค่า Video ที่ว่างเปล่าจะสืบทอดการตั้งค่ามาจาก Vision หากว่างเปล่าทั้งคู่ ตัวเลือกเส้นทางอัตโนมัติของ Vision จะเลือกโมเดลที่มีความสามารถด้านการมองเห็นที่ใช้งานได้จริง คำบรรยายที่สำเร็จจะแทนที่ส่วนเดิมด้วยคำนำหน้า `[Video description:` ที่เสถียร ซึ่งทำเครื่องหมายข้อความว่าเป็นข้อสังเกตที่มาจากสื่อที่ไม่น่าเชื่อถือ และบอกโมเดลปลายทางว่าอย่าทำตามคำแนะนำที่พบในสื่อนั้น คีย์แคชคำบรรยายเฟรมประกอบด้วยไบต์ JPEG, พรอมต์, แสตมป์เวลา และโมเดลที่ใช้งานจริง โดยจะแคชเฉพาะคำบรรยายที่สำเร็จเท่านั้น รายการในแคชจะเก็บรักษาโมเดลผู้ผลิตที่สำเร็จจริงรวมถึงโมเดลสำรองไว้ โดยบริดจ์จะรายงานสถานะเป็น `mixed` เมื่อเฟรมต่างๆ ถูกผลิตโดยโมเดลที่ต่างกัน การเจอแคช (cache hit) จะนำตัวตนของผู้ผลิตรายนั้นกลับมาใช้ใหม่ แทนที่จะเปลี่ยนป้ายกำกับให้เป็นแผนการกำหนดเส้นทางที่ร้องขอ แคชผลลัพธ์วิดีโอทั้งชิ้นจะใช้คีย์จากทุกอินพุตที่ส่งผลให้เอาต์พุตเปลี่ยนแปลง ได้แก่ พรอมต์, โมเดลที่ใช้งานจริง, นโยบายการสุ่มตัวอย่าง, จำนวนเฟรม, โหมดการวิเคราะห์เชิงความหมาย, ลายมือชื่อ (fingerprint) SHA-256 ของคำใบ้การโฟกัสที่ปรับมาตรฐานแล้ว, หน้าต่างโฟกัส, `transcript`, `audioTranscript`, และแฟล็ก contact-sheet ดังนั้นการเปลี่ยนแปลงมิติใดๆ เหล่านี้จะทำให้เกิดการแคชพลาด (cache miss) และไม่มีการนำข้อมูลเก่ากลับมาใช้ซ้ำอย่างเด็ดขาด เวอร์ชันนโยบายการตัดรายการซ้ำทางภาพ (visual dedup), ค่าเกณฑ์ (threshold), และจำนวนเฟรมผู้สมัครที่มีขอบเขต จะถูกระบุไว้อย่างชัดเจนในคีย์และเมทาเดตาของแคชผลลัพธ์เช่นกัน ดังนั้นการเปลี่ยนแปลงนโยบายจึงไม่สามารถนำคำบรรยายวิดีโอทั้งชิ้นที่เก่าแล้วกลับมาใช้ใหม่ได้ เมทาเดตาของแคชผลลัพธ์ v4 จะเก็บรักษาโหมดและลายมือชื่อ (fingerprint) ไว้ แต่จะไม่เก็บงานของผู้ใช้แบบดิบๆ เมทาเดตาของเกราะป้องกัน (guardrail) จะรายงานทั้งโหมดการวิเคราะห์ที่ร้องขอและโหมดที่ใช้งานจริง โดยโหมด `focused` ที่ถูกร้องขอแต่ไม่มีข้อความผู้ใช้ที่ใช้งานได้ จะถูกรายงานเป็นโหมด `full` ในทางปฏิบัติ

เกราะป้องกันจะดึงข้อมูลส่วนวิดีโอทั้งหมดที่รองรับ แต่จะอธิบายไม่เกิน `modalityBridgeVideoMaxVideos` รายการ สำหรับเป้าหมายที่พิสูจน์แล้วว่ามี `supportsVideo === false` วิดีโอที่ล้มเหลวและเกินขีดจำกัดจะกลายเป็นข้อความระบุความปลอดภัยที่ชัดเจน เพื่อไม่ให้มีวิดีโอดิบหลงเหลืออยู่ เมื่อไม่ทราบความสามารถ ส่วนเหล่านั้นจะยังคงรักษาพาหะวิดีโอของตนไว้ โดยข้อความถอดเสียงสำรองใดๆ จะเป็นไปตามการแปลงข้อความแบบมีขอบเขตด้านบน เป้าหมายที่มี `supportsVideo === true` จะข้ามบริดจ์ไป สัญญาณยกเลิกคำขอจากไคลเอนต์จะแพร่กระจายผ่านกระบวนการดาวน์โหลด, คิวของโบรเกอร์, ซับโพรเซส, และการเรียกคำบรรยาย โดยการยกเลิกจะหยุดระหว่างวิดีโอและจะไม่เปิดเผยสื่อดิบออกไปในกรณีที่เกิดข้อผิดพลาด

| `modalityBridgeVideoMaxVideos`      | `1`         | 1–4                                                                                                  |
| `modalityBridgeVideoTimeout`        | `120000`    | 1000–120000 มิลลิวินาที                                                                              |

ค่าหมดเวลาของวิดีโอแบบเดิมที่บันทึกไว้ซึ่งมีค่ามากกว่า 120 วินาทีจะถูกจำกัดไว้ที่กำหนดเวลาของโบรเกอร์ ส่วนการเขียนการตั้งค่าใหม่ที่เกินขีดจำกัดดังกล่าวจะถูกปฏิเสธ `GET /api/modality-bridge/video/runtime` กำหนดให้ต้องมีตำแหน่ง loopback ที่ประทับเวลาอย่างน่าเชื่อถือ ก่อนที่จะทำการตรวจสอบสิทธิ์หรือตรวจสอบรันไทม์ จากนั้นจึงต้องมีการตรวจสอบสิทธิ์ระดับการจัดการ ระบบจะส่งคืนเฉพาะสถานะ `available`, เวอร์ชัน FFmpeg/ffprobe ที่ผ่านการทำความสะอาดข้อมูลแล้ว, และเหตุผลตายตัวเมื่อรันไทม์ไม่พร้อมใช้งาน เอนด์พอยต์การดึงข้อมูลภายในไม่ใช่ API อัปโหลดสาธารณะ โดยเมื่อคิวเต็มจะส่งคืนรหัส `503` พร้อมกับ `Retry-After`, หากผู้เรียกตัดการเชื่อมต่อจะส่งคืน `499`, และเมื่อครบกำหนดเวลาตายตัวของโบรเกอร์จะส่งคืน `504` การตอบกลับที่แปลงแล้วจะเพิ่ม `video->text;model=<visionModel>;parts=<videos>` ลงในส่วนหัวส่วนกลาง `x-omniroute-modality-bridge` โดยไม่ลบส่วน Vision หรือ Audio ออก

### PII Masker (`piiMasker.ts`)

ทำงานใน **ทั้งสอง** ขั้นตอน

- **`preCall`** ทำการโคลนเพย์โหลด (payload), วนลูปผ่าน `system`, `messages`, `input` และ `prompt` (รวมถึงรายการที่เป็นสตริงธรรมดา) และเรียกใช้งาน `processPII()` (จาก `@/shared/utils/inputSanitizer`) กับฟิลด์ `content`/`text` ที่เป็นสตริง เมื่อ `PII_REDACTION_ENABLED=true` ข้อมูลส่วนบุคคล (PII) ที่ตรวจพบจะถูกซ่อนในเพย์โหลดขาออก การทำงานนี้เป็นอิสระจาก `INPUT_SANITIZER_MODE` (ซึ่งควบคุมเฉพาะนโยบายป้องกันการแทรกแซงพรอมต์) เมื่อปิดการซ่อนข้อมูล การเรียกนี้จะบันทึกจำนวนครั้งที่ตรวจพบโดยไม่มีการเขียนเนื้อหาใหม่
- **`postCall`** ทำการโคลนการตอบกลับแบบเชิงลึก (deep-clone), รันฟังก์ชัน `sanitizePIIResponse()` ร่วมกับตัวกรองรูปแบบ Responses-API (`maskResponsesOutput` — ครอบคลุม `output_text` และ `output[].content[].text`) หากมีการซ่อนข้อมูลเกิดขึ้น การตอบกลับที่ถูกแก้ไขจะแทนที่ต้นฉบับ

ระบบป้องกัน (guardrail) จะไม่มีการบล็อกใดๆ ทั้งสิ้น แต่จะทำการใส่คำอธิบายประกอบ (`meta.detections`, `meta.redacted`) หรือเขียนใหม่เท่านั้น

#### Per-type selection, custom patterns and detection counters

**Dashboard → Settings → Security → PII masking** ใช้สำหรับเลือก_สิ่งที่_ต้องการซ่อนข้อมูล โดยจะไม่ใช่ตัวเปิดใช้งานการซ่อนข้อมูล: ซึ่งสถานะนั้นยังคงถูกควบคุมโดย `PII_REDACTION_ENABLED` (สำหรับคำขอ) และ `PII_RESPONSE_SANITIZATION` (สำหรับการตอบกลับ + SSE) โดยทั้งคู่ถูกปิดไว้โดยค่าเริ่มต้น

- **Per-type selection** — ID ที่มีมาให้ในตัวจะแสดงรายการอยู่ใน `src/shared/constants/piiTypes.ts` (`PII_BUILTIN_TYPES`) หากไม่ได้กำหนดค่าหมายถึงทุกประเภท (พฤติกรรมเดิมก่อนที่จะมีตั้งค่านี้) รูปแบบ `ssn_us` ของเอ็นจิ้นคำขอจะแมปกับ `ssn` เทมเพลตต่างๆ (Minimal, Standard, Financial, Brazilian, USA, Full) ทำหน้าที่เพียงติ๊กช่องทำเครื่องหมายใน UI เท่านั้น
- **Custom patterns** — กำหนดรูปแบบ regex หรือ wildcard ได้สูงสุด 20 รูปแบบ (`*` = อักขระที่ไม่ใช่ช่องว่างสูงสุด 64 ตัว, `?` = หนึ่งตัว) ข้อความที่ตรงกันจะถูกแทนที่ด้วย `[CUSTOM_REDACTED]` รูปแบบทุกรูปแบบจะผ่านการประมวลผลผ่าน `compilePiiCustomPattern()` (`src/shared/utils/piiCustomPatterns.ts`): มีความยาวไม่เกิน 500 อักขระ, จำกัดแฟล็กเฉพาะ `g i m s u`, ต้องคอมไพล์ผ่าน, ต้องผ่านการตรวจสอบ `safe-regex` (ป้องกันปัญหา catastrophic backtracking) และต้องไม่ตรงกับสตริงว่างหรือตัวแทนการซ่อนข้อมูล รูปแบบใดที่ล้มเหลวจะถูกปฏิเสธเมื่อบันทึกและเมื่อทดสอบ และแถวข้อมูลที่จัดเก็บไว้ซึ่งล้มเหลวจะถูกข้ามในขณะรันไทม์แทนที่จะถูกคอมไพล์ รูปแบบกำหนดเองจะทำงานก็ต่อเมื่อเปิดการซ่อนข้อมูลอยู่เท่านั้น
- **Detection counters** — นับจำนวนตามประเภท (ไม่เก็บบันทึกค่าที่ตรงกัน), เก็บไว้ในหน่วยความจำและรีเซ็ตเมื่อรีสตาร์ท (`src/lib/pii/piiDetectionStats.ts`) ตัวนับเหล่านี้จะเพิ่มขึ้นเฉพาะในขณะที่เปิดใช้งานการซ่อนข้อมูลเท่านั้น

การตั้งค่านี้ถูกจัดเก็บบบนตาราง `key_value` (เนมสเปซ `pii_settings`, `src/lib/db/piiSettings.ts`) และอ่านผ่านแคชขนาด 1 วินาที API:

| Method | Path                     | Purpose                                                                    |
| ------ | ------------------------ | -------------------------------------------------------------------------- |
| `GET`  | `/api/settings/pii`      | สถานะแฟล็ก, `enabledTypes`, `customPatterns`, ตัวนับการตรวจจับ             |
| `PUT`  | `/api/settings/pii`      | แทนที่ `enabledTypes` (`null` = ทั้งหมด) และ/หรือ `customPatterns`         |
| `POST` | `/api/settings/pii/test` | ทดสอบจำลองหนึ่งรูปแบบกับชุดตัวอย่างขนาดไม่เกิน 8 KB; ไม่มีข้อมูลถูกจัดเก็บ |

ทั้งสามเอ็นพอยต์ต้องมีการยืนยันตัวตนระดับผู้จัดการ (management auth) และตรวจสอบความถูกต้องของเนื้อหาด้วย Zod (`src/shared/validation/schemas/piiSettings.ts`)

### Prompt Injection (`promptInjection.ts`)

ตรวจจับโครงสร้างที่เป็นอันตรายในเนื้อหาที่ผู้ใช้ป้อนเข้ามาและบังคับใช้นโยบายที่กำหนด พฤติกรรมการทำงานถูกควบคุมโดยตัวแปรสภาพแวดล้อมและตัวเลือกคอนสตรัคเตอร์:

| Setting         | Env var                                                                                               | Default | Effect                                                                                                                                                                                 |
| --------------- | ----------------------------------------------------------------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Enabled         | `INPUT_SANITIZER_ENABLED`                                                                             | `true`  | เมื่อเป็น `false`, ระบบป้องกันจะทำงานแบบลัดวงจร (short-circuit)                                                                                                                        |
| Mode            | `INJECTION_GUARD_MODE` / `INPUT_SANITIZER_MODE`                                                       | `warn`  | นโยบายการแทรกแซง: `block`, `warn` หรือ `log` (รองรับ `redact` เพื่อความเข้ากันได้ย้อนหลัง แต่จะ**ไม่**ตัดข้อความแทรกแซงออก การเขียน PII ซ้ำในคำขอถูกควบคุมโดย `PII_REDACTION_ENABLED`) |
| Block threshold | `blockThreshold` option / `INPUT_SANITIZER_BLOCK_THRESHOLD` (alias `INJECTION_GUARD_BLOCK_THRESHOLD`) | `high`  | ระดับความรุนแรงขั้นต่ำที่จำเป็นสำหรับการบล็อก ค่า Medium จะเป็นการสังเกตการณ์อย่างเดียวโดยค่าเริ่มต้น                                                                                  |

**ลำดับความสำคัญของโหมด** (`getMode`): `options.mode` จากผู้เรียก → การแทนที่ฟีเจอร์แฟล็กในฐานข้อมูล `INJECTION_GUARD_MODE` (Dashboard → Settings → Feature Flags) → ตัวแปรสภาพแวดล้อม `INJECTION_GUARD_MODE` → ตัวแปรสภาพแวดล้อม `INPUT_SANITIZER_MODE` → `warn` ดังนั้น การตั้งค่าแทนที่ผ่านแดชบอร์ดจึงมีความสำคัญเหนือกว่าตัวแปรสภาพแวดล้อม ทำให้ UI ของ Feature Flags สามารถควบคุมระบบป้องกันที่กำลังทำงานอยู่ได้แบบสดๆ (ไม่ต้องรีสตาร์ท) การอ่านค่าจากฐานข้อมูลมีความปลอดภัยแบบ fail-safe: หากเกิดข้อผิดพลาด ระบบป้องกันจะกลับไปใช้พฤติกรรมตามตัวแปรสภาพแวดล้อม และเมื่อไม่มีการตั้งค่าแทนที่ พฤติกรรมจะเหมือนกับการแก้ปัญหาผ่านตัวแปรสภาพแวดล้อมเท่านั้น

แหล่งที่มาของการตรวจจับ:

1. `sanitizeRequest()` จาก `@/shared/utils/inputSanitizer` (ชุดตัวตรวจจับที่ใช้ร่วมกันในส่วนอื่นๆ ของไปป์ไลน์)
2. `DEFAULT_GUARD_PATTERNS` ที่มีมาให้ในตัว (ปัจจุบันคือ `system_override_inline` และ `markdown_system_block` ซึ่งทั้งคู่มีความรุนแรงระดับ `high`)
3. `customPatterns` ทางเลือกที่ส่งผ่านตัวเลือกคอนสตรัคเตอร์ (สตริง, regex, หรือเรคคอร์ด `{ name, pattern, severity }`)

เมื่อ `mode === "block"` **และ** การตรวจพบอย่างน้อยหนึ่งรายการตรงตามเกณฑ์ความรุนแรง `preCall` จะส่งค่ากลับเป็น `{ block: true, message: "Request rejected: suspicious content detected" }` ในโหมด `warn`/`log` ระบบป้องกันจะทำการบันทึก Log แต่ยังคงอนุญาตให้มีการเรียกใช้งานได้ ฟังก์ชันตัวช่วยส่วนกลาง `evaluatePromptInjection()` ก็ถูกส่งออกเช่นกันสำหรับผู้เรียกใช้งานที่จำเป็นต้องประเมินพรอมต์โดยไม่ต้องผ่านเรจิสทรี

**ขอบเขตการสแกน (v3.8.20):** ตัวตรวจจับจะตรวจสอบเฉพาะ **16 KB แรก** ของข้อความพรอมต์ที่รวมกัน — `MAX_INJECTION_SCAN_BYTES = 16 * 1024` (16 384 ไบต์) ใน `src/shared/utils/inputSanitizer.ts` ทั้ง `detectInjection()` และ `evaluatePromptInjection()` จะทำการ `slice(0, MAX_INJECTION_SCAN_BYTES)` ก่อนที่จะรันลูปตรวจสอบรูปแบบ คำสั่งแทรกแซงมักจะอยู่ใกล้ส่วนบนสุดของอินพุต ดังนั้นวิธีนี้จึงช่วยจำกัดการใช้ CPU/GC ของ regex บนเพย์โหลดขนาดหลายร้อย KB โดยที่ประสิทธิภาพการตรวจจับไม่ลดลง (อ้างอิง #3932, #4041)

### Credential Masker (`credentialMasker.ts`)

ทำงานบน **ทั้งสอง** ขั้นตอน โดยอยู่เป็นลำดับสุดท้ายในเชนเริ่มต้น (ลำดับความสำคัญ `95`) ทำการซ่อนรูปแบบคีย์ API / โทเค็นลับที่รู้จักจากเพย์โหลดขาออก (เนื้อหาข้อความ, อาร์กิวเมนต์ของการเรียกใช้เครื่องมือ, ผลลัพธ์ของเครื่องมือ) **และ** การตอบกลับจากผู้ให้บริการ เพื่อไม่ให้ข้อมูลรับรองที่ถูกวางลงในพรอมต์ (หรือถูกสะท้อนกลับผ่านผลลัพธ์ของเครื่องมือ) รั่วไหลไปยังผู้ให้บริการต้นทางหรือกลับไปยังไคลเอนต์

- **ต้องเปิดใช้งานด้วยตนเองเท่านั้น** เป็นไปตามข้อตกลงเดียวกันกับการซ่อนข้อมูล PII (ใกล้เคียงกับกฎข้อบังคับเข้มงวด #20): จะถูกปิดใช้งานเว้นแต่ `settings.credentialRedactionEnabled === true` **หรือ** `CREDENTIAL_REDACTION_ENABLED=true` หากปิดใช้งาน ระบบป้องกันนี้จะไม่มีผลใดๆ (no-op) — โดยจะไม่ทำการบล็อกหรือเขียนทับใดๆ
- `redactCredentials()` จะทำการท่องไปในโครงสร้างต้นไม้ของเพย์โหลด/การตอบกลับทั้งหมด (`walkValue()`, ปลอดภัยจากการปนเปื้อนโปรโตไทป์, ปลอดภัยจากวงรอบผ่าน `WeakSet`) และแทนที่ค่าที่ตรงกันด้วยตัวยึดตำแหน่ง `[REDACTED:<type>]` โดยทำการโคลนเฉพาะกิ่งก้านที่มีการเปลี่ยนแปลงจริงๆ เท่านั้น
- `CREDENTIAL_PATTERNS` ครอบคลุมถึงคีย์ของผู้ให้บริการ LLM (OpenAI, OpenAI-proj, Anthropic, Google, Hugging Face, Replicate), โทเค็น VCS/SaaS (GitHub, Slack, Linear, Notion, npm, Postman, Discord), คีย์การชำระเงิน (Stripe, Square), คีย์คลาวด์ (AWS access key, Twilio, SendGrid, Mailgun), ไพรเวตคีย์ / JWT, สตริงการเชื่อมต่อที่มีข้อมูลรับรอง (`mongodb://user:pass@...` ฯลฯ) และรูปแบบค่าเฮดเดอร์ทั่วไป `Authorization`/`x-api-key`/`api-key`/`apikey` โดยคีย์ที่มีลักษณะเป็นเฮดเดอร์ (`authorization`, `x-api-key`, `api-key`, `apikey`) จะถูกซ่อนในระดับโครงสร้าง (เฉพาะค่าเท่านั้น โดยยังคงรักษาคำนำหน้าสคีม เช่น `Bearer `/`Basic ` ไว้) แทนการใช้เรกเกกซ์ข้อความทั่วไป
- ระบบป้องกันจะไม่ทำการบล็อก แต่จะทำการเขียนทับ (`modifiedPayload` / `modifiedResponse`) และเพิ่มคำอธิบายประกอบ (`meta.credentialsRedacted`, `meta.count`) เท่านั้น

ตัวป้องกัน Regression: `tests/unit/credential-masker-guardrail.test.ts`.

## สัญญาพื้นฐาน (`base.ts`)

```typescript
class BaseGuardrail {
  enabled: boolean;
  name: string;
  priority: number;

  constructor(name: string, options?: { enabled?: boolean; priority?: number });

  async preCall(payload: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;

  async postCall(response: unknown, context: GuardrailContext): Promise<GuardrailResult | void>;
}

interface GuardrailResult<TValue = unknown> {
  block?: boolean; // true จะทำให้ลัดวงจรห่วงโซ่ทันที
  message?: string; // แสดงผลเมื่อมีการบล็อก
  meta?: Record<string, unknown> | null;
  modifiedPayload?: TValue; // คืนค่าโดย preCall เพื่อเขียนทับคำขอ
  modifiedResponse?: TValue; // คืนค่าโดย postCall เพื่อเขียนทับการตอบกลับ
}

interface GuardrailContext {
  apiKeyInfo?: Record<string, unknown> | null;
  disabledGuardrails?: string[] | null;
  endpoint?: string | null;
  headers?: Headers | Record<string, unknown> | null;
  log?: GuardrailLog | Console | null;
  method?: string | null;
  model?: string | null;
  provider?: string | null;
  signal?: AbortSignal;
  sourceFormat?: string | null;
  stream?: boolean;
  targetFormat?: string | null;
}
```

การ์ดเรลจะส่งสัญญาณว่า "ไม่มีการเปลี่ยนแปลง" โดยการคืนค่าเป็น `void`, `{}`, หรือ
`{ block: false }` การคืนค่า `modifiedPayload`/`modifiedResponse` จะเป็นการแทนที่
ค่าที่ไหลผ่านห่วงโซ่สำหรับการ์ดเรลในลำดับถัดไป
`signal?: AbortSignal` จะส่งวงจรชีวิตของผู้เรียกเข้าไปในการ์ดเรล การยกเลิกคำขอคือข้อยกเว้นแบบ fail-open ที่ตั้งใจไว้: สะพานสื่อจะหยุดการทำงานและทำความสะอาดโดยไม่กู้คืนสื่อดิบไปยังเป้าหมายที่ทราบว่าไม่รองรับ

## รีจิสทรี (`registry.ts`)

ซิงเกิลตัน `guardrailRegistry` จะเปิดเผย:

- `register(guardrail)` — เพิ่ม (หรือแทนที่ด้วยชื่อที่ปรับมาตรฐานแล้ว) การ์ดเรล และ
  เรียงลำดับใหม่ตาม `priority` จากน้อยไปมาก
- `clear()` / `list()` — ตัวช่วยสำหรับการจัดการระบบ
- `runPreCallHooks(payload, context)` — วนลูปผ่านการ์ดเรลที่ใช้งานอยู่, ส่งเพย์โหลด
  ผ่าน `modifiedPayload`, และหยุดทำงานเมื่อพบ `block: true` ตัวแรก
- `runPostCallHooks(response, context)` — กระบวนการเดียวกันในฝั่งการตอบกลับ
- `resetGuardrailsForTests({ registerDefaults })` — ล้างสถานะและลงทะเบียนค่าเริ่มต้นใหม่อย่างเป็นทางเลือก เพื่อความสะอาดในการแยกทดสอบ

ตัวรันทั้งสองจะคืนค่า `{ blocked, payload|response, results, guardrail?, message? }`
โดยที่ `results` คืออาร์เรย์ของเรคอร์ด `GuardrailExecutionResult` ซึ่งประกอบด้วยฟิลด์
`blocked`, `skipped`, `modified`, `error`, และ `meta` ในแต่ละการ์ดเรล
ซึ่งมีประโยชน์สำหรับการติดตาม

### การปิดใช้งานการ์ดเรลต่อหนึ่งคำขอ

`resolveDisabledGuardrails({ apiKeyInfo, body, headers })` จะรวบรวมรายชื่อ
การ์ดเรลที่ถูกตัดรายการที่ซ้ำกันออก ซึ่งควรจะถูกข้ามสำหรับการร้องขอปัจจุบัน
มีช่องทางทั้งหมด 5 ช่องทาง อ่านตามลำดับนี้และรวมเป็นรายการเดียว
(รายการแรกที่พบจะมีผลเมื่อทำการตัดรายการซ้ำ):

1. `apiKeyInfo.disabledGuardrails`
2. `disabledGuardrails` ใน Request body (ระดับบนสุด)
3. `metadata.disabledGuardrails` ใน Request body (เฉพาะเมื่อ `metadata` เป็นออบเจ็กต์)
4. Header `x-omniroute-disabled-guardrails`
5. Legacy header `x-disabled-guardrails`

ทั้ง 5 ช่องทางจะถูกรวมเข้าด้วยกัน รวมถึงเฮดเดอร์ทั้งสองตัว: การส่งทั้ง
`x-omniroute-disabled-guardrails` และ `x-disabled-guardrails` พร้อมกันจะทำการข้ามยูเนียน
ของรายการทั้งสอง และเฮดเดอร์สมัยใหม่ที่ว่างเปล่าจะไม่ซ่อนเฮดเดอร์แบบเก่าอีกต่อไป
([#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412), แก้ไขใน
[#16805](https://github.com/diegosouzapw/OmniRoute/pull/16805))

ค่าต่างๆ อาจเป็นอาร์เรย์ของสตริงหรือสตริงที่คั่นด้วยจุลภาค; ชื่อจะถูกตัดช่องว่าง
และปรับให้อยู่ในรูปแบบ lowercase kebab-case (`pii_masker` → `pii-masker`), และรายการที่ว่างเปล่าจะถูกตัดทิ้ง ผลลัพธ์จะถูกส่งผ่าน `context.disabledGuardrails`
ไปยังรีจิสทรี ซึ่งจะทำการข้ามการ์ดเรลที่ตรงกัน (`skipped: true` ใน `results`)

รายการที่ปิดใช้งานจะมีผลกับ **รีจิสทรี** เท่านั้น โหมด `block` สำหรับการฉีดคำสั่งพร้อมท์เป็น
ขอบเขตบังคับ: มิดเดิลแวร์ป้องกันการฉีด
(`src/middleware/promptInjectionGuard.ts`) จะเรียก `evaluatePromptInjection()`
โดยไม่มีรายการปิดใช้งานใดๆ ที่ควบคุมโดยผู้เรียก (การเรียก
`resolveDisabledGuardrails({ body })` แบบตายตัวที่เคยใช้ถูกลบออกใน
[#16934](https://github.com/diegosouzapw/OmniRoute/pull/16934)), ดังนั้นคำขอ
ที่ปิดใช้งาน `prompt-injection` จึงยังคงถูกปฏิเสธในโหมด `block` นี่คือการออกแบบ
ตามความตั้งใจ ช่องทางการปิดใช้งานเหล่านี้ถูกควบคุมโดยผู้เรียก (request body,
metadata, headers) และผู้เรียกต้องไม่สามารถปิดการควบคุมความปลอดภัยที่ผู้ดูแลระบบตั้งค่าไว้ได้
([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)). ยูเนียนเฮดเดอร์
จาก [#16412](https://github.com/diegosouzapw/OmniRoute/issues/16412)
จะเปลี่ยนเฉพาะการ์ดเรลในรีจิสทรีตัวใดที่จะถูกข้ามเท่านั้น; โดยไม่อนุญาตให้ไคลเอนต์
ข้ามมิดเดิลแวร์ได้ นโยบายการ์ดเรลบังคับต่อคีย์และต่อกลุ่มถูกติดตามอยู่ใน v4 RFC [#16417](https://github.com/diegosouzapw/OmniRoute/issues/16417).
ดูเพิ่มเติมที่ [Coverage and limits](#coverage-and-limits).

## ลำดับการทำงาน

สำหรับแต่ละคำขอที่ไหลผ่าน `src/sse/handlers/chat.ts` และ
`open-sse/handlers/chatCore.ts` (เส้นทางตระกูลแชทที่แสดงอยู่ภายใต้
[Coverage and limits](#coverage-and-limits)):

1. `resolveDisabledGuardrails(...)` จะสร้างรายชื่อการข้าม (skip list) จากคีย์ API, ส่วนเนื้อหาคำขอ (body)
   และส่วนหัว (headers)
2. `guardrailRegistry.runPreCallHooks(body, ctx)` จะรันการ์ดเรล (guardrails) ตามลำดับความสำคัญจากน้อยไปมาก:
   - การ์ดเรลที่ถูกปิดใช้งานจะถูกบันทึกเป็น `skipped`
   - ฟังก์ชัน `preCall` ของการ์ดเรลแต่ละตัวอาจเขียนเพย์โหลด (payload) ใหม่ผ่าน `modifiedPayload`
   - เงื่อนไข `block: true` ตัวแรกจะทำให้ห่วงโซ่นี้ลัดวงจร (short-circuit) และตัวจัดการจะส่งคืน
     การตอบกลับที่ปฏิเสธจากการ์ดเรล
3. เพย์โหลด (ที่อาจถูกเขียนใหม่แล้ว) จะไหลเข้าสู่การกำหนดเส้นทางแบบคอมโบ (combo routing) และการส่งต่อไปยังต้นน้ำ (upstream dispatch)
4. **เฉพาะแบบไม่ใช่สตรีมมิ่งเท่านั้น (Non-streaming only):** หลังจากที่ประกอบการตอบกลับเรียบร้อยแล้ว
   `guardrailRegistry.runPostCallHooks(...)` จะรันห่วงโซ่เดียวกันกับข้อมูลตอบกลับ `block: true` ในขั้นตอนนี้จะทิ้งการตอบกลับจากต้นน้ำและส่งคืน HTTP 400 การตอบกลับแบบสตรีมมิ่งจะข้ามขั้นตอนนี้ไปโดยสิ้นเชิง

การ์ดเรลที่เกิดข้อผิดพลาด (throw) จะถูกบันทึกด้วย `error: <message>` และบันทึกลง log ผ่าน
`logger.warn` แต่ห่วงโซ่จะยังคงทำงานต่อไป ซึ่งเป็นการออกแบบให้ล้มเหลวแบบเปิด (fail-open by design)

## ขอบเขตความครอบคลุมและข้อจำกัด

เมธอดรีจิสทรีของการ์ดเรลถูกเชื่อมต่อเข้ากับไปป์ไลน์แชทเท่านั้น ข้อจำกัดเหล่านี้
ถูกกำหนดไว้โดย `tests/unit/guardrail-pipeline-wiring-characterization.test.ts` และ
`tests/unit/guardrail-pipeline-characterization.test.ts` โปรดอัปเดตการทดสอบเหล่านั้นอย่างตั้งใจเมื่อพฤติกรรมเปลี่ยนแปลงไป

### จุดที่ฮุกทำงาน

| Hook / control                      | Runs on                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `runPreCallHooks`                   | คำขอที่จัดการโดย `handleChat` (`src/sse/handlers/chat.ts`): `/v1/chat/completions`, `/v1/completions`, `/v1/messages`, `/v1/responses` (และ `/v1/responses/*`), `/v1/relay/chat/completions`, `/v1/providers/{provider}/chat/completions`, `/v1/api/chat`, `/v1/antigravity`, `/v1beta/models/*` รวมถึงพร็อกซีแชท Telegram และยังรวมถึงเอนด์จุดทดสอบแดชบอร์ด `/api/guardrails/test` ด้วย การบล็อกก่อนการเรียกใช้งานจะส่งคืน HTTP 400 |
| `runPostCallHooks`                  | เฉพาะการตอบกลับแชทแบบ **ไม่ใช่สตรีมมิ่ง** (`open-sse/handlers/chatCore/nonStreamingResponse.ts`) เท่านั้น การตอบกลับแบบสตรีมมิ่งจะไม่มาถึงจุดนี้                                                                                                                                                                                                                                                                                     |
| Streaming PII                       | `createPiiSseTransform` (`src/lib/streamingPiiTransform.ts`) ซึ่งถูกส่งผ่านไปป์ (piped) ใน `streamingPipeline.ts` เมื่อเปิดใช้งาน `PII_RESPONSE_SANITIZATION` นี่ไม่ใช่การ์ดเรล ดังนั้นช่องทางการปิดใช้งานจึงไม่มีผลกระทบต่อสิ่งนี้                                                                                                                                                                                                  |
| Injection-guard middleware (legacy) | ทุกเส้นทาง `/v1` ที่มีพรอมต์ รวมถึงตระกูลแชทด้วย (ดู [route coverage](#injection-guard-route-coverage--red-team-phase-8--block-d)) สำหรับการฉีดพรอมต์เท่านั้น                                                                                                                                                                                                                                                                        |

### สิ่งที่ไม่ครอบคลุม

- **เส้นทางสื่อ, การฝังตัว (embeddings) และข้อมูล** (`/v1/images/*`, `/v1/embeddings`,
  `/v1/audio/*`, `/v1/videos/generations`, `/v1/music/generations`,
  `/v1/rerank`, `/v1/search`, `/v1/moderations`) จะไม่เข้าสู่รีจิสทรี จะไม่มีการทำ
  PII masking, การซ่อนข้อมูลรับรอง (credential masking) หรือบริดจ์โมดัลลิตี้ทำงานที่นั่น การตรวจสอบเดียว
  ที่มีคือมิดเดิลแวร์ป้องกันการฉีดโค้ดแบบดั้งเดิม (legacy injection-guard middleware)
- **การตอบกลับแบบสตรีมมิ่ง** จะไม่มีการ์ดเรลหลังการเรียกใช้งาน: ไม่มี `pii-masker` หรือ
  `credential-masker` หลังการเรียก และไม่มีการบล็อกหลังการเรียก มีเพียงการแปลง PII แบบสตรีมมิ่ง
  เท่านั้นที่จะทำงาน (เมื่อเปิดใช้งาน `PII_RESPONSE_SANITIZATION`) ข้อมูลรับรอง
  ที่ถูกสะท้อนกลับมาในการตอบกลับแบบสตรีมมิ่งจะไม่ถูกปกปิด (redacted)
- **ช่องทางการปิดใช้งานเทียบกับมิดเดิลแวร์ (โดยการออกแบบ):** มิดเดิลแวร์จะประเมินการฉีดพรอมต์ด้วยการเรียกใช้
  `evaluatePromptInjection()` ของตนเอง โดยไม่ต้องส่งรายชื่อการปิดใช้งานที่ควบคุมโดยผู้เรียก โหมด `block` เป็นขอบเขตบังคับ
  ที่การปิดใช้งานซึ่งควบคุมโดยผู้เรียกจะไม่สามารถข้ามได้ รวมถึงบนเส้นทางตระกูลแชทด้วย
  ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)) การปิดใช้งาน
  `prompt-injection` จะข้ามเฉพาะการ์ดเรลในรีจิสทรีเท่านั้น

### สิ่งที่เห็นการตอบกลับก่อนการเรียกหลังการทำงาน

บนเส้นทางแบบไม่ใช่สตรีมมิ่ง ลำดับคือ: การสกัดความจำ (memory extraction) → การทำงานของเครื่องมือในตัว (built-in tool
execution) → การ์ดเรลหลังการเรียก (post-call guardrails) → การออกจากบล็อกหลังการเรียก (post-call block exit) → การจัดเก็บในแคชเชิงความหมาย (semantic-cache store)

- **Memory extraction** และ **tool execution** จะมองเห็นการตอบกลับก่อนที่ post-call guardrails จะสามารถเขียนทับหรือบล็อกได้ นับตั้งแต่ [#16401](https://github.com/diegosouzapw/OmniRoute/pull/16401) เป็นต้นมา memory extraction จะรันข้อความที่ดึงมาผ่าน `sanitizePII` เมื่อเปิดใช้งาน `PII_RESPONSE_SANITIZATION` (ทั้งแบบ streaming และ non-streaming) แต่การตอบกลับที่ถูกบล็อกในเวลาต่อมาโดย post-call จะยังคงถูกส่งไปยังหน่วยความจำและเครื่องมืออยู่
- **Semantic cache** จะจัดเก็บการตอบกลับหลังจาก post-call ดังนั้นจึงจัดเก็บการตอบกลับที่ถูกเขียนทับแล้ว และการตอบกลับที่ถูกบล็อกจะไม่ถูกแคชไว้เลย โดยรายการแคชจะถูกกำหนดคีย์ตาม API key

## การกำหนดค่า

ตัวแปรสภาพแวดล้อมที่อ่านโดยระบบป้องกัน (guardrails) ในตัว:

| ตัวแปร                                | ใช้โดย                    | ผลลัพธ์                                                                                                         |
| ------------------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `INPUT_SANITIZER_ENABLED`             | `prompt-injection`        | ตั้งค่าเป็น `false` เพื่อปิดใช้งานการตรวจจับทั้งหมด                                                             |
| `INPUT_SANITIZER_MODE`                | `prompt-injection`        | นโยบายการฉีดข้อมูล: `warn`, `block` หรือ `log` ค่าเดิม `redact` จะไม่เขียนข้อความที่ถูกฉีดทับ                   |
| `INJECTION_GUARD_MODE`                | `prompt-injection`        | โหมดสำหรับระบบป้องกันการฉีดข้อมูล; รวมถึงเป็นฟีเจอร์แฟล็กในฐานข้อมูลที่**เขียนทับ**ตัวแปรสภาพแวดล้อม (DB > ENV) |
| `INPUT_SANITIZER_BLOCK_THRESHOLD`     | `prompt-injection`        | ระดับความรุนแรงต่ำสุดที่ `MODE=block` จะปฏิเสธ: `high` (ค่าเริ่มต้น), `medium` หรือ `low`                       |
| `INJECTION_GUARD_BLOCK_THRESHOLD`     | `prompt-injection`        | ชื่อเรียกเดิม (alias) สำหรับ `INPUT_SANITIZER_BLOCK_THRESHOLD`                                                  |
| `PII_REDACTION_ENABLED`               | `pii-masker`              | เมื่อเป็น `true` ข้อมูล PII ในคำขอจะถูกเซ็นเซอร์ (ไม่ขึ้นอยู่กับโหมดการฉีดข้อมูล)                               |
| `PII_RESPONSE_SANITIZATION` / `_MODE` | `pii-masker` (downstream) | ควบคุมพฤติกรรมของการเซ็นเซอร์ฝั่งการตอบกลับ                                                                     |

ระบบป้องกัน Modality Bridge จะอ่านการตั้งค่าขณะรันไทม์จากที่เก็บการตั้งค่าที่สำรองข้อมูลด้วยฐานข้อมูล (`getSettings()`) ไม่ใช่จากตัวแปรสภาพแวดล้อม คีย์หลักของ Vision ได้แก่ `modalityBridgeVisionEnabled`, `modalityBridgeVisionMode`, `modalityBridgeVisionModel`, `modalityBridgeVisionTaskAware`, `modalityBridgeVisionPrompt`, `modalityBridgeVisionTimeout`, `modalityBridgeVisionMaxImages`, `modalityBridgeVisionMaxChars`, `modalityBridgeCacheEnabled`, `modalityBridgeCacheTtlMinutes` และ `modalityBridgeCacheMaxEntries` คีย์ `visionBridge*` แบบเดิมจะยอมรับเฉพาะการสำรองข้อมูลแบบอ่านรอบเดียวตามที่ระบุไว้ในเอกสารเท่านั้น การเขียนผ่านแดชบอร์ดจะใช้คีย์หลัก ค่าเริ่มต้นและตัวแก้ไขการสำรองข้อมูล (fallback resolver) อยู่ใน `src/shared/constants/modalityBridgeDefaults.ts` โดยมีค่าคงเดิมถูกเก็บไว้ใน `src/shared/constants/visionBridgeDefaults.ts`

Audio ใช้ `modalityBridgeAudioEnabled`, `modalityBridgeAudioModel`, `modalityBridgeAudioTimeout` และ `modalityBridgeAudioMaxClips` รวมถึงการตั้งค่า `modalityBridgeCache*` ที่ใช้ร่วมกัน Audio ไม่มีคีย์สำรองแบบเดิม เนื่องจากคีย์เหล่านี้ถูกนำมาใช้พร้อมกับสคีมา Modality Bridge

Video ใช้ `modalityBridgeVideoEnabled`, `modalityBridgeVideoAnalysisMode`, `modalityBridgeVideoModel`, `modalityBridgeVideoFrameCount`, `modalityBridgeVideoSamplingPolicy`, `modalityBridgeVideoMaxVideos` และ `modalityBridgeVideoTimeout` รวมถึงการตั้งค่า `modalityBridgeCache*` ที่ใช้ร่วมกัน ฟีเจอร์นี้ถูกปิดใช้งานโดยค่าเริ่มต้น เนื่องจาก FFmpeg/ffprobe เป็นการพึ่งพาในการปฏิบัติงานเสริม (optional operational dependencies) และการทำคำบรรยายเฟรมจะเพิ่มความหน่วง (latency) รวมถึงต้นทุนของโมเดล

## ระบบป้องกันแบบกำหนดเอง

```typescript
import { BaseGuardrail, guardrailRegistry } from "@/lib/guardrails";

class BudgetGuardrail extends BaseGuardrail {
  constructor() {
    super("budget", { priority: 50 });
  }

  async preCall(payload, ctx) {
    if (ctx.apiKeyInfo?.budgetExceeded) {
      return { block: true, message: "Daily budget exceeded" };
    }
    return { block: false };
  }
}

guardrailRegistry.register(new BudgetGuardrail());
```

ขั้นตอน:

1. สร้าง `src/lib/guardrails/myGuardrail.ts` ที่สืบทอดจาก `BaseGuardrail`
2. ดำเนินการฟังก์ชัน `preCall` และ/หรือ `postCall`
3. ลงทะเบียนขณะนำเข้า (ส่งค่าจาก `registerDefaultGuardrails`) หรือ
   เรียกใช้ `guardrailRegistry.register(...)` ในขณะรันไทม์ — ตัวจัดการการลงทะเบียน (registry) จะแทนที่
   ตัวป้องกันเดิมที่มีชื่อฟอร์แมตเดียวกัน
4. เพิ่มการทดสอบภายใต้ไดเรกทอรี `tests/unit/` (ตัวอย่างที่มีอยู่:
   `tests/unit/guardrails-registry.test.ts`,
   `tests/unit/prompt-injection-guard.test.ts`,
   `tests/unit/guardrails/visionBridge.test.ts`)

## การทดสอบ

ใช้ `resetGuardrailsForTests()` ระหว่างการทดสอบเพื่อเริ่มต้นจากสถานะที่ทราบล่วงหน้า
ส่งค่า `{ registerDefaults: false }` เพื่อเริ่มต้นด้วยเรจิสทรีว่างเปล่าและ
ลงทะเบียนเฉพาะตัวป้องกันที่อยู่ภายใต้การทดสอบเท่านั้น Vision Bridge รองรับการทำ dependency
injection (`deps.getSettings`, `deps.callVisionModel`); ในขณะที่ Audio Bridge มีจุดเชื่อมต่อที่เทียบเท่ากัน
สำหรับการตั้งค่า ความสามารถ การเลือกโมเดล STT การตรวจสอบข้อมูลประจำตัว (credentials)
และการถอดเสียง ดังนั้น การทดสอบจึงสามารถรันทั้งสองโฟลว์ได้โดยไม่ต้องเข้าถึงฐานข้อมูล
หรือเครือข่าย

## การครอบคลุมเส้นทาง (Route coverage) ของระบบป้องกัน Injection และทีมเจาะระบบ (Red-team) (Phase 8 · Block D)

ระบบป้องกัน injection (`createInjectionGuard` / `withInjectionGuard`) ครอบคลุมเส้นทางทั้งหมด
ที่ยอมรับข้อความแจ้ง (prompts) จากผู้ใช้ โดยจะอิงตามค่า `INJECTION_GUARD_MODE` (ค่าเริ่มต้น `warn` = บันทึก log เท่านั้น;
`block` = ส่งคืน HTTP 400 `SECURITY_001`).

| ประเภท                  | เส้นทาง (Routes)                                                                                                                                     | โหมดเริ่มต้น |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| ข้อความ (ที่มีอยู่แล้ว) | `/v1/chat/completions`, `/v1/completions`, `/v1/relay/chat/completions`                                                                              | warn         |
| เชิงสร้างสรรค์          | `/v1/messages`, `/v1/responses`, `/v1/images/generations`, `/v1/images/edits`, `/v1/videos/generations`, `/v1/music/generations`, `/v1/audio/speech` | warn         |
| ข้อมูล                  | `/v1/embeddings`, `/v1/rerank`, `/v1/search`, `/v1/moderations`                                                                                      | warn         |

การดึงข้อความ (`extractMessageContents`) ครอบคลุม `messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system`.

**ทีมเจาะระบบ (Red-team) (รันทุกคืน, `nightly-llm-security.yml`):** promptfoo ตรวจสอบว่าแต่ละเส้นทางบล็อก
ชุดข้อมูล OWASP-LLM เมื่อตั้งค่า `INJECTION_GUARD_MODE=block`; ในขณะที่ garak จะรันการทดสอบ (ข้ามไปหากไม่มี secret).
รวม `moderations` ไว้ด้วยเพื่อให้มีความสอดคล้องกัน โหมด block เป็นขอบเขตบังคับ: `evaluatePromptInjection()`
จะละเว้นรายการปิดการใช้งานต่อคำขอ (per-request disable list) ที่ middleware ส่งมา ดังนั้น `disabledGuardrails` จึง
**ไม่สามารถ** ยกเว้นเส้นทางใดๆ จากการตรวจสอบนี้ได้ ([#16413](https://github.com/diegosouzapw/OmniRoute/issues/16413)).

เวิร์กโฟลว์รันประจำคืน (`.github/workflows/nightly-llm-security.yml`, กำหนดเวลาแบบ cron + สั่งรันด้วยตนเอง)
มี 2 งาน (jobs):

- **`promptfoo-guard` (แบบบล็อก)** — รันคำสั่ง `promptfoo eval -c promptfooconfig.yaml`
  พร้อมตั้งค่า `INJECTION_GUARD_MODE=block` โดยแต่ละกรณีตัวอย่างการโจมตี (เช่น "ignore all
  previous instructions…", การเจาะระบบแบบ DAN) จะต้องยืนยันว่าการตอบกลับมีค่า
  `error.code === "SECURITY_001"` ซึ่งหมายความว่าระบบป้องกันได้ปฏิเสธคำขอนั้นจริงๆ
- **`garak` (แบบแนะนำ/เตือน)** — รัน garak ด้วยพารามิเตอร์ `--probes promptinject,dan,leakreplay`
  กับอินสแตนซ์ OmniRoute ท้องถิ่น (`http://localhost:20128/v1`). ควบคุมด้วย provider secret
  (`PROMPTFOO_PROVIDER_KEY`); จะข้ามไปอย่างเรียบร้อยหากไม่มีและต่อท้ายด้วย
  `|| true` เพื่อให้รายงานผลได้โดยไม่ทำให้ CI ล้มเหลว.

การครอบคลุมของ helper ตัวป้องกัน (`createInjectionGuard` / `withInjectionGuard`)
ครอบคลุมทุกเส้นทาง `/v1` ที่รับ prompt; โดยข้อความ prompt จะถูกดึงมาจาก
`messages`/`input`/`prompt`/`query`+`documents`/`instructions`/`system` ผ่านฟังก์ชัน
`extractMessageContents()` ใน `src/shared/utils/inputSanitizer.ts`.
